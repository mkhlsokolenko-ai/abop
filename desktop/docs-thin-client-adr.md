# ADR + Архитектура: APE Desktop как встраиваемый тонкий клиент ABOP под RBAC

Статус: **accepted** (2026-09-18). Разворот стратегии десктоп-оболочки: это не «ещё один чат»,
а **среда запуска агентов конечным пользователем** — тонкий клиент с доступом ко всем сервисам
и системам компании по **RBAC пользователя**, вызываемый как из своего UI, так и **прямо из систем,
в которых человек работает**. Связано с [[abop-architecture]] (Agent/Tool/Data-плоскости,
governance-конверт — ABOP_ADR ADR-028/029).

---

## 1. ADR (Nygard)

**Контекст.** Пользователю (менеджеру) нужна единая точка, откуда он выбирает и запускает агентов,
и чтобы агенты работали с реальными системами компании под его правами. Отдельные веб-чаты и
разрозненные интеграции этого не дают: нет единой сессии, нет контроля доступа, нет вызова «по месту».

**Решение.** **APE Desktop = тонкий клиент-рантайм ABOP.** Локальный сайдкар (уже есть: Electron +
Python на `127.0.0.1`) держит идентичность пользователя (Keycloak JWT), каталог агентов, память и
модули. Все вызовы идут через шлюз под JWT пользователя; **RBAC энфорсится на сервере**. Клиент
имеет **несколько поверхностей вызова, одна сессия**: своё окно, глобальный хоткей/лаунчер и
встраивание в host-системы (Office-надстройка, контекстное меню, deep-link) — все они стучатся в
**один локальный API сайдкара**.

**Альтернативы (отклонены).**
- *Только веб-портал-чат* — нельзя локальные ML (OCR/NLP), нет вызова из систем, слабый контроль доступа к внутренним данным.
- *Плагин в каждую систему по отдельности* — N интеграций без общей сессии/каталога/governance; дублирование и дыры в RBAC.
- *Толстый клиент со своими ключами моделей* — нельзя (слив бюджета, нет учёта, нет RBAC).

**Последствия.**
- (+) Один рантайм, много точек входа, единый SSO; локальные ML доступны; governance в одном месте.
- (+) «Рабочие источники + RBAC» из бэклога становятся **костяком**, а не опцией.
- (−) Растёт значимость безопасности: **делегированный доступ к системам** и серверный энфорс RBAC — обязательны, не «потом».
- (−) Нужен **стабильный версионированный локальный API** сайдкара как продукт (в него встраиваются host-системы).

## 2. Архитектура

```
Поверхности вызова (одна сессия / один JWT):
  окно APE · глобальный хоткей/лаунчер · Office-надстройка · контекст-меню ОС · deep-link ape:// · локальный API
        │  всё → один локальный рантайм
┌──────────────────────────────────────────────┐
│ APE Desktop (тонкий клиент)                    │
│  сайдкар :127.0.0.1  — держит JWT, каталог,     │
│  память, модули; ЛОКАЛЬНЫЙ API (контракт)       │
└──────────────────────────────────────────────┘
        │ Bearer JWT пользователя
        ▼
Шлюз (MCP / portal-api) — ЕДИНАЯ точка энфорса RBAC
  политика: агент × инструмент × источник данных → роль/группа Keycloak
        ▼
Модели (self-host 30B/DeepSeek) · Tool plane (MCP+локальные OCR/NLP) · Data plane (коннекторы к системам)
```

**Слои (маппинг на ABOP):**
- **Идентичность/контроль (governance):** Keycloak → JWT c ролями/группами. Шлюз проверяет каждый вызов. Клиент лишь **фильтрует каталог** для UX — доверять клиенту нельзя.
- **Тонкий клиент (Agent Plane surface):** сайдкар — локальный рантайм агентов + реестр модулей.
- **Каталог агентов:** что пользователь может дёрнуть; видимость по роли; сюда же «конструктор агента» (скилл/шаги/DoD/анти-паттерны, цепочки).
- **Tool plane:** MCP-инструменты + локальные модули.
- **Data plane / коннекторы:** доступ к Office/CRM/ИС через ABOP Data Plane (источник→canonical), **под правами пользователя** (делегированный доступ), не сервис-аккаунт.

**Поверхности вызова — приоритет (выбрано):**
1. **Глобальный хоткей / квик-лаунчер** — оверлей по Ctrl+Space из любого приложения: выделил текст → выбрал агента → результат. Быстро, без интеграции с конкретной системой. Технически: Electron `globalShortcut` + маленькое окно + чтение выделения/буфера.
2. **Office-надстройка (Word/Excel)** — task-pane + кнопка на ленте → **локальный API сайдкара** (та же сессия). Самое ценное для менеджеров (контекст текущего документа/листа как источник). Технически: Office.js add-in (manifest, sideload/AppSource) → `fetch http://127.0.0.1:<port>`.
- Далее: контекстное меню ОС «Отправить в APE» + deep-link `ape://agent/<id>?...`.

**Локальный API сайдкара (контракт для host-систем):** уже есть база (`/api/modules/*`, auth,
health). Формализовать: `/api/agents` (каталог по роли), `/api/run` (запуск агента с контекстом:
текст/файл/выделение), `/api/session` (кто вошёл). Версионировать (`/api/v1/...`), CORS/локальный
токен для host-приложений.

**RBAC — как именно:**
- **Уровни:** агент × инструмент × источник данных (гранулярность на всех трёх).
- **Энфорс:** сервер (шлюз) по ролям/группам Keycloak в JWT. Клиент фильтрует каталог (UX), сервер запрещает по факту.
- **Делегированный доступ к системам:** токен-обмен через Keycloak (impersonation/token-exchange) или пер-юзер OAuth к каждой системе; коннектор ходит **от имени пользователя**. Граница доверия и хранение токенов — отдельное решение (черновик: token-exchange на шлюзе, пер-юзер refresh в защищённом хранилище).

## 3. Влияние на roadmap

Порядок работ пересобирается вокруг тонкого клиента:
1. **UX-фичи тонкого клиента** (juser-friendly, см. `docs-ux-usability.md`) — делают само окно удобным. Идут первыми, они дёшевы (фронт).
2. **Каталог агентов + конструктор агента** — «что дёргаем».
3. **RBAC-модель** (роли/группы Keycloak → политика шлюза → фильтр каталога).
4. **Поверхности вызова:** глобальный хоткей (быстро) → Office-надстройка (ценно) → контекст-меню/deep-link.
5. **Коннекторы с делегированным доступом** (Office/ИС) — самый ответственный кусок (безопасность).
6. Локальный API сайдкара → версионировать как продукт.

Продуктовые фичи (Word/Excel-экспорт, OCR/NLP) встраиваются как модули/инструменты в этот каркас.

## 4. Открытые вопросы (зафиксировать отдельными ADR)
- Механизм делегированного доступа к системам (token-exchange vs пер-юзер OAuth; хранение токенов).
- Модель каталога агентов и привязка видимости/запуска к ролям.
- Формат и версионирование локального API + аутентификация host-приложений к сайдкару.
- Дистрибуция Office-надстройки (sideload в организации vs AppSource).
