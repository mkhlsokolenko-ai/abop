## Что нашли и починили по ходу

1. **Сервер падал под нагрузкой** — инструмент `rag_search` тянул CLI-логин (`token()` → «Ты не вошёл» → `SystemExit`), а `SystemExit` из потока инструмента завершал uvicorn с кодом 0. Убрали CLI-зависимый инструмент из серверного реестра, вокруг вызова инструмента — `BaseException`-guard.
2. **Задания, убитые рестартом, висели в `running` навсегда** — переклад протухших делался только при старте и только по `heartbeat_at` (у задания, умершего до первого heartbeat, поле пустое). Теперь переклад раз в минуту, порог `ABOP_RUN_STALE_SEC=90` (heartbeat каждые 15 с), критерий `COALESCE(heartbeat_at, started_at, created_at)`. Иначе лимит «1 прогон на пользователя» блокировал новые задания этих пользователей.
3. **Чтение Data Plane и детерминированный движок проверок** выполнялись в event loop — вынесены в поток (`asyncio.to_thread`), чтобы HTTP не ждал файловые чтения при больших снапшотах.
4. Клиент теста: ретраи на сетевых ошибках, лимит соединений.

## Выводы

- Узкое место — **число воркеров × задержка LLM**, не память и не CPU (CPU ~14 %, RSS < 100 МБ при лимите 1,5 ГБ). Удвоение воркеров дало ×2,5 по пропускной способности; на стенде оставлено `ABOP_RUN_WORKERS=4`. Дальше упрёмся в `ABOP_RUN_LLM_CONCURRENCY` (3) и в сам LLM-инстанс.
- Приём в очередь под нагрузкой — сотни миллисекунд, HTTP остаётся отзывчивым.
- Шина (Redpanda на сервере-2) на волну не влияла: результаты и DLQ публикуются асинхронно.
- Для «сотен пользователей» нужны: воркеры 6–8 на реплику, вторая реплика API (Postgres должен быть доступен обеим), лимит LLM-параллелизма под инстанс, приоритетные классы очереди.
