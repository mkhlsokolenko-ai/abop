# Объединённое демо: веб-расследование + 2 менеджерских (десктоп → веб)

> Актуализировано 27.09.2026 под текущий стенд: очередь прогонов, шаблоны навыков (51/56), доставка результата в системы через превью, PDF-отчёт по шаблону, десктоп 1.0.8, своя модель за 0 ₽. Что изменилось за неделю — [SESSION_SUMMARY_2026-09-27.md](SESSION_SUMMARY_2026-09-27.md).

Гайд-сценарий выступления. Три идеи, которые продаём одним потоком:
1. **ABOP — инженерная платформа** для сборки агентов; **десктоп-чат — рабочая среда** пользователя.
2. **«Код считает истину, LLM объясняет»** — цепочки/расхождения/находки считает детерминированный движок, модель только объясняет и цитирует норму. Числа в отчёте не галлюцинированы.
3. **Управляемая автономия (HITL)** — всё, что уходит наружу/меняет системы, только по подтверждению человека; конверт задал инженер в ABOP. **Результат живёт в системе заказчика**: перечень находок — это превью того, что уйдёт в трекер, вики или на почту, а не счётчик на экране.

Демо из двух частей:
- **Часть A (веб):** сложный экспертный кейс — «Расследование по симптомам» (агент **«Следователь 1С»**). Показываем засев, схему шаблона, красивый отчёт.
- **Часть B (десктоп → веб):** два простых менеджерских агента гоняем **цепочкой из десктопа**, видим ценность — и тут же **пересобираем их в вебе с нуля и делаем общими** (доступными всему отделу по ABAC/RBAC).

Всё на **реальных** системах стенда `5.129.192.63` (не слайды). Модель — своя (Qwen3-30B на GPU-боксе), прогон стоит 0 ₽; облако включается только как запасной путь.

# ЧАСТЬ A. Веб-сценарий «Расследование по симптомам» (invest1c)

## A.1. Суть (для продажи)

Агент **«Следователь 1С»** не выдаёт плоский список нарушений — он **ведёт расследование от симптома**: берёт каждую реализацию и протягивает всю цепочку операции **реализация → взаиморасчёты (оплата на р/с) → НДС (счёт-фактура выданный)** по *реальным* basis-ссылкам 1С (`ДокументОснование`), сверяет суммы по звеньям и показывает, **на каком именно звене рвётся связь и на сколько рублей расходятся суммы**. Норму НК РФ гл.21 (счёт-фактура ст.169, вычет ст.171–172, момент базы ст.167) агент подтягивает из корпуса (RAG/sLAVA) и **цитирует**, а не пересказывает по памяти.

Ключевой месседж: **«LLM не решает то, что решается запросом»** — цепочки и расхождения считает детерминированный код (`ape.audit1c_trace_chains`, `cli/ape.py`), LLM только объясняет и цитирует норму.

## A.2. Что за агент (контракт + граф)

**Контракт** `demo/invest1c/contract_invest1c.json`:

| Поле | Значение |
|---|---|
| `audit_id` | `invest1c-holding-2026` |
| `family` | **audit** (семья = отдел, ABAC) |
| `навыки` | `audit1c-extract`, `audit1c-graph-build`, `invest1c-trace`, `invest1c-verdict` |
| доступ (read) | «Снимок 1С · doc1c/ref1c»; «Нормы НК гл.21 / ФСБУ · sLAVA» |
| `autonomy_level` | **A1** · `criticality` **T2** |
| HITL | **1** — `главбух-подтверждает-заключение` |
| residency | on-prem, egress `sLAVA-proxy (анти-SSRF)` |
| baseline (до агента) | first_time_right **0.55**, escalation **0.45** → цель 0.9 / 0.15 |

**Граф** `demo/invest1c/agent_body.json` (агент **«Следователь 1С»**) — линейная цепочка:
```
audit1c-extract → audit1c-graph-build → invest1c-trace → invest1c-verdict (HITL)
   → OUT: BookStack (book_id 1, «Заключение по расследованию 1С», run:false, hitl:true)
```
Единственный HITL внутри — на `invest1c-verdict`; OUT-узел `run:false,hitl:true` → наружу ничего без подтверждения.

## A.3. Засев данных

invest1c **переиспользует канонический снимок 1С кейса audit1c** (сущности `doc1c`/`ref1c`). Данные приходят рецептами:
- `demo/audit1c/recipes/audit1c_docs.json` → `doc1c` (source `http://201.51.5.24:8092/audit-data/dump.json`, секция `documents`);
- `demo/audit1c/recipes/audit1c_refs.json` → `ref1c` (та же URL, секция `catalogs`).

Ключевые поля `doc1c`: `СуммаДокумента`, `СуммаНДС`, **`Основание_uuid`** (ДокументОснование — ключ цепочки), `Основание_тип`. Типы, которые ищет расследование: `РеализацияТоваровУслуг`, `СчётФактураВыданный`, `ПоступлениеНаРасчётныйСчёт`.

**Нормы для RAG-вердикта** (корпус `slava_audit1c_norms`) — из `demo/audit1c/norms/*.md`: `01_nds_scheta_faktury.md` (ст.168/169/171/172 НК), `05_deb_kred_raschety.md` (дебиторка/кредиторка сч.60/62), `06_period_cutoff.md` (cut-off), `03_vgo_konsolidatsiya.md` (ВГО).

> ⚠️ **Конкретные суммы/номера документов в репо не хранятся** — реальный дамп отдаёт удалённый сервис `201.51.5.24:8092`. Точные числа для гайда **снять с живого прогона на стенде** (см. A.5 — что записать). Единственное зашитое число — `110000 ₽` в demo-превью шаблона (заглушка).

## A.4. Что производит расследование (структура)

Ядро — `ape.audit1c_trace_chains()` (`cli/ape.py`), вызывается **детерминированно ДО LLM** в `execute_agent_run`. Для каждой реализации находит по обратному индексу `referenced_by` детей (счёт-фактуру, оплату), считает `diff = sum_real − sum_pay`, фиксирует **симптомы**:
- нет СФ → «НДС не предъявлен покупателю (нет счёта-фактуры выданного)»;
- нет оплаты → «нет оплаты — открытая дебиторская задолженность»;
- `|diff|>0.01` → «сумма оплаты ≠ сумме реализации (разница {diff} ₽)».

Одна investigation:
```
{ id:"INV-<Номер>", серьёзность:"высокая|средняя", симптом,
  цепочка:[ {звено:"Реализация", есть:true, примечание:"СуммаДокумента X ₽, НДС Y ₽"},
            {звено:"Счёт-фактура выданный (НДС)", статус:"есть|РАЗРЫВ"},
            {звено:"Оплата · взаиморасчёты", примечание:"поступило Z ₽|нет"} ],
  сверка:{ реализация_₽, оплачено_₽, разница_₽, ндс_₽, ндс_предъявлен },
  нормы_rag:[ «процитированная норма НК гл.21» ] }
```
Сводка `investigations_summary`: `{ total, broken, by_sev:{высокая,средняя} }`. График (детерминир.): bar **«Расхождения по расследованиям, ₽»** (`charts.py`).

**Что добавляет LLM по шаблонам навыков** (`skills/invest1c-trace/template.json`, `skills/invest1c-verdict/template.json`): trace отдаёт `цепочки / сводка / итог`, verdict — `заключения[] / требуется_подтверждение / итог` строго по JSON-схеме (structured output своей модели). Эти структуры попадают в `result.skill_outputs`, на доску прогона (читаемый текст, не JSON) и в отчёт — секции «Вердикт» и «Трассировка» таблицами.

## A.5. Показ в ВЕБЕ (пошагово)

1. **Канва → сценарий «Расследование по симптомам»** (ключ `invest1c`).
2. **«▶ Собрать и запустить»** → `POST /api/demo/prepare {scenario:"invest1c"}` → примет контракт, создаст «Следователь 1С» (audit, A1). *(нужен доступ к семье audit)*.
3. **Прогон.** Ставится в очередь (в модалке — статус задания), порядок: extract → graph-build → **trace** → **verdict(HITL)** → OUT. Код строит граф и трассирует цепочки, LLM объясняет по шаблонам навыков. На своей модели — 0 ₽, в карточке прогона видны токены и модель.
4. **В модалке прогона появляется:**
   - карточка «Расследований: N» + разбивка по серьёзности;
   - список `INV-<номер>` с симптомом, **цепочкой звеньев** (Реализация → СФ выданный → Оплата) с «есть»/**«РАЗРЫВ»** и **расхождением ₽**;
   - **bar-чарт «Расхождения по расследованиям, ₽»**;
   - каждое расследование с **цитатой нормы НК гл.21** (RAG);
   - **заключение по шаблону verdict** — таблица заключений (цепочка, звено-разрыв, норма, что проверить) и флаг «требуется подтверждение».
5. **HITL.** `invest1c-verdict` + OUT BookStack → заявка в очередь, наружу ничего. Главбух открывает **превью** (в вебе — очередь HITL, в десктопе — «Посмотреть и подтвердить»): видно ровно тот отчёт, который уйдёт.
6. **После подтверждения** — публикация отчёта по шаблону **`invest`** в **BookStack** (book_id 1, «Заключение по расследованию 1С»). Тот же отчёт можно получить по требованию: `GET /api/runs/{run_id}/report?format=pdf` или кнопка **«📄 Отчёт PDF»** на карточке прогона в десктопе (файл в «Загрузки»).

## A.6. Схема шаблона отчёта invest («красивый отчёт без мусора»)

Принцип: **разделение содержания и представления** — код/LLM дают ДАННЫЕ, шаблон в БД (`report_templates`) задаёт ВИД, рендер — безопасная подстановка `{{ключ}}` (без exec/Jinja). Меняешь шаблон в Postgres → меняется вид без передеплоя.

**Шаблон `invest`** лежит в репо — `reports/invest.html` (+ общий `reports/base.css`, имена в `reports/index.json`), при старте сеется в `report_templates`; в рантайме источник правды — БД, правка в UI имеет приоритет над посевом. Блоки по порядку:
```
шапка (title · Агент/дата · verdict)
[карточка-сумма] Расследований: {{investigations_total}}
{{charts}}                              ← bar-чарт расхождений ₽
<h2>Вердикт</h2> {{skill_invest1c_verdict}}      ← структурированный ответ навыка таблицей
<h2>Расследования от симптома</h2> {{investigations}}
<h2>Трассировка</h2> {{skill_invest1c_trace}}
{{findings}}                           ← аудит-находки A/B/C/D, если есть
<h2>Доставка</h2> {{deliveries}}
футер (Сформировано ABOP · агент · дата)
```
Плейсхолдеры `{{skill_<sid>}}` (дефисы → подчёркивания) и общий `{{skills}}` рендерят JSON-ответ навыка по его шаблону извлечения: объект — строки «ключ: значение», список объектов — таблица, список строк — маркеры (`report_store.struct_html`). Подробно — `reports/README.md`, [SKILL_TEMPLATES.md](SKILL_TEMPLATES.md).

**Авто-выбор шаблона** (`_auto_template_id`): есть `investigations` → **invest**; `by_class` → **audit1c**; structured-навык → **digest**; иначе → **default**. OUT-узел может задать `report_template_id` явно; эндпоинт отчёта принимает `?template=`.

Рендер каждой investigation (`_report_context`) — карточка `.inv`: `.sev` серьёзность, `.sym` «INV — симптом», `.chain` цепочка звеньев моноширинно, `.delta` «расхождение Δ N ₽» на песочном фоне, `.norm` «§ норма» зелёным курсивом со ссылкой. **Не `json.dumps` — человекочитаемо.**

> **Как править шаблон в UI:** экран **«Данные» → «🧩 Редактор шаблонов»** → выбрать `invest` → правка HTML в textarea → **Предпросмотр** (на демо-данных) → **Сохранить** (нужен admin). Правки переживают рестарт и пересборку образа: builtin с `editor='seed'` обновляются из `reports/`, пользовательские — нет.

# ЧАСТЬ B. 2 общеменеджерских: цепочка в десктопе → пересбор в вебе как общие

Оба агента — семья **`management`** («Менеджмент», отдел). Демо-пакеты `demo/mailtasks/`, `demo/bft/`.

## B.1. Агенты и засев

### Агент 1 — «Дайджест задач» (mailtasks, роль `task-digester`)
Разбирает входящую почту в задачи → 2 приоритетные на день → письмо заказчику; заводит задачи в Redmine и шлёт письмо — обе доставки под HITL (A1, T3).
- Навыки: `mail-triage` (read) → `daily-plan` (read) → `client-letter` (**write, hitl**).
- Шаблоны извлечения (`skills/<sid>/template.json`): mail-triage → `писем_разобрано / задачи[] / без_действия / требуют_уточнения`; daily-plan → `дата / приоритетные[] / очередь / риски`; client-letter → `кому / тема / в_работе / план_на_сегодня / сроки / нужно_от_вас`. На доске — читаемый текст, в отчёте `digest` — таблицы.
- OUT: `redmine` («Задачи из почты») + `email` (`client@demo.local`) — оба `run:false, hitl:true`; отчёт по шаблону **`digest`** (разбор почты, план дня, письмо).

### Агент 2 — «Аналитик БФТ» (bft, роль `bft-writer`)
Берёт задачу из трекера → пишет БФТ (цель/контекст/функц.требования/критерии/границы) → публикует в BookStack + письмо автору — обе под HITL.
- Навык: `bft-draft` (**write, hitl**); шаблон — `задача / название / цель / контекст / роли[] / функциональные_требования[] (FR-n, must/should/could) / нефункциональные / критерии_приёмки[] (дано/когда/тогда) / границы / открытые_вопросы / готовность_к_публикации`.
- OUT: `bookstack` (book_id 1) + `email` (`author@demo.local`) — `run:false, hitl:true`.

> **Доставка в системы по шаблону** (секция `delivery` в template.json — задача/страница/письмо собираются из полей ответа, превью → «да» → коннектор → ссылка в карточке) сейчас включена у аудитора 1С (`audit1c-explain`, `audit1c-rank` → задачи Redmine; проверено: Redmine #18 за 4 с). Для менеджерских кейсов она в плане (дайджест → письмо, БФТ → задача); на демо их результат уходит через OUT-узлы, как описано выше — тоже под HITL с превью.

## B.2. Шаг 1 — прогон ЦЕПОЧКИ в ДЕСКТОПЕ

Осмысленная цепочка **«Дайджест задач» → «Аналитик БФТ»**: Агент 1 триажит почту, среди задач выделяет письмо o.director «проверить БФТ»; его выход уходит контекстом Агенту 2, который по этой задаче пишет БФТ.

**Как показать:**
1. ABOP Desktop → **Чат** → бар **«🔗 Цепочки агентов»** → **«＋ Собрать»**.
2. Имя «Почта → БФТ»; шаги: **Дайджест задач**, затем **Аналитик БФТ**; доставка результата — **BookStack** (или чат).
3. **▶ Запустить**. Цепочка идёт через очередь (между шагами может ждать вашего «да»). В чате — карточка по каждому шагу: находки шага 1 (задачи, план дня), находки шага 2 (БФТ), **🎫 токены на шаг и сумму по цепочке**, строки доставки (`bookstack → … · ожидает вашего подтверждения`), `trace_id`, кнопка **«📄 Отчёт PDF»**.
4. **HITL** всплывает в чате: «🛡 Агент подготовил внешнее действие» → **«Посмотреть и подтвердить»** открывает превью (кто/куда/тема и текст целиком; для команд коннектора — Действие/Куда/Навык) → подтвердить → БФТ уходит в BookStack. Для команд в системы ссылка на созданный объект возвращается в карточку («✓ выполнено: …»).

*Реплика: «Менеджер собрал из готовых агентов конвейер за 20 секунд, прогнал — выход одного стал входом другого, результат в вики под его подтверждением».*

> Механика цепочки: `POST /api/pipelines/{id}/run` (задание очереди `kind=pipeline`) — выход шага → `_result_to_context` → контекст следующего («=== РЕЗУЛЬТАТ ПРЕДЫДУЩЕГО АГЕНТА ЦЕПОЧКИ ===»). Если у шага есть доставка под HITL — задание уходит в `awaiting_hitl` с чекпоинтом и продолжается после решения. Промежуточные шаги — только в чат, последний — как настроено. Есть и **авто-сборка**: `POST /api/pipelines/suggest {q}` — семантика + LLM собирают цепочку под задачу.

## B.3. Шаг 2 — ПЕРЕСОБРАТЬ в вебе с нуля + сделать ОБЩИМИ

*Реплика: «Понравилось — заведём это как штатных агентов отдела, доступных всем менеджерам, а не только на моём десктопе».*

### Собрать агента (веб)
**Путь А — авторинг из семьи/навыков** (`POST /api/agents/author`, manager+):
1. Веб → «Агенты/Строю» → создать → семья **Менеджмент** → роль **Дайджест задач** (навыки `mail-triage, daily-plan, client-letter` подтянутся) / **Аналитик БФТ** (`bft-draft`).
2. Сохранить → draft-агент.

**Путь Б — граф + контракт** (`/api/contracts/ingest` → `/api/agents`): принять LUDA-бандл (или готовый `mailtasks-daily-2026` / `bft-writer-2026`), собрать граф на канве, сохранить — семья/роль берутся из контракта.

### Что делает агента «ОБЩИМ» vs «моим» (ABAC/RBAC)
Ключ — поле **`source`** + флаг **`owner`** (`GET /api/agents`):
- `source="authored"` → **«мой»** (owner=true), собран под себя, `edit_scope="user"`.
- `source="contract"` (через `/api/contracts/ingest`+`/api/agents` или `/api/demo/prepare`) → **ОБЩИЙ**, привязан к семье-отделу контракта.
- **Доступность по роли:** `GET /api/agents` фильтрует `can_see_family(u, family)` — агент виден сотрудникам своего отдела (`family == department`), admin/support — всем.

**Чтобы сделать общим (шаги):** собрать граф → привязать к контракту семьи-отдела (`mailtasks-daily-2026`) → `POST /api/agents {name, contract_audit_id:"mailtasks-daily-2026", graph}` → `source=contract` → **виден всему отделу `management`**. Чтобы «мой» authored-агент стал общим — пересобрать как contract-агента.

*В десктопе это видно сразу: модуль **«Мои агенты»**, вкладки **Мои агенты / Общие** — общие приезжают в «Общие» по ABAC.*

## Отчёты и схемы — что подчеркнуть про «красивые отчёты без мусора»

- **4 шаблона отчётов** в репо `reports/` (`default`, `audit1c` — пояснения/рейтинг/первопричины + находки A/B/C/D, `invest` — вердикт/расследования/трассировка, `digest` — разбор почты/план дня/письмо), посев в БД, правка в веб-редакторе. Общий CSS `reports/base.css` — единый визуальный язык (индиго-шапка, карточки-суммы, бейджи классов, таблицы). PDF — `GET /api/runs/{id}/report?format=pdf`, кнопка в десктопе, OUT-узлы email/BookStack/pdf.
- **Шаблоны навыков** (`skills/<sid>/template.json`, **51 из 56**): строгая JSON-схема ответа + инструкция + `max_tokens` (+ `delivery`). Модель отвечает structured output'ом (vLLM xgrammar), обрезанный ответ чинится (`_repair_json`), на доске — читаемый текст (`_render_struct`), в отчёте — таблицы. Источник правды — БД: импорт без пересборки `scripts/push_templates.py`, правка в UI снимает builtin, `/reset` возвращает версию репо.
- **Дефолтная схема находок** для навыков без шаблона: `{находки:[{запись, наблюдение*, сумма, норма}], итог}` → `• наблюдение [запись] — сумма · норма: …`.
- **Графики авто** (`charts.py`): «Находки по классам» (bar), «Расхождения по расследованиям, ₽» (bar), «Задачи по приоритету» (pie) — inline-SVG, числа из результата детерминированно.

## Нарратив / 4 тезиса (проговорить)
1. **Один рантайм, свои данные.** Веб и десктоп ходят в тот же ABOP; агент под правами менеджера (RBAC/ABAC); модель на self-host — данные не уходят.
2. **Код считает истину, LLM объясняет.** Цепочки/расхождения/находки — детерминированный движок; LLM объясняет и цитирует норму (RAG), не выдумывает числа.
3. **Управляемая автономия (HITL).** Наружу — только по подтверждению с превью; конверт задал инженер в ABOP. Результат живёт в системе заказчика (задача, страница, письмо, PDF-отчёт), а не в счётчике на экране.
4. **Платформа vs среда.** В вебе собрал/сделал общим → сразу доступно менеджеру в десктоп-чате по его роли.
