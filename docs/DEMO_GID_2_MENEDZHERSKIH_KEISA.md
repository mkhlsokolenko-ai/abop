# Объединённое демо (воскресенье): веб-расследование + 2 менеджерских (десктоп → веб)

Гайд-сценарий выступления. Три идеи, которые продаём одним потоком:
1. **ABOP — инженерная платформа** для сборки агентов; **десктоп-чат — рабочая среда** пользователя.
2. **«Код считает истину, LLM объясняет»** — цепочки/расхождения/находки считает детерминированный движок, модель только объясняет и цитирует норму. Числа в отчёте не галлюцинированы.
3. **Управляемая автономия (HITL)** — всё, что уходит наружу/меняет системы, только по подтверждению человека; конверт задал инженер в ABOP.

Демо из двух частей:
- **Часть A (веб):** сложный экспертный кейс — «Расследование по симптомам» (агент **«Следователь 1С»**). Показываем засев, схему шаблона, красивый отчёт.
- **Часть B (десктоп → веб):** два простых менеджерских агента гоняем **цепочкой из десктопа**, видим ценность — и тут же **пересобираем их в вебе с нуля и делаем общими** (доступными всему отделу по ABAC/RBAC).

Всё на **реальных** системах стенда `5.129.192.63` (не слайды).

# ЧАСТЬ A. Веб-сценарий «Расследование по симптомам» (invest1c)

## A.1. Суть (для продажи)

Агент **«Следователь 1С»** не выдаёт плоский список нарушений — он **ведёт расследование от симптома**: берёт каждую реализацию и протягивает всю цепочку операции **реализация → взаиморасчёты (оплата на р/с) → НДС (счёт-фактура выданный)** по *реальным* basis-ссылкам 1С (`ДокументОснование`), сверяет суммы по звеньям и показывает, **на каком именно звене рвётся связь и на сколько рублей расходятся суммы**. Норму НК РФ гл.21 (счёт-фактура ст.169, вычет ст.171–172, момент базы ст.167) агент подтягивает из корпуса (RAG/sLAVA) и **цитирует**, а не пересказывает по памяти.

Ключевой месседж: **«LLM не решает то, что решается запросом»** — цепочки и расхождения считает детерминированный код (`ape.audit1c_trace_chains`, `cli/ape.py:3675`), LLM только объясняет и цитирует норму.

## A.2. Что за агент (контракт + граф)

**Контракт** `demo/invest1c/contract_invest1c.json`:

| Поле | Значение |
|---|---|
| `audit_id` | `invest1c-holding-2026` |
| `family` | **audit** (семья = отдел, ABAC) |

| HITL | **1** — `главбух-подтверждает-заключение` |
| residency | on-prem, egress `sLAVA-proxy (анти-SSRF)` |
| baseline (до агента) | first_time_right **0.55**, escalation **0.45** → цель 0.9 / 0.15 |

**Граф** `demo/invest1c/agent_body.json` (агент **«Следователь 1С»**) — линейная цепочка:
```

```
Единственный HITL внутри — на `invest1c-verdict`; OUT-узел `run:false,hitl:true` → наружу ничего без подтверждения.

## A.3. Засев данных

invest1c **переиспользует канонический снимок 1С кейса audit1c** (сущности `doc1c`/`ref1c`). Данные приходят рецептами:
- `demo/audit1c/recipes/audit1c_docs.json` → `doc1c` (source `http://201.51.5.24:8092/audit-data/dump.json`, секция `documents`);
- `demo/audit1c/recipes/audit1c_refs.json` → `ref1c` (та же URL, секция `catalogs`).

Ключевые поля `doc1c`: `СуммаДокумента`, `СуммаНДС`, **`Основание_uuid`** (ДокументОснование — ключ цепочки), `Основание_тип`. Типы, которые ищет расследование: `РеализацияТоваровУслуг`, `СчётФактураВыданный`, `ПоступлениеНаРасчётныйСчёт`.

**Нормы для RAG-вердикта** (корпус `slava_audit1c_norms`) — из `demo/audit1c/norms/*.md`: `01_nds_scheta_faktury.md` (ст.168/169/171/172 НК), `05_deb_kred_raschety.md` (дебиторка/кредиторка сч.60/62), `06_period_cutoff.md` (cut-off), `03_vgo_konsolidatsiya.md` (ВГО).

> ⚠️ **Конкретные суммы/номера документов в репо не хранятся** — реальный дамп отдаёт удалённый сервис `201.51.5.24:8092`. Точные числа для гайда **снять с живого прогона на стенде** (см. A.5 — что записать). Единственное зашитое число — `110000 ₽` в demo-превью шаблона (заглушка).

## A.4. Что производит расследование (структура)

Ядро — `ape.audit1c_trace_chains()` (`cli/ape.py:3675`), вызывается **детерминированно ДО LLM** (`web_api.py:2946`). Для каждой реализации находит по обратному индексу `referenced_by` детей (счёт-фактуру, оплату), считает `diff = sum_real − sum_pay`, фиксирует **симптомы**:
- нет СФ → «НДС не предъявлен покупателю (нет счёта-фактуры выданного)»;
- нет оплаты → «нет оплаты — открытая дебиторская задолженность»;
- `|diff|>0.01` → «сумма оплаты ≠ сумме реализации (разница {diff} ₽)».

Одна investigation:
```
{ id:"INV-<Номер>", серьёзность:"высокая|средняя", симптом,
  цепочка:[ {звено:"Реализация", есть:true, примечание:"СуммаДокумента X ₽, НДС Y ₽"},
            {звено:"Счёт-фактура выданный (НДС)", статус:"есть|РАЗРЫВ"},
            {звено:"Оплата · взаиморасчёты", примечание:"поступило Z ₽|нет"} ],
  сверка:{ реализация_₽, оплачено_₽, разница_₽, ндс_₽, ндс_предъявлен },
  нормы_rag:[ «процитированная норма НК гл.21» ] }
```
Сводка `investigations_summary`: `{ total, broken, by_sev:{высокая,средняя} }`. График (детерминир.): bar **«Расхождения по расследованиям, ₽»** (`charts.py:165`).

## A.5. Показ в ВЕБЕ (пошагово)

1. **Канва → сценарий «Расследование по симптомам»** (ключ `invest1c`).
2. **«▶ Собрать и запустить»** → `POST /api/demo/prepare {scenario:"invest1c"}` → примет контракт, создаст «Следователь 1С» (audit, A1). *(нужен доступ к семье audit)*.
3. **Прогон.** Порядок: extract → graph-build → **trace** → **verdict(HITL)** → OUT. Код строит граф и трассирует цепочки, LLM объясняет.
4. **В модалке прогона появляется:**
   - карточка «Расследований: N» + разбивка по серьёзности;
   - список `INV-<номер>` с симптомом, **цепочкой звеньев** (Реализация → СФ выданный → Оплата) с «есть»/**«РАЗРЫВ»** и **расхождением ₽**;
   - **bar-чарт «Расхождения по расследованиям, ₽»**;
   - каждое расследование с **цитатой нормы НК гл.21** (RAG).
5. **HITL.** `invest1c-verdict` + OUT BookStack → заявка в очередь, наружу ничего. Главбух подтверждает.
6. **После подтверждения** — публикация HTML-отчёта (шаблон `invest`) в **BookStack** (book_id 1, «Заключение по расследованию 1С»).

## A.6. Схема шаблона отчёта invest («красивый отчёт без мусора»)

Принцип: **разделение содержания и представления** — код/LLM дают ДАННЫЕ, шаблон в БД (`report_templates`) задаёт ВИД, рендер — безопасная подстановка `{{ключ}}` (без exec/Jinja). Меняешь шаблон в Postgres → меняется вид без передеплоя.

**Шаблон `invest`** (`_INVEST_HTML`, `server/report_store.py:169`), имя «Отчёт расследования от симптома». Блоки по порядку:
```
шапка (title · Агент/дата · verdict)
[карточка-сумма] Расследований: {{investigations_total}}
{{charts}}                              ← bar-чарт расхождений ₽
<h2>Расследования от симптома</h2> {{investigations}}
{{findings}}                           ← аудит-находки A/B/C/D, если есть
<h2>Доставка</h2> {{deliveries}}
футер (Сформировано ABOP · агент · дата)
```
**Авто-выбор шаблона** (`_auto_template_id`, `web_api.py:2408`): есть `investigations` → **invest**; `by_class` → **audit1c**; structured-навык → **digest**; иначе → **default**. OUT-узел может задать `report_template_id` явно.

Рендер каждой investigation (`web_api.py:2446`) — карточка `.inv`: `.sev` серьёзность, `.sym` «INV — симптом», `.chain` цепочка звеньев моноширинно, `.delta` «расхождение Δ N ₽» на песочном фоне, `.norm` «§ норма» зелёным курсивом со ссылкой. **Не `json.dumps` — человекочитаемо.**

> **Как править шаблон в UI:** экран **«Данные» → «🧩 Редактор шаблонов»** → выбрать `invest` → правка HTML в textarea → **Предпросмотр** (на демо-данных) → **Сохранить** (нужен admin). Правки переживают рестарт (builtin с `editor='seed'` обновляются из кода, пользовательские — нет).

## B.2. Шаг 1 — прогон ЦЕПОЧКИ в ДЕСКТОПЕ

Осмысленная цепочка **«Дайджест задач» → «Аналитик БФТ»**: Агент 1 триажит почту, среди задач выделяет письмо o.director «проверить БФТ»; его выход уходит контекстом Агенту 2, который по этой задаче пишет БФТ.

**Как показать:**
1. ABOP Desktop → **Чат** → бар **«🔗 Цепочки агентов»** → **«＋ Собрать»**.
2. Имя «Почта → БФТ»; шаги: **Дайджест задач**, затем **Аналитик БФТ**; доставка результата — **BookStack** (или чат).
3. **▶ Запустить**. В чате — карточка по каждому шагу: находки шага 1 (задачи, план дня), находки шага 2 (БФТ), **🎫 токены на шаг и сумму по цепочке**, доставка финала (**awaiting_hitl → BookStack**), `trace_id`.
4. **HITL** всплывает в чате: «⏸ Требуется подтверждение» → подтвердить → БФТ уходит в BookStack.

*Реплика: «Менеджер собрал из готовых агентов конвейер за 20 секунд, прогнал — выход одного стал входом другого, результат в вики под его подтверждением».*

> Механика цепочки: `POST /api/pipelines/{id}/run` (`web_api.py:3199`) — выход шага → `_result_to_context` → контекст следующего («=== РЕЗУЛЬТАТ ПРЕДЫДУЩЕГО АГЕНТА ЦЕПОЧКИ ===»). Промежуточные шаги — только в чат, последний — как настроено. Есть и **авто-сборка**: `POST /api/pipelines/suggest {q}` — семантика + LLM собирают цепочку под задачу.

## B.3. Шаг 2 — ПЕРЕСОБРАТЬ в вебе с нуля + сделать ОБЩИМИ

*Реплика: «Понравилось — заведём это как штатных агентов отдела, доступных всем менеджерам, а не только на моём десктопе».*

### Собрать агента (веб)
**Путь А — авторинг из семьи/навыков** (`POST /api/agents/author`, manager+):
1. Веб → «Агенты/Строю» → создать → семья **Менеджмент** → роль **Дайджест задач** (навыки `mail-triage, daily-plan, client-letter` подтянутся) / **Аналитик БФТ** (`bft-draft`).
2. Сохранить → draft-агент.

**Путь Б — граф + контракт** (`/api/contracts/ingest` → `/api/agents`): принять LUDA-бандл (или готовый `mailtasks-daily-2026` / `bft-writer-2026`), собрать граф на канве, сохранить — семья/роль берутся из контракта.

### Что делает агента «ОБЩИМ» vs «моим» (ABAC/RBAC)
Ключ — поле **`source`** + флаг **`owner`** (`web_api.py:1999`):
- `source="authored"` → **«мой»** (owner=true), собран под себя, `edit_scope="user"`.
- `source="contract"` (через `/api/contracts/ingest`+`/api/agents` или `/api/demo/prepare`) → **ОБЩИЙ**, привязан к семье-отделу контракта.
- **Доступность по роли:** `GET /api/agents` фильтрует `can_see_family(u, family)` — агент виден сотрудникам своего отдела (`family == department`), admin/support — всем.

**Чтобы сделать общим (шаги):** собрать граф → привязать к контракту семьи-отдела (`mailtasks-daily-2026`) → `POST /api/agents {name, contract_audit_id:"mailtasks-daily-2026", graph}` → `source=contract` → **виден всему отделу `management`**. Чтобы «мой» authored-агент стал общим — пересобрать как contract-агента.

*В десктопе это видно сразу: модуль **«Мои агенты»**, вкладки **Мои / Общие** — общие приезжают в «Общие» по ABAC.*

## Отчёты и схемы — что подчеркнуть про «красивые отчёты без мусора»

- **4 шаблона** (`report_store.py`): `default` (всё), `audit1c` (находки A/B/C/D + нормы), `invest` (расследования + расхождения ₽), `digest` (задачи/дайджест). Общий CSS — единый визуальный язык (индиго-шапка, карточки-суммы, бейджи классов A=красный/B=оранж/C=жёлт/D=циан).
- **Схема находок навыка** (`runner.py:_FINDINGS_SCHEMA`): `{находки:[{запись, наблюдение*, сумма, норма}], итог}`. Рендерится читаемо `• наблюдение [запись] — сумма · норма: …` (НЕ сырой JSON — `_extract_json` вытаскивает JSON даже из преамбулы/забора; freeform-навыки не обрезаются).
- **Схема извлечения** (`schema_store`): кастомные JSON-схемы под навык (`schema_template_id`) — «схема шаблона», меняешь в БД → меняется структура данных.
- **Графики авто** (`charts.py`): «Находки по классам» (bar), «Расхождения по расследованиям, ₽» (bar), «Задачи по приоритету» (pie) — inline-SVG, числа из результата детерминированно.

## Нарратив / 4 тезиса (проговорить)
1. **Один рантайм, свои данные.** Веб и десктоп ходят в тот же ABOP; агент под правами менеджера (RBAC/ABAC); модель на self-host — данные не уходят.
2. **Код считает истину, LLM объясняет.** Цепочки/расхождения/находки — детерминированный движок; LLM объясняет и цитирует норму (RAG), не выдумывает числа.
3. **Управляемая автономия (HITL).** Наружу — только по подтверждению; конверт задал инженер в ABOP.
4. **Платформа vs среда.** В вебе собрал/сделал общим → сразу доступно менеджеру в десктоп-чате по его роли.

## Тайминг (≈15 мин)
