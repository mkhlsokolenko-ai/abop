# План: единый вид навыков, исполнение графа, ветвление, мультиагент

План закрытия разрывов, вскрытых аудитом 29.09.2026, и перехода к мультиагентности. Порядок выбран
так, чтобы каждый этап давал работающий результат сам по себе и не ломал демо-стенд.

## Корень проблемы

Аудит показал три вещи, которые связаны друг с другом:

1. **Граф агента не исполняется.** Волны считаются, но реальный прогон запускает все навыки одним
   махом, игнорируя рёбра. Навык не может получить выход другого навыка.
2. **Вход навыка нигде не объявлен.** Схема описывает только выход, вход задан прозой в инструкции.
   Поэтому совместимость шагов приходится угадывать по совпадению имён полей.
3. **Каталог разнороден.** Из 58 навыков: 53 со схемой, 37 с областью данных, 6 с доставкой, 1 со
   слотом. Одинаковые по смыслу поля названы по-разному в разных навыках.

Пока вход не объявлен, любая динамическая сборка цепочки будет угадывать. Поэтому фундамент — не
ветвление и не мультиагент, а контракт навыка.

---

## Этап 0. Контракт навыка и канонические поля

**Зачем.** Дать планировщику и канве проверяемый ответ на вопрос «можно ли поставить этот навык
после того».

**Что делаем.**

Расширяем `skills/<sid>/template.json` двумя разделами.

```json
"inputs": {
  "required": [
    { "from": "data",  "entity": "roadmap_item", "fields": ["проект", "пункт", "план_финиш"] },
    { "from": "skill", "skill": "audit1c-checks", "path": "находки", "fields": ["id", "класс"] },
    { "from": "slot",  "name": "проект" },
    { "from": "context", "note": "письмо руководителя или задача трекера" }
  ],
  "optional": [ ... ]
},
"produces": { "key": "находки[].id", "joins": ["находка"] }
```

Четыре источника входа: данные канонической сущности, выход другого навыка, значение слота, текст из
контекста. Поле `produces.key` объявляет сквозной ключ, по которому результат соединяется с другими
шагами.

**Канонические имена полей.** Заводим реестр: одно понятие — одно имя (`находка.id`, `сумма`,
`срок`, `проект`, `счёт_дт`). Навык либо использует каноническое имя, либо объявляет соответствие.
Это лечит расхождения вроде `дебет` против `счёт_дт` и `функциональная_работа` против
`функциональное`, из-за которых финансовый и бухгалтерский блоки сейчас не стыкуются.

**Инструменты.** Валидатор контракта (расширяем `scripts/check_templates.py`), проверка в тестах,
отчёт «каталог: что объявлено, что нет» одной командой.

**Готово, когда:** валидатор работает, реестр имён заведён, контракты описаны у навыков двух
вертикалей (аудит 1С и проектный контроль) и проходят проверку.

**Объём:** небольшой по коду, средний по продумыванию реестра имён.

## Этап 1. Детерминированное исполнение графа

**Зачем.** Это уже сломано в бою: порядок навыков внутри агента не соблюдается, и передать результат
одного навыка другому нельзя.

**Что делаем.**

1. Прогон исполняет навыки **по волнам**, которые уже умеет считать движок. Внутри волны параллельно,
   между волнами последовательно.
2. Выходы волны складываются в **контекст прогона** под ключом навыка. Следующая волна получает не
   всё подряд, а ровно то, что объявила во входах: сущность, путь, поля.
3. Передаётся **структура, а не проза**. Прозаический блок остаётся как запасной вариант для навыков,
   которые объявили вход `context`.
4. Навык, чьи обязательные входы не покрыты, **не запускается**: в прогоне появляется честная отметка
   «пропущен: нет входа X», вместо тихого мусора на выходе.

**Готово, когда:** на аудите 1С видно, что объяснение получает находки от проверок, а рейтинг
получает объяснения; в карточке прогона видно порядок волн; пропуск по непокрытому входу отображается.

**Риск:** прогоны станут длиннее, потому что появится настоящая последовательность. Смягчение:
параллелизм внутри волны и бюджеты из этапа 4.

---

## Этап 2. Проверка совместимости при сборке агента

**Зачем.** Ошибку сборки надо ловить в канве, а не в прогоне.

**Что делаем.** При сохранении агента и по кнопке «Проверить»: для каждого навыка считаем, покрыт ли
каждый обязательный вход данными области, слотами или выходами предшественников. Непокрытый вход —
ошибка сборки с понятным текстом: какого поля не хватает и кто его производит. Подсказка «добавьте
навык X перед этим» строится по реестру `produces`.

**Готово, когда:** попытка собрать агента с разорванной цепочкой входов даёт конкретную ошибку и
предложение, а не молчаливое сохранение.

---

## Этап 3. Единый вид каталога

Самая объёмная часть, ведётся волнами по семьям, параллельно с этапами 4 и 5.

**Что приводим в порядок у каждого навыка:**

| Что | Сейчас | Цель |
|---|---|---|
| Схема результата | 53 из 58 | все, кроме стилевых гайдов |
| Входной контракт | нет ни у одного | у всех |
| Область данных | 37 | у всех, кто работает с данными |
| Слоты предмета | 1 | у всех, где предмет неоднозначен |
| Доставка | 6 | у всех, чей результат уходит в систему |
| Канонические имена полей | вразнобой | по реестру |

**Порядок семей:** аудит и расследование (вертикаль уже связная), менеджмент и проектный контроль
(там живёт новый кейс), финансы (там больше всего расхождений в именах), аналитика, остальные.

**Отдельно:** пять навыков без шаблона (`conventional-commits`, `docker-patterns`,
`fastapi-patterns`, `grill-me`, `test-writer`) — это стилевые гайды. Им контракт не нужен, им нужен
явный признак «справочный навык, в цепочку не встраивается».

**Кандидаты на слияние**, найденные аудитом: объяснение находок и вердикт расследования; письмо
заказчику и черновик письма; задачи из встречи и задачи из сырья; недельный отчёт, статус-отчёт и
финансовый отчёт. Решение по каждому принимаем отдельно: слияние уменьшает каталог, но ломает
привычные имена.

**Готово, когда:** отчёт по каталогу показывает сто процентов покрытия по обязательным полям для
выбранных семей, а валидатор стоит в тестах.

## Этап 4. Ветвление цепочек

**Зачем.** Сейчас цепочка строго линейна, между шагами едет проза с обрезкой.

**Что делаем.**

1. Шаг цепочки получает поля: условие запуска (`when`), откуда берёт вход (`inputs_from`), куда
   отдаёт результат, бюджет.
2. Появляются **параллельные ветви** и **узел слияния** с явной политикой: собрать всё, взять первый
   успешный, свести по ключу, проголосовать.
3. Между шагами едет **структурированный результат**, а не текст.
4. Ошибка шага не рушит цепочку, но помечает ветвь и попадает в слияние как «нет результата».

**Готово, когда:** демо-цепочка разветвляется на двух подрядчиков и сходится в общую сводку;
в карточке видно ветви и их состояние.

---

## Этап 5. Бюджеты, дедлайны, управление группой

**Зачем.** Параллельные ветви без ограничений разносят стоимость и время.

**Что делаем.**

- Бюджет на прогон и на ветвь: токены, деньги, время. Превышение — честная остановка ветви с
  пометкой, а не тихий таймаут.
- Группа заданий: идентификатор группы, отмена всей группы, повтор одной упавшей ветви без
  перезапуска остальных.
- Наблюдаемость: родительская трасса прогона и дочерние трассы ветвей, экспорт метрик наружу
  процесса, видимость очереди на модель.

**Готово, когда:** десять веток видны в журнале как одна группа, любую можно повторить, стоимость
группы считается до завершения, а не после.

---

## Этап 6. Веер по предмету

**Зачем.** Это первый настоящий мультиагент, и он почти не требует нового.

**Что делаем.** Один агент, список предметов, параллельные задания через существующую очередь,
слияние в сводку. Сорок проектов, двести контрагентов, тридцать участков учёта.

Слоты и сужение данных уже работают, граф с условиями здесь не нужен. Нужны: тип задания «группа» из
этапа 5 и узел слияния из этапа 4.

**Готово, когда:** запрос «сверь план и факт по всем моим проектам» даёт сводку по трём проектам
стенда с разбивкой и общим выводом.

---

## Этап 7. Общая память прогона и арбитраж

**Зачем.** Параллельные ветви ничего не знают друг о друге, а противоречия между ними никто не
разрешает.

**Что делаем.**

- **Блэкборд прогона**: ветви пишут промежуточные выводы под ключами, читают чужие. Доступ по
  контракту, не «всё всем».
- **Арбитраж**: при конфликте выводов двух ветвей решает либо правило (приоритет источника, свежесть
  данных), либо отдельный навык-арбитр, либо человек, если расхождение существенное.
- **Снапшот данных на прогон**, чтобы параллельные ветви видели одну и ту же картину, а обновление
  источника посреди прогона не меняло результат на лету.

**Готово, когда:** две ветви, пришедшие к разным выводам по одной находке, дают в сводке явное
указание на расхождение и его разрешение.

---

## Этап 8. Динамическое подключение навыков по контексту

**Зачем.** Это цель, ради которой делались предыдущие этапы.

**Что делаем.** Планировщик по запросу человека собирает цепочку сам: разбирает задачу на этапы,
подбирает навыки по контрактам (а не по совпадению слов), проверяет покрытие входов, добирает
недостающее инструментами, выбирает шаблон отчёта под форму результата.

Ключевое отличие от нынешнего подбора: решение принимается по **объявленным контрактам**, поэтому
собранная цепочка исполнима по построению, а не «скорее всего подойдёт».

**Готово, когда:** на наборе эталонных запросов планировщик собирает исполнимые цепочки без ручной
правки в большинстве случаев, а там, где не может, честно говорит, какого навыка или входа не хватает.

---

## Сквозные условия

**Регрессия.** Набор эталонных запросов и прогонов с известным правильным результатом. Гоняется на
каждом этапе. Метрики: доля исполнимых цепочек без правки, доля запусков не на тех данных, среднее
число уточнений, стоимость и время прогона.

**Демо не ломается.** Каждый этап выкатывается за признаком включения, старый путь работает, пока
новый не проверен на стенде.

**Железо.** Узкое место параллелизма не в коде: сейчас три вызова модели на прогон и двенадцать на
процесс, два воркера очереди. Перед этапом 6 нужно решение по мощности: второй бокс или платное
облако для пиков. Иначе десять ветвей упрутся в очередь к модели.

**Документация.** Каждый этап закрывается правкой схемы архитектуры и описанием механизма, иначе
через месяц никто не вспомнит, почему сделано так.

## Порядок и зависимости

```
0 контракт навыка ──┬──▶ 1 исполнение графа ──▶ 2 проверка сборки
                    │
                    └──▶ 3 единый вид каталога (волнами, параллельно)
                                    │
1 ──▶ 4 ветвление цепочек ──▶ 5 бюджеты и группы ──▶ 6 веер по предмету
                                                          │
                                                          ▼
                                              7 блэкборд и арбитраж
                                                          │
                                                          ▼
                                        8 динамическое подключение
```

Этапы 0, 1, 2 — фундамент, без них остальное строится на песке. Этап 3 идёт фоном и не блокирует
ничего, кроме полноты каталога. Этапы 4 и 5 делают цепочки управляемыми. Этап 6 — первая честная
мультиагентность. Этапы 7 и 8 имеет смысл начинать, только когда на реальных прогонах станет видно,
каких связей и разрешений не хватает.
