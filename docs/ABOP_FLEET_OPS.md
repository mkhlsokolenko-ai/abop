# ABOP — Управление флотом агентов в проде (Fleet / Operations)

**Что это:** недостающий РЕЖИМ продукта. Сейчас UI разработко-центричен (собрал → протестировал → обзор собранных), но НЕ управляет агентами В РАНТАЙМЕ прода: не видно, кто работает сейчас, сколько экземпляров, что делают, кем запущены; нет отзыва версии / пересмотра / вывода прод-агента. Этот документ вводит слой Operations.
**Почему критично:** без него ABOP — конструктор агентов (IDE), а НЕ «операционная система управления агентными процессами» (позиционирование из ревью). Заявленное позиционирование требует этого слоя.
**Связка:** PRD `ABOP_PRD.md` (добавляет FR-O), экраны `ABOP_SCREENS.md` (новая вкладка), безопасность `ABOP_DESIGN_GAPS.md` (ре-аттестация), рантайм `ABOP_RUNTIME_ARCHITECTURE.md` (трекинг инстансов).
**Статус:** концепция v1.0, к обсуждению.

---

## 1. Диагноз пробела

Сейчас жизненный цикл в UI обрывается на «протестировал»:
```
[Собрать на канве] → [Проверить исполнимость] → [Тест-прогон] → [Обзор собранных] ← ОБРЫВ
                                                                    ✗ что дальше в проде — не видно
```
Не хватает всего, что справа от «развернул»:
- **кто работает сейчас** (живые экземпляры), что делают, на каком шаге, кем инициированы;
- **сколько экземпляров** одного агента запущено параллельно, нагрузка;
- **на каких участках процесса / по каким задачам** сидят агенты (карта);
- **управление версией в проде:** отозвать (rollback), пересмотреть через канву (новая версия), вывести/удалить;
- **здоровье флота:** ошибки, стоимость, HITL-очередь по всем прод-агентам, дрейф качества.

**Вывод:** это не мелкая UI-прореха — это отсутствующий режим **Operations** рядом с существующими Авторинг и (одно-прогонным) Рантайм.

---

## 2. Понятийная модель (развести чётко)

| Понятие | Что | Живёт | Есть сейчас? |
|---|---|---|---|
| **Прогон (Run)** | одна задача от постановки до результата | ephemeral (минуты) | ✅ Пульт (§3) |
| **Агент-спека (Build)** | собранный на канве агент (роли/навыки/поток/конверт) | артефакт в сторе | ✅ Канва/Паспорт |
| **Развёртывание (Deployment)** | агент-спека **посажена на участок процесса** с триггером и политикой; работает постоянно | долго (недели+) | ❌ НЕТ |
| **Экземпляр (Instance)** | конкретный запущенный воркер развёртывания, обрабатывает поток/событие СЕЙЧАС | секунды-минуты, много параллельно | ❌ НЕТ трекинга |
| **Флот (Fleet)** | все развёртывания + их живые экземпляры | постоянно | ❌ НЕТ |

**Ключевое отличие:** прогон запускает человек разово; **развёртывание** само запускает прогоны по триггеру (событие из Data Plane push-адаптера / расписание / входящая задача) — экземпляр = один такой авто-прогон. То есть Deployment переиспользует run-механику + добавляет триггер, участок, версию, политику и ЖЦ.

## 3. Функции (FR-O) — что добавить

- **FR-O1 · Реестр развёртываний.** Список прод-агентов: имя, версия, участок процесса/триггер, статус (активен/пауза/отозван), владелец, автономия (≤ контракт LUDA), с какого времени.
- **FR-O2 · Живые экземпляры (live).** Сколько экземпляров каждого агента работает сейчас; что делает (задача/шаг/навык), кем/чем инициирован (событие/человек/расписание), длительность, стоимость, статус (думает/HITL/ошибка).
- **FR-O3 · Карта процессов.** Где какой агент сидит на потоке процесса (участок → агент → автономия) — перекличка с размещением/флоучартом LUDA (AS-IS/TO-BE).
- **FR-O4 · Жизненный цикл версии.** Развернуть (deploy) · Пауза/возобновить · **Отозвать версию** (rollback к предыдущей) · **Пересмотреть через канву** (открыть deployed → новая версия draft) · **Вывести/удалить** (retire, type-to-confirm; дренаж живых экземпляров).
- **FR-O5 · Здоровье флота.** Агрегаты: активные/ошибки/в HITL; стоимость флота (cost_journal); дрейф качества (падение прохождения DoD); алерты.
- **FR-O6 · Ре-аттестация** (стык с вкладкой Безопасность): периодический пересмотр прод-агентов и их прав — уже требовалась в GAPS §7, здесь получает объект (развёртывания).

## 4. Где в UI

- **Новая вкладка «Эксплуатация» / «Флот»** (Operations) в маршруте — рядом с Прогонами (одноразовыми) и Паспортом:
  - таб **Развёртывания** (реестр FR-O1 + ЖЦ FR-O4),
  - таб **Живые** (инстансы FR-O2, авто-обновление),
  - таб **Карта процессов** (FR-O3),
  - таб **Здоровье** (FR-O5).
- **Обзор (§2) дополнить:** не только «собрано/протестировано», но и «**в проде сейчас: N агентов · M экземпляров · что делают**» + HITL-очередь флота.
- **Паспорт агента (§7):** добавить прод-статус, версии, число живых экземпляров, кнопки ЖЦ.
- **Канва (§6):** действие «**пересмотреть развёрнутого**» → открывает deployed-версию как новый draft (FR-O4).

Маршрут после: `Обзор · Канва · Данные · Навыки · Прогоны · **Эксплуатация** · Паспорт · Безопасность · Настройки`.

## 5. Модель данных и рантайм (влияние на бэк — почему до достройки)

- **Агент получает статус и версии:** `draft → tested → deployed(vN) → retired`; откат = активировать предыдущую версию. Реестр развёртываний в сторе.
- **Deployment = {агент-спека vN, триггер, участок, политика автономии, владелец, статус}.** Триггер: push-событие Data Plane / расписание / входящая задача.
- **Instance = авто-прогон развёртывания:** переиспользует run-механику (волны/доска/аудитор), но помечен `deployment_id + instance_id`, инициатор, участок. Реестр живых инстансов (in-memory + стор).
- **Трекинг на 1-боксовом MoE-рантайме:** экземпляры делят единый MoE-движок (continuous batching); контроль параллелизма (лимит инстансов на развёртывание — не выесть VRAM/KV); `cost_journal` уже пишет per-run → агрегировать per-deployment/per-instance.
- **Governance в проде:** конверт/автономия/HITL/аудит применяются на КАЖДОМ экземпляре; аудит-след флота; отзыв версии при нарушении. Именно здесь governance из «проверки при сборке» становится «постоянным контролем в эксплуатации».

## 6. Мой вердикт (честно)

- **Наблюдение точное и важное.** Это не косметика — отсутствующий режим. Продукт сейчас доводит агента до «протестирован» и бросает; управления флотом в проде нет.
- **Бьёт по позиционированию:** твоё же ревью требовало «операционную систему управления агентными процессами». Без Fleet/Operations это IDE, не OS. Этот слой — то, что делает позиционирование правдой.
- **Правильно поднял до достройки бэка:** влияет на модель данных (версии/развёртывания/инстансы) и рантайм (трекинг живых экземпляров, лимиты параллелизма на боксе). Достраивать RUN/STREAM надо уже с прицелом на инстансы флота, а не только на одиночный прогон.
- **Приоритет:** высокий, но ПОСЛЕ базового рантайма — сначала должен работать одиночный прогон через SSE (task #15), затем развёртывание = автозапуск прогонов по триггеру + реестр/live/ЖЦ. То есть Fleet надстраивается над рабочим Run, не вместо него.

**Предложение:** внести **FR-O** в PRD, добавить вкладку «Эксплуатация» в экраны, и при реализации RUN/STREAM (#15) сразу закладывать `deployment_id/instance_id` + реестр, чтобы флот встал сверху без переделки.
