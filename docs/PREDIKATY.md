# Предикаты и правила: как добавить проверку

> Первая глава руководства разработчика, написанная вместе с библиотекой (шаг 1 плана «правила —
> данные»). Остальные главы — после шага 3, когда устоится интерфейс правил.
> Код: `cli/checks.py`. Тесты: `tests/test_predicates.py`.

## Три уровня и граница между ними

| Уровень | Кто делает | Где живёт | Цена изменения |
|---|---|---|---|
| **Правило** | методолог | данные (набор правил) | минуты, без релиза |
| **Составное правило** | методолог | данные | минуты |
| **Новый предикат** | разработчик | `cli/checks.py` | релиз с тестами |

Правило — это **предикат плюс параметры, и больше ничего**. Как только в параметрах заводится
арифметика, цикл или условие на условии, получается язык программирования без отладчика, типов и
тестов, который умеем читать только мы. Это хуже обычного Python.

**Три маркера «здесь нужен предикат, а не правило»** — если попало под любой, правило не
собирается:

1. вычисление по **множеству** записей (агрегация, сверка двух наборов);
2. обход **графа связей** (цепочка документов-оснований);
3. нетривиальная **нормализация** (нечёткое сопоставление, разбор текста).

## Что есть в библиотеке сегодня

| Предикат | Параметры | Пример применения |
|---|---|---|
| `поле_обязательно` | `поля`, `в` (опц.), `при` (опц.) | обязательные атрибуты категории |
| `единицы_измерения` | `единицы`, `в` (опц.) | «300 мм» там, где витрина ждёт литры |
| `не_меньше` | `поле`, `минимум` | изображений меньше минимума |
| `не_длиннее` | `поле`, `предел` | название длиннее лимита |
| `не_содержит` | `поле`, `запреты` | рекламная формулировка в названии |
| `значение_из_словаря` | `поле`, `допустимые`, `нарушение_если` | бренд вне списка допущенных; внутригрупповой оборот — наоборот, «входит» |
| `связанный_документ_есть` | `из`, `по` | реализация без счёта-фактуры, поступление без оплаты |
| `период_совпадает` | `поле`, `с`, `точность` | переходящая операция: оплата и основание в разных годах |
| `есть_строка_со_значением` | `в`, `поле`, `равно`, `через_справочник` | среди проводок нет дебета счёта 90.02 |
| `дубль_по_ключу` *(агрегатный)* | `ключ`, `где`, `подпись` | один ИНН у нескольких карточек контрагента |
| `разные_значения_по_ключу` | по одному ключу встречаются РАЗНЫЕ значения поля (один номер счёта — два ИНН поставщика) | `ключ`, `поле`, `подпись`, `где` | агрегатный: считается по всему набору. Отличие от дубля принципиальное — дубль сливают, а здесь две записи, которые слить НЕЛЬЗЯ, и одна из них неверна |
| `старше_дней` | `поле`, `дней`, `на_дату` (опц.), `если_остаток` (опц.) | аванс висит дольше квартала; документ не закрыт N дней |
| `парные_значения` *(агрегатный)* | `ключ`, `поле`, `пары`, `суммы` (опц.) | по контрагенту одновременно долг (60.01) и аванс (60.02) — сальдо не свёрнуто |
| `сверка_сторон` | `наши`, `их`, `дата`, `дебет`, `кредит`, `зеркально`, `подпись` (опц.), `проверять`, `остатки`, `порог` | строка расчётов, которой нет у второй стороны; расхождение входящих остатков |

Агрегатный предикат (помечен в библиотеке `по_набору`) вызывается один раз на весь набор, а не
на каждую запись: «дубль по ключу» — это вычисление по множеству, и по тому же маркеру оно и
попало в код, а не в правило.

### Сверка двух сторон: зеркальность и отказ

`сверка_сторон` сопоставляет наши строки расчётов со строками контрагента. Две вещи в нём не
случайны, и обе пойманы на живых данных заказчика:

* **`зеркально`** объявляет правило, а не угадывает код: в акте сверки наш дебет — это кредит
  контрагента, но та же форма нужна для сверки двух выгрузок ОДНОЙ стороны (своя 1С против своей
  банковской выписки), где переворачивать нельзя. Сравнение без зеркала дало «не сошлась ни одна
  строка» там, где сходились все.
* **Пустая вторая сторона — отказ, а не находка.** Из 107 актов в живой базе сторона контрагента
  заполнена в 4. Если считать её отсутствие расхождением, отчёт покажет 2147 находок, которых
  нет. Правило при этом тоже объявляет `применять_если`, но отказ стоит в предикате: это свойство
  сверки, а не настройка заказчика.

`проверять: "остатки"` отделяет спор о документе от спора обо всей истории до периода. Если
остаток второй стороны не заявлен вовсе, исход так и называется — «остаток контрагента не
заявлен», а не «разошлось на эту сумму»: по незаполненному полю судить нельзя.

### Правило применяется не ко всем записям

```json
"применять_если": { "тип": ["СписаниеСРасчётногоСчёта", "ПоступлениеНаРасчётныйСчёт"] }
```

Фильтр намеренно примитивен — равенство или вхождение в список. Логика сложнее означает, что
проверка просится в предикат.

### Цепочка находки

То, что человек читает в карточке расследования («реализация есть, счёта-фактуры нет, оплаты
нет»), описывается метками в правиле:

```json
"цепочка": [
  { "звено": "Реализация", "документ": "$запись" },
  { "звено": "Счёт-фактура выданный (НДС)", "есть": false, "примечание": "счёта-фактуры нет" },
  { "звено": "Оплата · взаиморасчёты", "документ": "@оплата",
    "примечание_если_нет": "поступления на р/с нет" }
]
```

`$факт.<ключ>` в примечании подставляет значение, которое вернул предикат. Иначе каждая новая
проверка снова требовала бы Python ради трёх подписей.

## Как устроено правило

```json
{
  "код": "ATTR_MISSING",
  "предикат": "поле_обязательно",
  "параметры": { "поля": "@правила.обязательные_атрибуты", "в": "атрибуты" },
  "причина": "не заполнен обязательный атрибут категории",
  "серьёзность": "высокая",
  "чинится": "из данных",
  "подсказка": "запросить значения у поставщика"
}
```

**Предикат не знает о вертикали.** Он отвечает только «нарушено или нет» и доказательством. Код
находки, причина, серьёзность и «чинится» приходят из правила — поэтому один предикат служит и
карточкам товара, и бухгалтерским документам.

### Ссылки — ровно две формы

```
$запись.поле      значение поля проверяемой записи
@имя.поле         поле справочника, связанного в блоке «контекст» набора
```

Расширять набор форм — только через ADR. Третья форма — это начало языка.

### Контекст: как правило дотягивается до справочника

```json
"контекст": [
  { "имя": "категория", "из": "category_map",
    "по": { "категория_поставщика": "$запись.категория_поставщика" },
    "взять": "категория_витрины",
    "если_нет": { "код": "CATEGORY_UNMAPPED", "чинится": "человеком",
                  "причина": "категория поставщика не сопоставлена категории витрины" } },
  { "имя": "правила", "из": "showcase_rule", "по": { "категория": "@категория" } }
]
```

Связь, которая ничего не нашла, — **не техническая ошибка, а находка по существу**. Либо она
объявлена в `если_нет` (и тогда это предметная находка вроде «категория не сопоставлена»), либо
движок сам вернёт `КОНТЕКСТ_НЕ_РАЗРЕШЁН`. Молчания быть не должно: правило, которому нечем
параметризоваться, просто не сработает, и запись окажется «чистой».

> Это не теория. При переезде витрины на общий движок в наборе стояло `$категория` вместо
> `@категория`. Ссылка разрешилась в саму себя, справочник не нашёлся, шесть правил молча не
> сработали — полнота упала с 74 % до 20 %, и все карточки выглядели исправными. Отсюда две
> защиты: громкая находка в прогоне и `проверить_набор()` при сохранении.

Если связь действительно необязательна — пишется `"необязательно": true`. Осознанно и видно.

## Как добавить предикат

1. **Проверьте, что он нужен.** Предикат добавляется, когда его просят **два разных заказчика**
   или он закрывает **пять и больше правил** в одной вертикали. Иначе библиотека превращается в
   свалку из двухсот блоков, где нужный не находится.
2. **Напишите функцию** `(запись, параметры, контекст, наборы) -> list[{поле, доказательство, факты}]`
   (агрегатный — `(записи, параметры, наборы)` и помечается `по_набору`). Никаких
   обращений к хранилищу: данные приходят аргументами — иначе предикат нельзя прогнать на
   исторической выгрузке.
3. **Объявите в `ПРЕДИКАТЫ`**: `применить`, `параметры` (по ним редактор строит форму), `описание`.
4. **Доказательство — обязательно и конкретно.** Не «нарушено правило», а «2 при минимуме 3»,
   «„300 мм“ — ожидается единица „л“». Находка без доказательства неаудируема.
5. **Тесты**: срабатывание, несрабатывание, пустые и битые данные. Предикат не имеет права падать
   на кривой записи — прогон не должен умирать из-за одной строки фида.
6. **Приёмка на исторических данных.** Там, где есть метка (лог отказов витрины, слепая разметка
   эксперта), новый предикат прогоняется по прошлому периоду: сколько сработал, сколько совпало с
   фактом, сколько ложных. Не совпал — не принят.

## Что уже переведено на правила

| Вертикаль | Проверок | Осталось кодом |
|---|---|---|
| карточка для витрины | 7 | — |
| аудит данных 1С | 9 | — |

Аудит переехал целиком: инварианты проводок, пять разрывов цепочек, дубли НСИ, внутригрупповой
оборот и переходящая операция. Приёмка — совпадение с базовой линией **поле в поле, включая
цепочки**: `tests/test_audit1c_rules.py` сверяет вывод с фикстурой, снятой со стенда до переезда.

Это не значит, что кодом не останется ничего и впредь. Три маркера выше никуда не делись:
агрегация, обход графа и нетривиальная нормализация так и живут предикатами — просто теперь
это **четыре строчки в библиотеке**, а не отдельный движок на вертикаль. Для сравнения: аудит
добавил в библиотеку `связанный_документ_есть`, `период_совпадает`, `есть_строка_со_значением`
и `дубль_по_ключу` — и три из четырёх уже переиспользуемы в любой предметной области.

**Метрика сработала:** вторая вертикаль потребовала четыре новых предиката. Третья должна
потребовать ноль-один — если снова четыре, набор пора пересматривать.

**Закрытие периода (15.10.2026).** Проверки готовности — непроведённые документы, документы без
основания, незакрытые авансы, неразвёрнутое сальдо — живут сущностью `close_rule` и исполняются
этой же библиотекой. Код не знает ни про счёт 60.02, ни про порог в 90 дней: у заказчика другой
план счетов и другие пороги, и менять их должен методолог, а не релиз.

Отличать блокер от предупреждения — тоже свойство правила (`серьёзность: блокирующая`):
непроведённый документ закрывать период не даёт, а висящий аванс закрыть не мешает, но его
спросит аудитор. Смешать их — значит либо парализовать закрытие, либо пропустить искажение.

## Кому что можно

| Роль | Правила | Предикаты |
|---|---|---|
| методолог заказчика | да, в интерфейсе | нет |
| партнёр-внедренец | да, в пакете вертикали | нет: пакет **не несёт** чужой Python |
| разработчик вендора | да | да, в библиотеку |

Запрет на чужой код в пакете вертикали — это тот же принцип, что в конверте агента: нельзя то,
что не объявлено. Загрузка стороннего Python в периметр с данными заказчика откроется только
вместе с песочницей, и это будет отдельное решение с ADR, а не побочный эффект формата пакета.

**Цена выбора названа прямо:** пока предикаты пишем только мы, потолок масштабирования — наша
пропускная способность. На первых клиентах это приемлемая плата за то, что в периметре не
исполняется чужой код.

## Где модель, а где нет

Модель может **написать кандидата-предиката и тесты к нему** — это авторинг. В исполнении
проверок её нет: находки считает код, иначе «почему карточку развернули» перестаёт быть
воспроизводимым ответом. Сгенерированный предикат принимается так же, как написанный руками:
ревью человека и зелёная приёмка на исторических данных.

## Здоровье библиотеки

Одна метрика: **сколько новых предикатов потребовала очередная вертикаль**. Ноль-один — библиотека
живая. Пять — библиотека не работает, и это сигнал пересмотреть набор, а не дописать ещё пять.
