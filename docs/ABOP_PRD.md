# ABOP v1.1 — Product Requirements Document

**Продукт:** ABOP (Agent-Based Operations Platform) — **среда разработки и исполнения агентов** в верифицированном конверте безопасности
**Версия документа:** 1.1 (переформулировка: рантайм → среда разработки; v1.0 описывал только рантайм)
**Статус:** draft, к утверждению
**Связанные документы:** `ABOP_ARD.md` (архитектура), `ABOP_ADR.md` (решения), `ABOP_TDR.md` (технические детали), `AGENT_FAMILIES_GUIDE.md` (работа с семьями)
**Внешние зависимости:** LUDA v2 (PRD, ADR, TDR, AOP) — 3 контракта; sLAVA (RAG-контур)
**Ядро (реализовано):** CLI `ape` (`cli/ape.py`) + FastMCP-шлюз (`server/`) — онтология/волны/Blackboard/Data Plane/навыки/память/аудитор. **Больше не «полигон перед переносом», а рабочее ядро**, над которым встают клиенты (CLI сегодня, веб-среда — надстройка).

---

## 1. Одним абзацем

ABOP — **среда, в которой собирают агента и тут же его исполняют**, не выходя из верифицированного конверта безопасности, внутри регулируемого периметра (ФСТЭК / ФЗ-152 / ДСП). Разработчик решения (доменный эксперт, не программист) **собирает** агента из готовых блоков — семей ролей, навыков с объявленной безопасностью, декларативных рецептов данных от систем-источников — на канве; **запускает** его прогоном волн с живым пультом, HITL-подтверждениями и governance-петлёй (Definition of Done); и всё это **под конвертом LUDA** — автономия агента не выше `DeploymentContract`, каждый перешаг в аудит-следе с провенансом и стоимостью. Три режима одной среды: **Авторинг** (собрать) → **Рантайм** (запустить) → **Governance** (доказать, что не вышел за конверт). Ключевой архитектурный принцип: **единое ядро, много клиентов** — CLI и веб-среда дёргают одни и те же функции ядра через тонкий API, а не парсят друг друга.

Продуктизация LUDA v2 как среды исполнения, эволюция VRATA на паттернах openclaw. Отдельный продукт и репозиторий; связь с LUDA/sLAVA — только версионированные контракты.

---

## 2. Что изменилось в v1.1 и почему

v1.0 описывал ABOP как **рантайм** — движок, который исполняет уже собранного агента. Но чтобы агента собрать, эксплуатировать и предъявить аудиту, рантайма мало: нужны авторинг (где агент рождается) и governance-поверхность (где видно, что он в конверте). ABOP переформулирован в **среду разработки агентов** — Agent IDE для регулируемого периметра.

### 2.1. Фронт — надстройка над ядром, а не обёртка над CLI

CLI `ape` уже содержит всё ядро: оркестрацию волнами, семьи/роли/навыки, Data Plane, память, аудитор. Соблазн — «натянуть веб поверх CLI-процесса». Это ловушка: CLI интерактивен (REPL, ANSI-рендер), парсить его вывод хрупко.

**Решение:** CLI и веб — **два тонких клиента над общим ядром**. Функции ядра (`cmd_agents`, `data_run`, `family_system`, `data_schema`, …) уже возвращают структуры, а не текст — проверено программным вызовом. Веб-среда дёргает их через тонкий API-слой (расширение FastMCP-шлюза `server/`), тем же контрактом `session_id` + JWT + `cost_journal`. CLI остаётся как есть. Это и есть «нативное встраивание в бэк на основе CLI».

### 2.2. Авторинг вводится в границы продукта

Раньше сборка агента и рецептов данных была вне PRD (подразумевалось «руками/в конфиге»). Теперь это **первоклассная часть среды**: канва сборки агента, no-code редактор рецептов данных, каталог навыков и коннекторов — с миграцией готовых паттернов из LUDA (канва СВОД, паспорт агента, Пульт HITL, дизайн-система, Keycloak-авторизация).

### 2.3. Что сознательно оставлено жёстким (из v1.0, неизменно)

- Оркестрация — только волнами (не свободный ReAct-цикл): ломает аудируемость.
- Числа — только из источника (`cite`); отсутствие данных — результат, а не повод к генерации.
- Автономия сверху ограничена контрактом LUDA всегда.
- Рецепты данных — декларативны, пишет человек, без исполняемого кода.
- Безопасность — на уровне навыка (`mode` × `egress` × `cite`), не контура.

## 3. Проблема

### 3.1. Со стороны заказчика

Компания хочет отдать часть операционной работы агентам, но упирается не в модель, а в четыре стены.

1. **Данные не готовы для агентов машиночитаемо.** Каждый агент переизобретает извлечение из почты, трекера, ERP; результат хрупок и неаудируем. Нет стабильного слоя типизированных сущностей с провенансом.
2. **Нет безопасного аудируемого рантайма ролей.** Оркестраторы дают либо свободный цикл (служба ИБ не согласует), либо жёсткий пайплайн без ролей и памяти (не покрывает работу аналитика/финансиста).
3. **Некому и негде собрать агента под конверт.** Собрать роль из навыков, привязать источники данных, задать точки HITL и предъявить это аудиту — сегодня делается кодом и разрозненно. Нет **среды**, где сборка, запуск и доказательство соблюдения конверта — единый маршрут.
4. **Нет управления агентами в проде.** Агента собрали и протестировали — а как он исполняется в эксплуатации, не видно: кто работает сейчас, сколько экземпляров, на каких участках процесса сидят, кем запущены; нет отзыва версии, пересмотра и вывода прод-агента. Маршрут обрывается на «протестирован», рантайм флота остаётся слепой зоной. *(концепция — `ABOP_FLEET_OPS.md`; решения — ADR-022..027)*

### 3.2. Со стороны поставщика (нас)

LUDA ставит диагноз и выпускает контракты, но контракт без среды, которая его исполняет и **соблюдает** видимо, — отчёт в стол. Нужна среда, которая принимает `DeploymentContract` как закон и предъявляет доказательство соблюдения на каждом прогоне.

### 3.3. Почему это отдельный продукт

Диагностика (LUDA) и среда исполнения (ABOP) покупаются в разные моменты и разными бюджетами, имеют разные релизные циклы и критерии приёмки. Связь — только через версионированные схемы контрактов.

## 4. Границы продукта

### В границах

**Авторинг (design-time):**
- **Канва сборки агента** — палитра семья/роль/навык, drag-and-drop, гибрид «проводной поток + LLM-узлы», LLM-черновик потока.
- **Редактор рецептов данных** — no-code `source → map → rules → emit` + предпросмотр на реальной выборке.
- **Каталог навыков** (карточка + тело + безопасность) и **Коннекторы** (реестр адаптеров источников, подключение/тест).
- **Паспорт агента** — превью конверта (роль + навыки + безопасность + схема потока) до запуска.

**Рантайм (run-time):**
- Оркестрация волнами, онтология Семья → Роль → Навык, переключение (`use_skill` / `become` / `handoff`), Blackboard.
- Пульт прогонов (живые волны, доска, эстафеты, вердикт аудитора, `cost_journal`); HITL-пульт (`dry_run` → approve).
- Data Plane: адаптеры источник → каноническая сущность → контракт; `data_query` / `data_get` / `data_schema`.
- Память: Blackboard (рабочая, per-run), долговременная с забыванием по TTL, диалоговая (дистилляция).

**Governance (конверт):**
- Приём 3 контрактов LUDA; автономия ≤ `DeploymentContract`; governance-петля (Definition of Done).
- Аудит-след каждого перешага, билинг, единый контракт вызова `session_id` + JWT + `cost_journal`.

**Платформа:**
- Единое ядро + тонкий API; CLI и веб-среда — клиенты. Авторизация (Keycloak SSO). Мультитенантность.

### Вне границ

- Аудит готовности процесса, вывод автономии, выпуск контрактов — **LUDA**.
- RAG по нормативке, ответы с цитатами из корпуса — **sLAVA**.
- Обучение/хостинг моделей — ABOP использует готовые LLM.
- Портфельная приоритизация — **MIRA**.
- Решение о допустимой автономии — назначает LUDA, ABOP исполняет в рамках.

### Продуктовая лестница

```
MIRA        →  LUDA         →  sLAVA          →  ABOP
портфель       диагноз          восполнение       СРЕДА разработки
инициатив      готовности       контекста         и исполнения агентов
               процесса         (RAG/норматив)    (собрать → запустить → конверт)
```

MIRA приоритизирует, LUDA ставит диагноз и выпускает контракты, sLAVA восполняет контекст, **ABOP — среда, где по контракту собирают агента и исполняют процесс в границах конверта.**

## 5. Пользователи

| Роль | Кто это | Что делает в среде | Что получает |
|---|---|---|---|
| **Разработчик решения** | Доменный эксперт, методолог, аналитик (не программист) | Собирает агента на канве, пишет рецепты данных, привязывает источники и навыки | Рабочий агент без написания кода |
| **Заказчик** | Владелец процесса, ИТ/фин-директор | Согласует запуск в рамках контракта LUDA, читает результат и аудит | Исполненная работа + доказательство конверта |
| **Оператор** | Дежурный, контролёр | Обрабатывает HITL-подтверждения (`action`/`dry_run`), разбирает исключения | Контроль ровно там, где действие необратимо/наружу |
| **Платформа (LUDA)** | Продукт-источник контрактов | Поставляет 3 контракта | Гарантию, что среда не превысит выданную автономию |

Явно: ABOP не рассчитан на бесконтрольное самообслуживание. Автономия — из контракта, действия — через HITL там, где предписано. Это определяет весь UX среды.

## 6. Функциональные требования

Сгруппированы по трём режимам среды + платформа + слой эксплуатации. Приоритет: **M** (MVP), **S** (следующий), **L** (позже).

### Ключевые концепции (развести чётко)

- **Прогон (Run)** — одна задача от постановки до результата; ephemeral (минуты), запускает человек разово. Есть сегодня (Пульт прогонов).
- **Развёртывание (Deployment)** — агент-спека, посаженная на участок процесса с триггером и политикой автономии; работает постоянно (недели+) и **само** запускает прогоны по триггеру (событие Data Plane / расписание / входящая задача). Отличие от прогона: развёртывание не разовое — оно порождает прогоны.
- **Экземпляр (Instance)** — конкретный запущенный воркер развёртывания = один авто-прогон, помеченный `deployment_id + instance_id` и инициатором; много параллельно, секунды-минуты.
- **Флот (Fleet)** — все развёртывания + их живые экземпляры; объект управления в проде.

Детали модели данных/рантайма (статусы `draft → tested → deployed(vN) → retired`, трекинг на 1-боксовом MoE) — `ABOP_FLEET_OPS.md §5`, ADR-022..027.

### FR-A. Авторинг (собрать агента)
- **FR-A1 · S** Канва сборки: палитра семей/ролей/навыков и источников; drag-and-drop узлов; связи (проводной поток) + LLM-узлы (гибрид); LLM-черновик потока по описанию цели. *(миграция канвы СВОД)*
- **FR-A2 · M** Редактор рецептов данных: no-code форма `source → map → rules → emit`; выбор адаптера (csv/http/sqlite/computed); предпросмотр канонических записей на реальной выборке до сохранения. *(поверх `data_run`)*
- **FR-A3 · M** Каталог навыков: список 37 навыков, карточка (название/когда применять), полное тело (`use_skill`), пометки безопасности (`mode`/`egress`/`cite`); фильтр по семье/режиму.
- **FR-A4 · M** Коннекторы: реестр подключённых источников (`SOURCE_ADAPTERS`); подключение нового; тест-прогон рецепта.
- **FR-A5 · S** Паспорт агента: перед запуском показать конверт — роль, навыки с безопасностью, схему потока, требуемую автономию vs выданную LUDA. *(миграция из LUDA)*

### FR-R. Рантайм (запустить)
- **FR-R1 · M** Запуск прогона: цель → план волн (с детерминированной декомпозицией по семьям), назначение семьи/роли на задачу.
- **FR-R2 · M** Пульт прогонов: живой прогресс волн (семья·роль·навык·статус), доска прогона (`/board`), эстафеты `handoff`, вердикт аудитора DoD, синтез, `cost_journal`.
- **FR-R3 · S** HITL-пульт: очередь действий `action`/`external` в режиме `dry_run`; предпросмотр (письмо/тикет/коммит) → approve/reject оператором; ничего не уходит наружу без одобрения. *(миграция Пульта из LUDA)*
- **FR-R4 · S** Память: просмотр доски per-run и архива прогонов; долговременная память с классом критичности и TTL; забывание; preflight-recall.

### FR-G. Governance (конверт)
- **FR-G1 · M** Приём 3 контрактов LUDA; жёсткий инвариант: автономия прогона ≤ `DeploymentContract.autonomy_level`.
- **FR-G2 · M** Governance-петля видима: Definition of Done, чеклист сверки, пробелы, ремедиация — в UI прогона.
- **FR-G3 · M** Аудит-след и билинг: каждый перешаг с провенансом; токены/стоимость per-node и per-run.

### FR-I. Платформа
- **FR-I1 · M** Единое ядро + тонкий API поверх функций `ape.py`/шлюза; CLI и веб — клиенты одного контракта вызова.
- **FR-I2 · M** Авторизация: Keycloak SSO, роли (разработчик/оператор/заказчик/admin). *(переиспользование из LUDA)*
- **FR-I3 · L** Мультитенантность источников и прогонов (общие креды vs BYO на арендатора).

### FR-O. Operations / Fleet (управлять флотом в проде)

Слой эксплуатации: управление агентами в РАНТАЙМЕ прода, где governance превращается из «проверки при сборке» в «постоянный контроль в эксплуатации». Надстраивается над рабочим одиночным прогоном (Рантайм), не вместо него. Концепция — `ABOP_FLEET_OPS.md`; решения — ADR-022..027.

- **FR-O1 · S** Реестр развёртываний: список прод-агентов (имя, версия, участок процесса/триггер, статус активен/пауза/отозван, владелец, автономия ≤ контракт LUDA, с какого времени). *(S — после того, как работает MVP-прогон Рантайма)*
- **FR-O2 · S** Живые экземпляры (live): сколько экземпляров каждого агента работает сейчас, что делает (задача/шаг/навык), кем/чем инициирован (событие/человек/расписание), длительность, стоимость, статус (думает/HITL/ошибка); авто-обновление.
- **FR-O3 · S** Карта процессов: где какой агент сидит на потоке (участок → агент → автономия), перекличка с размещением/флоучартом LUDA (AS-IS/TO-BE).
- **FR-O4 · S** Жизненный цикл версии: развернуть (deploy) · пауза/возобновить · **отозвать версию** (rollback к предыдущей) · **пересмотреть через канву** (открыть deployed → новый draft) · **вывести/удалить** (retire, type-to-confirm, дренаж живых экземпляров).
- **FR-O5 · S** Здоровье флота: агрегаты активные/ошибки/в HITL; стоимость флота (`cost_journal` per-deployment/per-instance); дрейф качества (падение прохождения DoD); алерты.
- **FR-O6 · L** Ре-аттестация: периодический пересмотр прод-агентов и их прав (стык с вкладкой Безопасность, GAPS §7 — здесь получает объект: развёртывания).

## 7. Навигация — канва-центричная (ADR-030)

**Корневая модель:** не 8 вкладок-ровней, а **один граф (канва) в центре + линзы над ним + палитра + конверт-рамка**. Всё нативно вытекает из центра; три режима среды (Авторинг/Рантайм/Governance) + Operations — это не разные экраны, а **способы смотреть на один и тот же граф** (линзы). Обоснование и оговорки — ADR-030; раскладка — `ABOP_SCREENS.md §0`.

**Линзы (переключаются над графом, объект не меняется):**
| Линза | Режим | Что на графе |
|---|---|---|
| **Строю** | Авторинг | сборка потока: drag-and-drop из палитры, LLM-узлы, LLM-черновик, настройки в инспекторе узла |
| **Запускаю** | Рантайм | волны/доска/аудитор/cost + HITL-полоса — оверлеем на узлах (б. Пульт) |
| **Эксплуатирую** | Operations | semantic-zoom того же графа до Организация→процесс, живые Instance, здоровье флота *(FR-O; ADR-022..027)* |
| **Конверт** | Governance | рамка+потолок автономии на узлах, стык с контрактами LUDA, аудит-след (б. Паспорт как оверлей) |

**Палитра (кормит канву, слева):** Агенты·Навыки (каталог 37 с телами/безопасностью)·Данные (рецепты+предпросмотр)·Коннекторы — источники для drag-and-drop В граф, а не отдельные пункты назначения.

**Вокруг центра:**
| Элемент | Роль |
|---|---|
| **Обзор** | нулевая линза/вход: портфель графов/агентов (статус конверта, расход) → провал в единый центр |
| **Конверт-рамка** | всегда видима вокруг канвы (value prop): автономия ≤ контракт · egress · HITL · семафор |
| **Инспектор** | настройки выбранного узла (агент/навыки/автономия/mode·egress·cite) или связи (data-контракт/handoff) |
| **Вызываемые поверхности** | Безопасность/RBAC · Настройки среды (модели/подключения/арендаторы) · Билинг/аудит-журнал — контекстные, привязаны к канве, не вкладки-ровни |

## 8. Что мигрирует из LUDA (не строим заново)

- **Канва сборки** (drag-and-drop, палитра-каталог, LLM-черновик потока, гибрид проводной+LLM) — из СВОД v2.
- **Паспорт агента** (verified envelope: scope + гарантии + flow-схема).
- **Пульт HITL** (очередь pending → одобрение → исполнение).
- **Фронт-стек:** buildless React (UMD + Babel, вендоренные файлы), дизайн-система, авторизация Keycloak/OIDC.
- Принцип «конверт лёгкий, гейт детерминирован, LLM его не решает» — переносится в governance-петлю.

---

## 9. Что ABOP не делает, хотя его об этом попросят

- Не повышает автономию сверх контракта LUDA (→ переаудит в LUDA).
- Не отвечает по нормативке из корпуса (→ sLAVA).
- Не диагностирует готовность процесса (→ LUDA, до ABOP).
- Не додумывает числа (навык с `cite` — только из источника).
- Не даёт писать исполняемый код в рецепт данных (декларатив + валидация схемой).
- Не парсит человеческие интерфейсы за пределами Data Plane-адаптеров.

## 10. Метрики успеха продукта

| Метрика | Смысл |
|---|---|
| Доля прогонов, не превысивших `autonomy_level` контракта | 100% — жёсткий инвариант |
| Доля `action`/`external`, прошедших HITL/`dry_run` до исполнения | 100% |
| Доля результатов, прошедших governance-петлю (DoD) | все задачи с объявленным DoD |
| Доля данных через Data Plane, а не скрейпингом | рост к 100% по покрытию источников |
| **Time-to-first-agent** (собрать рабочего агента в среде) | ключевая метрика среды разработки — минуты, не дни |
| Число семей/навыков/адаптеров, добавленных без правки ядра | расширяемость |
| Полнота аудит-следа: каждый перешаг в `cost_journal` с провенансом | 100% |
| **Агентов в проде** (активных развёртываний) | охват эксплуатации — Fleet как режим, не IDE *(FR-O)* |
| **Uptime развёртываний** | непрерывность работы флота, доля времени активен vs пауза/ошибка |
| **Доля инстансов в границах конверта** | 100% — governance в эксплуатации: каждый живой экземпляр ≤ автономии контракта |

Первые две — проверка того, что конверт реален. **Time-to-first-agent** — новая метрика v1.1: она мерит ABOP именно как среду разработки, а не только рантайм.
