# Пакет вертикали: как собрать и поставить

> Вторая глава руководства разработчика (шаг 4 плана «правила — данные»). Первая — про предикаты и
> правила: [PREDIKATY.md](PREDIKATY.md). Экономика поставки — [MONETIZATION.md](MONETIZATION.md).
> Код: `server/routes/verticals.py`. Тесты: `tests/test_verticals.py`.

## Что такое вертикаль

**Вертикаль — единица поставки.** Не папка по соглашению, не «набор настроек», а то, что
устанавливают одной операцией и за что платят. До шага 4 поставить вертикаль заказчику значило:
принять контракт, сохранить агента, залить рецепты, не забыть наборы правил — четыре операции
руками, и ни одна не проверяла остальные.

Вертикаль **не равна** демо-сценарию. Демо живёт в `demo/` и существует, чтобы показать; вертикаль
живёт в `verticals/` и существует, чтобы работать у заказчика. Путать их значит однажды привезти
заказчику демо-данные.

## Раскладка

```
verticals/<id>/
  vertical.json        манифест: что это, версия, что содержит, что требует, чем мерить
  contract.json        DeploymentContract — конверт прав агента (проходит ingress)
  agent_body.json      граф агента: узлы-навыки, связи, автономия
  rules/*.json         наборы правил (предмет + контекст + правила)
  recipes/*.json       рецепты «источник → каноническая сущность»
  norms/*.md           (опц.) экспертный справочник норм для вердикта
```

Чего в пакете **нет и не будет**: Python. Ни предикатов, ни адаптеров, ни навыков как кода. Это не
ограничение лицензии, а условие периметра — в контуре с данными заказчика не исполняется код,
который мы не видели. Отсюда блок `требует`: навыки и адаптеры должны быть в системе **заранее**.

## Манифест

```json
{
  "id": "omninet",
  "название": "Открытый протокол e-com: карточка для чужой витрины",
  "версия": "1.0.0",
  "область": "management",
  "описание": "...",
  "автор": "вендор",
  "источник": "опубликованные требования витрины B + лог отказов за период",
  "требует": {
    "сущности": ["feed_card", "showcase_rule", "category_map", "showcase_reject"],
    "адаптеры": ["json"],
    "навыки": ["feed-checks", "feed-fix", "feed-scorecard"]
  },
  "содержит": {
    "контракт": "contract.json",
    "агент": "agent_body.json",
    "правила": ["showcase-b"],
    "рецепты": ["omninet_catmap", "omninet_feed", "omninet_rejects", "omninet_rules"]
  },
  "метрика": {
    "как": "полнота и точность против лога отказов витрины (feed-scorecard)",
    "почему": "обещать процент нельзя — он считается на прошлом периоде заказчика"
  }
}
```

### Манифест не имеет права врать

Сверка идёт **в обе стороны**: что объявлено в `содержит`, то обязано лежать в папке, и наоборот —
файл, который есть, но не объявлен, тоже ошибка. Причина простая: пакет читают глазами по
манифесту, а ставят по файлам. Если они разошлись, заказчик получит не то, что прочитал в
описании, и узнает об этом на прогоне.

Плюс к этому при сверке прогоняется `checks.проверить_набор` по каждому набору правил: пакет с
неразрешимой ссылкой на справочник не «почти работает» — правила по нему молча не сработают, а
записи окажутся чистыми.

Невалидный пакет **не ставится**. Не «ставится с предупреждением».

### `метрика` — обязательное поле, а не украшение

Пилот продаётся как измерение, а не как обещание (принцип 5 в [MONETIZATION.md](MONETIZATION.md)).
Пакет обязан сказать, **чем** мерить его работу на данных заказчика и **почему** именно этим. Тест
проверяет, что оба поля заполнены: вертикаль без метрики нельзя ни принять, ни защитить.

## Установка

```
POST /api/verticals/<id>/install        # manager+
     {"перезаписать_правки": false}
```

Четыре шага, и каждый отчитывается словом **поставлен / обновлён / пропущен** с причиной:

| Шаг | Что происходит | Идемпотентность |
|---|---|---|
| контракт | ingress-валидация и приём | уже принят → пропущен |
| правила | поставочный набор читается из пакета | есть правка методолога → **пропущен** |
| рецепты | нормализация и запись в Data Plane | перезапись, рецепт один на имя |
| агент | `save_draft` из `agent_body.json` | версии не плодятся (ADR-024) |

**Правку методолога установка не трогает.** Это главное обещание формата: заказчик, который
правил правило в интерфейсе, не должен потерять свою работу от того, что вендор выпустил новую
версию пакета. В отчёте так и написано — «в системе есть правка v3 (buh.analyst), установка её не
трогает». Снять правку можно только явным `перезаписать_правки: true`, и тогда отчёт скажет
«правка снята по запросу, действует версия пакета».

**Агент ставится черновиком.** Посадка на участок карты — отдельное решение человека (ADR-043):
установка пакета не имеет права сама начать работать в чужом процессе.

## Как поставить из командной строки

```bash
export ABOP_API=https://abop.example.com   # адрес сервера
export ABOP_TOKEN=<JWT>                    # токен manager+
ape verticals                              # что есть и что уже стоит
ape verticals omninet                      # поставить
ape verticals omninet --overwrite          # поставить, сняв правки методолога
```

CLI ходит **в ту же ручку**, что интерфейс. Второго пути установки быть не должно: он разойдётся с
проверками — сверкой манифеста, требуемыми навыками, бережным отношением к правкам. Тест это
сторожит: в `cmd_verticals` запрещены прямые обращения к сторам.

## В интерфейсе

**Админка → Вертикали.** По каждому пакету видно: состояние (`установлена` / `готова к установке`
/ `не годна`), состав (наборы правил с пометкой «правка в системе», рецепты с их сущностями),
требования, метрика и источник. Если в системе чего-то нет — красной строкой, с прямым текстом:
«Пакет это не привозит: навыки и адаптеры ставит вендор».

После установки показывается отчёт — построчно, что именно изменилось. Кнопка «Поставить с
перезаписью правок» появляется **только** когда правки есть: кнопка «снести» там, где сносить
нечего, однажды снесёт нужное.

## Как собрать свою вертикаль

1. **Опишите предмет.** Какие канонические сущности нужны и есть ли они в `CANONICAL_SCHEMAS`.
   Нет — это задача вендору, а не поле в манифесте.
2. **Напишите рецепты** «источник → сущность». Один рецепт на сущность; `system_id` берите из
   реестра систем, а не вписывайте адрес руками — иначе права агента по этому адресу не проверить.
3. **Соберите наборы правил** из существующих предикатов. Если формы не хватает — читайте
   [PREDIKATY.md](PREDIKATY.md): три маркера «здесь нужен предикат» и правила вклада.
4. **Соберите агента** и контракт: какие навыки, какая автономия, какой выход наружу. Конверт
   проверяет ingress, и он откажет, если граф просит больше, чем объявлено.
5. **Назовите метрику** — на каких исторических данных заказчика будет считаться полнота и
   точность. Без этого пакет не принимается.
6. **Прогоните установку на чистой системе** и прочитайте отчёт целиком. Пакет готов, когда отчёт
   не содержит ни одного «пропущен» по причине, которой вы не ожидали.

## Чего формат пока не умеет

Сказано прямо, чтобы не выяснялось на внедрении:

- **Навыки пакет не везёт.** Карточка навыка — markdown, технически безопасна, но навык тянет за
  собой шаблон извлечения, источники данных и места в семьях. Пока это поставка вендора.
- **Карта процесса в пакет не входит.** Агент ставится черновиком, участок карты заказчик
  создаёт сам. Для первой вертикали это нормально, для десятой — повод вернуться к формату.
- **Нет версионного обновления.** Установка новой версии пакета поверх старой не считает разницу
  и не предлагает миграцию: рецепты перезаписываются, правила остаются. Нужен диff — это
  отдельное решение.
- **Нет арендаторов.** Пакет ставится в одну систему, у записей и агентов нет тенанта. Это шаг 5
  и блокер лицензионной модели целиком ([MONETIZATION.md](MONETIZATION.md)).
