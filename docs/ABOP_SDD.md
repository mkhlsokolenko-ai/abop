# ABOP — System Design Document (SDD, для инженеров)

**Назначение:** сквозной системный дизайн для инженеров — как части ABOP связаны в жизни, как ABOP **подхватывает уже работающих агентов** в организации (brownfield, рыночная совместимость) и как **контракты LUDA физически попадают в ABOP**. Дополняет: `ABOP_ARD.md` (архитектура), `ABOP_TDR.md` (модель данных/API), `ABOP_RUNTIME_ARCHITECTURE.md` (модели/исполнение), `ABOP_FLEET_OPS.md` (флот).
**Два фокуса этого документа (пробелы):** §3 Interop (подхват внешних агентов) · §4 Contract Ingress (LUDA→ABOP).
**Статус:** v0.1, к утверждению.

---

## 1. Позиционирование, определяющее дизайн

**ABOP — не ещё один агентный фреймворк, а governance-конверт НАД любым рантаймом агентов.** Организация уже держит агентов (на **LangChain/LangGraph** как де-факто основе; сверху — OpenClaw, Hermes, свои). Требование рынка: ABOP не заставляет переписывать — он **подхватывает существующих агентов и надевает на них верифицированный конверт безопасности** (автономия ≤ контракт LUDA, `mode/egress/cite`, HITL, аудит-след, ИБ). Это brownfield-стратегия: «не выкинь и перепиши», а «подхвати и заверни».

Следствия для дизайна:
- Ядро ABOP (Семья→Роль→Навык, волны, governance) — **референс-рантайм**, но НЕ единственный источник агентов.
- Между «чужими» агентами и governance-конвертом — **Agent Adapter Layer (AAL)**.
- Ров ABOP = governance/аудируемость/конверт, которых нет у LangGraph/OpenClaw/Hermes; совместимость = говорим на их языке (LangGraph IR, MCP, A2A).

## 2. Системный контекст и сквозная топология

```
┌── LUDA (диагноз) ──┐   3 контракта + EvidencePack     ┌────────────── ABOP ──────────────────┐
│ аудит готовности   │ ───────────────────────────────▶│  Contract Ingress (§4)                 │
│ → autonomy A0..A4  │   (файл / API / реестр)          │   валидация схем · привязка к Deploy   │
└────────────────────┘                                  │                                        │
                                                         │  Agent Adapter Layer (§3)              │
┌── Существующие агенты организации ──┐                  │   LangGraph/LangChain/OpenClaw/Hermes  │
│ LangGraph StateGraph · LangChain    │ ── импорт/wrap ─▶│   → унифицированный ABOP-агент         │
│ OpenClaw · Hermes · свои            │   (MCP/A2A/API)  │                                        │
└─────────────────────────────────────┘                 │  Governance-конверт (ядро)             │
                                                         │   волны · mode/egress/cite · HITL ·    │
┌── sLAVA (RAG/GraphRAG) ─────────────┐  knowledge_search│   автономия≤контракт · аудит · cost    │
│ Qdrant + эмбеддер + граф знаний     │◀────────────────▶│                                        │
└─────────────────────────────────────┘                 │  Data Plane (факты систем) · Fleet (§Ops)│
                                                         └────────────────────────────────────────┘
```
Три входа в ABOP: **контракты от LUDA** (что можно), **агенты организации** (кого исполнять), **данные/знания** (Data Plane факты + sLAVA/GraphRAG знания). Выход — исполненная работа под конвертом с аудит-следом.

## 3. Agent Adapter Layer (AAL) — подхват внешних агентов ⭐

**Цель:** принять агента, построенного вне ABOP, и исполнять его под тем же конвертом, что нативного. Единый внутренний контракт агента (роль/навыки/tools/автономия/безопасность) — внешние формы приводятся к нему.

### 3.1. Общий IR — LangGraph
LangGraph `StateGraph` (узлы + рёбра + состояние) структурно близок к ABOP-потоку/волнам → берём его как **промежуточное представление (IR)**. LangChain `Runnable`/agent — оборачивается как узел/навык. Прочие рантаймы (OpenClaw/Hermes/свои) приводятся к IR через их API или к «чёрному ящику» (§3.3).

### 3.2. Два режима интеграции
| Режим | Что делает | Governance | Когда |
|---|---|---|---|
| **Translate (трансляция)** | LangGraph-граф → ABOP-поток: узлы→операции, рёбра→связи/волны, tools→навыки с безопасностью | **тонкий** — на каждом узле (mode/egress/cite, HITL, автономия per-node) | есть доступ к графу (LangGraph/LangChain) — предпочтительно |
| **Wrap (обёртка)** | внешний агент = чёрный ящик; ABOP оборачивает его I/O прокси-слоем, перехватывает вызовы инструментов/egress | **грубый** — на границе (весь агент = один узел с политикой; действия наружу → HITL; I/O в аудит) | нет доступа к внутренностям (закрытый OpenClaw/Hermes/бинарь) |

### 3.3. Governance Wrapper (перехват)
Ключевой механизм совместимости: **прокси вокруг чужого рантайма**, который делает внешнего агента governance-compliant, не меняя его код:
- **Egress-перехват:** все внешние вызовы агента (API/почта/запись) идут через прокси ABOP → применяются `egress`-политика, анти-SSRF, PII-маска, `action→HITL` (dry_run+approve). Чужой агент физически не может выйти наружу мимо конверта.
- **Инструменты через MCP:** внешнему агенту отдаются tools ABOP по **MCP** (наш шлюз уже MCP) — `data_query`, `knowledge_search`, `save` и пр.; так LangGraph/OpenClaw-агент получает наши Data Plane/RAG и остаётся в периметре.
- **Автономия-гейт:** обёртка не даёт агенту превысить `autonomy_level` из DeploymentContract (ADR-013) — необратимые шаги блокируются/уходят в HITL.
- **Аудит I/O:** вход/выход/перешаги чужого агента пишутся в общий аудит-след + `cost_journal` (унифицированный контракт вызова: `session_id`+JWT+cost).

### 3.4. Протоколы совместимости (что говорим на рынке)
- **MCP** (Model Context Protocol) — уже базовый транспорт шлюза; чужие агенты получают наши tools и модели через MCP.
- **A2A** (Agent-to-Agent) — межагентное взаимодействие: ABOP-агент ↔ внешний агент как равноправные узлы (адаптер A2A→AAL).
- **LangGraph/LangChain SDK** — прямой импорт графа/Runnable (§3.2 Translate).
- **OpenClaw/Hermes** — через их API/gateway → Wrap (§3.2) или, где открыт граф, Translate.

### 3.5. Регистрация внешнего агента (поток)
```
Внешний агент (LangGraph/OpenClaw/…) 
  → AAL.import(source)                      # translate → ABOP-поток  |  wrap → чёрный ящик
  → маппинг на Семья/Роль (или «внешняя роль») + tools через MCP
  → навесить Governance Wrapper (egress/HITL/автономия/аудит)
  → AgentVersion(draft, origin=external:langgraph)   # версионируется как свой (ADR-024)
  → тест-прогон под конвертом → Паспорт → Развёртывание (Fleet)
```
Внешний агент дальше живёт как нативный: канва (пересмотр), паспорт (конверт), флот (эксплуатация), governance — одинаково.

## 4. Contract Ingress — как данные из LUDA попадают в ABOP ⭐

**Пробел:** «связь через версионированные контракты» была продекларирована, но не описан механизм. Вот он.

### 4.1. Что передаёт LUDA
LUDA-аудит выпускает **бандл** (`emit_contracts` → уже реализовано в LUDA):
- **CapabilityRequest** (`luda.capability_request/1.0`) — что должно уметься: семейство, навыки, модули/доступ, data-контракты.
- **DeploymentContract** (`luda.deployment_contract/1.0`) — на каких условиях: `autonomy_level` (A0–A4), критичность T1–T3, HITL-точки, резидентность, ограничения.
- **BaselineMeasurement** (`luda.baseline_measurement/1.0`) — как процесс работает сейчас: метрики + провенанс.
- **EvidencePack** — ссылки на свидетельства (провенанс аудита).

### 4.2. Транспорт (3 опции, поддержать минимум одну на старте)
| Опция | Как | Когда |
|---|---|---|
| **Файл-бандл** | экспорт JSON из LUDA (экран «Итог/ABOP» / `GET /api/audits/handoff`) → импорт в ABOP `POST /api/contracts/ingest` | MVP, ручной handoff |
| **Pull по audit_id** | ABOP тянет `GET {luda}/api/contracts?audit_id=…` | LUDA доступен по сети |
| **Реестр контрактов** | общий стор (обе системы читают/пишут по `audit_id`) | зрелая интеграция |

Связь — **только версионированные схемы** (ADR-027 LUDA / стык), без общего кода (CI `check-no-foreign-imports`).

### 4.3. Приём и валидация на границе ABOP
```
LUDA bundle → POST /api/contracts/ingest
  → валидация против схем luda.*/1.0 (jsonschema; отклонить невалидный)
  → сохранить как ContractSet{audit_id, capability, deployment, baseline, evidence_pack, version}
  → привязать к AgentVersion / Deployment
```
- **Инвариант границы:** ABOP не доверяет содержимому вслепую — валидирует схему + версию; несовпадение версии схемы → отказ с явной ошибкой.
- **EvidencePack** сохраняется для аудит-следа (провенанс: почему такая автономия).

### 4.4. Как контракт УПРАВЛЯЕТ агентом в ABOP
| Контракт | Куда применяется |
|---|---|
| **DeploymentContract.autonomy_level** | → `Deployment.autonomy_ceiling` — **потолок автономии** (ADR-013); Governance Wrapper и слайдер прав не дают превысить |
| **DeploymentContract.hitl_points** | → обязательные точки HITL в потоке агента |
| **DeploymentContract.residency** | → egress-политика (что не выходит из периметра) |
| **CapabilityRequest.skills/modules** | → чеклист сборки: агент (свой или внешний) должен покрывать требуемые навыки/доступы; недостаток — предупреждение |
| **BaselineMeasurement.metrics** | → база для Fleet-здоровья: с чем сравнивать эффект/дрейф в проде |
| **EvidencePack** | → аудит-след развёртывания (обоснование конверта) |

### 4.5. Жизненный цикл контракта
- Контракт версионируется вместе с `audit_id`; **переаудит в LUDA → новый контракт → новая версия развёртывания** (может поднять/опустить потолок автономии).
- Развёртывание без валидного контракта возможно только в «песочнице» (автономия A0/тест) — прод требует контракт (governance-инвариант).

## 4-bis. Обратная петля результата (ABOP → LUDA) ⭐

**Пробел (ADR-031):** Contract Ingress (§4) — это LUDA→ABOP. Но цикл замыкается только если **факт исполнения возвращается в LUDA** для сравнения с baseline. Без этого экран «baseline vs факт» (бриф экран 11) нечем наполнить. Вот обратный канал.

### 4-bis.1. Что публикует ABOP
После/во время пилота ABOP агрегирует **фактические метрики прогонов** развёртывания в контракт `abop.run_metrics/1.0`:
```
RunMetrics {
  deployment_id,                    // какое развёртывание
  baseline_ref: {audit_id, baseline_version},  // с каким снимком LUDA сравнивать (из ContractSet §4)
  window: {from, to},               // окно агрегации
  actuals: {                        // ТЕ ЖЕ метрики, что в BaselineMeasurement (сопоставимость)
    time_to_close, manual_intervention_rate, first_time_right, cost_per_run, ...
  },
  provenance: {run_ids[], instance_ids[], n_runs, cost_journal_ref},  // чем подтверждается (аудируемо)
  governance: {autonomy_used, hitl_count, envelope_violations},       // как шло под конвертом
  emitted_at
}
```
**Инвариант сопоставимости:** `actuals` использует те же ключи метрик, что `BaselineMeasurement.metrics` — иначе сравнение бессмысленно. Схема метрик приходит из baseline (LUDA — источник истины по составу метрик процесса).

### 4-bis.2. Транспорт (симметрично §4.2)
| Опция | Как |
|---|---|
| **Push** | ABOP по завершении окна шлёт `POST {luda}/api/run-metrics/ingest` |
| **Pull** | LUDA тянет `GET {abop}/api/deployments/{id}/metrics?window=` |
| **Реестр** | общий стор по `deployment_id`+`audit_id` |

Как и в §4 — **только версионированные схемы**, без общего кода. Провенанс (`run_ids`, `cost_journal_ref`) обязателен: LUDA показывает не «−34%», а «−34%, подтверждено N прогонами».

### 4-bis.3. Что делает LUDA с этим
- Экран **«baseline vs факт»** (бриф 11): `BaselineMeasurement.metrics` (план) ↔ `RunMetrics.actuals` (факт) → дельта по каждой метрике + провенанс.
- **Дрейф-детекция:** actuals уезжают от baseline → сигнал на **ре-аттестацию** (может изменить автономию → новый контракт → §4.5, цикл замыкается).
- **Обоснование эффекта:** фактический ROI/экономия для decision-карточки следующего процесса — доказательно, не прогноз.

### 4-bis.4. Инварианты
- ABOP публикует **только агрегаты и провенанс-ссылки**, НЕ сырьё прогонов (данные не покидают периметр сверх необходимого — egress-инвариант).
- LUDA валидирует `abop.run_metrics/1.0` на границе (как ABOP валидирует `luda.*` в §4.3) — двусторонняя граница доверия.
- Метрики без `baseline_ref` не принимаются (не с чем сравнивать).

## 5. Сквозные потоки (end-to-end, для инженеров)

**П1 · Нативный агент под контрактом:** LUDA-аудит → bundle → Ingress(§4) → сборка в канве (навыки покрывают CapabilityRequest) → тест под конвертом → Паспорт(автономия≤DeploymentContract) → Развёртывание(триггер) → инстансы-прогоны(волны на MoE) → аудит/cost → Fleet-мониторинг.

**П2 · Подхват внешнего агента:** существующий LangGraph-агент → AAL.import(translate|wrap, §3) → Governance Wrapper(egress/HITL/автономия) → сопоставить с DeploymentContract от LUDA → AgentVersion(external) → тест → развёртывание. Дальше как П1.

**П3 · Данные и знания:** прогон → `data_query` (Data Plane факты, freshness) + `knowledge_search` (sLAVA/GraphRAG знания с провенансом) → навык с `cite` не выдумывает.

**П4 · Эксплуатация:** развёртывание → триггер(webhook Data Plane/расписание) → инстанс(помеченный прогон) → governance на экземпляре → карта Операций(живые Эйп) → дрейф vs BaselineMeasurement → ре-аттестация/откат версии.

**П5 · Замыкание цикла (ABOP→LUDA):** прогоны накопили факт → ABOP агрегирует `RunMetrics`(§4-bis) → LUDA сравнивает с BaselineMeasurement на экране «baseline vs факт» → дрейф → ре-аттестация → новый контракт(§4.5). Цикл LUDA↔ABOP замкнут: диагноз → исполнение → факт → новый диагноз.

## 7. Открытые инженерные вопросы
1. **Глубина Translate LangGraph:** какие конструкции графа маппятся 1:1 на волны, какие требуют Wrap (циклы/условия/подграфы).
2. **Governance Wrapper для закрытых рантаймов:** перехват egress без доступа к коду — через сетевой прокси/sidecar? гарантии полноты перехвата.
3. **Contract Ingress транспорт для прода:** файл vs pull vs реестр; кто хранит истину по `audit_id`.
4. **Соответствие CapabilityRequest ↔ навыки внешнего агента:** авто-маппинг или ручная сверка при импорте.
5. **A2A-роль:** ABOP как A2A-хаб (внешние агенты как равноправные) vs только импорт.
6. **Версии схем контрактов:** политика совместимости при апгрейде `luda.*/1.x`.
