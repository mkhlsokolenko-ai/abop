# ABOP — Архитектура рантайма: модели, GraphRAG, кеши, план имплементации

**Цель:** перевести APE (полигон на курсовом шлюзе) в **локальный прод-рантайм ABOP** на ОДНОЙ карте **32–48 ГБ**: иерархия моделей (крупный оркестратор + мелкие 1.5–2B специалисты по семьям) + GraphRAG-подпитка знаниями, всё в закрытом периметре (ФСТЭК/ФЗ-152 — egress наружу закрыт, модели on-prem).
**Что переносим:** ядро `ape.py` (8 семей / роли / 37 навыков / Data Plane / память TTL / аудитор / handoff / волны) — уже готово. **Что меняем:** курсовой шлюз (`_mcp_call` → engineer-ai.pro) → локальный inference-слой.
**Статус:** v1.0, архитектура к утверждению.

## 1. Модельная иерархия (3 уровня)

```
┌──────────────────────────────────────────────────────────────┐
│ L1 · ОРКЕСТРАТОР — «мозг» (крупная reasoning-модель)          │
│   план волн · маршрут семья/роль · аудитор DoD · синтез       │
│   Qwen3-14B (thinking) AWQ-Int4 · резидентен · 1 экземпляр    │
├──────────────────────────────────────────────────────────────┤
│ L2 · СПЕЦИАЛИСТЫ ПО СЕМЬЯМ — «руки» (1.5–2B + LoRA)           │
│   исполнение навыков в роли: ReAct-шаги, tool-calling,        │
│   доменная генерация. Одна БАЗА 1.7B + 8 LoRA per-family      │
│   (vLLM multi-LoRA / S-LoRA), continuous batching             │
├──────────────────────────────────────────────────────────────┤
│ L3 · GraphRAG — «память знаний» (fallback при нехватке)       │
│   граф знаний домена семьи + embedder + retrieval             │
│   специалист неуверен → запрос знания → аугментация → повтор  │
└──────────────────────────────────────────────────────────────┘
```

**Разделение труда:** reasoning-тяжёлое (план/маршрут/аудит/синтез) — на крупном оркестраторе (редкие вызовы, качество); массовое исполнение навыков — на дешёвых 1.5-2B специалистах (много параллельно, быстро); знания, которых нет в 2B-параметрах — из GraphRAG.

### L1 · Оркестратор
- **Роль:** декомпозиция цели на волны (детерминированный фолбэк уже есть в ядре — `detect_families`); назначение семьи/роли; **агент-аудитор** (Definition of Done — сейчас `_audit_gate`); синтез итога; сложные LLM-узлы канвы.
- **Модель:** Qwen3-14B (режим thinking для план/аудит), квант **AWQ/GPTQ Int4** ≈ 9–10 ГБ. Для 32 ГБ — Qwen3-8B Int4 ≈ 5.5 ГБ.
- **Независимость аудитора** (честный вопрос из ADR): сейчас аудитор — та же модель. Для настоящей независимости — отдельный лёгкий judge (напр. база L2 с LoRA-critic) или иной quant; на одной карте — отдельный system + high-temp-0 проход. Компромисс задокументирован.

### L2 · Специалисты по семьям
- **База:** Qwen3-1.7B (fp16 ≈ 3.5 ГБ, или Q8 ≈ 1.8 ГБ) — одна резидентная.
- **Специализация:** **LoRA-адаптер на семью** (8 адаптеров: analytics/finance/architecture/management/research/engineering/critic/decisions), rank 16–32, ≈ 20–40 МБ каждый. Обучены на доменных данных семьи (тела навыков + прошлые прогоны + доменный корпус).
- **Почему LoRA, а не 8 полных 2B:** 8×2B резидентно = 16 ГБ; база+8 LoRA = ~4 ГБ. **vLLM S-LoRA** обслуживает базу + N адаптеров одновременно, роутинг per-request по `family`.
- **Роль-уровень:** внутри семьи роли (5 у Аналитики) различаются промптом (`family_system(family, member)` — уже есть), не отдельным LoRA (иначе адаптеров слишком много). LoRA — на семью, промпт — на роль.

### L3 · GraphRAG — знания-fallback
- **Зачем:** 1.5-2B держит мало параметрических знаний. Когда своих не хватает — тянет из **графа знаний домена** (не из Data Plane! Data Plane = ФАКТЫ задачи из систем; GraphRAG = ЗНАНИЯ/МЕТОД: что значит термин, как считать DCF, паттерны архитектуры).
- **Граф:** узлы = понятия/сущности домена семьи, рёбра = связи; источники — тела навыков (SKILL.md), доменные корпуса, canonical-сущности, дистиллят прошлых прогонов (долговременная память).
- **Retrieval:** гибрид dense (**BGE-M3**, мультиязычный, ≈ 2.3 ГБ) + graph-traversal; reranker **bge-reranker-v2-m3** (≈ 1.1 ГБ).
- **Триггер «знаний не хватает»** (комбинация):
  1. **явный tool** `knowledge_search(query)` — специалист сам решает спросить (как `data_query`, но для знаний);
  2. **предзагрузка оркестратором** — оркестратор предвидит нужду и кладёт релевант в контекст роли до старта;
  3. (опц.) порог неуверенности по энтропии логитов → авто-retrieval.
  Практично: (1)+(2) на старте, (3) — оптимизация позже.
- **Связь с анти-галлюцинацией:** знание из графа приходит **с источником** (провенанс узла) → навык с `cite` цитирует граф, не выдумывает.

## 2. Inference-стек

- **Движок:** **vLLM** (S-LoRA / multi-LoRA `--enable-lora` + **Automatic Prefix Caching**) — один сервер обслуживает оркестратор-эндпоинт и базу+8 LoRA. Альтернатива: SGLang (RadixAttention — сильный prefix-cache).
- **Квантизация:** оркестратор AWQ/GPTQ **Int4**; база специалистов fp16 или Q8 (мелкая — качество важнее); embedder/reranker fp16.
- **Батчинг:** continuous batching — волна из N специалистов исполняется одним батчем на базе+LoRA.
- **Единый клиент в ядре:** абстрагировать `_mcp_call("chat", {profile,system,...})` → `infer(model, lora, system, prompt)`; `profile=research/code` маппится на оркестратор/специалиста; `family` → LoRA-роут.

## 3. Backend-спецификация: горячие кеши и пути (ключевое для VRAM и латентности)

| Кеш / горячий путь | Что кешируем | Зачем | Где |
|---|---|---|---|
| **Prefix cache (APC)** | system-промпты ролей + тела навыков (`family_system` ≈2.4к симв, SKILL.md ≈5.8к) — **повторяются между шагами/агентами** | не пере-prefill'ить один и тот же префикс на каждом ReAct-шаге и у каждого агента волны — огромная экономия | vLLM APC / SGLang RadixAttention (VRAM) |
| **KV-cache (paged)** | ключи/значения внутри прогона/волны | PagedAttention, переиспользование между шагами агента | VRAM-пул |
| **LoRA warm-pool** | 8 family-адаптеров **резидентно** (горячие ≈0.3 ГБ) | нет cold-load адаптера на каждый запрос; LRU-выгрузка если адаптеров станет много | VRAM |
| **Model warm-pool** | оркестратор + база всегда loaded (не lazy) | нет холодного старта на первый прогон | VRAM |
| **GraphRAG cache** (2 уровня) | (a) embedding-кеш `запрос→вектор`; (b) retrieval-кеш `запрос→узлы+знание` | повторные однотипные запросы знаний (термины/методы) не гоняют граф заново; TTL + инвалидация при обновлении графа | RAM/Redis |
| **Skill-body cache** | тела SKILL.md (progressive disclosure `use_skill`) | редко меняются — держать в RAM, не читать файл на каждый `use_skill` | RAM (ядро) |
| **Blackboard hot** | доска ПРОГОНА (event-sourced) в RAM | горячая рабочая память волн; снапшот на диск (bb_compact) | RAM + диск |
| **Долговременная память** | recall-индекс последних/критичных находок | preflight-recall без полного скана `longterm.jsonl`; TTL-забывание уже есть | RAM-индекс + диск |
| **Data Plane freshness** | canonical-записи с TTL (уже реализовано) | не отдавать протухшее; не пере-`data_run` | диск + freshness-гейт |

**Приоритеты очереди инференса:** оркестратор (план/аудит/синтез — на критическом пути) > специалисты волны (батчатся) > GraphRAG-traversal. Волна fan-out → один батч специалистов; аудит/синтез — отдельные приоритетные вызовы оркестратора.

**Роутер (gateway):** запрос → выбор (оркестратор | база+LoRA[family]) + приоритет + APC-хит; за Keycloak JWT (уже есть в `web_api`); egress наружу — только через контролируемый прокси (закрыт по умолчанию).

## 4. VRAM-бюджет

### Карта 48 ГБ (напр. L40S / A6000 / RTX 6000 Ada) — комфортно
| Компонент | VRAM |
|---|---|
| Оркестратор Qwen3-14B AWQ-Int4 | ~10 ГБ |
| База специалистов Qwen3-1.7B fp16 | ~3.5 ГБ |
| 8× LoRA (rank 32) warm-pool | ~0.3 ГБ |
| Embedder BGE-M3 | ~2.3 ГБ |
| Reranker bge-v2-m3 | ~1.1 ГБ |
| **Веса итого** | **~17 ГБ** |
| KV-cache + Prefix-cache пул (concurrency) | ~25 ГБ |
| Overhead/фрагментация | ~3 ГБ |
| **ИТОГО** | **~45 ГБ** |

### Карта 32 ГБ (напр. V100-32 / 5090 / A100-нарезка) — впритык
- Оркестратор → **Qwen3-8B Int4** (~5.5 ГБ); база 1.7B **Q8** (~1.8 ГБ); LoRA 0.3; embedder+reranker 3.4 → **веса ~11 ГБ**; KV/prefix ~18 ГБ; overhead ~3 → **~32 ГБ**. Меньше concurrency, короче KV-окна.
- Если тесно: **унификация** — оркестратор и специалисты на ОДНОЙ 8B-базе (оркестрация без LoRA + семьи через LoRA), убрать отдельную 1.7B. Экономит, но специалист дороже на параллелизме — тюним под нагрузку.

## 5. План имплементации APE → ABOP (фазы)

| Фаза | Что | Итог/чек-поинт |
|---|---|---|
| **Ф0** (готово) | Ядро в APE: семьи/роли/навыки/DataPlane/память/аудитор/handoff/волны; `web_api` read | база для переноса |
| **Ф1 · Локальный inference** | поднять vLLM (оркестратор Int4 + база; APC вкл); абстрагировать `_mcp_call`→`infer()`; профили research/code → оркестратор/специалист | прогон `/agents` на ЛОКАЛЬНЫХ моделях (без курсового шлюза) |
| **Ф2 · Multi-LoRA роутинг** | 8 family-LoRA в vLLM; `_agent_run` роутит LoRA по `family`; warm-pool | специалист семьи отвечает своим адаптером; батчинг волны |
| **Ф3 · GraphRAG** | построить граф знаний (из навыков+корпусов+долгопамяти); `knowledge_search` tool + предзагрузка оркестратором; BGE-M3+reranker; 2-уровневый кеш | специалист при нехватке тянет знание с провенансом (cite) |
| **Ф4 · RUN/STREAM локально** (task #15) | `cmd_agents` в фон + event-bus→SSE на локальном движке; HITL-очередь в сторе | Пульт получает живые волны/доску/вердикт |
| **Ф5 · Обучение LoRA** | датасет per-family (навыки+прогоны+домен) → fine-tune адаптеры; eval per-family; сначала промпт-специализация, потом LoRA | измеримое качество специалистов на домене |
| **Ф6 · Упаковка на карту** | VRAM-профиль (§4) под целевую карту; кеши (§3); нагрузочный тест concurrency; governance-гейт (безопасность навыка/HITL/автономия≤контракт) | «балалайка» стартует и держит нагрузку на 32–48 ГБ |

**Порядок ценности:** Ф1 (локальность — снимает зависимость от шлюза, закрывает периметр) → Ф2 (специализация) → Ф4 (живой Пульт) → Ф3 (знания) → Ф5 (обучение) → Ф6 (упаковка). Ф3/Ф5 можно начинать промпт-специализацией (без обучения) и нарастить LoRA позже.

## 6. Governance и безопасность (усиливается локальностью)

- **Локальный inference = закрытый периметр:** модели on-prem, egress наружу закрыт по умолчанию (только через контролируемый прокси) — идеально для ФСТЭК/ФЗ-152/ДСП. Это **усиливает конверт**: и данные, и модели не покидают контур.
- **Governance-инварианты сохраняются** (из ядра): безопасность навыка `mode/egress/cite`; действие→HITL (`dry_run`+approve); числа-из-источника (теперь и GraphRAG с провенансом); автономия ≤ `DeploymentContract` LUDA.
- **GraphRAG под анти-галлюцинацию:** знание приходит с источником — навык `cite` цитирует, не выдумывает; отсутствие в графе = «не знаю», а не генерация.

## 7-bis. Пересмотр: MoE-оркестратор + 2 бокса (research-backed)

Вопрос владельца: взять MoE вместо роя мелких? Есть второй бокс со стендом обучения, на нём Qwen3 MoE ~27–30B. Провёл research — он **меняет акценты** изначальной архитектуры.

### Что говорят исследования
1. **MoE и multi-agent — НЕ конкуренты, а разные слои** ([MoE vs Multi-Agent](https://gurusup.com/blog/moe-vs-multi-agent-systems), [MoA ICLR'25](https://proceedings.iclr.cc/paper_files/paper/2025/file/5434be94e82c54327bb9dcaf7fca52b6-Paper-Conference.pdf)): MoE = token-level роутинг ВНУТРИ модели (compute-эффективность); multi-agent = task-level роутинг на уровне СИСТЕМЫ (роли/tools/память/governance). Сильнейшие прод-архитектуры 2025 **комбинируют оба**.
2. **Производительность системы определяется ОРКЕСТРАТОРОМ, а не специалистами** ([Can Small Agents Beat a Single LLM?, arXiv 2601.11327](https://arxiv.org/abs/2601.11327)): «system performance is driven primarily by orchestrator capacity rather than sub-agent capacity». → **вкладываться надо в оркестратор**, а не в 8 сильных LoRA.
3. **Малые агенты + структурированная память бьют крупную одиночную модель** и дешевле: 8B-мультиагент без thinking — 2.8× быстрее 8B-direct, 4.2× быстрее 32B-direct; структурированная память даёт −43% токенов ([2601.11327](https://arxiv.org/abs/2601.11327), [SLM = будущее агентов, arXiv 2506.02153](https://arxiv.org/pdf/2506.02153)). У нас структурированная память УЖЕ есть (Blackboard + долговременная + GraphRAG).
4. **В MoE НЕТ бизнес-доменных экспертов** ([Illusion of Specialization, arXiv 2601.03425](https://arxiv.org/pdf/2601.03425), [Do Domain Experts Exist in MoE?, arXiv 2604.05267](https://arxiv.org/pdf/2604.05267)): эксперты MoE — domain-invariant «standing committee», НЕ «финансист/аналитик». → нельзя повесить на эксперта MoE права/безопасность семьи. **Governance-специализация обязана жить на agent-слое.**

### Вывод для ABOP (пересмотр)
- **Оркестратор = Qwen3 MoE ~27–30B на боксе-2** — да, это правильный ход. Research: качество системы = качество оркестратора → сюда и вкладываемся; MoE даёт качество 30B по цене ~3B active (3–5× дешевле dense). Это **решает мой риск №1** (слабость специалистов не критична при сильном оркестраторе).
- **Специалисты остаются маленькими и простыми** — но LoRA-обучение из «обязательного» становится «опциональным/поздним»: research говорит sub-agent capacity вторична. **Начинаем с промпт-специализации** мелких (или того же MoE), LoRA — только для доказанно проваливающихся доменов.
- **Governance/семьи/безопасность — НЕ в MoE, а наш agent-слой** (illusion of specialization): онтология Семья→Роль→Навык + `mode/egress/cite` + HITL + автономия≤контракт остаются системными. MoE — только эффективный движок под капотом.
- **Это ровно «combine both»:** MoE (эффективность модели) × multi-agent (governance/специализация/аудируемость системы).

### Топология под 2 бокса
```
БОКС-2 (стенд обучения, Qwen3 MoE 27-30B)        КАРТА-1 / БОКС-1 (48GB)
├─ ОРКЕСТРАТОР (MoE): план/маршрут/аудит/синтез   ├─ Специалисты (мелкие/промпт-спец) волнами
├─ Обучение LoRA per-family (когда понадобится)    ├─ Embedder BGE-M3 + reranker (GraphRAG)
└─ Тяжёлые роли (финансы/архитектура) — тоже MoE    └─ Blackboard + Data Plane + governance-гейт
        ↕ единый контракт вызова (JWT + cost_journal), egress закрыт (on-prem)
```
Вариант компактнее: **всё на боксе-2**, если VRAM MoE + KV + специалисты влезают — тогда карта-1 не нужна, оркестратор и специалисты делят один MoE-движок (оркестратор без LoRA + семьи через промпт/LoRA), GraphRAG рядом. Это упрощает и усиливает (один сильный движок вместо роя слабых).

### Что уточнить
- **Точная модель бокса-2:** «Qwen-3.8 27B» — вероятно **Qwen3-30B-A3B** (MoE, 30B total / 3B active) или Qwen3-32B (dense). MoE-A3B идеален под оркестратор (качество/цена). Уточнить total/active params и квант.
- **Доступность бокса-2 под ABOP-рантайм** (не только обучение) и связность с боксом-1/картой.

### Итог пересмотра
Изначально: оркестратор 14B + рой 8×(2B+LoRA) на одной 48GB карте. **Пересмотр:** оркестратор = **MoE 27–30B (бокс-2)**, специалисты мелкие с промпт-специализацией (LoRA — позже и точечно), governance — наш слой. Меньше работы (не 8 LoRA сразу), выше качество (research: оркестратор решает), лучше ложится на вашу инфру (MoE-бокс + стенд обучения).

## 7-ter. ВЫБРАННАЯ конфигурация: 1 бокс (MoE-движок) + вынесенный RAG

Бюджет: **только 1 карта / 1 бокс**, второй не тянем. RAG — на отдельном/существующем сервере. Research-оптимальное решение под это ограничение:

### Один MoE-движок обслуживает ВСЁ (оркестратор + специалисты)
Ключ: **Qwen3-30B-A3B** (MoE, 30B total / **3B active**) — качество 30B по стоимости инференса ~3B. Один экземпляр = и оркестратор, и специалисты:
- **Оркестратор** = MoE без LoRA, thinking-режим (план/маршрут/аудит/синтез).
- **Специалисты семей** = тот же MoE + **промпт-специализация** (`family_system(family, member)` — уже есть); LoRA per-family — опционально/позже и только для доказанно проваливающихся доменов.
- **Рой отдельных 2B НЕ НУЖЕН.** MoE-A3B один тянет и оркестрацию, и исполнение волн (active 3B → дёшево на параллелизме), при этом качество несопоставимо выше 2B. Это снимает мой риск №1 целиком.

Обоснование: research §7-bis — «производительность = оркестратор»; MoE-A3B даёт сильный оркестратор дёшево; специалисты вторичны, промпт-спец достаточно на старте.

### RAG вынесен с GPU-бокса (освобождает VRAM + бюджетно)
- GraphRAG (embedder BGE-M3 + reranker + граф + retrieval) — **НЕ на GPU-боксе рантайма**.
- **Рекомендация: переиспользовать существующий sLAVA-сервер** (у него уже Qdrant + ONNX-эмбеддер + reranker — RAG-контур работает). Граф знаний кладём туда; специалист/оркестратор ходят по HTTP (`knowledge_search`). Ноль новой инфры.
- Альтернатива: дешёвая аренда CPU/малая-GPU (T4) под RAG — если не хотим нагружать sLAVA.
- Retrieval не на критическом пути каждого токена → сетевой хоп приемлем; кеш GraphRAG (§3) гасит повторы.

### VRAM-бюджет (1 карта, RAG вынесен)
| Компонент | 48 ГБ (рекоменд.) | 32 ГБ (впритык) |
|---|---|---|
| Qwen3-30B-A3B **AWQ-Int4** (веса) | ~17 ГБ | ~17 ГБ |
| опц. LoRA warm-pool (позже) | ~0.3 ГБ | ~0.3 ГБ |
| KV + Prefix-cache (A3B → KV умеренный; concurrency волн) | ~25 ГБ | ~11 ГБ |
| Overhead | ~3 ГБ | ~3 ГБ |
| **ИТОГО** | **~45 ГБ ✓** | **~31 ГБ ✓ (меньше concurrency)** |
| Embedder/reranker | — (на RAG-сервере) | — |

- **48 ГБ (L40S / RTX 6000 Ada / A6000)** — рекомендую: MoE-30B-A3B Int4 комфортно + запас на concurrency волн.
- **32 ГБ (5090 / V100-32)** — влезает, но concurrency ниже (короче KV-окна, меньше параллельных специалистов в волне). Если карта 32 и тесно — fallback на Qwen3-14B dense Int4 (~10 ГБ), но 30B-A3B предпочтительнее по качеству.

### Итог выбора
**1× 48 ГБ бокс · Qwen3-30B-A3B (единый MoE-движок: оркестратор + специалисты через промпт-спец) · vLLM (APC + опц. multi-LoRA) · RAG вынесен на sLAVA-сервер.** Один бокс, один движок, RAG переиспользует рабочую инфру. Проще роя, сильнее 2B, укладывается в бюджет.

## 7. Риски и открытые вопросы

1. **Качество 1.5-2B специалистов** на домене — main risk. Митигация: LoRA-обучение (Ф5) + GraphRAG-подпитка (Ф3); эскалация сложных шагов на оркестратор.
2. **Независимость аудитора** — на одной карте аудитор = та же база. Для строгой независимости — отдельный judge-LoRA / иной quant (VRAM-вопрос).
3. **Concurrency vs VRAM на 32 ГБ** — KV/prefix-пул ограничен; тюнить размер батча/окна; возможно унификация моделей.
4. **Стоимость обучения 8 LoRA** — датасеты per-family (навыки+прогоны); начать с промпт-специализации.
5. **GraphRAG-построение** — источники/актуализация графа; связь с обновлением навыков и Data Plane.
6. **Карта-цель** — уточнить конкретную GPU (48 vs 32 меняет оркестратор 14B↔8B).
