# Руководства ABOP (поставочные документы)

Три документа, которые уходят заказчику вместе с продуктом.

| Файл | Кому | О чём |
|---|---|---|
| [`RUKOVODSTVO_POLZOVATELYA.html`](RUKOVODSTVO_POLZOVATELYA.html) · [PDF](RUKOVODSTVO_POLZOVATELYA.pdf) | менеджер, аналитик, любой ежедневный пользователь | Десктоп и веб: от первой задачи до разбора результата, карточки, **карта процессов** (слои, редакции, посадка агентов, подтверждение прогонами), подтверждения, бюджеты, регулярные запуски, типовые ошибки, словарь |
| [`RUKOVODSTVO_ADMINISTRATORA.html`](RUKOVODSTVO_ADMINISTRATORA.html) · [PDF](RUKOVODSTVO_ADMINISTRATORA.pdf) | тот, кто разворачивает и настраивает | Установка, окружение, авторизация и роли, модель, реестр систем, Data Plane, навыки и контракты, агенты, лимиты, очередь и веер, шина, доставка, безопасность, наблюдаемость, диагностика, **карта процессов** (таблицы, области, согласование, перенос со старого стенда), три приложения-справочника |
| [`RUKOVODSTVO_RAZRABOTCHIKA.html`](RUKOVODSTVO_RAZRABOTCHIKA.html) · [PDF](RUKOVODSTVO_RAZRABOTCHIKA.pdf) | партнёр-внедренец, разработчик вендора | Как добавить своё: что данные а что код, Data Plane и рецепты, навыки, **предикаты и правила**, правила в интерфейсе, агент и конверт, **пакет вертикали**, **арендаторы**, приёмка; три приложения — библиотека предикатов, формат пакета, карта репозитория |

Снимки экранов — в `img/`. Все сделаны с работающей системы на демонстрационных данных:
оранжевой рамкой и номером отмечены поля, о которых идёт речь в тексте рядом.

**В руководстве разработчика снимков нет сознательно**: его предмет — файлы, форматы и код, а не
экраны. Единственный экран, который там описан («Данные → Правила»), показан в руководстве
пользователя. Если решим добавить снимки — порядок тот же, что ниже.

## Как пересобрать PDF

```bash
pip install playwright && playwright install chromium
python docs/guide/build_pdf.py
```

HTML — источник правды; PDF собирается из него печатной вёрсткой с колонтитулами.

## Как обновить снимки экрана

Снимки делались с локального стенда, поднятого на демо-данных, чтобы в кадр не попали ни реальные
имена, ни рабочие данные. Порядок:

1. Поднять ABOP локально с `ABOP_DEV_AUTH=1` и наполнить canonical store демо-данными
   (`ops/seed_projects.py`).
2. Поднять сайдкар десктопа отдельным портом и каталогом (`APE_SIDECAR_PORT`, `ABOP_DESKTOP_HOME`),
   указав ему локальный ABOP через `ABOP_BASE_URL`.
3. Снять экраны браузером с подсветкой нужных полей, привести к ширине 1800 px и заменить файлы
   в `img/`.

Важное правило: **в кадре не должно быть реальных персональных данных и рабочих систем заказчика.**
Демо-учётка для снимков — вымышленная.

## Соответствие руководств коду

Руководства проверяются тестами наравне с документацией разработчика:

* `tests/test_guide_docs_sync.py` — числа порогов подбора в разделе 12 админского руководства
  сверяются с константами кода: меняется константа — обязан измениться документ;
* `tests/test_guide_developer.py` — таблица предикатов в приложении А сверяется с библиотекой
  (`cli/checks.py`), а числа на обложке — с кодом: предикат добавили, строку забыли — тест падает;
* `tests/test_docs_process_model_sync.py` — оба руководства обязаны описывать карту процессов
  (слои и редакции для пользователя, таблицы, области, согласование и перенос — для администратора),
  а нумерация разделов и оглавление не должны разъезжаться при вставке новых разделов.

Нумерация разделов ведётся руками, поэтому новые темы добавляются **подразделами** (`14.9`,
`8.4-бис`, `16.4`), а не новыми разделами: вставка нового `h2` сдвигает приложения и ломает ссылки
в оглавлении. Тест это проверяет, но дешевле не создавать себе работу.
