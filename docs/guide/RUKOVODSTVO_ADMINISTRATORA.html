РАЗДЕЛ 1Состав поставки и топология

ABOP ставится одним контейнером на сервер заказчика. Всё остальное — опционально и включается по мере надобности.

Ключевой принцип ABOP ничего не отправляет в ваши системы сам. Он формирует команду, показывает человеку, что именно уйдёт, и только после подтверждения публикует её. Исполняет команду отдельный воркер, у которого есть доступ к системам, — у ядра этих доступов нет.

РАЗДЕЛ 2Требования и подготовка

2.1 Сервер приложения

ОСLinux x86-64 с Docker 24+ (проверено на Ubuntu 22.04/24.04)
Процессор4 ядра — минимум; 8 ядер — комфортно при 20+ пользователях
Память4 ГБ минимум. Контейнеру ядра выделяется 1,5 ГБ: этого хватает на 4 воркера прогонов
Диск20 ГБ на систему и образы, плюс объём под данные Postgres и канонический слой
СетьИсходящий доступ к модели; входящий — только к порту веб-интерфейса, желательно за обратным прокси с TLS

2.2 Сервер модели

Модель — отдельная история. Есть два пути.

ПутьЧто нужноКогда выбирать
Свой боксGPU от 48 ГБ памяти (L40S, A6000, 6000 Ada), vLLM, модель уровня Qwen3-30B-A3B в FP8Данные не должны покидать контур; нужен предсказуемый расход
Облачный шлюзТолько ключ доступа к OpenAI-совместимому APIБыстрый старт, пилот, небольшие объёмы
Рекомендация по модели Для продуктивной работы берите модель с поддержкой строгого структурного вывода (response_format: json_schema). ABOP опирается на схемы результата: если модель умеет соблюдать схему на уровне декодирования, качество и стоимость заметно лучше, чем при разборе «свободного» ответа.

2.3 Что подготовить заранее

  • Учётные записи в системах, из которых агенты будут читать данные, — с правами только на чтение;
  • Отдельные учётные записи для систем, в которые агенты будут писать (трекер, вики, почта), — чтобы действия агентов отличались от действий людей;
  • Список отделов и того, какие системы каждому доступны: это ляжет в основу правил доступа;
  • Realm в Keycloak (или доступ к существующему) с ролями admin, support, manager, analyst.

РАЗДЕЛ 3Установка

Базовая установка занимает около получаса: разложить файлы, заполнить окружение, собрать образ, запустить, проверить.

  1. Разложите поставку Каталог /opt/abop. В нём должны оказаться server/, cli/, skills/, webapp/, reports/, desktop/ui/, ops/ и Dockerfile.webapi. 
    mkdir -p /opt/abop && cd /opt/abop
tar -xf abop-<версия>.tar
  2. Поднимите Postgres Можно взять существующий. Для отдельного: 
    docker run -d --name abop-pg --restart unless-stopped \
  -e POSTGRES_PASSWORD='…' -e POSTGRES_DB=abop -e POSTGRES_USER=abop \
  -p 127.0.0.1:5433:5432 -v ape_pg:/var/lib/postgresql/data postgres:16
    Порт наружу не открывайте: ядро ходит в базу по петле.
  3. Заполните .env Минимальный рабочий набор — в разделе 4. Файл лежит рядом: /opt/abop/.env, права 600.
  4. Соберите и запустите 
    cd /opt/abop && bash ops/deploy-webapi.sh
    Скрипт собирает образ, пересоздаёт контейнер с нужным томом и ждёт готовности. Эквивалент вручную: 
    docker build -q -f Dockerfile.webapi -t abop-webapi .
docker rm -f abop-webapi 2>/dev/null || true
docker run -d --name abop-webapi --network host --restart unless-stopped --memory=1536m \
  --env-file /opt/abop/.env -v abop_ape:/root/.ape abop-webapi
  5. Проверьте 
    curl -s http://127.0.0.1:8091/api/health
# {"ok":true,"families":10,"skills":58,"adapters":[...]}
    Если skills равно нулю — каталог навыков не попал в образ.
  6. Закройте периметр Порт 8091 наружу отдавайте только через обратный прокси с TLS. Прямой доступ к Postgres, Keycloak и шине снаружи должен быть закрыт.
Никогда не запускайте без тома Флаг -v abop_ape:/root/.ape обязателен. В этом томе лежат канонические записи Data Plane. Контейнер, запущенный без него, стартует и выглядит здоровым, но все данные, выгруженные рецептами, пропадут при следующем пересоздании.

3.1 Первый вход

Откройте https://<ваш-адрес>/. Вход идёт через Keycloak: ABOP проксирует логин, поэтому сам Keycloak можно держать закрытым от внешней сети. После входа в правом нижнем углу появится ваше имя, уровень доступа и отдел.

Режим разработки Переменная ABOP_DEV_AUTH=1 отключает проверку токенов и делает любого анонима администратором. Она предназначена для локальной разработки и автотестов. В продуктивной установке её быть не должно — проверьте перед сдачей: docker exec abop-webapi printenv | grep DEV_AUTH не должен ничего вернуть.

3.2 Руководства внутри продукта

Оба руководства едут в образе и отдаются самой платформой: каталог docs/guide монтируется на /guide, список — GET /api/guides. Пользователь открывает их кнопкой «Помощь» в вебе и блоком «Руководства» в кабинете десктопа. Если каталог не вошёл в сборку, список пуст, а интерфейс честно говорит об этом вместо битых ссылок.

3.3 Установка десктоп-клиента

Клиент ставится на машины пользователей отдельно. Установщик собирается командой npm run dist в каталоге desktop/ и публикуется вашим способом раздачи ПО. Клиенту нужно знать адрес сервера — он задаётся переменной окружения ABOP_BASE_URL при сборке или в конфигурации приложения.

Интерфейс десктопа подтягивается с сервера при каждом запуске (/desktop-ui-bundle), поэтому обновления интерфейса доезжают до пользователей без переустановки приложения — переустановка нужна только при смене версии оболочки или локального движка.

РАЗДЕЛ 4Переменные окружения

Файл /opt/abop/.env — единственный источник настроек уровня среды. Полный список с умолчаниями — в приложении Б; здесь минимум, который нужно заполнить осознанно.

4.1 Минимальный рабочий набор

# ── база ──
POSTGRES_DSN=postgresql://abop:пароль@127.0.0.1:5433/abop

# ── авторизация ──
KEYCLOAK_ISSUER=https://auth.example.ru/realms/abop
KEYCLOAK_JWKS_URI=https://auth.example.ru/realms/abop/protocol/openid-connect/certs
KEYCLOAK_AUDIENCE=abop-web

# ── модель: свой бокс ──
LOCAL_LLM_BASE_URL=http://10.0.0.20:8000/v1
LOCAL_LLM_MODEL=qwen3-30b-a3b
LOCAL_LLM_API_KEY=EMPTY

# ── исполнение прогонов ──
ABOP_RUN_WORKERS=4
ABOP_RUN_TIMEOUT=600
ABOP_USER_CONCURRENT=1
ABOP_RUN_LLM_TRUNCATE=0

4.2 Что стоит поменять под нагрузку

ПеременнаяПо умолч.Когда менять

ABOP_LLM_MAX_INFLIGHT12Общий потолок одновременных запросов к модели. Ставьте по ёмкости бокса

Лимиты прогона больше не живут в окружении Длина ответа навыка, шаги инструментов, размер выборки и параллельность настраиваются из интерфейса — Настройки → Прогон (раздел 11). Переменные окружения остались умолчаниями: настройка из интерфейса их перекрывает и действует со следующего прогона, без перезапуска.

РАЗДЕЛ 5Авторизация, роли и доступ

ABOP не ведёт своих учётных записей. Пользователи и роли живут в вашем Keycloak, а платформа читает их из токена.

5.1 Настройка Keycloak

  1. Создайте realm Например abop. Если у вас уже есть корпоративный realm — используйте его.
  2. Заведите клиента для веба abop-web, тип «public», поток «Direct access grants» включён — через него ABOP проксирует вход, не выставляя Keycloak наружу.
  3. Заведите роли уровня realm admin, support, manager, analyst.
  4. Добавьте атрибут отдела Атрибут пользователя department со значением-идентификатором семьи (management, finance, audit…). Пропишите его в маппер токена, чтобы он попадал в JWT. Значение * означает «все области».
  5. Пропишите адреса в .env KEYCLOAK_ISSUER и KEYCLOAK_JWKS_URI. Если Keycloak внутри той же сети, а issuer публичный, задайте KEYCLOAK_JWKS_INTERNAL — ключи будут забираться по внутреннему адресу, а issuer проверяться по публичному.

5.3 Доступ к данным: ABAC по отделу

Кроме уровня доступа, действует правило области. Агент принадлежит семье (отделу), а каждая система в реестре объявляет, каким семьям она доступна. Если сущность наполняется рецептом из системы, недоступной семье агента, — агент эту сущность не читает. В прогоне появляется явная пометка «доступ к данным запрещён», а отказ пишется в аудит.

Как это проверить Откройте результат прогона: блок «доступ» показывает, какие системы были разрешены агенту и по какой причине. Ничего не скрывается: видно и разрешённые, и закрытые.

5.4 Аудит

В аудит попадают: запуски прогонов, сохранение и удаление агентов, правка навыков и шаблонов, изменение настроек и лимитов, подтверждения и отклонения внешних действий, отказы по правам доступа. Запись содержит исполнителя, объект, время и краткое описание.

РАЗДЕЛ 6Модель: свой бокс или облако

ABOP работает с любым OpenAI-совместимым API. Адрес модели можно сменить на лету, не перезапуская сервис.

6.1 Свой бокс с vLLM

vllm serve Qwen/Qwen3-30B-A3B-Instruct-2507-FP8 \
  --port 8000 --max-model-len 32768 --gpu-memory-utilization 0.92 \
  --guided-decoding-backend xgrammar

Проверьте, что модель отвечает:

curl -s http://10.0.0.20:8000/v1/models

Затем пропишите адрес в .env (LOCAL_LLM_BASE_URL, LOCAL_LLM_MODEL) или задайте из интерфейса — «Настройки → Модели → Применить эндпоинт». Настройка из интерфейса переживает перезапуск контейнера: она хранится в базе.

6.2 Облачный шлюз

Задайте базовый адрес и ключ вашего провайдера. Каскад моделей описывается списком: если первая не отвечает, запрос уходит следующей. Откаты видны в метрике abop_llm_fallback_total — если она растёт, основная модель нестабильна.

6.3 Три профиля запроса

standardАгентский движок: все прогоны навыков
codeРабота с кодом и таблицами
researchДлинные разборы и исследования

Каждому профилю можно назначить свой каскад — например, тяжёлую модель только для исследований.

6.4 Проверка после смены модели

  1. GET /api/llm/status — адрес, активная модель, результат проверки связи;
  2. Запустите короткий прогон с бюджетом «короткий» — убедитесь, что ответ приходит и соблюдает схему;
  3. Посмотрите в результате прогона поле стоимости: если тариф для новой модели не задан, расход будет считаться нулевым.
Структурный вывод Если модель не поддерживает response_format: json_schema, включите ABOP_RUN_STRUCTURED=0. Схема результата тогда проверяется после ответа: навык, не уложившийся в схему, будет переспрошен один раз, а если и это не помогло — в результате появится честная пометка о несоблюдении схемы вместо выдуманных полей.

РАЗДЕЛ 7Реестр систем и коннекторы

Реестр систем — единый справочник того, куда ABOP вообще может ходить. Ни рецепт, ни доставка не работают с «просто адресом»: они ссылаются на систему из реестра.

7.1 Что описывает запись системы

Идентификаторкороткий slug: redmine, bookstack, erp
Типrest, postgres, s3, smtp, kafka
Адресбазовый URL или строка подключения
Выход наружуinternal — внутри контура, external — за его пределами. Влияет на правила и на то, требуется ли подтверждение
Области (scope)каким семьям система доступна. Пусто — доступна всем
Топики шиныесли включена шина, системе выделяется пара топиков: события и команды

7.2 Заведение системы

  1. Добавьте запись в реестр «Настройки → Подключения → добавить». Укажите slug, тип, адрес и области доступа.
  2. Создайте коннектор «Данные → Коннекторы». Коннектор — это способ авторизации: токен, логин и пароль, заголовок. Секреты хранятся на сервере и в интерфейсе больше не показываются.
  3. Проверьте связь Кнопка проверки делает настоящий запрос и показывает, сколько строк вернулось и какие колонки найдены. Если источник ответил, но строк ноль — скорее всего, данные лежат под другим ключом: укажите корневой путь.
  4. Закройте лишнее Учётная запись коннектора должна иметь ровно те права, которые нужны: чтение — для источников, запись — только для систем доставки.

7.3 Защита от выхода не туда

Запросы наружу проходят через проверку адреса: запрещены обращения к внутренним и служебным подсетям, если система не объявлена внутренней. Это защита от того, что подставленный адрес в рецепте заставит платформу сходить по внутреннему адресу вашей сети.

Раздельные учётные записи Не используйте одну учётную запись для чтения и записи. Если агент читает трекер и он же в нём создаёт задачи — ошибка в правиле доставки превращается в массовое создание задач под правами чтения-записи. Разделите: одна запись читает, другая пишет, и только в один проект.

8.3 Прогон рецепта

Результат прогона рецепта — честная сводка: записано / отброшено правилами / не прошло проверку схемы. Если отброшено много — смотрите правила: скорее всего, источник изменил формат.

Две ловушки, на которых теряют данные

«Начисто» действует на сущность, а не на рецепт. Если два рецепта пишут в одну сущность (например, платежи и счета — оба в transaction), начисто можно читать только первый, второй обязан идти дозаписью. Иначе второй прогон перепишет файл сущности своими строками, и вместо 180 записей останется 60. Заметно это только по счётчику записей в разделе «Данные» — ошибки не будет.

Рецепты перечитывайте через интерфейс или API, не скриптом мимо сервера. Рабочая версия рецепта лежит в Postgres; рядом может оставаться устаревшая файловая копия. Скрипт, запущенный в контейнере напрямую, берёт файл — и прогон отдаёт, например, «записано 0, не прошло проверку схемы 21», потому что в старой версии поле отправителя читалось из другой колонки источника. Правильно: POST /api/data/recipes/{name}/run или кнопка «Прогнать» в разделе «Данные».

8.4 Версии и время жизни записей

Хранилище append-only: повторный прогон рецепта не затирает старое, а добавляет новую версию записи. При чтении отдаётся последняя созданная версия. Важное свойство: последняя версия не протухает по времени — данные не исчезают сами. Время жизни (ttl_sec) вытесняет только перекрытые старые версии.

Практика Ставьте ttl_sec: 0 для справочников (они меняются редко) и сутки-двое для операционных данных. Регулярный прогон рецептов удобно повесить на планировщик через агента-обновлятора либо внешним cron через API.

8.5 Карта данных

Карта — первое место, куда стоит смотреть, когда прогоны возвращают ноль находок. Эндпоинт GET /api/data/entities отдаёт тот же список машинно: имя сущности, сколько записей лежит, сколько навыков её объявили.

РАЗДЕЛ 10Агенты и семьи

Агент — навыки, собранные под работу, с именем, отделом и границами. Семья определяет, что агенту доступно.

10.1 Семьи

В поставке десять семей: аналитика, архитектура, аудит, инженер, кредитование, критик, менеджмент, ресёрч, решения, финансы. Семья — это отдел или направление: она задаёт, какие системы и данные видят агенты, и какие навыки им доступны.

Свои семьи заводятся в интерфейсе (карточка навыка, блок «семьи», поле «своя семья») или через API. Идентификатор — латиницей: он же используется как значение атрибута department в Keycloak.

10.2 Сборка агента

Порядок работы: выбрать сценарий или создать нового агента, вытянуть узлы из палитры, соединить, настроить каждый в инспекторе, проверить и сохранить. Проверка перед сохранением не даст собрать агента, нарушающего конверт, — например, поставить узел внешнего действия без подтверждения при недостаточном потолке автономии.

Сборка живёт только здесь. Кнопка «＋ новый агент» открывает окно задачи, но собирает не «где-то в модалке»: среда разбирает задачу планировщиком по контрактам (раздел 12) и выкладывает результат на канву — источники из объявленных сущностей шага, навыки по порядку исполнения, рёбра по объявленным зависимостям after. Дальше агент правится руками там же. Построение не запускает прогон и не тратит ни токенов, ни денег, поэтому блок бюджета в этом режиме не показывается вовсе.

Режим «Прогон» показывает прогон, а не его имитацию. Источник один — последний прогон агента, открытого на канве (контракт → агент → /api/runs). Нет прогона — пустой экран с кнопкой запуска. Состояние маскота читается с прогона: идёт — думает, очередь подтверждений — ждёт человека, закончился — готово или замечания.

Что было до этого и почему это важно знать Лента «Прогон» рисовала ход работы из таймера: каждые 220 мс рос процент, и из этого числа выводилось всё — статусы узлов, этапы, события доски, отметки готовности. Экран выглядел работающим, когда не исполнялось ничего, а четыре места в интерфейсе открывали «пульт прогона демо» вообще без прогона. На показе заказчику это худший вид неправды — показывать занятость вместо работы. Таймер убран вместе с проп-скоростью симуляции. Практическое следствие для поддержки: если полоса не двигается, работа действительно не идёт — смотрите очередь (GET /api/runs/queue), а не ждите.

Черновик → Проверен → В прогоне → В проде. Черновик перезаписывается без создания версий: автосохранение не плодит историю. Осознанный пересмотр создаёт новую версию. Вывод из работы — «В Лимб» (архив): агент недоступен для запуска, но прогоны и находки остаются. Полное удаление доступно администратору и требует подтверждения вводом имени.

РАЗДЕЛ 12Подбор исполнителя: агент или цепочка навыков

Самый частый вопрос поддержки — «почему выбрался не тот». Этот раздел разбирает подбор целиком: кто принимает решение, по каким порогам, на что он опирается и как его настроить, не ломая остальное. Читать стоит целиком — пороги связаны, и правка одного без понимания остальных даёт обратный эффект.

12.1 Решение принимает оркестратор — одно, в одном месте

Раньше каждый канал (чат десктопа, веб, крон, шина) сам сшивал последовательность «достаточно ли описания → есть ли готовый агент → собрать ли из навыков». Каналы расходились: карточка в чате держала план, собранный до правки подбора, и человек запускал устаревший. Теперь решение принимает оркестратор — одна ручка POST /api/orchestrate, через которую идут все каналы.

Оркестратор решает, но не действует: запустить агента или собрать исполнителя вызывающая сторона идёт отдельными ручками. Это не формальность — у действия своя проверка прав и свой журнал.

Исходов ровно четыре:

ИсходКогдаЧто видит человек

Каждое решение возвращает трассу: why[] — человеческим языком, почему именно так, и facts{} — числа, на которых решение построено (счёт лидера, счёт второго, покрытие плана, порог). Трасса ложится в журнал. При разборе жалобы «выбрался не тот» смотреть надо сначала её, а не пороги.

Два механизма подбора — закрытая дыра До унификации «запустить готового» и «собрать цепочку» были независимыми механизмами: цепочка собиралась из агентов, не знала про навыки, и шаг в ней правился только если нужный агент существовал. Человек видел два разных ответа на одну фразу. Если вы расширяете среду своим каналом — вызывайте /api/orchestrate, а не собирайте последовательность заново.

12.4 Как планировщик строит цепочку

Планировщик (server/planner.py) строит цепочку по контрактам навыков, а не по догадке модели: выход предыдущего шага должен подходить входу следующего. Что он делает по порядку:

  1. Выделяет указание. Если к задаче приложен материал (длиннее _PASTE_FROM = 600 знаков), указание отделяется от материала: подбор идёт по указанию. Без этого вставленное письмо на три экрана разбиралось на одиннадцать «этапов» — по знакам препинания приложенного текста.
  2. Режет на работы. Не больше _MAX_STAGES = 4: больше четырёх работ в одной фразе человек не ставит, остальное — разметка текста. Второй и дальше фрагменты принимаются только если содержат глагол действия («сверь», «разбери», «подготовь», «отправь»…).
  3. Убирает ссылки. Адрес и его подпись («выгрузка: http://…») вырезаются до сопоставления. Иначе имя системы в ссылке притягивало посторонний навык: в финансовой задаче навык аудита 1С всплывал со счётом 0.49 только потому, что в ссылке встречалось слово «1с».
  4. Ранжирует навыки. По словам (стемминг, STEM_LEN = 4), по целевому артефакту (TARGET_BONUS = 0.3 — «письмо», «отчёт», «задача» в формулировке), по смыслу (12.5) и по предпочтениям пользователя (12.6). Кандидатов не больше MAX_CANDIDATES = 6, счёт ниже MIN_CANDIDATE = 0.08 не рассматривается.
  5. Продолжает цепочку по контрактам. Пока выход последнего шага кому-то подходит со счётом не ниже CONTINUE_MIN = 0.12 и шагов не больше CONTINUE_MAX = 4. Длина цепочки ограничена сверху ещё и числом разных глаголов действия в задаче: «собери дайджест и отправь письмом» — это две работы, и пятого шага там быть не может, даже если контракты сцепляются.
  6. Добавляет редактор. Навык report-editor исключён из ранжирования (он подходит ко всему и забивал бы подбор) и добавляется в конец отдельно, от EDITOR_FROM = 2 шагов.
Необязательные связи Связь между навыками бывает обязательной и необязательной. Раньше цепочка обрывалась на первой необязательной: формально следующий шаг «не требуется». Теперь она продолжается и по ним, если задача этого просит — именно так финансовая цепочка из шести шагов собирается без ручной правки.

12.5 Смысл: эмбеддинги

Сравнение по смыслу включается поверх словаря и считается через эмбеддинги описаний навыков (кэш в памяти процесса, чтобы не считать одно и то же на каждый запрос).

SEM_FLOOR0.45Ниже этой близости вклад смысла равен нулю: шум похож на сигнал и сбивает подбор.
SEM_CAP0.25Потолок прибавки за смысл. Смысл уточняет словарь, но не перебивает его: иначе подбор становится необъяснимым, а жалобы — неразбираемыми.

Эмбеддинги — best-effort: если модель эмбеддингов недоступна, подбор работает по словам, а в трассе у шага пустое поле sem. Это не повод считать, что всё в порядке: пустой sem на всех шагах означает, что смысловая часть отключена целиком — проверьте профиль эмбеддингов (раздел 6.3).

12.6 Подбор учится на решениях человека

Таблица plan_choices (server/choice_store.py) хранит исходы предложений по каждому пользователю отдельно: что было предложено, что человек в итоге взял и чем закончилось.

Итоговая прибавка нормируется и ограничена PREFER_CAP = 0.12 — намеренно мало: прибавка решает спор между двумя похожими навыками, но не назначает исполнителя вместо подбора по существу. Ручки: POST /api/plan/feedback (исход предложения; десктоп зовёт её при отказе), GET /api/plan/prefer (что выучено по текущему пользователю — первое, что стоит смотреть, если у одного человека подбор ведёт себя иначе, чем у остальных).

12.7 Правило: план строится без подсказок агента

Оркестратор запрашивает план с hints: false. Причина — замкнутый круг: подсказка от найденного агента поднимала его же навык в плане, план получался «агентским», и агент после этого «покрывал» план почти полностью. Среда подтверждала сама себе собственную догадку, а слабый подбор выглядел уверенным.

Подсказки (HINT_WEIGHT = 0.3 с потолком HINT_CAP = 0.1) остаются для вызовов, где плана и агента не сравнивают между собой. Если вы делаете свой канал — не включайте их в сценарии «сначала нашли агента, потом проверяем покрытие планом».

12.9 Проверка: песочница и регресс

Песочница. Поле «Проверить фразу» показывает разбор без запуска: на какие работы разложилась задача, какой исполнитель подобран на каждую и с какой уверенностью. Прогоняйте здесь реальные формулировки пользователей после каждого добавления агента.

Регресс. Скрипт ops/regress_pick.py гоняет набор задач через ту же ручку, что и десктоп, и печатает таблицу «задача → ожидаемый исход → фактический». Проверяется живой стенд: каталог навыков, реальные агенты и сущности с данными.

docker cp ops/regress_pick.py abop-webapi:/app/_rg.py
docker exec abop-webapi python /app/_rg.py

Набор покрывает оба случая: задачи, под которые агент есть (ждём agent), и задачи, под которые его нет (ждём build или ask). Ожидания в скрипте — проверенное поведение, а не пожелание: если строка краснеет, сначала смотрите трассу «почему», и только потом правьте ожидание. Рядом лежат юнит-тесты tests/test_orchestrator_regression.py — они проверяют правила, а скрипт проверяет, что на настоящем каталоге правила дают ожидаемые решения.

12.10 Разбор жалобы «выбирается не тот»

  1. Трасса. Откройте why[] и facts{} этого решения в журнале. В девяти случаях из десяти ответ там: лидер и второй стояли рядом (сработал SKILL_LEAD), либо агент не закрывал ведущий шаг (AGENT_COVER).
  2. Повторите фразу в песочнице. Та же формулировка, тот же пользователь.
  3. Посмотрите выученное: GET /api/plan/prefer. Если человек раньше трижды отказался от правильного навыка, подбор это запомнил.
  4. Проверьте смысл. Пустой sem у всех шагов — отключены эмбеддинги.
  5. Правьте в таком порядке: словарь агента → описание навыка → и только в последнюю очередь общие пороги. Порог меняет поведение всех задач сразу, словарь — одной.
Практика Соберите десяток реальных формулировок от пользователей и держите их в CASES регресса. Это дешевле, чем разбирать жалобы постфактум, и единственный способ заметить, что правка порога под одну задачу сломала пять других.

12.11 Документы по ссылке

Если в задаче есть ссылка, агент читает документ по ней и опирается на содержимое (server/doclink.py). Ограничения и защита:

ПеременнаяПо умолч.Что ограничивает

ABOP_DOC_MAX_BYTES2000000Размер сырого документа

Что важно для безопасности:

  • Открываются только адреса систем из реестра (раздел 7) плюс явно перечисленные в ABOP_DOC_HOSTS. Сервер стоит внутри периметра, и свободное «загрузи любой адрес» открыло бы агенту доступ к внутренним панелям и метаданным облака.
  • Переадресации проверяются на каждом шаге (не больше MAX_HOPS = 3): разрешённый адрес не должен уводить на неразрешённый.
  • Страница входа документом не считается. Если вики отдала форму логина, документ помечается непрочитанным, и навыку прямо сказано: ссылаться на него нельзя. Иначе агент делал выводы по тексту «Введите пароль».

Что прочитано и что не прочитано, видно в метриках прогона (run_metrics.documents) и в строке «Источник данных» отчёта.

12.12 Длинные прогоны: кэш частей

Многошаговые агенты не укладывались в таймаут запроса, и работа терялась целиком. Теперь готовая часть прогона складывается в таблицу run_parts (server/run_parts_store.py) по ключу «задание + отпечаток состава агента», и при повторном подходе прогон продолжается с места обрыва, а не с начала. Часть больше MAX_PART_BYTES = 256 КБ не кэшируется. После сведения итогового отчёта части удаляются; оставшийся мусор подчищает sweep.

Отпечаток состава важен: если агента пересобрали, старые части не подхватятся — иначе отчёт свёлся бы из результатов навыков, которых в агенте больше нет.

РАЗДЕЛ 13Очередь, группы и веер

Прогоны исполняются не прямо в запросе, а через очередь. Это даёт предсказуемость под нагрузкой и возможность отменить работу.

13.1 Как работает очередь

ВоркерыABOP_RUN_WORKERS потоков внутри процесса разбирают задания
Приоритетчем меньше число, тем раньше задание; прогоны из чата приоритетнее регулярных
Один на пользователяABOP_USER_CONCURRENT ограничивает одновременные прогоны одного человека
ТаймаутABOP_RUN_TIMEOUT; задание, не уложившееся в него, помечается честно, а не висит бесконечно

Состояние очереди — GET /api/runs/queue: сколько ждёт, сколько выполняется, среднее время ожидания, занятая память. Те же числа уходят в метрики.

13.2 Группы заданий

Несколько заданий можно объединить в группу — тогда ими управляют как одним целым:

  • GET /api/runs/groups/{id} — состояние: сколько в каком статусе;
  • POST /api/runs/groups/{id}/cancel — отменить всю группу;
  • GET /api/runs/groups/{id}/summary — сводка: результаты сведены по составному ключу, с итогами и разрешением расхождений;
  • POST /api/runs/jobs/{id}/retry-step — перезапустить одну ветвь, не трогая остальные.

13.3 Веер по предмету

Веер — запуск одного агента сразу по многим предметам: по всем проектам, всем договорам, всем контрагентам. Каждый предмет становится отдельным заданием со своим сужением данных, но с общей доской и общим снимком данных.

POST /api/runs/fan-out
{
  "agent_id": "authored-…-контролёр-проектов.v1",
  "slot": "проект",
  "query": "",
  "budget": { "max_tokens": 60000 },
  "limit": 10
}

Предметы берутся из явного списка (values), подбираются по запросу (query) или берутся все доступные записи сущности слота. Размер веера ограничен ABOP_FANOUT_MAX.

13.4 Общая память и арбитраж

Ветви одного запроса делят доску: выводы кладутся под ключами вместе с авторством, а читаются только те ключи, которые навык объявил во входах. Если две ветви разошлись в общем поле одной и той же записи, расхождение разрешается по возрастанию цены: правило (большинство, наиболее тяжёлый статус, число по краю, наличие первоисточника) → навык-арбитр → человек.

Спор о сроке, деньгах или предлагаемом мероприятии правилом не закрывается никогда: он остаётся открытым и явно адресован человеку. Нерешённое расхождение видно в записи свода, а не подчищено.

Снимок данных При запуске веера фиксируется объём и отпечаток выборки. Ветвь, увидевшая другой набор, помечает расхождение данных отдельно от спора ветвей — иначе разные цифры выглядели бы противоречием, хотя считали их по разным данным.

14.3 Коннектор-воркер

Отдельный процесс, который читает топики команд и исполняет их в ваших системах. У него — секреты доступа на запись; у ядра ABOP их нет. Воркер ведёт собственный учёт исполненных команд, поэтому повторная доставка одного сообщения не создаёт вторую задачу.

Здоровье воркера: /healthz и /metrics на его порту. Метрики abop_connector_{consumed,done,failed,dlq,duplicate} показывают, что он делает.

14.4 Очередь недоставленных

Сообщение, которое не удалось обработать, уходит в abop.dlq с указанием причины. Разбор — из интерфейса или через API:

  • GET /api/bus/dlq — что лежит и почему;
  • POST /api/bus/dlq/replay — повторить обработку после устранения причины;
  • POST /api/bus/dlq/ack — признать сообщение разобранным.
Следите за DLQ Растущая очередь недоставленных означает, что часть работы агентов не доезжает до систем. Заведите оповещение на abop_bus_dlq_total.

РАЗДЕЛ 18Биллинг и квоты

Стоимость считается по фактическим токенам ответа модели и тарифу, а не оценочно.

18.1 Как считается

После каждого вызова модели фиксируются входные и выходные токены. Стоимость получается умножением на тариф модели. Если тариф не задан (например, своя модель на своём железе), расход считается нулевым — и это честно: денег действительно не тратится.

18.2 Квоты

Квота токеновзадаётся в админ-настройках; видна пользователю в шапке и в кабинете
Мягкий предел70% — счётчик желтеет, 90% — краснеет
Бюджет прогонадополнительная защита на уровне одного запуска (раздел 11)

18.3 Как снизить расход

  • Сужайте предмет работы. Прогон по одному проекту дешевле прогона по всем сразу в разы.
  • Уменьшите «записей в примере для модели» на больших наборах: истину считает код, модель объясняет — ей не нужны все строки.
  • Уменьшите шаги инструментов у навыков, которым не нужен поиск: каждый шаг — отдельный вызов модели.
  • Включите кэш прогонов (ABOP_RUN_CACHE=1): повторный одинаковый запрос вернёт сохранённый результат.
  • Свой бокс. На собственном железе расход в деньгах равен нулю; ограничением становится время, а не бюджет.

19.4 Обновление

  1. Снимите бэкап Оба хранилища, прямо перед обновлением.
  2. Убедитесь, что очередь пуста 
    curl -s http://127.0.0.1:8091/api/runs/queue
    Обновление во время работающего прогона приведёт к его перезапуску.
  3. Разложите новую поставку и пересоберите 
    cd /opt/abop && tar -xf abop-<новая версия>.tar && bash ops/deploy-webapi.sh
  4. Проверьте здоровье и каталог 
    curl -s http://127.0.0.1:8091/api/health
    Число навыков не должно уменьшиться.
  5. Прогоните проверочный прогон Любой лёгкий агент с бюджетом «короткий»: убедитесь, что модель отвечает и данные читаются.

python scripts/push_templates.py --base https://<адрес> --user <admin> --password '…'

Навыки, правленные из интерфейса, без флага --force не перезаписываются.
