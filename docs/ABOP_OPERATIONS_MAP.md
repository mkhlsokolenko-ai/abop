# ABOP — Слой Операций: карта процессов с агентами (визуальная модель)

**Что это:** визуальная спецификация главного экрана слоя Операций (Fleet) — **живая карта процессов организации, в которые встроены агенты**, с semantic-zoom по уровням Организация → Value Chain → Процесс → Подпроцесс → Операция. Не таблица развёртываний, а карта: как Канва по движку, но для мониторинга флота. Для дизайнера — как отрисовать нативно в дизайн-системе ABOP.
**Дизайн-система:** максимально переиспользовать ABOP DS — маскот Эйп, glass-панели, семафор, индиго-акцент, «язык ожидания» (волны/скан). Полный kit — `ABOP_DESIGN_KIT.md`; вкладка/данные — `ABOP_SCREENS.md §8а`; концепция флота — `ABOP_FLEET_OPS.md`; модель — `ABOP_TDR.md §13`.
**Статус:** v1.0.

---

## 0. Идея за 30 секунд

Слой Операций = **«карта процессов организации, на которой живут агенты»**, с **семантическим зумом**: чем глубже — тем уже контекст, тем детальнее агенты и индикаторы.

```
Организация ─▶ Value Chain ─▶ Процесс ─▶ Подпроцесс ─▶ Операция
  (обзор)      (цепочка)      (один)     (внутри)      (лист: где живут агенты)
   агрегат ───────────────────────────────────────────▶ детализация
```
Наверху человек видит **цепочку создания ценности** (value chain) из бизнес-процессов + сколько агентов работает в каждом одной цифрой. Клик по плитке процесса → зум внутрь (подпроцессы), клик глубже → операции, где агенты подсвечены и показаны их состояния (маскот Эйп). Индикаторы **декомпозируются** по уровню: сверху сумма, внизу — по операции.

Аналогия для дизайнера: как карта (страна→город→улица) или service-map наблюдаемости, но по **бизнес-иерархии процессов**, и на «улицах» работают агенты.

## 1. Уровни представления (semantic zoom)

| Ур. | Контекст | Что видно | Как показаны агенты | Индикаторы (декомпозиция) |
|---|---|---|---|---|
| **L0** | **Организация / Value Chain** | горизонтальная цепочка бизнес-процессов (плитки-звенья), связанные стрелками ценности | **общей цифрой** на звене: «🐵 12 агентов» | агрегат по звену: агентов·живых экземпляров·в HITL·стоимость/день·здоровье (семафор-точка) |
| **L1** | **Процесс** (одно звено) | внутренняя схема процесса: подпроцессы плитками + потоки | цифра на подпроцессе: «🐵 4» | сумма по подпроцессу: экземпляры·HITL·дрейф DoD |
| **L2** | **Подпроцесс** | схема из операций (шагов) | цифра + семафор на операции с агентом | по операции: сколько экземпляров·статус·стоимость |
| **L3** | **Операция** (лист) | одна операция крупно + **живые агенты на ней** | **карточки экземпляров** с маскот-состоянием Эйп (idle/думает/HITL/стоп/DoD✓) | по каждому экземпляру: навык·инициатор·длительность·cost·автономия≤конверт |

**Правило декомпозиции индикаторов:** каждый индикатор на уровне N = агрегат его детей уровня N+1. «12 агентов» на процессе = Σ по подпроцессам = Σ по операциям = число живых экземпляров на листьях. Клик разворачивает агрегат в составляющие — ничего не теряется, всё сходится.

## 2. Раскладка экрана (full-screen карта + контекст)

```
┌─ КРОШКИ-УРОВНИ: Организация ▸ Закупки ▸ Проверка подрядчика ▸ [Операция] ──── [🔍 зум −/+] [AS-IS|LIVE] ─┐
├────────────────────────────────────────────────────────────────┬───────────────────────────────────────┤
│ КАРТА (full-screen, движок Канвы, read-only)                    │ КОНТЕКСТ-ПАНЕЛЬ (выбранный узел, 320px) │
│                                                                  │                                         │
│  ┌─Закупки──┐   ┌─Онбординг─┐   ┌─Оплата──┐  《value chain》     │  Процесс: Проверка подрядчика           │
│  │ 🐵 12    │──▶│ 🐵 5      │──▶│ 🐵 8    │                      │  ▓ 4 агента · 6 экземпляров живо        │
│  │ 🟢 ●     │   │ 🟡 ●1 HITL│   │ 🟢 ●    │                      │  1 в HITL · 0 ошибок · 2.4₽/день        │
│  └──────────┘   └───────────┘   └─────────┘                      │  автономия участков: A1–A2 ≤ контракт   │
│       ▲ клик → зум внутрь (L1)                                    │  ──────────────────────────────────    │
│                                                                  │  подпроцессы:                           │
│  (на L3 — плитки-операции с карточками                           │  · Сбор данных   🐵2  🟢               │
│   живых экземпляров Эйп)                                          │  · Скоринг       🐵1  🟡 HITL          │
│                                                                  │  · Решение       🐵1  🟢               │
│                                                                  │  [Открыть в Канве] [Здоровье ▸]         │
└──────────────────────────────────────────────────────────────────┴───────────────────────────────────────┘
```
- **Карта** — центральное пространство (движок Канвы, но read-only мониторинг): плитки-узлы = процессы/подпроцессы/операции, связи = потоки value chain. Активные (где идут агенты) — подсветка индиго + «язык ожидания» (мини-волны на работающих).
- **Крошки-уровни** — навигация зума (Организация ▸ Процесс ▸ Подпроцесс ▸ Операция); клик по любому уровню = зум-аут туда.
- **Контекст-панель** — агрегаты выбранного узла + список детей с их индикаторами + действия (в Канву / Здоровье / развернуть).
- **Тумблер AS-IS | LIVE** — статичная схема процесса (как спроектирован) vs живое наложение агентов (кто работает сейчас). Перекличка с AS-IS/TO-BE LUDA.

## 3. Визуальный язык (нативно из дизайн-системы ABOP)

| Элемент карты | Из ABOP DS |
|---|---|
| **Плитка-узел** (процесс/операция) | glass-карточка (`--surface` + blur + `--surface-line`), радиус 16; активная — бордер `--brand` |
| **Счётчик агентов** «🐵 N» | маскот-иконка Эйп + число (mono); Эйп в состоянии агрегата (думает, если хоть один работает) |
| **Семафор узла** ● | `--ok` норма · `--warn` HITL/ждёт · `--crit` ошибка/дрейф/вне конверта |
| **Работающая операция** | «язык ожидания» — мини-«Волны» на плитке (идёт исполнение), «Сканирование» при долгом |
| **Живой экземпляр** (L3) | карточка с маскот-состоянием Эйп (5 состояний = статусы прогона) + навык-чип + cost mono |
| **Связи value chain** | стрелки-потоки (как рёбра Канвы), подпись потока mono |
| **Автономия участка** | компонент `AutonomyEnvelope` L0–L3 (из DESIGN_KIT D5) на узле |
| **Индикаторы** | KPI-чипы стекло (агентов/живых/HITL/стоимость/дрейф) — те же, что на Обзоре |

**Эйп как носитель состояния операции:** на узле с агентами Эйп показывает агрегатное состояние (думает / ждёт-HITL / стоп); на L3 — по экземпляру. Маскот становится «пульсом карты» — консистентно с остальным продуктом.

## 4. Взаимодействие и user-flow (UI/UX паттерны)

**Паттерн — semantic zoom + focus & context:**
- **Zoom-in:** клик по плитке → плавное раскрытие её внутренней схемы (L→L+1); контекст-панель обновляется на выбранный узел. Крошка добавляется.
- **Zoom-out:** клик по крошке-уровню или `−` → назад к родителю.
- **Focus & context:** выбранный узел — в фокусе (панель справа), но карта уровня видна (не теряем, где мы).
- **Прогрессивное раскрытие:** индикаторы агрегированы наверху, детализируются при углублении — не перегружаем L0.

**Связь со всей средой (сквозной flow):**
- Клик по **живому экземпляру** (L3) → **§3 Пульт** этого инстанса (живые волны/доска/аудитор).
- **«Открыть в Канве»** на операции/агенте → **§6 Канва** (пересмотр развёрнутого → новая версия, ADR-024).
- **Здоровье/алерт** на узле → таб Здоровье (§8а) или конкретный проблемный инстанс.
- **«Посадить агента»** на пустую операцию (нет агента) → развернуть (модалка §9.5) на этот участок.
- Крит-точка на узле (вне конверта) → ссылка «разобрать в Безопасности» (ре-аттестация).

**Триггер обновления:** карта живая (auto-refresh состояний/счётчиков через SSE флота); переходы между уровнями — без перезагрузки.

## 5. Связь с моделью данных (почему это реализуемо)

Карта — визуализация уже определённой модели (`ABOP_TDR §13`, `ABOP_FLEET_OPS`):
- **Узел операции** = `Deployment.process_point` (агент посажен на участок процесса).
- **Счётчик/подсветка** = живые `Instance` этого развёртывания (`GET /api/instances`).
- **Индикаторы узла** = агрегат `GET /api/fleet/health` по ветке иерархии.
- **Иерархия процессов** (Организация→…→Операция) = дерево участков; источник — карта процессов (перекличка с размещением LUDA AS-IS/TO-BE) + привязки развёртываний.
- **AS-IS слой** = схема процесса (как спроектирован), **LIVE слой** = наложение живых экземпляров.

То есть визуальная модель ложится на Fleet-модель без новых сущностей — нужен лишь **иерархический индекс участков** (дерево value chain → операции) и агрегация индикаторов по нему.

## 6. Состояния (для каждого уровня)

| Состояние | Паттерн |
|---|---|
| **Пусто** (нет развёрнутых агентов) | карта процессов видна, узлы серые, «В проде пока никого · [Развернуть агента]» |
| **Загрузка** | скелетоны плиток (форма известна) + мини-спиннер счётчиков |
| **Ошибка данных** | баннер `--crit`, карта из кеша + пометка «данные устарели» |
| **Живой поток** | активные узлы с «волнами», счётчики auto-refresh, Эйп-пульс |
| **Дрейф/вне конверта** | узел `--crit`, алерт-бейдж, ссылка на разбор |

## 7. Приоритет и объём

- **Это ГЛАВНЫЙ экран слоя Операций** — переопределяет таб «Карта процессов» (§8а) из одного из четырёх в центральное представление; табы Развёртывания/Живые/Здоровье — дополняющие списки/агрегаты вокруг карты.
- **Отрисовка:** после MVP-экранов Run и базовой вкладки §8а; сначала L0 (value chain + агрегаты) и L3 (операция + живые Эйп) — они несут максимум ценности; L1/L2 — semantic zoom между ними.
- **Требование консистентности:** ни одного нового визуального языка — только элементы ABOP DS (Эйп, glass, семафор, волны, AutonomyEnvelope, KPI-чипы). Чек-лист приёмки — `ABOP_SCREENS §11`.
