# Бриф для LLM-дизайнера: укрупнение и «продуктификация» интерфейса ABOP Desktop

> Этот документ — самодостаточная задача. Скопируйте целиком в модель-дизайнера.
> Все числа — факты текущего кода, не приблизительные оценки.

## Роль

Ты — продуктовый дизайнер и дизайн-директор с опытом в ops-консолях, финансовых
платформах и developer-инструментах. Тебе дали полное описание интерфейса рабочего
приложения. Задача — не «причесать», а перевести его из состояния «набор экранов с
кнопками» в состояние «продукт»: уверенная композиция экранов, действия, попадающие
в смысл, стиль, по которому продукт узнаётся без логотипа.

## Что за продукт

**ABOP** — платформа «агентных отделов» для аутсорсинга учётных процессов. ИИ-агенты
(сверщик, аудитор 1С, супервайзер) сканируют учётные базы клиентов (1С), находят
расхождения (немодернизированные документы, незачтённые авансы, ошибки НСИ — сотни
находок на клиента), человек-расчётчик/руководитель принимает решения по каждой:
«это проблема» / «норма», выбирает способ устранения («Провести документ», «Запросить
счёт-фактуру»), часть действий — необратимые проводки в 1С через подтверждение (HITL).
Вечером отдел видит ИКА — индекс качества агентов (0–100), который двигает автономию
отдела по лестнице ADR-085: ≥90 — повышенная (меньше подтверждений), <70 — суженная.

**Главный пользователь** — руководитель отдела/расчётчик, который утром разбирает
поток находок, а вечером смотрит, сколько исправлено. Вторые роли: бухгалтер
клиента (получает отчёт), админ платформы. Права режутся ABAC по отделу семьи.

**Утверждённая метафора интерфейса — «диспетчерская отдела»**: пульт управления
потоком работы, не админ-панель с карточками. Принцип: mono-капсы как гравировка
на приборах, полоса значимости как главный жест, живые числа, ни одного
декоративного элемента.

## Технические рамки (менять нельзя)

- Electron-приложение, vanilla JS + один CSS-файл токенов (`theme.css`), без фреймворков
- CSP без внешних CDN: шрифты в бандле — **Manrope** (текст) + **IBM Plex Mono** (числа/капсы)
- Тёмная тема основная: фон `#060a12`, панели `#101726`, рамки `#22304e`, поле `#0d1526`,
  акцент фиолетовый `#8b5cf6` (ink `#c4b5fd`), ok `#34d399` / warn `#f0a63a` / danger `#f87171`
- Светлая тема вторичная (выведена из тех же ролей)
- Ступени текста выверены по WCAG AA и охраняются тестом-сторожем — предлагать
  «ослабить серые подписи» нельзя
- Контраст и плотность охраняются автотестами; каждое изменение должно быть
  выразимо токеном или классом (модули постепенно от них отказываются)

## Грамматика кнопок — лестница ответственности (уже принята)

Кнопка классифицируется по цене решения, не по цвету:

- **расчёт** — запускает пересчёт/прогон («Пересчитать», «Только вычитать») — станочная рамка
- **внутри** — обратимое действие внутри платформы («Признать», «Норма», «Отдать отделу»)
- **наружу** — что-то уходит вовне (письмо, egress) — объект адресации стоит НА кнопке
- **необратимое** — «Провести в 1С»: штриховка/предохранитель, обязательное подтверждение
  с полным перечнем того, что уйдёт
- **primary** — не ступень лестницы, а «главная цель экрана», одна на экран
- «ждёт человека» — не кнопка, а место для подписи (HITL-очередь)

**Проблема, которую надо решить:** в текущем коде кнопки пока размечены по виду
(`primary/ghost/ok/danger`), и на экранах рядом стоят «Признать», «Норма», «Отложить»,
«Провести в 1С», «Проверить» — визуально почти равноправные. Человек не считывает
цену решения до нажатия.

- **Рейл слева** (186px): секции «маршрут» + «быстрые» с капсами; бейджи-счётчики

- **Строка живой работы** над контентом: «что идёт, где оно и сколько стоило»
- **Панель модулей** — рабочая область
- **Чат**: слева список тредов (252px, поиск, избранное), лента сообщений (role=log,
  до 760px), композер с доком статуса, drawer инструментов (386px, справа)
- **Рейл сейчас**: до ~10 видимых разделов плоским списком. Целевое состояние
  (принято, переносится): **6 пунктов первого класса** — Пульт отдела · Чат · Решения ·
  Прогоны · Клиенты · Кабинет — плюс капса «сервис» с инженерными секциями
  (коннекторы, наблюдение, контроль, граф) только для админ-ролей

## Экраны (что сейчас)

1. **Пульт отдела** (главный, целевой экран диспетчерской) — уже собран по мокапу:
   полоса здоровья (ИКА 30px + 4 плитки пользы: найдено/признано/исправлено/доля
   признания + ярлыки NCR/первичка/методолог/карточка) → тулбар (чипы агентов семьи
   с запуском в чат + всегда видимый ввод задачи + «Отдать отделу») → чипы фирм
   с сортировкой (по значимости/по сумме) → ЭДО-окно (входящие из вычитки) →
   поток находок ГРУППАМИ причин (полоса значимости h/m/l, код причины, название,
   способ устранения, «×187 · 4,2 млн ₽», разворот группы → карточки с «Провести в 1С»
   / «Исправлено — проверить» / «Признать» / «Норма», пакетное «Признать группу» с
   подтверждением) → петля доведения (принятые находки с кнопкой проверки) →
   колонка фирм (компактные карточки: ждёт N, схема, период, пересчитать, отчёт)
2. **Чат** — основная поверхность диалога с агентами: треды, лента, HITL-карточки
   «что уйдёт — целиком» с подтверждением, цепочки шагов, общая доска фактов
3. **Решения** — реестр находок за всё время: фильтры, карточки с доказательством
   (цитата документа), способом, нормой; очередь первички (поля ниже порога)
4. **Прогоны** — журнал расчётов: ступени конвейера, стоимость в рублях и секундах,
   отчёт прогона
5. **Клиенты** — реестр клиентских баз: подключение (источник, граница расчёта,
   доступ), карточка клиента, вычитка, пересчёт
6. **Кабинет** — профиль, обновление приложения, релиз-канал
7. **Вертикали** — витрина отраслевых пакетов, переключатель представления
8. **Граф/конструктор агентов** — canvas цепочек, палитра навыков, выпуск версий
9. Служебные: наблюдение (watch), контроль (control) — для инженерных ролей

## Текущий юзер-флоу (кольцо работы)

```
Утро: открыл пульт своего отдела (ABAC сам режет чужое)
  → полоса здоровья: ИКА, сколько нерешённых, что горит
  → поток группами: топ-5 причин, верхняя — самая тяжёлая (значимость+сумма)
  → развернул группу → карточки с доказательством
  → «Признать» (в журнал, со способом) или «Норма»
  → «Провести в 1С» (необратимое, подтверждение) → «Исправлено — проверить»
    (система перечитывает базу и проверяет воспроизводимость находки)
  → что-то новое? «Отдать отделу» — супервайзер разложит на подзадачи с DoD
  → агент запускается из чипа на пульте → живёт в чате (HITL, стоимость)
Вечер: ИКА отдела вырос — «сколько я исправил»; автономия на следующей неделе выше
```

Критерии потока (приняты): расчётчик до кнопки действия — **≤1 клик от открытия**;
админ до любой сервисной секции — **≤2 клика**; «появилась находка» должна приходить
уведомлением (телега — в планах, не сделано).

## Задача — что от тебя нужно

**Фокус 1 — «укрупнить экраны».** Сейчас экраны собраны как виджет-сетки: полосы
мелких карточек, чипов и кнопок примерно одного визуального веса. Экраны не
используют полотно уверенно — нет «героя», нет крупной зоны состояния, нет
композиционной иерархии «смотрю → читаю → действую». Дай правила композиции
экранов диспетчерской: зонирование (что крупное, что мелкое, где человек смотрит
в первую секунду), типовые сетки для экранов «поток + детали», «журнал + карточка»,
«список + инспектор»; когда карточка имеет право быть крупной, а когда строкой.
Как должны выглядеть «продуктовые» экраны против текущих виджет-сеток — на примере
пульта отдела и прого­нов.

**Фокус 2 — «действия, попадающие в смысл».** Дай правила, как превратить ряды
равноправных кнопок в иерархию: сколько действий может быть на карточке/строке/экране,
как одно главное, как остальные уходят в меню/иконки, как лестница ответственности
читается ДО нажатия (форма/подпись/рамка для каждой ступени), как выглядит
необратимое действие, от которого глаз не отводится, и как рутинные признания
не превращаются в «можелклики» (массовые операции, клавиатурные пути).

**Фокус 3 — «логика экранов как в продукте».** Для каждого ключевого экрана
(пульт, чат, решения, прогоны, клиенты, кабинет) сформулируй: один вопрос, на который
экран отвечает; что является героем; что вторично; что лишнее и куда уходит;
переходы между экранами (куда человек попадает после действия). Проверь флоу на
разрывы: где человек теряется, где нет подтверждения, где нет пути назад.

**Фокус 4 — целостный стиль.** Ты знаешь, как выглядит «генерик AI-дашборд».
Назови конкретные приёмы, отличающие собранный продукт от набора экранов:
типографические контрасты, ритм отступов, работа с состоянием (пустое/загрузка/
ошибка/успех как первоклассные экраны, не послеthought), микро-контент (заголовки,
пустые состояния, подписи кнопок), что проверить первым.

**Формат ответа:**
1. Глобальные правила (10–15, каждое — с «почему» и с примером «было → стало»)
2. По экранам: пульт, чат, решения, прогоны, клиенты — зонирование, герой,
   иерархия действий, что убрать (с указанием куда), ASCII-схема композиции
3. Шкала компонентов: что укрупнить/ужать в таблице масштаба выше (с числами)
4. Разрывы флоу и их починка
5. Топ-10 изменений по убыванию эффекта на «ощущение продукта»

Предлагай до уровня чисел и классов: «крупная зона состояния пульта ≥120px высотой,
ИКА 48px mono», а не «сделать заметнее». Не предлагай то, что в списке решённого.

## Референсы — с чем сверять (что именно брать из каждого)

1. **Linear** (linear.app) — эталон «не-генерика»: плотность с воздухом, клавиатура,
   действия по иерархии (одна primary, остальные тихие), типографический ритм.
   Брать: дисциплину один-экран-один-вопрос, обращение с пустыми состояниями.
2. **Sentry** (issue stream) — ближайший аналог потока находок: ошибки сгруппированы
   по причине, полосы критичности, resolve/ignore/assign прямо в строке, массовые
   операции. Брать: паттерн «группа причин → строки с действиями», bulk-resolve,
   как выглядит «требует внимания» против «тихо».
3. **Mercury** (banking) — финансовые операции с подтверждением: объект платежа
   крупно, кнопка необратимого действия с адресом («Pay $X to Y»), States
   (draft/awaiting approval/sent). Брать: подачу необратимых проводок, «что уйдёт»
   как первоклассный экран, спокойный финансовый тон.
4. **Ramp** — учётная автоматизация с approval-цепочками: очередь согласований
   как рабочий список, контекст сделки рядом с действием. Брать: очередь решений
   как главный экран, скорость разбора.
5. **Vercel dashboard** — прогоны/деплои: ступени статусов, живой лог, стоимость
   функции. Брать: подачу исполняющегося прогона (маячок, ступени, цена), список
   прогонов как журнал продуктового вида.
6. **LangSmith / Langfuse** — LLM-трассы: шаги агента, токены, стоимость, HITL.
   Брать: как показывать цепочку шагов агента с ценой и исходом, трассировка.
7. **Stripe Dashboard** — таблицы денег: выравнивание сумм, фильтры, review queues.
   Брать: типографику таблиц, «review»-очередь, спокойствие.
8. **Temporal UI** — durable workflows с HITL-callbacks: history, inputs/outputs.
   Брать: показ длительных цепочек и точек ожидания человека.
9. **Грамматики компонентов**: shadcn/ui, Primer (GitHub), Polaris (Shopify) —
   как называть и масштабировать примитивы; Polaris — тон «продукт для работы».

**Анти-референсы** (как НЕ должно): типовые AI-дашборды с сеткой одинаковых
карточек-плиток, glassmorphism, градиентные «темы для дашбордов» с dribbble,
BI-конструкторы (Grafana/Metabase как стиль — они про мониторинг, не про работу).

## Ограничения на предложения

- Vanilla CSS + токены: никакой замены стека, никаких компонентных библиотек
- Данные приходят с задержкой (прогон ~минута): состояния загрузки/ожидания —
  первоклассные
- Русский интерфейс: помни про длину слов («Исправлено — проверить» не ужать)
- Доступность AA охраняется тестами; клавиатура — обязана быть
- Приложение живёт в окне 1280–1920px, минимум 900px
