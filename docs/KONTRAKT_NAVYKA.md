# Контракт навыка: справочник формата

Контракт отвечает на три вопроса о навыке: **чем его кормить**, **что он отдаёт** и **по какому ключу
это соединяется с результатами других навыков**. До появления контракта вход навыка был описан только
прозой в инструкции, а схема (`json_schema`) описывала лишь выход. Из-за этого граф агента нечем было
исполнять по порядку, совместимость шагов цепочки угадывалась по совпадению имён полей, а одно и то же
понятие в разных навыках называлось по-разному.

Формат живёт в `server/skill_contract.py` — модуль без побочных эффектов, чтобы его одинаково
использовали валидатор шаблонов, сборка агента, планировщик и рантайм.

Связанные документы: [SKILL_TEMPLATES.md](SKILL_TEMPLATES.md) — шаблон навыка целиком;
[GUIDE_SBORKA_AGENTOV.md](GUIDE_SBORKA_AGENTOV.md) — как объявлять вход и выход при сборке;
[ROADMAP.md](ROADMAP.md) — этапы 0–8, ради которых контракт появился.

---

## Где он лежит

`skills/<id>/template.json`, рядом со схемой результата:

```json
{
  "name": "Сверка плана и факта",
  "instruction": "…",
  "json_schema": { "properties": { "исполнение": {}, "решения": {} } },
  "slots":    [],
  "inputs":   { "required": [], "optional": [] },
  "produces": [ { "path": "исполнение", "key": "пункт", "join": "пункт_плана" } ]
}
```

Шаблон можно править и из интерфейса: **Настройки → Шаблоны навыков**. Правка через интерфейс
помечает шаблон как отредактированный, и обновление из поставки его больше не трогает — вернуть
поставочную версию можно сбросом (`POST /api/schema-templates/{id}/reset`).

---

## `inputs` — чем кормить

Два списка, `required` и `optional`. Каждый вход — объект с обязательным полем `from`, которое
называет источник. Источников ровно четыре.

| `from` | Обязательные поля | Что означает |
|---|---|---|
| `data` | `entity` | строки из Data Plane: сущность и, по желанию, нужные поля |
| `skill` | `skill` | выход другого навыка, который идёт раньше по графу |
| `slot` | `name` | предмет работы, который уточняет человек |
| `context` | — | свободный контекст прогона: письмо, задача трекера, вложение |

```json
"inputs": {
  "required": [
    {"from": "slot",    "name": "проект"},
    {"from": "data",    "entity": "roadmap_item",      "fields": ["проект", "пункт", "план_финиш"]},
    {"from": "data",    "entity": "contractor_report", "fields": ["проект", "пункт", "факт_финиш"]},
    {"from": "skill",   "skill": "audit1c-checks", "path": "находки", "fields": ["id", "класс"]},
    {"from": "context", "note": "письмо руководителя или задача трекера"}
  ],
  "optional": [
    {"from": "data", "entity": "project", "fields": ["id", "commissioning"]}
  ]
}
```

`fields` — список строк, подсказка о том, какие именно поля нужны. Он не ограничивает выборку, но по
нему видно, что сломается, если поле исчезнет из источника.

`path` у входа из навыка называет конкретный список: навык может отдавать несколько, и приёмнику
важно, какой из них он ждёт.

**Разница между `required` и `optional` не косметическая.** Необеспеченный обязательный вход — причина
не поставить навык в план и не дать собрать агента. Необеспеченный необязательный — просто чуть менее
полный результат.

## `produces` — что навык отдаёт

Объект или список объектов с тремя полями:

| Поле | Что это |
|---|---|
| `path` | имя списка в `json_schema.properties` — где в результате лежат записи |
| `key` | поле записи, которое её опознаёт (номер пункта, id находки) |
| `join` | имя сквозного понятия: по нему результат соединяется с выходами других навыков |

```json
"produces": [
  {"path": "исполнение", "key": "пункт",       "join": "пункт_плана"},
  {"path": "решения",    "key": "что_сделать", "join": "решение"}
]
```

Навык имеет право отдавать несколько списков: сверка плана и факта даёт и «исполнение» по пунктам для
исполнителя, и «решения» для руководителя, а следующие шаги берут разные из них.

`join` — то, чем контракт отличается от простого описания схемы. `key` опознаёт запись внутри одного
навыка, `join` называет понятие между навыками: если два навыка объявили `join: "пункт_плана"`, их
записи можно свести, даже когда поля называются по-разному.

---

## `slots` — предмет работы

Слот — это то, что нельзя вывести из данных: по какому именно проекту, договору, контрагенту работаем.
Агент один, предметов много, и без слота прогон уйдёт не по тому проекту.

```json
"slots": [{
  "name": "проект",
  "entity": "project",
  "required": true,
  "label": "Какой проект сверяем?",
  "search_fields": ["id", "name", "customer", "manager"],
  "display": {"title": "name", "subtitle": "customer", "badge": "id", "note": "commissioning"},
  "hint": "без проекта сверка даст мешанину: пункты с одинаковыми номерами из разных карт"
}]
```

Вход `{"from": "slot", "name": "…"}` обязан ссылаться на объявленный здесь слот — иначе контракт не
проходит проверку.

## Сквозной ключ сущности

Контракт есть не только у навыка, но и у сущности Data Plane (`CANONICAL_SCHEMAS` в `cli/ape.py`,
наружу — `GET /api/data/schema/{entity}`):

| Поле | Что значит |
|---|---|
| `required` | без этих полей запись невалидна и в хранилище не попадёт |
| `join` | по каким полям запись сопоставляется с записями ДРУГИХ сущностей |
| `hint` | что ещё лежит в записи |

`join` — не то же самое, что `id`. У пунктов дорожной карты, отчётов подрядчика и решений приёмки
идентификаторы разные по построению (`PRJ-2451/RM-02/ООО Стек-Интегро` против
`PRJ-2451/RM-02/приёмка`), а говорят они об одном пункте одного проекта. Поэтому у всей проектной
вертикали `join: ["проект", "пункт"]`, а не `["id"]`.

По нему сводка группы заданий выбирает ключ сведения. До того как ключ объявили, он угадывался
правилом «если в результате есть „исполнение“ — сводим по проекту и пункту, иначе по id», то есть
работал ровно на одном демо-кейсе.

## Реестр канонических имён

`CANON` в `server/skill_contract.py` собран из фактических схем каталога. Каноническое имя — то, что
уже преобладает; синонимы перечислены, чтобы валидатор подсказывал замену, а планировщик считал такие
поля совместимыми.

Примеры связок: `срок` ← дедлайн, дата_окончания, когда_нужно · `основание` ← почему, обоснование,
доказательство · `критичность` ← серьёзность, существенность, уровень_риска · `счёт_дт` ← дебет, дт ·
`задача` ← задачи, тикет, тикеты, issue · `находка` ← находки, расхождение, нарушение.

Реестр **не запрещает** свои поля: он нормализует общие понятия, по которым навыки соединяются друг с
другом. Поэтому несоответствие реестру — предупреждение (`field_hints`), а не ошибка.

Словарь понятий целиком виден в интерфейсе и через `GET /api/catalog/fields`: там же показано, где в
каталоге одно понятие названо по-разному.

## Контракт у системного агента и границы у личного

Контракт обязателен там, где агент создаётся **централизованно**: приходит бандл LUDA, в нём объявлен
конверт — потолок автономии, точки HITL, метрики приёмки, residency. Без ContractSet сервер агента не
примет (ADR-029), и это осознанно: прод-агент отвечает за работу отдела.

**Личный агент** (семья + навыки, собран человеком «под себя») контракта не имеет. Его границы не
объявляются, а **выводятся из навыков** — по строжайшему из них:

| Что | Как считается |
|---|---|
| режим | строжайший среди навыков: `action` > `write` > `read` |
| выход наружу | `external`, если хоть один навык ходит во внешнюю сеть |
| ссылка на источник | обязательна, если её требует хоть один навык |
| **потолок автономии** | **A1**, если есть действие наружу или внешний выход; иначе **A2** |

Выше A2 личный агент не поднимается никогда: A3 и A4 выдаёт только контракт. Правило объясняется
человеку словами прямо при сборке («A1: среди навыков есть действие наружу — каждое уйдёт только
после вашего подтверждения»), иначе оно выглядит произволом системы.

Остальные ограничения те же, что у системного: собрать агента можно только в своём отделе (ABAC),
нужен уровень manager, граф проверяется против выведенного конверта, а **покрытие входов считается по
тем же контрактам навыков** — человеку сразу говорят, какому навыку не хватает данных, предмета или
выхода соседа. Для личного агента это предупреждение, а не запрет: его собирают в том числе чтобы
попробовать.

Навыки личного агента связываются в цепочку в том порядке, в каком их выбрали, а поставщик
объявленного входа поднимается выше приёмника: порядок, обещанный конструктором, становится рёбрами
графа, иначе все навыки пошли бы одной волной и не увидели друг друга.

## Проверки

| Функция | Что проверяет |
|---|---|
| `validate_inputs` | источник из четырёх допустимых, обязательные поля источника, `fields` — список строк |
| `validate_produces` | `path`/`key`/`join` — строки, `key` не задан без `path`, нет лишних ключей |
| `validate_contract` | всё вышеперечисленное плюс: `produces.path` есть в `json_schema.properties`, вход из слота объявлен в `slots` |
| `field_warnings` | где стоит взять каноническое имя вместо синонима (предупреждение) |
| `coverage` | чего не хватает навыку для запуска здесь и сейчас |

`coverage(skill_inputs, entities=…, slots=…, upstream=…)` — та самая проверка, которая на сборке
агента говорит «нет данных сущности roadmap_item» или «нет результата навыка audit1c-checks до этого
шага» до прогона, а не посреди него.

Проверка контракта стоит в тестах, поэтому новая несостыковка не доедет до прогона.

## Кто читает контракт

| Потребитель | Что делает |
|---|---|
| Сборка агента (канва) | считает покрытие входов и подсвечивает, чего не хватает |
| Планировщик `server/planner.py` | собирает исполнимую цепочку: навык без обеспеченного входа в план не попадает, недостающее звено добирается тем навыком, который его производит |
| Рантайм `server/runner.py` | передаёт выходы по волнам: что объявлено в `produces`, то и уезжает дальше |
| Доска прогона `server/blackboard.py` | кладёт записи под ключом `produces.path` с авторством навыка |
| Арбитраж `server/arbiter.py` | сопоставляет записи разных авторов по `key` и ищет расхождения по общим полям |
| Отчёт | выбирает шаблон под форму результата (`planner.report_template`) |

## Частые ошибки

**`key` без `path`.** Непонятно, у какого списка ключ. Валидатор это ловит.

**`produces.path`, которого нет в схеме.** Навык объявил, что отдаёт «находки», а в
`json_schema.properties` их нет — приёмник получит пустоту. Валидатор ловит.

**Вход из слота без объявления слота.** Навык ждёт предмет, но интерфейс не знает, что спросить.
Валидатор ловит.

**Синоним вместо канонического имени.** «дебет» вместо «счёт_дт» — шаги формально исполнятся, но не
соединятся. Валидатор предупреждает, тест связности каталога ругается, если из-за этого разошлась
объявленная связь навык-навык.

**Обязательный вход там, где хватило бы необязательного.** Навык перестаёт попадать в планы, потому
что его вход редко обеспечен. Если без данных результат просто беднее — это `optional`.

**Вход из навыка без `path`, когда источник отдаёт несколько списков.** Формально допустимо, но
приёмник получит первый попавшийся. Лучше назвать явно.

## Как посмотреть контракт живьём

```
GET  /api/skills/{sid}/contract     # вход, выход, слоты, ошибки, подсказки по именам
GET  /api/skills/{sid}/slots        # какие предметы уточнять до запуска
GET  /api/catalog/coverage          # готовность всего каталога: схема, вход, выход, данные, слоты
GET  /api/catalog/fields            # словарь понятий и места, где одно понятие названо по-разному
POST /api/plan/auto                 # что из каталога реально соберётся под задачу
```

В интерфейсе то же самое: **Настройки → Шаблоны навыков** (контракт навыка), **Настройки → Каталог**
(покрытие и словарь понятий), кнопка **«Проверить план»** на канве.
