# Отделы агентов: как ABOP становится живым

> Проект, 14.11.2026. Решение владельца: перейти от «один процесс — один агент» к отделам с
> супервайзером, методологом и независимым аудитором. Первый отдел — **Бухгалтерия**, на нём
> откатываем всю цепочку: агентов, человека, наблюдаемость.
>
> Источник — размышления владельца (переписка «Концепция отделов агентов»). Здесь они разобраны
> по пунктам, сверены с тем, что в ABOP уже есть, и доведены до плана. Где я возражал и возражение
> снято решением владельца — это сказано прямо, чтобы потом не выяснять заново.

## 1. Что болит сегодня (числа, а не ощущения)

Разбор прода 13–14.11.2026 дал четыре отказа, и ни один не был виден на экране:

| что случилось | как выглядело | сколько стоило |
|---|---|---|
| агент «Аудитор данных в 1С» нёс граф следователя: `audit1c-checks` в нём не было | прогон зелёный, вердикт «ok» | находок **0**, никто не замечал недели |
| способы устранения написаны под чужую нумерацию (на «реализация без выданного СФ» стоял «запросить у поставщика») | карточка показывала рекомендацию | **198** находок с советом, который нельзя выполнять |
| поля способа терялись в трёх местах подряд (реестр → группа → сборка записи) | способ есть, инструкции нет | найдено только ручной проверкой |
| правило B3 выдавало то, что заказчик прямо назвал не-сигналом | очередь росла | **799 из 1438** находок, доля исправления **0 %** |

Общее у всех четырёх: **система не проверяет сама себя**. Конверт держит границы действий, LUDA
проверяет готовность до запуска, а в рантайме качество не смотрит никто. Это и есть дыра, которую
закрывают аудитор и методолог.

## 2. Разбор концепции: что берём, что меняем, что отвергаем

| идея из документа | решение | почему |
|---|---|---|
| отделы как кластеры агентов с ACL | **берём, уже есть** | `families_store`: семья = отдел, доступ по ABAC из JWT; у агента поле `family` |
| супервайзер отдела | **берём, строим** | новой сущности нет; ближайшее — оркестратор `/api/orchestrate`, но он разовый и без отдела |
| блэкборд отдела | **берём, уже есть** | `blackboard` с областями `usr-` и `fam-`, TTL, `run_id`, провенанс |
| четыре слоя доски (working / validated / cross-dept / user-facing) | **берём как поле, не как новую систему** | слой — атрибут записи доски; вторая доска рядом удвоит провенанс и разойдётся с первой |
| агент-методолог: регламент → конфигурация | **берём, маст-хэв** | есть `reglament_store` и правила-данные с версией и автором — методологу есть куда писать |
| независимый агент-аудитор, NCR, ИКА | **берём, маст-хэв** | ровно закрывает четыре отказа из раздела 1 |
| динамический конверт: ИКА поднимает автономию | **берём по решению владельца** | я возражал (метрика одной модели расширяет права другой); решение принято — реализуем с жёсткими оговорками, см. §6 |
| супервайзер правит промпты и графы | **берём, но через подтверждение человека** | правка идёт заявкой в ту же очередь HITL: атрибуция «кто изменил правило» сохраняется |
| семантический кэш артефактов по эмбеддингам | **отвергнуто** (согласовано) | замер 13.11: лучший эмбеддер даёт 83 % попадания в первое место — каждый шестой кэш-хит вернул бы чужой расчёт. Ключ точный: организация + период + правило + версия политики |
| «few-shot на каждое изменение» | **не берём** | владелец прав: в ИСМ это разделение корректирующих и предупреждающих действий. Косметика — порядок и инструменты, переработка — промпт |
| балльная оценка, которой агент не управляет | **берём** | ИКА считает только аудитор, из машинных фактов |

Отдельно о самом документе: он написан собеседником, который ни разу не возразил. Идеи от этого не
хуже, но решения ниже приняты не потому, что там написано «гениально», а потому что каждая ложится
на существующий механизм и закрывает названный отказ.

## 3. Кто есть кто в отделе

**Отдел** — семья (`families_store`). У него: миссия, роли, набор навыков, конверт (что вообще
разрешено), доска `fam-<id>`, регламент в RAG, ИКА.

| роль | что делает | чего НЕ делает |
|---|---|---|
| **Супервайзер** | принимает задачу человека, декомпозирует на подзадачи по *результату*, валидирует по DoD, публикует в слои, несёт заявки на изменение конфигурации | не считает сам, не правит конфигурацию без подтверждения человека |
| **Исполнители** | берут подзадачу с доски, выбирают путь и навыки, кладут результат в working | не ходят в чужой отдел напрямую, не выполняют внешние действия без HITL |
| **Методолог** (один на установку) | читает регламенты, выводит функции, сроки, TTL, состав ролей; готовит заявки на изменение конфигурации отделов | не правит промпты на лету, не оценивает качество |
| **Аудитор** (один на установку, независим) | проверяет артефакты и конфигурации, считает ИКА, выписывает NCR | ничего не чинит сам — это разделение обязанностей |

Методолог и аудитор — **общие**, а не внутри отдела: иначе отдел оценивает сам себя.

## 4. Как агенты работают внутри отдела (та самая недетерминированная свобода)

Сегодня агент — это граф навыков, исполняемый волнами: порядок задан заранее. Свободы нет, и
менять порядок можно только пересборкой агента. Новая механика:

### 4.1. Подзадача объявляет результат, а не шаги

Супервайзер раскладывает задачу человека на подзадачи вида **«нужен такой-то артефакт»**, а не
«сделай шаг 1, потом шаг 2». У подзадачи:

```
{ "отдел": "finance", "задача": "<id задачи человека>", "нужен": {"вид": "сверка_расхождений",
  "предмет": {"клиент": "sovetnik-may-dental", "период": "2026-10"}},
  "критерии": ["каждая находка несёт доказательство", "у находки объявлен способ или сказано,
                что его нет", "числа посчитаны кодом"],
  "бюджет": {"max_rub": …, "max_sec": …}, "срок": "…" }
```

Это ложится на существующую очередь: `run_queue.enqueue(kind="task", group_id=<задача>)`, захват
через `FOR UPDATE SKIP LOCKED` уже работает и уже проверен на нескольких процессах.

### 4.2. Исполнителя выбирает не супервайзер, а соответствие контракту

У каждого навыка объявлены входы и выходы (`skill_datasources_resolved`, контракты). Агент отдела
берёт подзадачу, если **его навыки производят нужный выход** и данные ему доступны. Механика
сопоставления уже написана в планировщике (`planner.plan` собирает цепочку по контрактам) — здесь
она применяется к одной подзадаче в рантайме, а не ко всему плану заранее.

Если подходящих исполнителей несколько — берёт тот, у кого выше ИКА; при равенстве — любой
свободный. Это даёт конкуренцию, о которой говорит владелец: агент с низким ИКА реже получает
работу, пока супервайзер не поправит его конфигурацию.

### 4.3. Свобода — в пути, не в числах

Исполнитель сам решает: какие навыки применить, в каком порядке, сколько шагов, какие инструменты
звать, нужно ли уточнение у смежного отдела. **Что не меняется ни при какой свободе:**

- числа считает код, модель объясняет (это не стиль, а защита от выдуманных сумм);
- провенанс обязателен: артефакт без источника не принимается супервайзером;
- конверт отдела не расширяется изнутри: нет навыка — нет действия;
- внешнее действие — только через HITL.

То есть свобода ограничена не процедурой, а **границей и критериями результата**. Ровно это и
называется «ответственность за результат вместо ответственности за шаги».

### 4.4. Смежные отделы — через доску, а не напрямую

Нужен чужой артефакт — исполнитель смотрит слой `cross-dept` (там лежит то, что другой отдел уже
посчитал и опубликовал). Нет — супервайзер выставляет **заявку смежному отделу**; её принимает
супервайзер того отдела. Прямых вызовов «агент → агент чужого отдела» нет: именно они превращают
систему в зоопарк и ломают ACL.

Исключение, которое стоит разрешить сразу (иначе получим бюрократию из документа): **чтение
справочников** — НСИ, нормы, курсы — доступно всем отделам напрямую, только на чтение.

### 4.5. Цикл подзадачи

```
супервайзер: разложил → подзадача на доску (working, статус «ждёт»)
исполнитель: взял → сделал как счёл нужным → результат в working + провенанс
супервайзер: проверил по критериям
      ├── не прошло → вернул с замечанием (не больше 2 раз, потом эскалация человеку)
      └── прошло   → validated; полезное другим → cross-dept; для человека → user-facing
аудитор: выборочно проверил, посчитал ИКА, при несоответствии выписал NCR
```

Предел в две попытки — из документа, и он обязателен: без него супервайзер и исполнитель будут
гонять задачу по кругу за ваши деньги.

## 5. Доска: четыре слоя на той, что есть

Добавляем к записи доски поле `слой` и правила доступа:

| слой | кто пишет | кто читает | срок |
|---|---|---|---|
| `working` | исполнители отдела | отдел + супервайзер | часы–дни |
| `validated` | только супервайзер | отдел; по ACL — другие | недели |
| `cross` | супервайзер (публикация) | супервайзеры и агенты других отделов | версионируется |
| `user` | супервайзер, завершивший задачу | человек | по политике хранения |

Это **поле, а не новая таблица**: `board_entries` уже несёт `scope`, `ttl_sec`, `run_id`, автора.
Вторая доска рядом означала бы два провенанса на одну истину.

Переиспользование расчётов — по точному ключу (организация + период + правило + версия политики),
а не по эмбеддингу. Протухание — по `ttl_sec`, который назначает методолог из регламента.

## 6. Конверт отдела и динамическая автономия

Конверт остаётся границей: набор навыков, доступные данные, разрешённые внешние действия, бюджет.
Новое — **автономия как переменная от ИКА** (решение владельца):

| ИКА отдела | автономия | что меняется |
|---|---|---|
| ≥ 90 | повышенная (до объявленного потолка) | рутинные внутренние действия идут без подтверждения |
| 70–89 | базовая | как сейчас |
| < 70 | суженная **автоматически** | подтверждение на каждый шаг, пока супервайзер не исправит |

Три оговорки, без которых это опасно, и они зашиваются в код, а не в договорённость:

1. **Потолок из контракта не перепрыгивается никогда.** ИКА двигает автономию только внутри
   `autonomy_max` агента (`_autonomy_for`: внешнее действие или egress → A1). Повышение — это
   «меньше подтверждений внутри», а не «можно наружу».
2. **Необратимое остаётся за человеком при любом ИКА.** Проводка в 1С, отправка письма, запись в
   чужую систему — HITL (ADR-078 это уже закрепил для проводки).
3. **Повышение автономии отделу человек включает один раз явно**; дальше ИКА двигает её в
   разрешённых пределах. Сужение — всегда автоматическое и немедленное.

## 7. ИКА: считаем из того, что уже есть

Ничего выдумывать не надо — все слагаемые уже пишутся:

| слагаемое | откуда берём сегодня |
|---|---|
| First-Time-Right | прогоны без повторного запуска той же задачи (`run_jobs`, `dedupe_key`) |
| принятие человеком | решения по находкам: подтверждено против «так и должно быть» (реестр) |
| доведение до конца | доля «исправлено» в цепочке найдено → признано → исправлено (ADR-073) |
| формат | доля шагов, где структура прошла схему (`skill_outputs.structured`) |
| свежесть | использование записей старше freshness (провенанс Data Plane) |
| цена | `cost_rub` и время прогона |

ИКА = взвешенная сумма, веса — **данные вертикали** (как веса приоритета находок), а не константы
в коде. Считает только аудитор; агент на свою оценку влиять не может.

## 8. Аудитор: что проверяет и как часто

| проверка | как | охват |
|---|---|---|
| формат артефакта | схема навыка, парсер | 100 %, дёшево |
| **соответствие агента назначению** | граф агента против роли семьи: есть ли обязательные навыки | 100 % при каждом сохранении |
| полнота артефакта | все объявленные поля заполнены либо сказано, почему нет | 100 % |
| свежесть | возраст записей против TTL из регламента | 100 % |
| семантика | сверка вывода с исходными данными доски через модель | выборка: тем чаще, чем ниже ИКА |

Проверка «агент не делает того, чем назван» — первая по важности: она ловит случай v11 за секунду
и не требует ни ИКА, ни NCR, ни супервайзеров. С неё и начинаем.

**NCR** (карточка несоответствия) несёт: что нарушено, цитату правила или регламента с его id,
ссылку на артефакт, тяжесть. Аудитор обязан цитировать источник — иначе он сам становится
источником галлюцинаций.

## 9. Методолог: регламент → конфигурация

Вход — регламент отдела в RAG (`reglament_store`, ключ НСИ). Выход — предложенная конфигурация:
состав ролей, какие правила активны, TTL артефактов, сроки. Форма выхода — **заявка на изменение**,
которую подтверждает человек: так сохраняется ответ аудитору «правило изменил такой-то такого
числа». Дальше методолог следит за изменениями регламента и помечает артефакты к пересчёту.

## 10. Что видит человек

**Бухгалтер (десктоп).** Отдел — это контекст, а не меню: он видит очередь своего отдела, карточку
с доказательством, способом и нормой, кнопку действия. Чужих находок (производство, поток) в его
очереди нет по принадлежности — это снимает сегодняшнюю задачу «почистить 87 чужих» без удаления
данных.

**Методолог и владелец (веб).** Карточка отдела: ИКА и его динамика, открытые NCR, что супервайзер
менял и что из этого помогло, расход. Заявки на изменение конфигурации — в той же очереди решений,
третьим потоком к подтверждениям и находкам.

**Чего не делаем:** отдельного «дашборда ИСМ». Здоровье отдела живёт на карточке отдела, иначе это
ещё один экран, который открывают раз в месяц.

Порядок выбран так, чтобы каждый шаг давал проверяемый результат сам по себе.

| 7 | **Аудитор качества**: формат, полнота, свежесть, выборочная семантика, NCR | четыре отказа из §1 ловятся машиной | всё выше |
| 8 | **Динамическая автономия по ИКА** | меньше подтверждений на рутине | §6 с тремя оговорками |

## 12. Риски, которые принимаем осознанно

| риск | чем держим |
|---|---|
| бюрократия и стоимость токенов | подзадача объявляет результат, а не шаги; две попытки; выборочный аудит; бюджет на задачу |
| осцилляция супервайзера | после двух правок без роста ИКА — эскалация человеку |
| гонки на доске | запись в `working` только своим агентом; в `validated` только супервайзером; уникальность по (scope, key, author) уже есть |
| фальсификация ради ИКА | ИКА считает только аудитор; главный вес — принятие человеком и смежником, его агент не контролирует |
| методолог ошибся в регламенте | изменения идут заявкой с диффом; человек подтверждает |
| автономия выросла не по делу | потолок контракта не перепрыгивается; необратимое всегда за человеком |

## 13. Чего эта архитектура не делает

Не отменяет детерминированный расчёт: числа по-прежнему считает код. Не делает агентов
самообучающимися: «выученные уроки» здесь — это изменение конфигурации, а не дообучение модели.
Не заменяет LUDA: та проверяет готовность до запуска, аудитор — качество в рантайме.
