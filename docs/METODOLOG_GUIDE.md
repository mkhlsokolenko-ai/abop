# Руководство методолога: системы, данные, шаблоны

> Для тех, кто готовит ABOP к работе в организации: подключает системы, собирает Data Plane,
> размечает данные и отвечает за то, в каком виде результат уходит обратно в системы.
> Смежное: [`DATA_RECIPES.md`](DATA_RECIPES.md), [`ARENDATORY.md`](ARENDATORY.md),
> [`API_ENDPOINTS_PORTS.md`](API_ENDPOINTS_PORTS.md), [`DEPLOY.md`](DEPLOY.md).

## Как это устроено на одном экране

```
система организации → рецепт (источник) → сущность Data Plane → навык → доставка → система организации
   реестр систем        адаптер + карта      canonical-схема      контракт   delivery     коннектор
```

Правило, из которого всё следует: **навык не ходит в систему сам**. Он читает сущность Data Plane
и возвращает структуру по контракту. Между ним и чужой системой с обеих сторон стоит слой, который
можно проверить, ограничить правами и починить без правки навыка.

## 1. Подключить систему

Система живёт в реестре (`/api/systems`, стор `systems_store`). Карточка:

| Поле | Зачем | Чем грозит ошибка |
|---|---|---|
| `base_url` | куда ходить | — |
| `auth_ref` | **имя переменной окружения** с секретом, а не сам секрет | секрет осядет в БД и в выгрузках |
| `egress` | `internal` / `external` — уходит ли запрос наружу | внешний вызов, которого никто не ждал |
| `scope` | отделы (семьи), которым система доступна | пусто = **видно всем** |
| `kind` | rest / db / s3 / vector / auth — определяет адаптеры | — |

**`scope` и есть разграничение доступа агентов.** Пустой scope означает «всем». Проверять нужно не
только то, что доступ выдан, но и то, что не выдан лишний: `/api/access/manifest` показывает, что
видит конкретная область.

## 2. Завести источник (рецепт)

Рецепт = адаптер + карта полей + правила + целевая сущность. Заводится в разделе «Данные» или
через `POST /api/data/recipes`.

### Адаптеры и их свойства

| Адаптер | Для чего | Обновляется перед прогоном агента |
|---|---|---|
| `http` | любой REST | **да** |
| `mailpit` | почта с телом и вложениями | **да** |
| `vector` | знания из sLAVA / Qdrant | **да** |
| `json`, `csv`, `xlsx`, `text`, `pdf` | файлы | нет — только ручной прогон |
| `postgres`, `sqlite` | базы | нет |
| `audit1c` | снимок 1С | нет |

Это важнее, чем кажется: **файловые и БД-рецепты сами не обновляются**. Положили файл и ждёте, что
данные появятся, — не появятся, пока не запустите рецепт (`POST /api/data/recipes/<имя>/run`).
Ровно по этой причине у нас долго пустовала сущность `feed_card`, а три навыка витрины не могли
работать: файл на диске лежал, в Data Plane было пусто.

### Дозапрос карточки — почти всегда обязателен

Список REST API отдаёт заголовки, а не содержимое: BookStack `/api/pages` возвращает имя без
`html`, Redmine `/issues` — без `description`. Без дозапроса сущность приедет из одних названий, и
навык будет «читать документ», в котором нет ни символа текста.

```json
"source": {
  "kind": "http",
  "url": "https://wiki.example/api/pages?count=100",
  "root": "data",
  "headers": {"Authorization": "Token ..."},
  "detail": {"url": "https://wiki.example/api/pages/{id}", "fields": ["html", "markdown"], "limit": 50}
}
```

`{id}` — подстановка из строки списка, `fields` — какие поля карточки подмешать, `limit` —
предохранитель: рецепт на тысячу строк не должен превращаться в тысячу запросов. Недоступная
карточка не роняет прогон — строка останется без обогащения, остальные доедут.

### Карта полей

`col:имя` — колонка, `const:значение` — константа, `lookup:сущность.поле` — подстановка из другой
сущности, `cast:` — приведение: `money`, `int`, `lower`, `upper`, **`text`** (HTML → чистый текст).

Для вики и трекеров почти всегда нужен `col:html · cast:text`: без приведения в запись попадёт
разметка, и навык будет читать теги.

### Обязательная гигиена рецепта

1. `entity` — из реестра canonical-схем. Обязательные поля схемы должны заполняться картой, иначе
   запись отбрасывается как невалидная: смотрите счётчик `invalid` в ответе прогона.
2. `system_id` — **привязка к системе реестра**. Без неё ABAC-гейт по данным не работает вовсе:
   сущность, не привязанная к системе, доступна всем.
3. `status: опубликован` — отметка, что рецепт боевой, а не черновик.
4. Прогон с `{"reset": true}` — когда записи в источнике **удаляли**: у удаления нет новой версии,
   и без сброса снесённая в трекере задача останется в Data Plane навсегда.

**Прежде чем проставить `system_id`, посчитайте, кого отрежете.** Если `scope` системы уже, чем
набор отделов, читающих сущность, включение гейта сломает работающие навыки. Это не повод не
включать — это повод сначала решить, кто и правда должен видеть эти данные.

## 3. Размечать данные

Канонические схемы задают `required` (без этих полей запись невалидна) и `join` (по чему
склеиваются версии). Записи **версионные**: последняя версия каждого `id` не протухает никогда,
перекрытые уходят по TTL. Отсюда три правила:

- `id` обязан быть стабильным между выгрузками. Если это «порядковый номер строки», при следующем
  прогоне старые записи не обновятся, а задвоятся;
- `ttl_sec` ставьте по скорости устаревания: почта — часы, справочники — сутки, нормативка — 0;
- провенанс (`recipe`, `source`, `fetched_at`) пишется сам. По нему потом выясняют, откуда у агента
  взялась цифра, — не убирайте его из карты.

Проверка: `/api/data/entities` показывает число записей по каждой сущности, `/api/data/lineage` —
кто её потребляет, вплоть до роли и отдела. Если у сущности нет потребителей, её незачем собирать.
Если у навыка нет данных, он ответит «не удалось определить» — это правильное поведение, а не сбой.

## 4. Доставка результата обратно в систему

Секция `delivery` в `template.json` навыка описывает, куда уходит ответ:

```json
"delivery": {
  "system": "redmine", "type": "issue.create",
  "each": "находки", "where": {"ранг": ["критично"]}, "limit": 10,
  "title": "Задача: {{заголовок}}",
  "payload": {"subject": "Аудит · {{тип}} · {{id}}", "description": "h2. Суть ..."}
}
```

Что платформа делает на выходе **сама** — подстраивать шаблоны под это не нужно:

- раздел без содержания выбрасывается вместе с заголовком: читатель не получит «h2. Рейтинг» и
  пустоту под ним;
- сегмент темы с пустой подстановкой выбрасывается целиком — не будет «…· порог» без порога;
- заголовок обрезается по границе слова, а не посреди;
- управляющие символы вычищаются;
- **если после очистки содержания не осталось, команда не создаётся**, а попадает в пропуски с
  причиной. Пустая задача в трекере хуже отсутствия задачи: по ней решают, что агент отработал.

ABOP ничего не отправляет сам: команда становится заявкой HITL с превью того, что уйдёт, и только
после подтверждения публикуется в шину, где её исполняет коннектор.

## 5. Шаблоны организации

Агент обязан собирать документ по **действующей** форме организации, а не по своей.

- Формы лежат в вики, в книге **«Шаблоны документов (ABOP)»**. Дополнительно подхватываются все
  страницы, чьё имя начинается на «Шаблон», — так в работу попали «ТЗ ГОСТ 34», «Коммерческое
  предложение», «Письмо заказчику»: реальные регламенты организации, а не наши выдумки.
- Рецепт `org_templates` кладёт их в сущность `template`.
- Навык берёт форму инструментом `doc_template`: `{"name": "письмо заказчику"}`; без имени —
  перечень доступных, чтобы агент не угадывал название.

**Как добавить форму:** создать страницу в книге шаблонов, назвать её «Шаблон …», написать текст с
плейсхолдерами в фигурных скобках и прогнать рецепт `org_templates`. Пересобирать ничего не нужно —
правка страницы меняет то, что выдаст агент.

Плейсхолдеры называйте по смыслу (`{период}`, `{ответственный}`), а не по номеру: имя подсказывает
модели, что подставлять. В конце формы полезна строка о том, какой навык её заполняет и чего в ней
быть не должно — например: «суммы только из данных; чего нет — „не удалось определить“».

## 6. Что просить от пользователей систем

Качество ответа агента задаётся не моделью, а тем, как люди ведут свои системы.

**Вики и документы.** Заголовок — короткое название, а не первая фраза документа: по заголовкам
строится перечень, и предложение в 190 символов читается как поломка. Содержание — в теле
страницы: пустая страница с хорошим названием для агента пуста. Шаблоны — в книге шаблонов, иначе
они не попадут в сущность `template`.

**Трекеры и заявки.** Заполняйте описание, а не только тему: тема идёт в заголовок, а решение
принимается по описанию. Один тикет — одна задача: по тикету «и то, и это» агент не сможет сказать,
что сделано. Документ-основание давайте номером и датой, а не «см. вложение».

**Учёт.** Документ-основание обязателен: расхождение без основания сверка считает «под вопросом», а
не объяснённым. Даты — в одном формате, суммы — числом, а не строкой с пробелами и валютой.
Контрагента заводите один раз: два «ООО Ромашка» с разными ИНН превращаются в расхождение, которое
потом разбирает человек.

**Почта.** Тема должна называть предмет — по ней идут разбор и маршрутизация. Вложение с данными
лучше в текстовом формате (csv / txt / json): скан таблицы агент прочитает OCR, но хуже.

## 7. Частые ошибки, которые мы уже сделали

| Симптом | Причина | Чем проверить |
|---|---|---|
| сущность «пуста», хотя источник есть | файловый рецепт ни разу не прогоняли | `/api/data/entities`, затем прогон рецепта |
| документ без текста | в рецепте нет дозапроса карточки | посмотреть запись: есть ли поле `text` |
| в записи разметка вместо текста | нет `cast:text` | то же |
| агенту доступно лишнее | у рецепта пуст `system_id` либо у системы пуст `scope` | `/api/access/manifest` |
| в трекере пустая задача | раздел шаблона без данных (чинится платформой с 10.2026) | пропуски в карточке прогона |
| записи задвоились после прогона | нестабильный `id` в карте | сравнить `id` двух выгрузок |
| имя страницы из «?????» | страница заведена не в UTF-8 | править в вики руками, рецепт тут ни при чём |
