# LUDA 2 ↔ ABOP — разделение ролей и аллокация «Product & UX Brief v0.1»

**Решение:** ADR-031. Воронка бизнес-заказчика из брифа ставится на **LUDA 2** (вход владельца процесса), **ABOP** остаётся платформой инженера (build/run, канва-центр ADR-030). Шов — контракты + Contract Ingress (ADR-028/029) + новая обратная петля результата.
**Назначение дока:** превратить бриф в план, ничего пока не ломая — куда какой экран, что дописать в LUDA 2, где швы.
**Статус:** v0.1.

---

## 1. Принцип

| | **LUDA 2** — вход бизнес-заказчика | **ABOP** — платформа инженера |
|---|---|---|
| Персона | владелец процесса (решает, платит) | AI-инженер / архитектор (строит, контролирует) |
| Джоба | диагноз + решение: что можно, безопасно ли, сколько сэкономит | сборка + запуск + эксплуатация агентов |
| Модель | Process → Analysis → Opportunities → Safety → Economics → Decision | Agent/Skill/Flow → Deployment → Run → Fleet |
| Природа цифр | **доказательно** (Evidence/BaselineMeasurement), не LLM-догадка | телеметрия исполнения (cost/latency/DoD) |
| Корневой UI | бизнес-воронка (эта аллокация) | канва-центр (ADR-030) |

> Правило границы: **LUDA не строит агентов, ABOP не диагностирует пригодность.** Пересечение — только через контракты.

## 3. Что дописать в LUDA 2 (фичи из брифа)

LUDA 2 уже имеет: аудит A0–A4, Evidence/Findings, BaselineMeasurement, экран «Задание для ABOP» (3 контракта + PDF), Keycloak-SSO. Добавить:

1. **Process intake** — приём процесса описанием И документами (регламент/BPMN/Word/Excel/Confluence); построение **карты процесса** (экран 03).
2. **Бизнес-язык поверх аудита** — перевод LUDA-артефактов в человеческие экраны 04–07: точки автоматизации (✓/⚠/○/🔒), таблица «Что AI может», границы безопасности, экономика (baseline→эффект→окупаемость). Таблица «user-facing ↔ technical» — §5.
2b. **Autonomy UX** — «Самостоятельность AI: средняя» вместо `A2/L2`, раскрытие «почему» (обратимость/наблюдаемость/критичность).
3. **Decision-карточка (экран 09)** — сводка (что берёт AI, автономия, безопасность, экономия, ограничения) + «Запустить пилот».
4. **Blueprint-превью (08)** — сценарий бизнес-языком из CapabilityRequest (read-only; правка уходит в канву ABOP).
5. **Экран результата (11)** — baseline vs факт (факты тянутся из ABOP, §4).
6. **Progressive disclosure L1/L2/L3** — техартефакты (LUDA internals/контракты) за «Подробнее».
7. **Редизайн под ABOP DS** — токены/бренд Эйп/glass/семафор (унификация, не переверстка; общая родословная MIRA v3).

## 4. Швы между продуктами

- **LUDA → ABOP (есть, спроектировано):** «Запустить пилот» (экран 09) → эмит `CapabilityRequest / DeploymentContract / BaselineMeasurement` → **Contract Ingress** (ADR-029, SDD §4) → Deployment в ABOP (экран 10). Автономия ABOP ≤ DeploymentContract.
- **ABOP → LUDA (спроектировано — `ABOP_SDD.md §4-bis`):** после/во время пилота ABOP агрегирует `RunMetrics{deployment_id, baseline_ref, actuals, provenance, governance}` (схема `abop.run_metrics/1.0`, те же ключи метрик, что в BaselineMeasurement) → транспорт push/pull/реестр → LUDA валидирует на границе и сравнивает с сохранённым BaselineMeasurement на экране 11 «baseline vs факт». Дрейф actuals от baseline → ре-аттестация → новый контракт (цикл замыкается). ABOP отдаёт только агрегаты+провенанс, не сырьё (egress-инвариант). Замыкает цикл LUDA↔ABOP (дифференциатор).
- **Сквозной journey:** SSO (Keycloak, общий) + единая DS + бесшовный переход «Решение(LUDA) → Пилот(ABOP) → Результат(LUDA)» — владелец воспринимает как один продукт, хотя это два приложения.

## 6. Гардрейлы (из оценки брифа)

- **Цифры экономики/автономии — доказательные.** «68% / 4 из 6 / 47ч» выводятся из Evidence + BaselineMeasurement, НЕ генерятся LLM (иначе — та же выдумка, что ловит наш гейт; CFO/CISO вскроют). Соблюдает «не строить магический автоподбор» + анти-галлюцинацию.
- **Карта процесса (03) — точка доверия.** Ошиблись с картой → доверие рушится на входе. Показывать как гипотезу с правкой владельцем, а не «AI всё понял».
- **Доказательность для эксперта сохранить.** Любой бизнес-вывод раскрывается до LUDA/Evidence/Contract (Level 3) — одновременно просто для владельца и защищаемо перед Enterprise/CISO.
