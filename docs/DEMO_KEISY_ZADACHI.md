# Демо: два новых кейса на канве ABOP (пошагово для показа)

> Как собрать и продемонстрировать два кейса на реальных сервисах стенда:
> **Кейс А «Дайджест задач»** (почта → Redmine → отчёт + письмо заказчику) и
> **Кейс Б «БФТ по задаче»** (задача из Redmine → БФТ → BookStack + письмо автору).
> Оба используют живые данные: почта Mailpit, трекер Redmine, вики BookStack.

---

## 0. Что показываем и почему это ценно (1 фраза для аудитории)

- **Кейс А:** «Агент сам разобрал входящую почту, выделил задачи, завёл их в трекер, собрал план на день и подготовил письмо заказчику — а человек только подтвердил отправку.»
- **Кейс Б:** «Агент взял задачу из трекера, написал по ней бизнес-функциональные требования, опубликовал в вики и подготовил письмо автору задачи — под подтверждением.»

Ключевые идеи для лектора: **данные из реальных систем**, **человек подтверждает действия наружу (HITL)**, **формат вывода — документ, а не таблица находок** (флаг навыка `freeform`).

---

## 1. Подготовка перед демо (один раз, до аудитории)

1. **Данные должны течь.** Кейсы читают сущности `email` (из Mailpit) и `issue` (из Redmine).
   Проверь, что они наполнены (в разделе «Данные» видны записи `email` и `issue`). Если пусто —
   прогони рецепты `mail_inbox` и `redmine_issues` (кнопка «прогнать рецепт» в Data Plane).
2. **LLM-инстанс поднят** (Qwen). Если ночная пауза ещё активна — убедись, что бокс запущен
   (иначе прогон уйдёт на резервный провайдер по каскаду — тоже сработает, просто медленнее).
3. **Проверь заранее один прогон** каждого кейса, чтобы на демо не ждать «первый холодный» запуск
   (после первого прогона повтор берётся из кэша — мгновенно).

> Для реальной отправки наружу (письмо/задача в Redmine) нужны токены в окружении. Без них шаги
> доставки показываются как «превью» (dry_run) — для демо этого достаточно; с токенами — уходит
> по-настоящему после подтверждения.

---

## 2. КЕЙС А — «Дайджест задач» (сборка на канве)

### 2.1 Быстрый путь (рекомендуется для демо)
1. Открой раздел **«Строю»** (канва).
2. Вверху выбери вкладку сценария **«Дайджест задач»**.
3. Нажми зелёную **«▶ Собрать и запустить»**.
4. Готово — смотри результат (раздел 2.3).

### 2.2 Что за схему увидит зритель (объясняй по узлам, слева направо)
```
[Источник: Входящие · email] → [mail-triage] → [daily-plan] → [client-letter] → [HITL]
                                     │                              │
                              разбор писем                   черновик письма
                              в задачи                       заказчику
                                     └──────────► [OUT: Задачи → Redmine]  (под HITL)
                                                  [OUT: Письмо → заказчику] (под HITL)
```
- **mail-triage** — читает входящие письма, выделяет конкретные задачи (тема/от/суть/срочность).
- **daily-plan** — выбирает 2 приоритетные задачи на день + план шагов.
- **client-letter** — черновик письма заказчику с планом (формат вывода — свободный текст).
- **OUT-узлы** — задачи в Redmine и письмо заказчику; оба **под HITL** (не уйдут без подтверждения).

### 2.3 Что показать в результате прогона
- **Нарратив навыков**: реальные задачи из писем (например «Счёт №… — согласовать оплату»),
  выбранные 2 приоритетные, черновик письма.
- **Выходное событие · доставка**: две строки со статусом **«ожидает подтверждения оператора»**
  (awaiting_hitl) — Redmine и письмо заказчику.
- Метрики: время прогона, стоимость, `trace_id` (наблюдаемость).

### 2.4 Кульминация демо — подтверждение человеком (HITL)
1. Открой **очередь HITL** (раздел подтверждений / «Запускаю»).
2. Увидишь заявки: «Задачи → Redmine» и «Письмо заказчику».
3. Нажми **«Подтвердить»** → действие выполняется РЕАЛЬНО (задача создаётся в Redmine / письмо
   уходит; при dry_run — показывается, что было бы отправлено).
4. Покажи в Mailpit пришедшее письмо / в Redmine созданную задачу.

## 3. КЕЙС Б — «БФТ по задаче» (сборка на канве)

### 3.1 Быстрый путь
1. «Строю» → вкладка **«Аналитик БФТ»** (или «БФТ по задаче»).
2. **«▶ Собрать и запустить»**.
3. Смотри результат.

### 3.2 Схема
```
[Источник: Задача · issue (Redmine)] → [bft-draft] → [HITL]
                                            │
                                    бизнес-функц. требования
                                    (цель/контекст/требования/
                                     критерии приёмки/границы)
                                            ├──► [OUT: БФТ → BookStack (вики)]  (под HITL)
                                            └──► [OUT: БФТ → автору задачи (почта)] (под HITL)
```
- **bft-draft** — берёт задачу из трекера и пишет БФТ; пробелы в задаче помечает «уточнить у автора».

### 3.3 Что показать
- Готовый документ БФТ по реальной задаче Redmine (структура: цель, контекст, требования,
  критерии приёмки, границы).
- Две HITL-заявки: публикация в BookStack и письмо автору.
- Подтверди → БФТ публикуется страницей в BookStack и/или письмо уходит автору.

---

## 4. Что подчёркивать голосом на демо

1. **Реальные системы, не мокапы** — Mailpit (почта), Redmine (аналог Jira), BookStack (аналог Confluence).
2. **Человек в контуре (HITL)** — ничего не улетает наружу без подтверждения; это управляемая автономия.
3. **Формат вывода — документ** — письмо/БФТ читаются как деловой текст, а не таблица (флаг навыка).
4. **Наблюдаемость** — у каждого прогона `trace_id`, время, стоимость; ошибки не «молчат».
5. **Скорость** — повторный показ того же кейса мгновенный (кэш результата), первый — секунды.

---

## 5. Если что-то пошло не так (быстрые ответы)

| Симптом | Что сказать / сделать |
|---|---|
| Прогон пустой / нет задач | Data Plane не наполнен — прогнать рецепты `mail_inbox`/`redmine_issues` |
| «нет демо-пакета» | выбран не тот сценарий; кейсы: «Дайджест задач», «Аналитик БФТ» |
| Долгий первый прогон | это холодный запуск LLM; повтор — из кэша мгновенно |
| Доставка «dry_run» | нет токенов внешних систем в окружении — показываем превью (для демо ок) |
| HITL-заявка не подтверждается | нужны права manager+ (войти под менеджером/админом) |

## 6. Технические детали (для вопросов «а как это внутри»)

- Вход: сущности `email` (рецепт `mail_inbox` из Mailpit), `issue` (рецепт `redmine_issues` из Redmine).
- Навыки: `mail-triage`, `daily-plan`, `client-letter` (Кейс А); `bft-draft` (Кейс Б).
  Семья агентов — «Менеджмент», роли `task-digester` и `bft-writer`.
- OUT-каналы: `redmine` (создать задачу), `email`/`bookstack` (письмо/вики). Действие наружу —
  `dry_run` по умолчанию, реально — только после подтверждения HITL (и при наличии токенов).
- Формат вывода документных навыков — `freeform` (флаг навыка, тумблер в редакторе навыка).
- Демо-пакеты: `demo/mailtasks/`, `demo/bft/` (контракт + тело агента).
