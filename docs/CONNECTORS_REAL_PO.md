# Коннекторы к реальному ПО компаний — что есть, как завести, что дописать

> Практический гайд: как перевести агента с демо-стенда (Mailpit/Redmine/BookStack) на **реальные
> системы заказчика** (его почта, его трекер, его вики, его БД). Что уже поддержано «из коробки»,
> что настраивается конфигом, а что требует нового адаптера — и как его сделать.

---

## 0. Модель коннекторов в ABOP (чтобы не путать вход и выход)

Два разных механизма — не смешивать:

- **ВХОД (источник данных → сущность):** **рецепт** тянет данные из системы и приводит к канонической
  `entity` (`email`, `issue`, `transaction`…). Работает через **адаптер источника**.
- **ВЫХОД (действие наружу):** **OUT-узел** доставляет результат в систему (письмо, задача, страница
  вики). Работает через **action-инструмент**, под HITL/dry_run.

```
   реальная система → [АДАПТЕР ВХОДА] → entity → агент → [ACTION ВЫХОДА] → реальная система
        (почта, БД)      csv/http/...    (canonical)         email/redmine/...   (задача, письмо)
```

---

## 1. Что уже поддержано (можно завести БЕЗ кода)

### 1.1 Адаптеры ВХОДА (источники)
| Адаптер | Реальное ПО под него | Как завести |
|---|---|---|
| **http** | Любой REST API (трекеры, CRM, self-service) — Redmine, Jira, YouTrack, Bitrix24, 1С через HTTP-сервис | URL эндпоинта + заголовки авторизации; маппинг JSON-полей в `entity` |
| **postgres** | Любая БД на PostgreSQL — 1С(PG), корпоративные хранилища, DWH | строка подключения (read-only) + SQL-выборка |
| **sqlite** | Локальные/встроенные БД, выгрузки | путь к файлу + SELECT |
| **csv / xlsx** | Выгрузки из Excel/1С/ERP, отчёты | файл + маппинг колонок |
| **json / text / pdf** | Файловые выгрузки, документы, регламенты | файл + правило извлечения |
| **vector / slava** | RAG-корпус (нормы, регламенты, база знаний) | коллекция знаний |

> **Ключевой вывод:** большинство корпоративных систем имеют REST API или PostgreSQL — значит
> заводятся адаптерами **http** или **postgres** БЕЗ написания кода. Нужен только эндпоинт/строка
> подключения, токен и маппинг полей в `entity`.

### 1.2 Каналы ВЫХОДА (доставка/действия)
| Канал | Реальное ПО | Что нужно (env / конфиг узла) |
|---|---|---|
| **yandex** | Яндекс.Почта (корп. и личная) — реальная отправка писем | `YANDEX_SMTP_USER`, `YANDEX_SMTP_PASSWORD` (пароль приложения) |
| **email** | Любой SMTP (демо — Mailpit; прод — корп. SMTP) | `MAILPIT_HOST/PORT` → заменить на корп. SMTP-хост |
| **redmine** | Redmine (аналог Jira) — создание задач | `REDMINE_BASE`, `REDMINE_API_KEY`, `REDMINE_PROJECT` |
| **yougile** | YouGile (рос. таск-трекер) — создание задач | `YOUGILE_TOKEN`, `YOUGILE_COLUMN_ID` |
| **bookstack** | BookStack (аналог Confluence) — публикация страниц | `BOOKSTACK_URL`, `BOOKSTACK_TOKEN` |
| **pdf / file** | Локальный отчёт-документ | — |

> Доставка по умолчанию — **dry_run** (превью). Реальная отправка — только при заданных токенах +
> флаге «Реальная отправка» на OUT-узле + вне HITL (или после подтверждения).

## 2. Как завести реальный ВХОД (пошагово, на примере)

**Пример: реальный трекер задач заказчика (REST API).**
1. Узнай у заказчика: базовый URL API, способ авторизации (токен/ключ/Bearer), эндпоинт списка задач.
2. Раздел «Данные» → создать рецепт → адаптер **http**:
   - URL: эндпоинт списка (например `.../issues.json?limit=100`).
   - Заголовки: авторизация (ключ хранится в env по `auth_ref`, не в открытом виде).
   - Root: где в JSON лежит массив записей.
3. Маппинг: поля системы → поля канонической `entity` (тема→`Тема`, автор→`Автор`, …). Задай `entity`
   (например `issue`).
4. Опубликуй и **прогони рецепт** — данные попадут в canonical store.
5. Проверь: сущность отдаёт записи; агент, читающий `issue`, теперь видит реальные задачи.

**Пример: реальная БД (PostgreSQL заказчика).**
- Адаптер **postgres**, строка подключения (обязательно **read-only** пользователь), SQL-выборка →
  маппинг → `entity`. Так подключаются 1С на PG, DWH, корпоративные базы.

**Реальная почта как источник (входящие письма):**
- Демо-Mailpit отдаёт письма по REST (`/api/v1/messages`) — адаптер **http**.
- Реальная корп. почта: если есть REST/Graph API (например корпоративный шлюз) — адаптер **http**;
  если только IMAP — нужен **новый адаптер imap** (см. §4).

## 3. Как завести реальный ВЫХОД (действие в систему)

1. Получи у заказчика доступ к целевой системе: для трекера/вики — **API-токен**; для почты —
   **SMTP-логин + пароль приложения**.
2. Добавь токен в окружение сервера ABOP (`.env` контейнера) — соответствующие переменные из §1.2.
   Токены **не в коде и не в git** — только в env.
3. На OUT-узле агента задай канал, адрес/проект/книгу, формат.
4. Включи «Реальная отправка» (и реши, оставлять ли «Под HITL»).
5. Перезапусти контейнер (env подхватывается при старте). Проверь: прогон → HITL-заявка → подтвердил
   → реальное действие в системе.

> **Безопасность:** реальные действия наружу должны идти **под HITL** на пилоте — человек видит и
> подтверждает каждое, пока агенту не начнут доверять. Это не «тормоз», а управляемая автономия.

## 4. Когда нужен НОВЫЙ адаптер/канал (и как его сделать)

Новый код нужен, только если у системы **нет ни REST, ни PostgreSQL** (например: почта только по IMAP,
проприетарный протокол, специфичный SDK). Паттерн добавления — простой и единообразный.

### 4.1 Новый адаптер ВХОДА
- Функция `_adapter_<kind>(src) -> list[dict]`: принимает конфиг источника, возвращает список сырых
  записей. Регистрируется `register_adapter("<kind>", fn, spec)` (файл `cli/ape.py`, там же где
  `http`/`postgres`). После этого он доступен в UI как тип источника.
- Пример спроса: **imap** (реальная почта) — читает ящик по IMAP, возвращает письма как записи →
  маппинг в `email`.

### 4.2 Новый канал ВЫХОДА
- Инструмент `_t_<system>(a)` в `cli/ape.py` (по образцу `_t_redmine_create_issue`/`_t_yougile_task`):
  dry_run по умолчанию, реальное действие при `run=true` и токене из env.
- Добавить ветку `channel == "<system>"` в `_send_channel` (`server/web_api.py`) и пункт в UI OUT-узла.
- Примеры спроса: **Jira** (REST, как Redmine, но своя схема), **Bitrix24**, **Telegram**, корп. SMTP.

### 4.3 Что уточнить у заказчика перед новым коннектором
- Есть ли REST API или доступ к БД? (тогда код НЕ нужен — §1/§2/§3).
- Тип авторизации: токен / OAuth / логин-пароль / сервис-аккаунт?
- Доступ **от имени пользователя** или сервис-аккаунт? (для делегированного доступа — отдельное
  решение по безопасности).
- Rate-limit / квоты системы?
- Формат данных на входе и требуемый формат на выходе.

## 5. Приоритет реальных коннекторов (что делать после подтверждения кейсов)

Порядок по «ценность / простота»:

1. **Реальный трекер задач** (Jira/YouTrack/Redmine прод) — вход `http`, выход action. Основа
   менеджерских кейсов. Часто уже покрыто http-адаптером.
2. **Реальная почта** — выход через корп. SMTP (заменить Mailpit-хост) сразу; вход — imap-адаптер,
   если нет REST.
3. **Реальная вики** (Confluence/BookStack) — выход action (публикация).
4. **Корпоративная БД / 1С** — вход `postgres`/`http` (read-only).
5. **CRM** (Bitrix24/amoCRM/Twenty) — вход `http`, при спросе выход action.

> Правило: сначала пробуем завести на **http/postgres/SMTP БЕЗ кода** (90% случаев), новый адаптер
> пишем только когда системе реально нечем отдать данные, кроме проприетарного протокола.

## 6. Текущее состояние (демо-стенд `5.129.192.63`)

| Роль | Демо-система | Реальный аналог | Как перевести |
|---|---|---|---|
| Почта | Mailpit (`:8025`) | Яндекс/корп. SMTP | канал `yandex` + токены; вход — imap-адаптер |
| Трекер | Redmine (`:3000`) | Jira/YouTrack/Redmine-прод | http-вход + redmine/новый action |
| Вики | BookStack (`:6875`) | Confluence/BookStack-прод | action `bookstack` + токен целевого |
| CRM | Twenty (`:3002`) | Bitrix24/amoCRM | http-вход |
| No-code БД | NocoDB (`:8090`) | корп. БД | postgres/http-вход |

Демо работает на этих системах «как есть»; для заказчика — тот же агент, другие URL/токены (и, при
необходимости, 1-2 новых адаптера по §4).
