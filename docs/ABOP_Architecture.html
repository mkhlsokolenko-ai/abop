ABOP — Архитектура платформы

Инженерная платформа для сборки и управления ИИ-агентами · десктоп-чат как рабочая среда пользователя · self-host LLM на GPU-боксе (данные не выходят наружу) · шина Redpanda + коннектор-воркер на server-2: результат навыка уходит в систему только после HITL-превью · предмет работы (проект, контрагент) сужает выборку данных до прогона · навыки связаны контрактами: цепочка собирается из тех, кто реально выполнится на текущих данных, выводы ветвей ложатся на общую доску, расхождения разрешаются правилом или человеком

Потоки и связи (ключевые)
1Вход: Desktop-чат → сайдкар (127.0.0.1) → ABOP /api/* под JWT (RBAC/ABAC)
2Подбор: текст → /api/agents/match (лексика+семантика) → «куда результат?»
3Прогон: Data Plane → runner (grounded, self-host Qwen) → находки по схеме из БД
4Governance: конверт автономии + HITL → внешнее действие только после подтверждения
5Доставка результата навыка: delivery шаблона → команды коннектора → HITL-заявка с превью (система/действие, тема, описание) → «да» → abop.<система>.commands → коннектор (server-2) → Redmine/BookStack/Mailpit/1С
6Обратно по шине: command.done|failed → abop.<система>.events → результат (issue_id, url) в заявку → «✓ выполнено: ссылка» в карточке; сбои → abop.dlq; события систем → триггеры агентов (ABAC по семье)
7Отчёт: OUT-узлы (почта/BookStack/PDF) и GET /runs/{id}/report?template=&format=pdf по reports/<id>.html с {{skills}} / {{skill_<sid>}}; агент адресен (Identity Map)
8Очередь: POST /runs?async → run_jobs (SKIP LOCKED) → воркеры; цепочки и HITL-возобновление через очередь; нагрузка 20×3: 4 воркера ≈ 16,9 прогона/мин
9Аудит: provenance-трасса + метрики webapi/Redpanda/коннектора в Prometheus → Grafana abop-overview (секция «Шина и коннектор»), langfuse; расписания через планировщик
