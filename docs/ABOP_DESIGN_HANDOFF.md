# ABOP — Пакет дизайнера (Design Handoff / точка входа)

**Зачем:** единая точка входа для дизайнера — какие доки читать, в каком порядке, и **привязка каждого экрана к реальным данным и исполнению** (как оно будет в жизни), чтобы **ничего не придумывать**. Всё, что рисуется, имеет источник: данные — из API, сущности — из TDR, состояния — из SCREENS, тексты — из UX_FIXES, элементы — из DESIGN_KIT.
**Правило:** нет источника → не рисуем «на глаз», а спрашиваем/фиксируем как открытый вопрос.
**Статус:** v1.0.

---

## 1. Порядок чтения (за что браться)

> **⚠️ Корневая модель UI — канва-центричная (ADR-030).** Прежде всего усвоить: интерфейс — **один граф (канва) в центре**, а «вкладки» = **линзы** над ним (Строю/Запускаю/Эксплуатирую/Конверт) + **палитра** источников (Агенты/Навыки/Данные/Коннекторы кормят граф drag-and-drop) + **конверт-рамка** (всегда видима) + инспектор (настройки в узле/на связи). Всё в доках ниже читать через эту модель: где написано «вкладка/экран», понимать как линзу/панель над графом. Раскладка — `SCREENS §0`; решение — `ADR-030`.

1. **Понять продукт** → `ABOP_PRD.md` (что это, канва-центр + линзы Авторинг/Рантайм/Governance/Operations §7, FR).
2. **Взять инструменты** → `ABOP_DESIGN_KIT.md` + `docs/brand/` (токены, палитра, кнопки, спиннеры, маскот Эйп, «язык ожидания»).
3. **Рисовать экраны** → `ABOP_SCREENS.md` (каркас, каждый экран: зоны/компоненты/состояния/кликабельность).
4. **Главный экран Операций** → `ABOP_OPERATIONS_MAP.md` (semantic-zoom карта процессов с агентами).
5. **Довести до product clarity** → `ABOP_UX_REFINEMENT.md` (D1–D6) + `ABOP_UX_FIXES.md` (готовые тексты) + `ABOP_2MIN_TEST.md` (критерий приёмки понимания).
6. **Закрыть пробелы** → `ABOP_DESIGN_GAPS.md` (чего не хватало + **вкладка Безопасность**, слайдер прав, light-тема).
7. **Привязка к жизни** (этот документ, §3–§4): какие данные на каждом экране и как оно исполняется.

Справочно (если сомнение «почему так»): `ABOP_ADR.md` (решения), `ABOP_TDR.md` (модель данных), `ABOP_AOP.md` (протокол), `ABOP_ARD.md` (архитектура), `ABOP_API.md` (контракт данных), `ABOP_RUNTIME_ARCHITECTURE.md` (модели/исполнение), `ABOP_FLEET_OPS.md` (флот).

## 3. Матрица привязки: экран → данные → сущность → как исполняется (ГЛАВНОЕ)

> **Корневая модель — канва-центричная (ADR-030, `SCREENS §0`).** «Экраны» ниже — это НЕ вкладки-ровни, а **линзы над одним графом** (Строю=Канва · Запускаю=Пульт · Эксплуатирую=Operations · Конверт=Паспорт), **палитра** (Агенты/Навыки/Данные/Коннекторы — источники drag-and-drop) и **вызываемые поверхности** (Безопасность/Настройки). Матрица привязки данных/сущностей остаётся валидной — просто читается как «что показывает эта линза/панель на графе», а не «отдельный экран».

Чтобы дизайнер рисовал реальность, а не макет «из головы»:

| Экран (раскладка) | Данные (из `ABOP_API`) | Сущность (`ABOP_TDR`) | Как исполняется в жизни (`RUNTIME`/`FLEET`) |
|---|---|---|---|
| **Обзор** (SCREENS §2) | `/api/runs?active`, `/api/hitl/queue`, `/api/fleet/health`, `cost_journal` | Run, агрегаты флота | сводка активных прогонов + полоса «в проде сейчас» |
| **Пульт прогона** (§3) | `GET /api/runs/{id}/stream` (SSE: wave_start/agent_step/board_event/handoff/audit_verdict/hitl_request/run_done) | Run · Blackboard-события | волны fan-out на едином MoE (continuous batching); доска event-sourced; аудитор DoD; HITL dry_run→approve |
| **Навыки** (§4) | `/api/skills`, `/api/skills/{id}`, `/skills/{id}/safety` | Skill + `mode/egress/cite` | progressive disclosure: тело грузится по `use_skill`; безопасность read-only (инвариант ядра) |
| **Данные** (§5) | `/api/data/adapters`, `/schema/{entity}`, `/recipe/preview`, `/recipes` | Recipe · canonical-запись + provenance/ttl | `data_run` через адаптер (csv/http/sqlite/computed); freshness-гейт; preview на выборке |
| **Канва** (§6) | `/api/families`, `/api/skills`, `/api/flow/draft`, `/api/flow/save` | AgentVersion (draft) | сборка потока; **слайдер прав ≤ DeploymentContract** (потолок залочен); LLM-черновик на MoE-оркестраторе |
| **Паспорт** (§7) | `/api/agents/{id}/passport`, `/contracts`, `/versions` | AgentVersion + 3 контракта LUDA | конверт: автономия ≤ `DeploymentContract`; PDF (reuse LUDA render) |
| **Эксплуатация — Карта** (§8а + `OPERATIONS_MAP`) | `/api/deployments`, `/api/instances`, `/api/fleet/health` | Deployment (`process_point`) · Instance | semantic zoom по value chain; узел=участок, счётчик=живые Instance; лимит параллелизма на MoE; auto-refresh (SSE флота) |
| **Эксплуатация — ЖЦ** (§8а) | `POST /api/deployments/{id}/deploy\|pause\|retire\|rollback` | AgentVersion статусы draft→deployed(vN)→retired | развёртывание = автозапуск прогонов по триггеру (webhook/расписание/задача); откат=активация vN-1 |
| **Безопасность** (`GAPS §7`) | Keycloak-роли, `SKILL_SAFETY`, аудит-след | RBAC роли, развёртывания | ре-аттестация прод-агентов; scope ⊆ права создателя; аудит ИБ (хэш-цепочка) |
| **Настройки** (§8) | `/api/settings/*`, `/api/me` | конфиг среды | модели/подключения/арендаторы; сохранение — серверный конфиг |

**Как читать строку:** рисуя экран, дизайнер берёт поля из колонки «Данные» (не выдумывает метрики), называет объекты из «Сущность» (не «карточка чего-то», а `Instance`/`Deployment`), и показывает поведение из «Как исполняется» (волны/HITL/лимиты — реальные, не абстрактные).

## 4. Правила «не придумывать» (жёстко)

- **Данные/поля** — только из `ABOP_API.md`. Нет эндпоинта → не рисуем цифру; фиксируем как «нужен эндпоинт X».
- **Сущности и их поля** — только из `ABOP_TDR.md` (Deployment/Instance/AgentVersion/Recipe). Имена — как в модели.
- **Состояния экрана** (пусто/загрузка/ошибка/наполнено) — по `ABOP_SCREENS.md §10`; рисовать ВСЕ четыре.
- **Тексты/термины/tooltip** — из `ABOP_UX_FIXES.md` (человеческий язык, без нового жаргона). Новый текст — согласовать.
- **Элементы/цвета/маскот/спиннеры** — только из `ABOP_DESIGN_KIT.md` + брендкит. Ни одного нового визуального языка.
- **Поведение исполнения** (волны/инстансы/лимиты/автономия) — по `RUNTIME_ARCHITECTURE` и матрице §3. Не изобретать «как агент работает».
- **Термины продукта** (конверт/автономия/HITL/волна) — объяснять in-place (UX_FIXES), не оставлять голыми.

## 5. Чек-лист готовности экрана (перед сдачей)

- [ ] 2 темы (dark-first + light).
- [ ] Все 4 состояния (пусто/загрузка/ошибка/наполнено).
- [ ] Данные с реальными полями из API (не плейсхолдеры «из головы»).
- [ ] Термины объяснены in-place (tooltip из UX_FIXES); прошёл бы 2-мин тест.
- [ ] Один primary/экран, focus-ring, WCAG AA (особенно на стекле), `prefers-reduced-motion`.
- [ ] Маскот Эйп в корректном состоянии; семафор только из токенов.
- [ ] Кликабельность = переходы из SCREENS/OPERATIONS_MAP (для прототипа).
- [ ] Сверено с `ABOP_DESIGN_KIT` (элементы) и матрицей §3 (данные/исполнение).

## 6. Что уточнить у команды (открытые вопросы дизайну)

- Часть `/api/*` в матрице §3 — предварительные (RUN/STREAM/Fleet ещё реализуются, `ABOP_API §3–5`). Финальные поля появятся с реализацией — синхронизировать перед hi-fi.
- Иерархия процессов для карты Операций (value chain → операции) — источник дерева участков уточняется (перекличка с размещением LUDA).
- Точная целевая карта рантайма (48/32 ГБ) не влияет на дизайн, но влияет на числа concurrency в мокапах — брать из `RUNTIME_ARCHITECTURE §7-ter`.

## Приложение
Все доки — в `docs/`. Точка входа — этот файл. При расхождении между доком и этим навигатором — прав профильный док (API для данных, TDR для сущностей, SCREENS для раскладки, DESIGN_KIT для элементов), навигатор лишь связывает.
