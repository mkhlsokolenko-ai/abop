# Концепция: Enterprise-масштабирование и Observability ABOP

> Предварительная проработка (Трек B, Хартия агентных процессов v3.5). Статус: **черновик концепции**, до реализации. Опирается на фактическое состояние кода на 2026-09-16.

## 0. Зачем (постановка задачи)

Демо-контур ABOP функционально закрыт (Data Plane, 1С-Аудитор, «Расследование от симптома», конформанс, RBAC/ABAC, триггеры). Но **архитектурно это монолит с синхронным исполнением** — то самое «красивое демо в ноутбуке», о котором предупреждает Хартия. Чтобы стать enterprise-платформой на много пользователей/процессов, нужно развести исполнение и приём, убрать двойные запуски, сделать сервисы stateless и добавить сквозную наблюдаемость каждого этапа.

Правило Хартии: **быстрее ≠ успех**. Целевые метрики фиксируем ДО старта (см. §7).

## 2. Целевые принципы (из Хартии v3.5)

- **Принцип 12 «Один процесс — один агент».** Единая копия процесса (один промпт, одна инфра, предсказуемая стоимость). «Отдельные агенты на пользователя» = **эфемерные stateless worker-инстансы** одного процесса с изоляцией контекста per-задача/пользователь, а НЕ персональные боты-«зоопарк».
- **Stateless & наименьшие привилегии.** Воркер живёт от задачи до задачи, без долгой памяти; доступ scoped через ABAC/MCP.
- **Шина событий (Kafka).** Раздельные топики requests/results, DLQ, Schema Registry, audit log, трассировка через Kafka-заголовки.
- **Наблюдаемость всей цепочки.** OpenTelemetry + логи всех шагов + цифровой след каждого этапа (langfuse на server-2 — переиспользовать).
- **Adapter Layer.** Legacy через плоский JSON, кэш, circuit-breaker, TTL.
- **Graceful degradation.** Агент опционален, ручной маршрут всегда; агент «перескакивает» 3-5 этапов, не несущая конструкция.
- **Метрики приёмки до старта.** First-Time-Right, Escalation Rate, Time-to-Recovery, Cost per transaction.

### 3.1 Control plane (API + MCP-шлюз)
FastAPI остаётся синхронной поверхностью для CRUD/аутентификации/ABAC-манифеста, но **перестаёт исполнять прогоны** — только публикует `abop.run_request` в шину и сразу возвращает `202 Accepted {run_id, status:accepted}`. Делаем stateless: авторитетное состояние — только Postgres; in-process кэши либо request-scoped, либо инвалидируются через шину/`LISTEN/NOTIFY` (§6). Реплики за LB.

### 3.2 Message bus (Kafka)
Топики: `abop.runs.requests`, `abop.runs.results`, `abop.runs.dlq`, `abop.events.<source>`, `abop.audit`, `abop.hitl`, `abop.cache.invalidate`. Schema Registry со схемами `abop.run_request/1.0`, `abop.run_result/1.0` (совместимо с уже существующими `luda.*`/`abop.run_metrics/1.0`). Ключ партиционирования — `contract_audit_id` (порядок в рамках процесса + равномерная нагрузка). Идемпотентность — `run_request_id` (dedup в воркере).

### 3.3 Worker plane (stateless исполнители)
N идентичных воркеров в consumer-group читают `abop.runs.requests`, исполняют `runner.run_live` (уже async), пишут `run_store` + метрики + трейс, публикуют `abop.run_result`. Масштаб — числом партиций/реплик. Воркер принимает **scope агента** (ABAC) и ходит наружу только через Adapter Layer и MCP-шлюз. Это и есть «эфемерный worker-инстанс одного процесса» (Принцип 12).

### 3.4 Scheduler / trigger plane (единый владелец)
Планировщик выносится из API-реплик в **singleton** (или leader-elected через Postgres advisory-lock / отдельный сервис). Он только **публикует** запросы прогонов и опрашивает источники событий (курсор в PG, один владелец) — **не исполняет инлайн**. Это устраняет двойной запуск.

### 3.5 HITL state machine
Таблица `hitl_items {id, run_id, agent_id, gate, state, payload, created_at, decided_by, decided_at}`; конечный автомат `created → running → awaiting_hitl → approved|rejected → resumed → closed`. Воркер на HITL-гейте чекпоинтит продолжение и освобождает слот; `POST /api/hitl/{id}/approve` публикует resume в `abop.hitl` → воркер добирает. Реализуем заглушки `web_api.py:1703-1714`.

### 3.6 Observability spine
- **Трассировка:** OpenTelemetry, `trace_id` рождается в API, пробрасывается через Kafka-заголовки (`traceparent`) в воркер и дальше в каждый внешний вызов. Экспорт в OTel Collector → Tempo/Jaeger.
- **LLM-трейсы:** langfuse (уже на server-2 — переиспользуем) оборачивает `clients.chat/embed/rerank`; спан на волну/скилл с токенами/стоимостью/латентностью; линк на OTel `trace_id`.
- **Метрики:** Prometheus-клиент + middleware: run latency (p50/p95), глубина очереди/consumer-lag, размер DLQ, cost/run, FTR, escalation-rate; эндпоинт `/metrics`; дашборды Grafana.
- **Логи:** structured JSON c `trace_id/run_id/actor` → Loki.
- **Метрики приёмки** (§7) считаются из `runs`/`run_metrics` + baseline и выводятся и в Grafana, и в UI ABOP («Прогоны»/«Флот»).

### 3.7 Adapter Layer (устойчивость интеграций)
Единый резилиенс-хелпер поверх внешних вызовов (RouteAI, sLAVA, http/postgres/vector-адаптеры, опрос источников): timeout + retry с экспоненциальным backoff + circuit-breaker + bulkhead; TTL-кэш для emit рецептов (свежесть Data Plane управляемо). Legacy — через плоский JSON (модель уже такая).

## 4. Убрать stateful-ловушки (обязательный энейблер)

Инвентаризация in-process кэшей и перевод на общий источник:
- **Авторитет — Postgres** (уже так для агентов/контрактов/прогонов/систем/рецептов).
- **Кэши → инвалидация:** `ape.SKILL_DATASOURCES`, dataplane-кэш, `systems`, `admin_config` — держать с инвалидацией через `abop.cache.invalidate` (или Postgres `LISTEN/NOTIFY`), а не «рефреш только на своей реплике».
- **Курсоры триггеров** — только у scheduler-leader (устраняет гонку).
- **Убрать `_MEM`-фолбэки из горячего пути** прод-профиля (оставить для dev/тестов): в enterprise DSN обязателен.

## 5. Модель многопользовательности и изоляции

- **Один процесс — много воркер-инстансов**, изоляция контекста per-задача (никаких персональных ботов).
- **ABAC на шлюзе:** воркер исполняет под scope агента; данные семьи X недоступны агенту семьи Y (уже есть `access.can_reach_*`), Qdrant-тенант `slava_fam_<family>`.
- **Квоты/рейт-лимиты per-tenant** на публикацию запросов (расширение текущих `WEEKLY_TOKEN_LIMIT`/`cost_journal`).
- **Deny-by-default + аудит every allow/deny с trace_id.**

## 6. Дорожная карта миграции (crawl → walk → run, низкий риск)

**Фаза 0 — упрочнение без новой инфраструктуры (быстрый выигрыш):**
1. `trace_id`/correlation-id + structured JSON logs + `/metrics` (Prometheus).
2. Резилиенс-обёртка (timeout/retry/breaker) вокруг внешних вызовов + TTL-кэш адаптеров.
3. HITL state machine + реальные `/api/hitl/*` (resume).
4. Postgres advisory-lock guard на планировщике — **чинит двойной запуск без Kafka**.
5. Control plane → stateless-safe (инвалидация кэшей).

**Фаза 1 — асинхронное исполнение, минимальная шина:**
- Durable-очередь прогонов за интерфейсом `RunBus`. **Рекомендация: Postgres-очередь** (`SELECT … FOR UPDATE SKIP LOCKED`) + пул воркеров — ноль новой инфры, максимальное развязывание. Интерфейс спроектировать так, чтобы переход на Kafka был сменой драйвера.
- API отдаёт `202` + `run_id`; воркеры исполняют; результат — в `run_store` (+ SSE/polling для UI).

**Фаза 2 — Kafka по Хартии:**
- Kafka + Schema Registry; requests/results/events/audit/hitl → топики; consumer-group воркеры; DLQ; проброс trace-заголовков.
- Полный observability-стек: langfuse + OTel Collector + Tempo + Prometheus + Grafana + Loki.

**Фаза 3 — масштаб и HA:**
- Много воркер-реплик по партициям; автоскейл по consumer-lag; Postgres HA/read-replicas; Qdrant HA; DR и метрика Time-to-Recovery; per-tenant квоты/burst.

Каждая фаза самодостаточна и даёт ценность; Фаза 0 снимает главные production-риски (двойной запуск, зависший HITL, отсутствие следов) ещё до Kafka.

## 7. Метрики приёмки (фиксируем ДО старта)

| Метрика | Источник | Целевой ориентир (уточнить) |
|---|---|---|
| First-Time-Right | `runs.verdict_ok` vs baseline | ≥ acceptance контракта (напр. 0.90) |
| Escalation Rate | доля прогонов с HITL/замечаниями | ≤ acceptance (напр. 0.15) |
| Time-to-Recovery | время от сбоя до восстановления | задать SLA (напр. < 5 мин) |
| Cost per transaction | `run_metrics.cost.rub` / прогон | тренд вниз, потолок на прогон |
| p95 latency прогона | OTel/Prometheus | задать SLA |
| Consumer lag / DLQ | Prometheus | ≈ 0 в устойчивом режиме |

## 8. Открытые решения для владельца

1. **Шина сейчас или позже:** Postgres-очередь как Фаза 1 (рекомендую) → Kafka в Фазе 2, **или** сразу Kafka.
2. **Целевой рантайм:** остаёмся на docker-compose (два сервера) **или** переезд на Kubernetes (нужен для авто-HA/autoscale).
3. **Observability-стек:** подтвердить переиспользование langfuse на server-2 + разворачиваем ли Grafana/Prometheus/Loki/Tempo (или частично).
4. **Целевые SLA/масштаб:** сколько одновременных прогонов, пользователей, процессов, p95 — нужно для расчёта партиций/реплик.
5. **MCP-шлюз как сетевая граница:** оставить in-process enforcement или вынести egress данных/инструментов физически через шлюз-процесс (defense-in-depth).

## 9. Что НЕ трогаем

Доменную логику прогона (`runner.run_live`, детерминированные проверки/трассировка 1С, конформанс, RBAC/ABAC-правила) — она переезжает в воркер **как есть**. Меняется только оболочка исполнения и наблюдаемость, не бизнес-логика.

## 10. Поверхности запуска для простых пользователей (КЛЮЧЕВОЕ для «большого скачка»)

Сейчас агент запускается **только** с канвы «Строю» кнопкой «Собрать и запустить» (синхронный `POST /api/runs`, держит HTTP всю раскладку). Это годится для инженера-сборщика, **но не для простого пользователя в масштабе**. Простому пользователю нужны поверхности, где НЕ надо знать канву, контракты и графы — «нажал → получил результат», а система сама async-исполнит и уведомит.

### 10.1 Персоны и что им нужно
- **Специалист-предметник** (бухгалтер, аналитик): «проверь мне 1С за сентябрь» — задача, не схема.
- **Руководитель**: получить готовый отчёт/сводку, подтвердить HITL.
- **Смежная система** (1С, Redmine, YouGile): дёрнуть агента по событию и получить результат обратно.
- **Инженер-сборщик** (уже покрыт): канва «Строю».

### 10.2 Каталог поверхностей запуска
| # | Поверхность | Кто | Как запускает | Что нужно построить |
|---|---|---|---|---|
| 1 | **Витрина/каталог агентов** (внутри ABOP) | специалист | плитки готовых агентов, кнопка «Запустить» + 1-2 параметра (период/организация), без канвы | обёртка над `demo/prepare`+`runs`; async-запуск (202) |
| 2 | **Рабочее место специалиста** (task-page) | специалист | умный поиск (sLAVA) + запуск агентов + лента результатов/находок с действиями (подтвердить/отправить) | новая страница; в беклоге |
| 3 | **Триггеры (агент сам)** | никто (авто) | расписание / событие (письмо, тикет, ночная выгрузка 1С) | движок ЕСТЬ; вынести планировщик в singleton (см. §3.4) |
| 4 | **Встроенные точки в чужих системах** | смежная система | кнопка/webhook «Запустить аудит» в 1С/Redmine/YouGile → агент кладёт результат обратно (задача в YouGile — доставка уже есть) | webhook-приём `POST /api/hooks/{source}`; исходящий callback |
| 5 | **Чат / Telegram-бот** | специалист | «проверь 1С за сентябрь» → NLU → нужный агент → ответ в чат | бот + intent→agent-роутер |
| 6 | **Почта как триггер** | специалist | письмо на ящик → агент стартовал | event-триггер на ящик (Mailpit/реальный IMAP) |
| 7 | **API / SDK / embed-виджет** | интегратор | REST/iframe-кнопка в чужом портале | публичный API-контур + ключи |

### 10.3 Асинхронный запуск + уведомление (обязательный сдвиг)
Простой пользователь **не ждёт крутилку**. Модель для ВСЕХ поверхностей:
```
POST /runs → 202 Accepted {run_id, status:"queued"}   (мгновенно)
      → воркер исполняет (мультиноды, §11)
      → NOTIFICATION PLANE: уведомить туда, откуда запустили
        (in-app badge/toast · письмо · Telegram · webhook в 1С/YouGile)
```
**Notification plane** — новый элемент архитектуры (сейчас нет). Связывает поверхность запуска с результатом: канал уведомления = канал запуска. Прогресс отдаём через SSE/поллинг для in-app, webhook/письмо — для внешних.

## 11. Мультиноды и шардирование (детально)

### 11.1 Партиционирование очереди
- **Ключ партиции = `contract_audit_id`** (процесс). Гарантия: порядок в рамках одного процесса + равномерное распределение процессов по нодам. Разные процессы исполняются параллельно на разных воркерах.
- **Consumer group из N воркер-нод**: шина (Kafka / Postgres `FOR UPDATE SKIP LOCKED`) раздаёт партиции. Добавил ноду → ребаланс → выше throughput. Автоскейл по **consumer-lag**.

### 11.2 Изоляция тенантов (шумный сосед)
- **Шард по тенанту/семье**: тяжёлый тенант не топит остальных — отдельные партиции/квоты/приоритеты на тенанта.
- **Приоритетные классы очередей**: T1-критичные процессы → высокоприоритетный пул воркеров; фоновые/демо → низкоприоритетный. Критичное не ждёт за демо-нагрузкой.
- **Per-tenant rate-limit** на публикацию запросов (расширение `WEEKLY_TOKEN_LIMIT`/`cost_journal`).

### 11.3 Шардирование данных
- **Postgres**: сначала вертикаль + **read-replica** для тяжёлого чтения (журнал/биллинг/дашборды/Флот) — снимает нагрузку с мастера. Позже — партиционирование `runs`/`audit_log` по времени (range) или тенанту (hash).
- **Qdrant**: знания уже шардированы естественно — коллекции **per-family** (`slava_fam_*`). Масштаб — распределением коллекций/шардов Qdrant по нодам.
- **Объекты (отчёты/PDF)**: MinIO/S3 — уже внешнее хранилище, масштабируется отдельно.

### 11.4 Надёжность доставки при мультинодах
- **Идемпотентность запуска**: `run_request_id` → дедуп в воркере (ретрай/двойная доставка из очереди не плодит прогоны).
- **Идемпотентность эффекта (OUT-доставка)**: ключ идемпотентности на отправку наружу — ретрай не пошлёт письмо/задачу дважды (важно теперь, когда есть реальные YouGile/Яндекс).
- **DLQ + backpressure**: непереваренное → dead-letter; переполнение очереди → `429/queued+ETA`, не падение.

### 11.5 Как поверхности ложатся на фазы (расширение §6)
- **Фаза 0 (быстрый выигрыш):** Витрина/каталог агентов (обёртка над готовым API) + async-обёртка `202+notify` на Postgres-очереди + trace_id/метрики. → простой пользователь запускает без канвы уже сейчас.
- **Фаза 1:** Рабочее место специалиста + Notification plane + Telegram/почта-триггер + HITL-resume.
- **Фаза 2:** Kafka + мультиноды + шарды (партиции по процессу, изоляция тенантов) + webhook-embed в 1С/Redmine/YouGile + приоритетные очереди + полный observability-стек.
- **Фаза 3:** автоскейл по lag, Postgres/Qdrant HA + read-replicas, DR (Time-to-Recovery), per-tenant SLA.

## 12а. ВЫБРАННОЕ НАПРАВЛЕНИЕ (решения владельца, 2026-09-17)

**Первая поверхность запуска = разговорный оркестратор (чат-бот-приложение над всеми системами).**
- Работает **под JWT пользователя** → наследует его доступы (ABAC/least-privilege «из коробки»: агент видит ровно то, что пользователь).
- Общается на **естественном языке**, сам **подбирает и запускает** нужного агента под задачу.
- Пользователь описывает задачу по **конкретному шаблону** — отвечает на вопросы (structured intake через Q&A), а не рисует граф.
- Запускает **эфемерные экземпляры** агента (Принцип 12: 1 процесс = много stateless-инстансов) на **некритичных операциях** (чтение почты, составление писем и т.п.) для работы внутри бизнес-процесса — **без критических действий** без HITL.
- Запуск — **прямо из среды ИС** (встроенный) или откуда угодно.

Архитектурно чат-оркестратор = поверхность №5 (чат) + №1 (каталог, но выбор делает LLM, а не человек) + async-запуск (§10.3) + Notification plane. Требует: intent→agent-роутер, шаблоны intake, эфемерная инстанциация под JWT, гейты действий (некритичное — авто, критичное — HITL). Ложится на event-driven арх. и governance создания агентов ([[demo-6cases-scaling]], Принцип 12).

**Инфраструктурный скачок начинаем с Observability (Фаза 0), ДО перестройки исполнения.**
Причина: нельзя масштабировать то, что не видно. Сначала сквозной `trace_id`, структурные логи, тайминги прогона/шагов, `/metrics`, LLM-трейсы (langfuse) — чтобы видеть узкие места и метрики приёмки ПЕРЕД вынесением в очередь/мультиноды. Затем async-исполнение (Postgres-очередь → Kafka), потом чат-оркестратор поверх.

**Порядок работ:** Observability (Фаза 0) → async `202`+Notification → чат-оркестратор (под JWT, intake-шаблоны, эфемерные инстансы) → Kafka+мультиноды+шарды (Фаза 2) → HA/автоскейл (Фаза 3).

**Уточнение 2026-09-18:** async-исполнение и чат-оркестратор (следующий большой шаг) **ПОКА НА ХОЛДЕ**. Владелец параллельно делает **менеджерский интерфейс** (проект обучения); позже — **смычка ABOP ↔ этот интерфейс**, и она станет **точкой входа простого пользователя** (вместо/до чат-оркестратора). Т.е. интеграция пойдёт через готовый внешний UI (поверхность №4/№7 из §10.2: embed/API), а не через собственный чат ABOP на первом шаге. Observability (Фаза 0) — доведена (trace_id/метрики/Prometheus+Grafana/тайминги/langfuse-каркас/не-молчащие ошибки).

## 12. Резюме «большого скачка» одним абзацем

Разорвать синхронный запуск: API принимает и кладёт в очередь (`202`), **пул stateless воркер-нод** исполняет (партиции по процессу, изоляция по тенанту, приоритет по критичности), а **Notification plane** возвращает результат в ту поверхность, откуда пришёл запрос. Поверх — **сквозной trace_id** от кнопки/письма/вебхука до внешней доставки, метрики приёмки (FTR/escalation/cost/p95) в Grafana. Простые пользователи запускают из **витрины/рабочего места/чата/своих систем**, не зная про канву и контракты. Данные шардируются естественно (Qdrant per-family, Postgres read-replica→партиции), доставка наружу — идемпотентна. Фаза 0 (витрина + async на Postgres-очереди) даёт ценность простым пользователям **до** Kafka; Kafka+мультиноды приходят в Фазе 2 под реальную нагрузку.

## 14. Блок 1 РЕАЛИЗОВАН (2026-09-26): цепочки через очередь, HITL-возобновление, метрики очереди, gzip

Проверено на стенде end-to-end: `POST /api/pipelines/{id}/run?async=1` → 202 → queued → running (прогресс 1/2) → done за 40 с, оба шага с run_id; в `/metrics` появились gauge-метрики и гистограммы.

- **Цепочки (pipelines) через очередь.** Задание `kind=pipeline` в той же таблице `run_jobs`; шаги исполняются последовательно внутри одного задания, прогресс в `checkpoint` (`step, steps_total, steps, prev_ctx, hitl_ids, hitl_decisions`), `GET /api/runs/jobs/{id}` отдаёт `progress{steps_done/steps_total/awaiting_hitl}` и при done — `steps` с run_id/находками/доставкой. Синхронный вызов без `async` сохранён.
- **HITL-возобновление.** Если шаг цепочки создал HITL-доставку (`awaiting_hitl`), задание уходит в статус `awaiting_hitl` с checkpoint и освобождает воркер. `approve/reject` в `/api/hitl/{id}` находят задание по `checkpoint->'hitl_ids'`, кладут решение и возвращают задание в очередь; следующий шаг получает в контекст пометку об одобрении/отклонении. HITL-элементы триггер-узла (`channel=spawn`) при approve ставят прогон в очередь. Payload HITL получает `job_id` (contextvar `CURRENT_JOB`).
- **Метрики очереди в Prometheus/Grafana.** `observability.gauge()`; gauges `abop_run_queue_depth`, `abop_run_queue_jobs{status}`, `abop_run_workers`, `abop_process_rss_mb`, `abop_run_memory_pressure`, `abop_run_queue_avg_wait_seconds_1h`; гистограммы `abop_run_queue_wait_seconds`, `abop_run_job_seconds{kind}`; счётчики `abop_run_jobs_total{status}`, `abop_run_backpressure_total`. Обновление раз в 15 с (`run_queue.gauges_loop`). В `ops/grafana/dashboards/abop-overview.json` — 4 stat-панели (ждут / выполняются / ждут решения HITL / RSS) и timeseries p95 ожидания и исполнения + глубина; Grafana на стенде читает дашборд из смонтированной папки.
