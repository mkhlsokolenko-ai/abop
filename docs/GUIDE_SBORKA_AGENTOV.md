# ABOP — полный гайд: как с нуля собрать агента и получить ценность

> Практическое руководство от «пустого места» до работающего агента, приносящего пользу.
> Максимум конкретики: что готовить, как настраивать навыки/данные/граф, что критично уточнить,
> на что смотреть, где типовые грабли. Основано на реальной механике ABOP.

---

## Часть 0. Ментальная модель (прочитай первой — сэкономит часы)

**Агент в ABOP — это НЕ «большой умный промпт».** Это:

```
КОНТРАКТ (что можно, какой потолок автономии, метрики приёмки)
   → ГРАФ на канве (Триггер → Источники → Навыки → HITL → Выход)
      → ПРОГОН (исполнение по волнам, с governance и наблюдаемостью)
```

Три принципа, без которых агент будет «красивым, но бесполезным/опасным»:

1. **Истину считает КОД, LLM — объясняет.** Детекция фактов/находок/расчётов — детерминированный
   код на полных данных (воспроизводимо, с доказательством). LLM формулирует и объясняет, но НЕ
   является источником фактов. Где это неприменимо (генерация текста — письмо, БФТ) — LLM работает
   на **реальных данных** (grounded), а не «из головы».
2. **Governance-конверт.** У агента есть потолок автономии (A0–A4) и точки HITL. Действие наружу
   (письмо, запись в систему) — только под подтверждением/явным флагом. Безопасно по умолчанию.
3. **Данные — через контракт, не из сырых систем.** Агент читает канонические сущности (`entity`)
   из Data Plane, не зная, из какой системы они пришли.

**Ключевой вопрос перед стартом:** *что здесь ФАКТ (считает код), а что — ФОРМУЛИРОВКА (пишет LLM)?*
Правильно проведённая граница = надёжный агент. Размытая = галлюцинации в проде.

## Часть 1. Что подготовить ДО сборки (предусловия)

| Нужно | Зачем | Как проверить |
|---|---|---|
| **Данные в Data Plane** | агент читает `entity`, а не систему напрямую | в разделе «Данные» видны записи нужной сущности |
| **Доступ (RBAC/ABAC)** | пользователь/семья агента видит нужные системы и данные | вход под нужной ролью; ABAC режет чужое |
| **LLM доступен** | навыки-объяснения используют модель | self-host Qwen3-30B (`local/qwen3-30b-a3b`, 0 ₽) → при недоступности каскад откатится на облако (лог `llm.cascade_fallback`) |
| **Понимание процесса** | что автоматизируем и в чём ценность | см. Часть 6 (критерии пилота) |

> Если данных нет — сначала заведи **рецепт** (Часть 2). Без данных прогон отработает за <1с,
> LLM не вызовется, находок будет 0.

## Часть 2. Данные: рецепт → каноническая сущность (`entity`)

Агент работает с **сущностями** (`entity`: `doc1c`, `transaction`, `email`, `issue`…), а не с
форматами систем. Связка данных во всей системе — по ключу **`entity`**.

### 2.1 Рецепт (recipe) — «как достать и привести к сущности»
Рецепт описывает: **источник** (адаптер: csv/http/postgres/vector/…) → **преобразование** (маппинг
полей) → **эмит** в каноническую `entity` (со схемой, версией, provenance).

**Шаги:**
1. Раздел «Данные» → создать рецепт: выбрать адаптер и источник.
2. Задать `entity` (имя сущности) и маппинг колонок в поля.
3. Опубликовать и **прогнать рецепт** — записи попадут в canonical store.
4. Проверить: сущность отдаёт записи (просмотр данных / прогон покажет объём).

### 2.2 Критично про данные (частые ошибки)
- **Один `entity` — единый смысл.** Если два рецепта пишут в одну сущность — они дополняют её
  (напр. `ref1c` из двух источников). Убедись, что схемы совместимы.
- **Версионность:** последняя созданная версия записи НЕ протухает по времени; старьё вытесняется
  только когда перекрыто более новой версией. Данные не исчезают «через сутки». (Это про durability
  demo/прода.)
- **Свежесть ≠ часы:** не полагайся на «TTL истёк». Полагайся на «есть последняя версия».
- **Provenance:** у каждой записи фиксируется, откуда и когда — это основа доверия к находкам.

## Часть 3. Навыки (skills) — ядро агента

Навык = одна конкретная способность. Агент = цепочка навыков. **Качество агента = качество навыков.**

### 3.1 Поля навыка (что настраивается — редактируется в UI)
| Поле | Значения | Что определяет | Как выбрать |
|---|---|---|---|
| **mode** | read / write / action | что навык делает с миром | read — только читает; write — формирует артефакт; action — действие наружу |
| **egress** | internal / external | выходит ли за периметр | external → тянет наружу (анти-SSRF, обычно под HITL) |
| **cite** | true / false | обязана ли ссылаться на источник/норму | true для регуляторных/финансовых — числа/нормы из источника, не из памяти |
| **output** | structured / freeform | формат вывода | **structured** — навык-детектор (список находок → JSON); **freeform** — навык-документ (письмо/план/БФТ → текст) |
| **data-need** | список `entity` | какие данные навык реально читает | ровно те сущности, что нужны — не больше (ABAC + объём токенов) |
| **template.json** | схема + инструкция + `max_tokens` + `delivery` | точная структура ответа и куда он уходит | см. 3.5; есть у 51 из 56 навыков |
| **tools** (frontmatter) | список инструментов | что навык может вызвать по ходу (данные, публикация) | действия наружу — только через `publish_command_governed` (реестр систем + ABAC + HITL) |

> **`output` — ключевое и часто путают.** Детектор (находит расхождения, список задач) → `structured`
> (грамматика JSON, минус «вода рассуждений», вывод парсится). Документ (пишет письмо, БФТ, план) →
> `freeform` (иначе схема ломает форму: модель напишет «расхождений нет» вместо письма).

### 3.2 Методика навыка (SKILL.md) — от неё зависит толк
Тело навыка — это **инструкция для LLM/оркестрации**. Плохая методика = плохой результат, даже с
идеальными данными. Структура (проверенная):

```
---
name: <id>
description: <одна фраза: что делает, на чём, чего НЕ делает>
---
# Название
<1 абзац: суть, что ценит заказчик>
## Когда применять
## Метод (пошагово)   ← самое важное: КОНКРЕТНЫЕ шаги, а не «проанализируй»
## Definition of Done ← чек-лист, по которому проверяется результат
## Анти-паттерны      ← что НЕ делать (галлюцинации, вода, домыслы)
## Безопасность       ← mode/egress/cite обоснованы
## Интеграция         ← вход (сущности), результат, handoff к след. навыку
```

**Что делает методику хорошей:**
- **Конкретные шаги**, а не «примени экспертизу». «Построй граф по ссылкам X/Y», «сверь сумму A с B».
- **Явные анти-паттерны**: «не выдумывай рёбра — их отсутствие само есть находка», «пробелы помечай
  „уточнить“, не додумывай».
- **DoD как чек-лист** — по нему видно, выполнен ли навык.
- **Указание границы факт/формулировка**: если детекцию делает код — методика говорит «объясняй
  найденное, не ищи заново».

### 3.3 data-need (что навык читает)
Навык получает в контекст **дайджест** своих `entity` (счётчики по типам = полный объём + сэмпл
записей), а не весь дамп. Это осознанно: экономит токены/время, не влияя на детекцию (её считает
код на полных данных). Задавай data-need **точно** — лишние сущности = лишние токены и риск ABAC-отказа.

### 3.4 Цикл уточнения навыка (skill refinement) — как довести до толка
1. Прогони агента, прочитай нарратив навыка в результате.
2. Диагностируй:
   - **«расхождений нет», хотя код нашёл** → навык в `structured` пытается искать сам на сэмпле;
     переключи на **grounded** (объясняет находки кода) или на `freeform` для документа.
   - **Вода/markdown-простыня** → включи `structured` (для детектора) или ужми методику; проверь
     `max_tokens`.
   - **Выдуманные числа/нормы** → это должен считать КОД; поставь `cite=true` и норму из RAG.
   - **Обрыв текста** → мал `max_tokens`; или вынеси детали в код.
3. Правь: методику (шаги/анти-паттерны), `output`, data-need, шаблон (3.5). Сохрани (версия навыка в PG).
4. Перепрогони, сравни. **Критерий:** находки/числа стабильны и совпадают с кодом; нарратив
   читаем и не противоречит фактам.

### 3.5 Шаблон навыка и доставка (`skills/<sid>/template.json`)

Общая схема «находки/итог» узка для ранжирования, вердикта, DCF или письма. Поэтому у навыка есть **шаблон
извлечения** — файл `skills/<sid>/template.json`:

```json
{
  "name": "Аудит 1С · объяснительный отчёт (explain)",
  "instruction": "Объясни КАЖДУЮ находку … по четырём блокам: что не сходится / откуда / чем грозит / что проверить …",
  "json_schema": { "type": "object", "additionalProperties": false, "required": ["резюме_для_главбуха", "находки", "…"], "properties": { "…": {} } },
  "max_tokens": 7000,
  "delivery": {
    "system": "redmine", "type": "issue.create",
    "each": "находки", "where": {"ранг": ["критично", "существенно"]}, "limit": 10,
    "title": "Задача Redmine: {{заголовок}}",
    "payload": {
      "subject": "Аудит 1С · {{ранг}} · {{id}} · {{заголовок}}",
      "description": "h2. Что не сходится\n\n{{что_не_сходится}}\n\nh2. Откуда\n\nДокументы:\n{{#откуда.документы}}\n…\nРезюме: {{$.резюме_для_главбуха}}"
    }
  }
}
```

- **`json_schema`** — подробная схема результата, strict-совместимая (только `type / properties / required / items / enum /
  additionalProperties:false`; без `$ref`, `pattern`, `oneOf`). Модель отвечает строго по схеме (vLLM xgrammar),
  рантайм рендерит читаемый текст на доску и кладёт объект в `structured` / `result.skill_outputs`. Имена полей — русские,
  как в предметной области; суммы и даты — строками; `enum` для всего закрытого (ранг, риск, приоритет).
- **`instruction`** — инструкция-парсер: что и как извлекать, что считать гипотезой, чего не выдумывать. Попадает в системную
  часть промпта навыка вместе с описанием полей схемы.
- **`max_tokens`** — лимит ответа под длину схемы (explain — 7000, verdict/dcf — 5000, rank/bft — 4000). Обрезанный ответ
  чинится `_repair_json` (маркер `_truncated`, на доске «⚠ ответ модели обрезан…») — значит, лимит надо поднять.
- **`delivery`** (необязательно) — **куда уходит результат**: `system` + `type` = адаптер коннектора (`redmine/issue.create`,
  `bookstack/page.publish`, `mailpit/email.send`, `1c/export.request`); `each` — массив ответа, по команде на элемент
  (без `each` — одна команда на весь ответ); `where` — фильтр по enum-полям; `limit` — потолок; `payload` — поля команды с
  подстановками `{{поле}}` из элемента, `{{$.поле}}` из корня ответа, `{{#список}}` — маркированный список.
  Неизвестный путь → пусто, ничего не выдумывается.

**Как доставка работает в прогоне** (после OUT-узлов): `delivery.build_commands` собирает команды из structured-ответа →
ABAC проверяет доступ семьи агента к системе (иначе строка `доступ закрыт`) → каждая команда становится **HITL-заявкой
канала `command` с превью** (система/действие, тема, описание) и строкой в карточке прогона
«redmine → issue.create · «тема» · ожидает вашего подтверждения» → оператор смотрит превью («Посмотреть и подтвердить»)
→ «да» публикует команду в `abop.<система>.commands` → коннектор-воркер (server-2) исполняет и возвращает
`command.done|failed` → в карточке «✓ выполнено: http://…/issues/N». «Только в чат» (`deliver_filter="chat"`) выключает доставку.
Наружу до подтверждения не уходит ничего.

**Правка без пересборки.** Источник правды — таблица `schema_templates` в БД, репо — посев. Шаблон правится в UI
(редактор schema-templates; ручная правка снимает `builtin`) или через API: `POST /api/schema-templates/{id}`,
`POST /api/schema-templates/import` (пачкой из репо, `scripts/push_templates.py`), `POST /api/schema-templates/{id}/reset`
(вернуть версию из репо). Проверка strict-совместимости: `python scripts/check_templates.py skills/<sid>/template.json`.
Подробно — `docs/SKILL_TEMPLATES.md`; протокол коннектора — `docs/CONNECTOR_WORKER.md`.

Покрытие сейчас: шаблоны у 51 из 56 навыков (все 4 демо-кейса); `delivery` — у `audit1c-explain` (задача на каждую
критичную/существенную находку) и `audit1c-rank` (одна сводная задача). Для остальных кейсов доставка по шаблонам в плане
(инвест → BookStack, дайджест → письмо, БФТ → задача).

## Часть 4. Контракт, семья, роль

Агент рождается из **контракта** (что за процесс, семья, навыки, потолок автономии, метрики приёмки)
и принадлежит **семье** (домен: аудит, аналитика, менеджмент…) с **ролью**.

**Что критично задать в контракте:**
- **autonomy_level (A0–A4)** — потолок; автономия любого узла ≤ этого. Не завышай: чем выше, тем
  меньше человека в контуре.
- **hitl_points** — где обязателен человек (обычно перед действием наружу).
- **acceptance-метрики** (ДО старта!): First-Time-Right, Escalation Rate — с чем сравнивать прогоны.
- **data_residency / egress** — куда можно ходить.

**Семья/роль** определяют ABAC: агент видит только данные/системы своей семьи; знания (RAG)
изолированы по семье. Аналитик не увидит данные архитектуры — это не настройка агента, а его атрибут.

## Часть 5. Граф на канве («Строю») — сборка потока

Узлы слева направо:

| Узел | Роль | Что настроить |
|---|---|---|
| **Триггер** | стартовое событие | тип (вручную/расписание-cron/событие); политика spawn (кого/сколько/HITL-на-создание/потолок автономии) |
| **Источник** | данные | привязка к `entity` (рецепт резолвится по entity) |
| **Навык** | шаг работы | навык + автономия узла + HITL-флаг |
| **LLM-ветвление** | развилка | условие (напр. «находка существенна?») |
| **HITL** | подтверждение человеком | точка, где ждём «ок» оператора |
| **Выход (OUT)** | доставка результата | **канал** (почта/BookStack/Redmine/YouGile/PDF), **адрес**, **формат**, **шаблон отчёта**, **dry_run / реальная отправка**, **под HITL** |

**Критично про OUT:** по умолчанию **dry_run** (превью). Реальная отправка наружу — только если
явно включено «Реальная отправка» И снят «Под HITL» И есть доступ/токены. Так случайно ничего не улетит.

**Два пути наружу — не путать:**
- **OUT-узел** доставляет *отчёт прогона целиком* по шаблону отчёта (`reports/<id>.html` → `report_templates` в БД,
  веб-редактор с превью; шаблоны `default`, `audit1c`, `invest`, `digest`). В контекст отчёта входят structured-ответы навыков:
  `{{skills}}` (все) и `{{skill_<sid>}}` (дефисы → подчёркивания, напр. `{{skill_audit1c_rank}}`) — таблицы/списки из JSON.
  Тот же отчёт по требованию: `GET /api/runs/{run_id}/report?template=<id>&format=html|pdf`; в десктопе — кнопка «Отчёт PDF»
  на карточке прогона.
- **`delivery` шаблона навыка** (3.5) доставляет *отдельные результаты навыка* (задача на находку, страница, письмо)
  командами коннектора — всегда через HITL-превью, флаги OUT-узла на неё не влияют.

**Быстрый путь:** выбрать готовый сценарий-вкладку → «▶ Собрать и запустить». Это идемпотентно
принимает контракт, сохраняет агента и запускает.

## Часть 6. Как получить ЦЕННОСТЬ (а не «демо в ноутбуке»)

Ценность = автоматизирован процесс, где агент реально экономит время/деньги и не создаёт риск.

### 6.1 Выбор процесса под пилот (критерии)
- **Богатый цифровой след** (есть данные и по шагам, и по результату).
- **Данные через API** (не «скопируй руками»).
- **Автопроверяемый критерий качества** (можно сказать «правильно/нет» без спора).
- **Низкая дисперсия времени** (процесс предсказуем).
- **Критичность T1–T2** (важно, но не «жизнь и смерть» на первом пилоте).

### 6.2 Метрики приёмки — ЗАФИКСИРОВАТЬ ДО СТАРТА
| Метрика | Смысл |
|---|---|
| First-Time-Right | доля результатов, принятых без переделки |
| Escalation Rate | доля, ушедшая на человека/HITL |
| Cost per transaction | стоимость одного прогона (токены/₽) |
| Time-to-Recovery | как быстро восстановились после сбоя |

Правило: **быстрее ≠ успех.** Если агент быстрый, но FTR низкий — ценности нет.

### 6.3 Что даёт доверие (обязательные элементы)
- **Grounded**: находки/числа из кода и реальных данных; нормы — из RAG с провенансом.
- **HITL** на действиях наружу.
- **Наблюдаемость**: у прогона есть trace_id, время, стоимость, находки; ошибки не «молчат».

## Часть 7. Критичный чек-лист (перед выкаткой агента)

- [ ] Проведена граница **факт (код) / формулировка (LLM)**; факты не отданы на генерацию.
- [ ] Данные текут: нужные `entity` наполнены, свежая версия отдаётся.
- [ ] У каждого навыка **корректный `output`** (structured — детектор, freeform — документ).
- [ ] **data-need** навыков точный (не больше нужного).
- [ ] Регуляторные навыки: **cite=true**, норма из RAG (не из памяти модели).
- [ ] Действия наружу — под **HITL** и dry_run по умолчанию; адреса/каналы заданы верно.
- [ ] У навыков есть **template.json** (схема проходит `check_templates.py`, `max_tokens` под длину ответа);
      если результат должен жить в системе — секция `delivery` и превью проверены на прогоне.
- [ ] **autonomy** узлов ≤ потолок контракта.
- [ ] Методики навыков конкретны (шаги + анти-паттерны + DoD), не «вода».
- [ ] **acceptance-метрики** заданы до старта; есть с чем сравнивать.
- [ ] ABAC: агент видит только свою семью/данные (проверить под ролью).
- [ ] Прогон прогрет (первый холодный ~секунды; повтор — из кэша мгновенно).

## Часть 8. Типовые проблемы → причина → решение

| Симптом | Причина | Решение |
|---|---|---|
| Прогон <1с, 0 находок | Data Plane пуст/не наполнен | прогнать рецепт нужной сущности |
| Навык пишет «расхождений нет», код нашёл | детектор ищет сам на сэмпле | grounded (объяснять находки кода) / проверить output |
| Много «воды», markdown-простыни | документный режим у детектора | output=structured; ужать методику; проверить max_tokens |
| Выдуманные числа/статьи закона | факт отдан LLM | считать кодом; cite=true + норма из RAG |
| Обрыв текста на полуслове / «⚠ ответ модели обрезан» | мал `max_tokens` шаблона | поднять `max_tokens` в `template.json` (или в UI/через API) |
| Строка доставки «доступ закрыт» | ABAC: семья агента не видит систему | дать семье доступ к системе в реестре или запустить под нужной семьёй |
| Превью подтверждено, а «✓ выполнено» не появилось | коннектор не ответил (шина/адаптер/система) | `GET /api/bus/dlq`, логи `abop-connector`; повторная публикация — новым id |
| «нет доступа к семье» | ABAC режет чужое | войти под нужной ролью / проверить family |
| OUT ушёл/не ушёл не так | флаги доставки | «Реальная отправка» + снять «Под HITL» + токены; иначе dry_run |
| Долгий первый прогон | холодный LLM | это норма; повтор из кэша мгновенный |
| Дорогой/медленный прогон | много данных в LLM | дайджест (не полный дамп); structured; детекцию — в код |

## Часть 9. Мини-рецепт «с нуля за 8 шагов»

1. **Определи процесс и границу факт/формулировка** (Часть 0, 6).
2. **Заведи данные**: рецепт источник→`entity`, прогони, проверь (Часть 2).
3. **Подбери/создай навыки**: методика (шаги/DoD/анти-паттерны), mode/egress/cite/**output**,
   data-need, **template.json** (схема + `delivery`, если результат должен жить в системе) (Часть 3).
4. **Оформи контракт**: семья, autonomy-потолок, HITL-точки, acceptance-метрики (Часть 4).
5. **Собери граф**: Триггер → Источники → Навыки → HITL → OUT (канал/адрес/формат/dry_run) (Часть 5).
6. **Запусти** («Собрать и запустить»), прочитай результат.
7. **Уточни навыки** по нарративу (цикл refinement, Часть 3.4).
8. **Подтверди ценность** по acceptance-метрикам; включи реальную доставку под HITL (Часть 6).

## Как ABOP понимает фразу и собирает цепочку (28.09.2026)

Запрос на естественном языке разбирается детерминированно, до обращения к модели (`server/nlu.py`):

1. **Лексемы.** Слова приводятся к основе лёгким стеммером: «проверь», «проверка», «проверить» — одна основа;
   «отчёт» и «отчёты» совпадают. Короткие термины (`1С`, `НДС`, `БФТ`) не режутся. Маркеры порядка
   («сначала», «потом», «затем») в лексемы не попадают.
2. **Этапы.** Фраза режется на этапы по маркерам последовательности и перечислению действий. Порядок этапов —
   это порядок шагов цепочки; модель его не меняет. Фрагмент без действия приклеивается к предыдущему этапу
   («проверь 1С за квартал» остаётся одним этапом).
3. **Триггер и окружение.** В этапе ищется слово-действие (проверь, найди, объясни, подготовь, напиши, заведи,
   опубликуй, посчитай) и делится окружение: слова ДО него — предмет, ПОСЛЕ — цель и адресат. Канал доставки
   берётся только из части после триггера и только у действий, которые что-то отдают наружу. Этап без своего
   предмета («объясни их») наследует предмет предыдущего этапа.
4. **Словарь агента.** У каждого агента есть словарь лексем (`server/lexicon.py`, таблица `agent_lexicon`),
   собранный из описаний его навыков: заголовок и описание навыка, инструкция шаблона извлечения, тело SKILL.md,
   роль, семья, каналы доставки. Словарь пересчитывается при сохранении агента (хук `agent_store.on_save`)
   и засевается по всем агентам при старте — **новый агент сразу приносит свои слова в подстановку**.
5. **Подбор и уверенность.** На каждый этап выбирается агент по совпадению лексем со словарём. Возвращаются
   `confidence` (худший этап), `low_confidence`, `ambiguous` (равные кандидаты) и `warning`. При низкой
   уверенности запускается **реранк моделью** среди уже отобранных кандидатов этапа — порядок этапов при этом
   не меняется. В десктопе карточка цепочки показывает разбор по этапам, оценку каждого шага и предупреждение.

Ответ `POST /api/pipelines/suggest` содержит `steps`, `stages` (разбор с агентом и оценкой на каждый этап),
`parse` (лексемы и этапы), `confidence`, `low_confidence`, `warning`, `reranked`.
