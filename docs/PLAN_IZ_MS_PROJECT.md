# План из MS Project: как ABOP читает настоящий график проекта

> Актуально на 17.10.2026. Сторожат `tests/test_msproject_adapter.py` и `tests/test_plan_shift.py`.

## 1. Зачем

Агент «Управляющий графиком» строит справку о смещении сроков. Пока дорожная карта была демо-файлом,
справка была правдой про демо. У заказчиков график живёт в MS Project, и путь к доверию один:
прочитать их настоящий план и показать, что расчёт сходится с тем, что они видят у себя.

Проверка проведена на настоящем плане: 562 задачи, девять уровней вложенности, 429 связей,
92 ресурса, 94 календаря. Именно он вскрыл четыре ошибки движка, которых демо-данные не показывали
(раздел 4).

## 2. Формат: XML, а не .mpp

Адаптер `msproject` читает **MSPDI XML**. Разбор двоичного `.mpp` требует Java (MPXJ), и ставить
JVM на сервер ради одного формата незачем. MS Project сохраняет XML штатно: **Файл → Сохранить как
→ XML**. Если на руках уже выгруженный `.mpp`, разовую конверсию делает
`demo/plan/msproject/mpp_to_xml.py` (нужны `pip install mpxj JPype1` и установленная Java).

> Грабля Windows: JVM не читает jar-ы по пути с кириллицей. Скрипт копирует их во временный каталог
> с латинским путём — иначе `Class ... is not found` без всякого объяснения.

## 3. Что знает код и что приходит рецептом

Код знает только формат: элементы `Task`, `PredecessorLink`, `Assignment`, псевдонимы
пользовательских полей и единицы измерения (резерв — десятые доли минуты, длительность — ISO-8601).
Всё остальное объявляет рецепт:

| Параметр рецепта | Что задаёт |
|---|---|
| `target` | файл выгрузки |
| `проект` | код проекта (по умолчанию — `Title` самой выгрузки) |
| `ветка` | код WBS: берём только эту ветку плана (в плане на 562 задачи справка по всему плану нечитаема) |
| `без_сводных`, `уровень_не_глубже` | какие строки считать пунктами |
| `источник_стадии` | `название` задачи, `родитель` (сводная задача) или поле |
| `критично_по` | `веха` — по вехам плана; `эталон` — по собственному признаку критичности MS Project; иначе поле |
| `связи` | какие виды связей означают «ждёт» (по умолчанию `FS` и `FF`; `SS` и `SF` — нет) |
| `поля` | соответствие наших полей элементам MSPDI или пользовательским полям по псевдониму |

**Стадию адаптер не переводит.** Он отдаёт то, как задача названа, а смысл названию придаёт
регламент: `stage_rule.признаки` — список слов и фраз, по которым стадия узнаётся. Словарь собран
из настоящего плана: «Скрининг в ИБ» → АПСЕК, «Развертывание поставки в ПИМ» → развёртывание,
«Тестирование Е2Е» → E2E, «Приёмо-сдаточные испытания» → ПСИ, «Согласованы ЗНИ Релизов» → ЗНИ,
«Релиз на ПРОД» → вывод в пром, «Тиражирование (подключение пользователей)» → тиражирование.
У заказчика терминология своя — это правка регламента, а не релиза.

Признак ищется **по словам**: «ПСИ» не находится внутри другого слова, а «вывод на пром» обязано
находиться целой фразой.

## 4. Чему научил настоящий план

| Что было | Что стало |
|---|---|
| Стадия искалась только по идентификатору норматива. Живой источник отдаёт название — норматив не находился, остаток стадий считался нулём, и справка выглядела спокойной | Точное сопоставление по идентификатору и названию, затем по признакам регламента. Нераспознанная стадия попадает в отчёт строкой «пропуск» |
| Завершённая работа прогнозировалась наравне с незавершённой: по закрытой в августе поставке справка писала «опоздание на 95 дней» | При 100 % берётся фактический финиш |
| Строка плана считалась функционалом, проходящим весь процесс: к прогнозу прибавлялся остаток ВСЕХ последующих стадий | Охват пункта объявляет источник: `стадия` (работа) или `процесс` (функционал). Прямой и обратный проходы пользуются одной арифметикой |
| Резерв считался расстоянием до даты ввода | Обратный проход по последователям (PMBOK 6, 6.5.2.2) |
| Критический путь восстанавливался по связям, которые СЕГОДНЯ двигают прогноз: цепочка из восьми работ схлопывалась в один пункт | Назад по предшественникам с нулевым резервом |
| Работы вне производственного процесса (найм, обучение, нагрузочное тестирование — 18 из 44) считались мгновенными, получали ложный резерв и рвали путь | Нет норматива — длительность берётся из самого плана (`Duration`) |
| Перечень смещений составляла модель: из 33 смещённых пунктов в справку попал один | Перечень дополняется расчётом: критический путь, затем по величине сдвига, до 12 строк |

## 5. Сверка с расчётом самого плана

MS Project уже посчитал свой критический путь и резервы. ABOP сверяется с ними и показывает
результат отдельной строкой справки: сколько пунктов сошлось, сколько разошлось и по каким.

Расхождение — не обязательно ошибка. План считает по собственным длительностям задач, справка —
по нормативам стадий регламента: там, где они разные, разойдутся и пути. Это и есть ценность
справки — она отвечает на вопрос «что будет, если работать по регламенту», а не пересказывает план.

Завершённые работы из сверки исключаются: план помечает критической всю пройденную цепочку, и
спорить там не о чем.

## 6. Как подключить план заказчика

```bash
# 1. выгрузка рядом с данными демо (в репозиторий план заказчика не кладётся)
docker cp "План проекта.xml" abop-webapi:/app/demo/plan/msproject/<проект>.xml

# 2. рецепт — копия plan_roadmap_mpp с другим target и веткой; правится в UI «Данные → Рецепты»
#    или скриптом через dataplane_store.save_recipe

# 3. расчёт: рецепт вида `plan` с проектом и отчётной датой плана
# 4. прогон агента — справка собирается на этих данных
```

В репозитории лежит демо-выгрузка `demo/plan/msproject/plan.xml` той же формы: сводные задачи,
последовательность стадий, связи четырёх видов, вехи, проценты, резервы и признак критичности —
всё, за что цепляется адаптер. Настоящих планов заказчиков в репозитории нет и быть не должно:
в них живые фамилии и внутренние системы.
