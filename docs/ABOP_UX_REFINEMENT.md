# ABOP — Доработки UX по ревью прототипа v2

**Что это:** формализация экспертного ревью прототипа v2 в конкретные доработки. Фокус ревью — **не добавлять функции, а отполировать сильное ядро** и поднять два слабых показателя: *простота освоения (6.5)* и *product clarity (7)*. Функционально прототип оценён 8/10 (потенциал 9+).
**Связка:** экраны — `ABOP_SCREENS.md`; kit — `ABOP_DESIGN_KIT.md`; расхождения — `ABOP_DESIGN_GAPS.md` (в т.ч. вкладка Безопасность).
**Статус:** v1.0, к работе дизайнера/фронта.

---

## 0. Диагноз ревью (кратко)

- **Сильно (не ломать):** explainable-валидация (реальная проверка связности/циклов/вход-выход/timeout/HITL/autonomy с объяснением, а не green/red), operational dashboard как control plane, цветовая семантика состояний, dark-enterprise стиль, Inter+JetBrains Mono. Enterprise-readiness 8.5.
- **Слабо (бить сюда):** интерфейс читается как **инженерный tool**, а не как продукт для Product Owner/Operations. Не видно сразу: *какую бизнес-задачу решаю и какой результат получу*. Термин «конверт LUDA» новичку ничего не говорит.
- **Репозиционирование:** от «IDE для агентов» → к **«операционной системе управления агентными процессами»** (agent process control plane). Это сильнее и точнее.

---

## 1. Организующий принцип — сквозная UX-история

Полировка ведётся вокруг ОДНОЙ истории; каждый экран = её шаг. Провести пользователя по ней визуально:

```
Intent → Build Graph → Validate → See Waves → Execute → HITL → Result → Audit
 (что   (собрать      (проверить (увидеть   (запустить (подтвер- (резуль- (аудит-
  хочу)   граф)        исполнимость)  волны)    прогон)   дить)    тат)     след)
```

Это превращает продукт из «дерева фич» в «понятный маршрут». Онбординг и прогресс-индикатор строятся по этим 8 шагам.

## 2. Доработки по замечаниям (D1–D6)

### D1 · Outcome-oriented главный экран (decision interface) — **приоритет M**
**Проблема:** dashboard говорит «у тебя есть агентная система», а не «что она делает и насколько готова сделать это сама».
**Решение:** каждый прогон/агент подаётся как **решение**, а не как техносводка. Статус-хедер:
```
RUN #1842 · Оценка подрядчика
READY TO EXECUTE ▓
7 agents · 3 waves · 1 HITL gate · ₽127 est · L2 autonomy
```
Сверху — **бизнес-задача**; крупно — **готовность** (READY / BLOCKED / RUNNING / DONE); ниже — компактная техносводка. Outcome-язык вместо узлового.
**Где:** Обзор (§2, карта-прогона) + шапка Пульта (§3).
**Как:** карта строится вокруг названия задачи + бейдж готовности + строка-сводка; клик → Пульт.

### D2 · Граф — центральный объект + Execution Inspector — **приоритет M**
**Проблема:** сейчас dashboard→карточки→граф→проверки; граф вторичен.
**Решение:** **Workflow/Agent Graph — главное пространство** рабочего экрана. Справа постоянный **Execution Inspector** выбранного узла:
```
DCF Valuation
──────────────
Agent    Financial Analyst
Input    transactions_2026
Skills   • data-query • dcf-valuation
Autonomy L2
Cost     ₽14.20    Latency ~4.2s    Risk LOW
```
**Где:** Канва (§6) и Пульт (§3) — граф доминирует по площади, инспектор всегда виден с метриками узла.
**Как:** усилить 3-зонный layout §6 (палитра · **граф-центр** · инспектор); инспектор показывает agent/input/skills/autonomy/cost/latency/risk на любом экране с графом.

### D3 · Визуализация волн (WAVE 01–04) — **приоритет M**
**Проблема:** концепция волн есть в ядре (граф → ацикличность → раскладка в волны), но UI её не показывает.
**Решение:** авто-раскладка графа по горизонтальным волнам:
```
WAVE 01   [Data Query]  [Documents]
                └────┬────┘
WAVE 02        [Valuation]
WAVE 03        [HITL gate]
WAVE 04        [Send Email]
```
Наглядно объясняет архитектуру ABOP даже тем, кто не видел orchestration.
**Где:** Пульт (§3, режим «волны») + превью плана при запуске (§9.1).
**Как:** топологическая раскладка DAG по уровням; параллельные узлы в ряд; подписи WAVE N; текущая волна — акцент (брендкит: прогресс «волна N/M» уже есть — связать с графом).

### D4 · Explainable validation — вывести в UI как первоклассный шаг — **приоритет M**
**Проблема:** это сильная сторона (реальная проверка + объяснение), но живёт «в коде», не как заметный UX-шаг.
**Решение:** панель **«Проверка исполнимости»** перед запуском — список проверок с explainable-результатом и «как починить»:
```
✓ Компоненты на месте        ✓ Связность графа
✓ Вход/выход определены       ✗ Внешнее действие без HITL
✗ Цикл A→B→A                    → «Поток нельзя исполнять без
✓ Timeout в норме                 подтверждения оператора»
```
Не green/red, а **объяснение проблемы + действие**. Это зачаток настоящего control plane — подчеркнуть его.
**Где:** Канва §6 (перед `[Запустить]`) + модалка запуска §9.1 (гейт: нельзя запустить, пока есть ✗).
**Как:** проверки = компоненты/связность/вход-выход/циклы/timeout/HITL/autonomy-envelope; каждая с текстом-объяснением из ядра.

### D5 · LUDA autonomy envelope — объяснить как control mechanism — **приоритет M**
**Проблема:** «всё в конверте LUDA» новичку не значит ничего.
**Решение:** визуальный компонент автономии + tooltip:
```
AUTONOMY
L0 ─ L1 ─ [L2] ─ L3
              ↑ current
Policy ceiling: L3
```
Tooltip: «LUDA autonomy envelope — максимальный уровень автономии агента, разрешённый политикой системы». LUDA перестаёт быть внутренним термином, становится понятным **security/control mechanism**.
**Где:** везде, где автономия — Паспорт §7, шапка прогона §3, инспектор узла §6. В брендките бар «автономия vs конверт» уже есть — дополнить шкалой L0–L3 + current-маркером + policy-ceiling + tooltip.
**Как:** компонент `AutonomyEnvelope(current, ceiling)`; при `current>ceiling` — крит-состояние (блок запуска, ссылка в Безопасность).

### D6 · Меньше glass в рабочих зонах — **приоритет S**
**Проблема:** glassmorphism (`blur(16px)`, `rgba(..,.05)`) снижает плотность и читаемость в сложном workflow.
**Решение:** два уровня поверхностей — **glass наверху** (Обзор/лендинг/hero/отдельные карты), **плоский control-plane внутри** (Канва/Пульт/таблицы): сплошные поверхности, чёткие границы, выше плотность.
**Где:** рабочие экраны §3/§6 — плоско; §2/дашборд — glass ок.
**Как:** в токенах ввести `--surface-glass` (dashboard) и `--surface-flat` (workflow); правило применения — в UI-kit.

## 3. Что сознательно НЕ трогаем (сильное ядро)

- Explainable-валидация — **усиливаем видимость** (D4), логику не меняем.
- Operational dashboard как control plane — сохраняем, добавляем outcome-слой (D1).
- Цветовая семантика (HITL amber / error red / ok green / workflow indigo) — эталон.
- Dark-enterprise, Inter+JetBrains Mono, маскот Эйп, «язык ожидания».

Ревью прямо просит: **не добавлять функций сейчас** — только полировка ядра по истории §1.

## 5. Product clarity — репозиционирование в UI

Чтобы поднять «простоту освоения» и «product clarity»:
1. **Outcome-язык** вместо узлового везде (D1): «Оценка подрядчика · готово к исполнению», не «7 nodes · valid».
2. **Объяснённые термины** (D5): LUDA/автономия/HITL/волны — с tooltip при первом появлении.
3. **История как навигация** (§1): прогресс-шаги вместо голого дерева вкладок для нового пользователя.
4. **Онбординг золотого пути** (из ABOP_SCREENS): один сквозной сценарий «собрал → проверил → увидел волны → запустил → подтвердил → результат → аудит».
