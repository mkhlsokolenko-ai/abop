# Рецепты данных в APE (`/data`) — полное руководство

**Зачем это нужно.** Агент потребляет данные не как человек. Человеку можно дать «грязный»
CSV — он глазами разберётся. Агент же на сыром файле начинает угадывать формат, путается в
запятых/пробелах, галлюцинирует по числам. **Рецепт данных** — это декларативное описание
(обычный JSON), как превратить сырой источник в **чистый типизированный слой** для агента:
с проверенными типами, валидацией, маскировкой персональных данных и происхождением
(provenance).

Поток один и тот же: **источник → маппинг+типизация → правила → canonical JSON → запрос**.
Рецепт пишет **человек** (ты), агент только потребляет результат.

---

## 1. Четыре команды

```
/data new <имя>          создать шаблон рецепта ~/.ape/recipes/<имя>.json
/data run <имя>          применить рецепт: источник → canonical-хранилище
/data query <entity> [k=v]   прочитать чистые данные (с фильтром)
/data recipes            список всех рецептов
```

Рецепты лежат в `~/.ape/recipes/*.json`, готовые данные — в `~/.ape/data/<entity>.jsonl`.

---

## 2. Быстрый старт за 4 шага

Допустим, есть выгрузка продаж `sales.csv`:

```
order_id,email,total,created_at
1001,anna@example.com,"1 250,50",2026-08-01
1002,BORIS@Example.com,"3 000",2026-08-02
1003,badrow@x.com,-50,2026-08-03
1004,dina@example.com,"999,99",2026-08-04
```

Проблемы: деньги по-русски (пробел + запятая), почта в разном регистре, есть мусорная строка
с отрицательной суммой.

**Шаг 1. Создай шаблон:**

```
/data new sales
```

**Шаг 2. Отредактируй `~/.ape/recipes/sales.json`** (любым редактором):

```json
{
  "recipe": "sales",
  "version": 1,
  "source": { "kind": "csv", "path": "C:\\Users\\Иван\\data\\sales.csv" },
  "entity": "transaction",
  "map": {
    "id":       { "col": "order_id" },
    "customer": { "col": "email", "cast": "lower" },
    "amount":   { "col": "total", "cast": "money" },
    "date":     { "col": "created_at" }
  },
  "rules": [
    { "assert": "amount > 0" },
    { "pii_mask": ["customer"] }
  ],
  "emit": { "schema": "transaction", "schema_version": "1.0", "ttl_sec": 86400 }
}
```

**Шаг 3. Применить:**

```
/data run sales
→ transaction → 3 записей (отброшено 1)
```

Что произошло: `"1 250,50"` стало числом `1250.5`, почта — в нижнем регистре и замаскирована
(`an***@example.com`), строка с `-50` отброшена правилом `amount > 0`, к каждой записи добавлены
схема, provenance (какой рецепт/источник/строка/время) и ttl.

**Шаг 4. Читать чистые данные:**

```
/data query transaction
/data query transaction date=2026-08-02
```

Получаешь готовый типизированный JSON — без ручного парсинга.

## 3. Структура рецепта (справочник)

Рецепт — JSON из четырёх блоков.

### `source` — откуда брать
```json
"source": { "kind": "csv",  "path": "путь/к/файлу.csv" }
"source": { "kind": "json", "path": "путь/к/файлу.json", "root": "items" }
```
- `kind`: `csv` или `json` (MVP).
- `path`: путь к файлу (Windows-пути с двойными слэшами `\\` или прямыми `/`).
- `root` (только json): ключ, под которым лежит массив записей. Если файл — сразу массив, не нужен.

### `entity` — как назвать сущность
Строка, например `transaction`, `customer`, `ticket`. Под этим именем данные лягут в
`~/.ape/data/<entity>.jsonl` и по нему же делается `/data query <entity>`.

### `map` — что во что превратить
Для каждого целевого поля указываешь источник и (опц.) тип:
```json
"map": {
  "id":       { "col": "order_id" },              // взять как есть
  "amount":   { "col": "total", "cast": "money" }, // с приведением типа
  "customer": { "col": "email", "cast": "lower" },
  "channel":  { "const": "web" }                   // константа для всех записей
}
```
**Касты (`cast`):**
- `money` — чистит `₽`, пробелы, меняет запятую на точку → число (`"1 250,50"` → `1250.5`).
- `int` — целое число.
- `lower` — строка в нижнем регистре.
- без `cast` — значение как есть (строка/дата).

> Обязательно сделай поле `id` — по нему идёт дедупликация при чтении (см. §5).

### `rules` — что проверить и почистить
Список правил, применяются по порядку к каждой записи:
```json
"rules": [
  { "assert": "amount > 0" },        // не прошло → строка отбрасывается
  { "assert": "date != ''" },
  { "pii_mask": ["customer", "phone"] }  // замаскировать персональные поля
]
```
- `assert`: выражение `поле ОПЕРАТОР значение`. Операторы: `>` `<` `>=` `<=` `==` `!=`.
  Сравнение с числом — числовое, со строкой — строковое.
- `pii_mask`: список полей для маскировки. Почта → `an***@example.com`, прочее → `ив***`.

### `emit` — как пометить результат
```json
"emit": { "schema": "transaction", "schema_version": "1.0", "ttl_sec": 86400 }
```
- `schema` / `schema_version` — тип и версия записи (агент понимает, что читает).
- `ttl_sec` — «срок годности» данных в секундах (86400 = сутки).

## 4. Что получается на выходе (canonical-запись)

Каждая строка `~/.ape/data/transaction.jsonl`:
```json
{
  "id": "1001",
  "customer": "an***@example.com",
  "amount": 1250.5,
  "date": "2026-08-01",
  "schema": "transaction",
  "schema_version": "1.0",
  "provenance": { "recipe": "sales", "source": "csv:.../sales.csv", "row": 0, "fetched_at": 1788372048.5 },
  "ttl_sec": 86400
}
```
Типы приведены, PII замаскирован, известно происхождение — это и есть «данные для машины».

## 5. Чтение и повторный прогон

```
/data query transaction                 все записи
/data query transaction id=1002          фильтр по точному совпадению
/data query transaction date=2026-08-02
```

- Хранилище **append-only** (только дозапись).
- При чтении идёт **дедуп по `id`** — остаётся последняя запись с этим id. Поэтому повторный
  `/data run` с обновлённым источником не плодит дубли: свежие записи вытесняют старые по id.

---

## 6. Как это использует агент

В `/agents` у агентов есть инструмент **`data_query`** — они берут чистый слой прямо в своём
цикле рассуждений, без парсинга файлов:

```
/agents посчитай суммарную выручку по transaction за август и назови топ-3 клиентов
```

Агент дёрнет `data_query(entity="transaction", ...)`, получит типизированный JSON и будет
считать по нему, а не по сырому CSV.

---

## 7. Типичные ошибки

| Симптом | Причина / решение |
|---|---|
| `Ошибка рецепта: ... No such file` | неверный `path`. На Windows экранируй слэши: `C:\\Users\\...` |
| Отброшено больше строк, чем ждал | слишком строгий `assert`, или `money`/`int` не распарсил значение (стало `null`) → проверь исходные данные |
| Суммы стали `null` | в колонке не число; проверь `cast` и содержимое ячейки |
| Дубли в `/data query` | у записей нет уникального `id` в `map` — добавь поле `id` |
| Почта/телефон видны | добавь поле в `pii_mask` |

---

## 8. Полный цикл одной строкой

```
/data new orders      → правишь ~/.ape/recipes/orders.json → /data run orders → /data query order
```

Это учебная обкатка паттерна Data Plane: **adapter → canonical → contract → query → agent**.
Тот же принцип масштабируется на боевые источники (почта, трекеры, БД) — меняется только
адаптер источника, остальное (маппинг, правила, запрос агентом) остаётся.
