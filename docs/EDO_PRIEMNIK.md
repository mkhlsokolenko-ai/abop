# Приёмник ЭДО: Диадок и СБИС — как входящая первичка попадает в конвейер

> План, 14.11.2026. Напоминание владельца: «подгрузка данных из ЭДО Диадок и СБИС». Сценарий
> ещё с 23.10: по ЭДО приходят счёт-фактуры и УПД по форме, но не разносятся автоматически по
> счетам и не исполняются проводками. Здесь — что уже подтверждено, чего ждём, и как приёмник
> встаёт в конвейер первички (ADR-075…078), когда доступы придут.

## 1. Что уже подтверждено техпроверкой 28.10 (docs/SS_TEHPROVERKA_2026-10-28.md)

| вопрос | ответ | что нужно |
|---|---|---|
| Забрать входящие из их Диадока | **да**, штатный HTTP API Контура; сертификат для **чтения** не нужен | заявка на интеграционное решение (наша сторона), `boxId` их ящика, доступ пользователю |
| Записать результат в их облачную 1С | **да**, штатный OData — ничего в базу не устанавливаем | адрес приложения, служебный пользователь с ролью `УдаленныйДоступOData`, тестовая база |
| Создать непроведённый и провести отдельно | **да**, у документа есть `Post`/`Unpost` | решение владельца о границе — принято: **ADR-078** (запись до проводки разрешена, проводка — человека) |
| Ключ дубля | **да**, это данные | (организация, контрагент, тип, номер, дата, сумма) — уже в правилах, раздел 11 техпроверки |

Чего ждём от «Статского Советника» (письменно, отправлено): интеграционное решение Контура,
ИНН организации-владельца ящика, доступ; **10–20 реальных входящих УПД — XML как приходит из
Диадока + 2–3 печатных PDF того же типа**; письменный ответ о проведении (создаём непроведённым
или сразу проведённым — расхождение Елены и Дмитрия снято на встрече 13:38, но без бумаги не
начинаем, ADR-078).

**Про СБИС — честно: техпроверки не было.** У СБИС (СБИС ЭДО, company.sbis.ru) тоже есть
штатный HTTP API (аутентификация по логину/паролю или сертификату, метод выгрузки входящих
документов с бинарниками и XML-структурой). До проверки на живом контуре считаем его
**гипотезой того же класса**: «забрать входящие штатным API без установки чего-либо».
В план приёмника встраивается с теми же границами, но статус — «не проверено», и это
названо, а не спрятано.

## 2. Куда встаёт приёмник: лестница приёма (ADR-075), а не отдельный конвейер

```
Диадок API ──►  XML (УПД/счёт-фактура) ──► структурный слой ──► тип документа (doc_type_rule) ──►
СБИС API  ──►  XML                        │                     поля с уверенностью (ADR-076)   │
выгрузка XML кнопкой (fallback)           └─► печатная форма PDF ──► текстовый слой ──► OCR только сканов
                                                                                    └─► 1С: непроведённый (OData, ADR-078)
```

1. **Приёмник — источник Data Plane**, как OData-коннектор 1С: рецепт `edo-diadoc` / `edo-sbis`
   тянет входящие (метаданные + XML + бинарники) в сущность `эдодокумент`. Провенанс обязателен:
   каждый документ несёт, откуда взят (ящик, дата загрузки, id в системе ЭДО).
2. **XML — первый слой**: для УПД/счёт-фактуры структура уже машина-читаема, распознавание не
   нужно вовсе (pdf-inspector-подход: сначала понять, что внутри, потом решать, что требует
   тяжёлой обработки). OCR включается только для печатных форм без XML-дорожки.
3. **Классификация и поля** — по существующему конвейеру: тип документа объявлен правилом
   (`doc_type_rule`), уверенность — свойство ПОЛЯ, «проверьте 3 из 24» (ADR-076), правка
   человека сохраняется эталоном.
4. **Разнос в 1С** — по ADR-078: создаём **непроведённый** документ через OData с пометкой
   в комментарии, проводка — отдельное решение человека (HITL, кнопка «Провести»).
5. **Дубль** — ключ (организация, контрагент, тип, номер, дата, сумма): повтор из ЭДО не
   плодит вторую запись в 1С, а прикрепляется к уже созданной.

## 3. Что строим, когда придут доступы (порядок работ)

| # | работа | на чём стоит |
|---|---|---|
| 1 | Адаптер `edo-diadoc` в коннекторе (GET входящих, boxId, пагинация, бинарники в MinIO) | системы_store + рецепт Data Plane; формат — по документации Контура, первый запрос — на тестовом ящике |
| 2 | Рецепт `эдодокумент` → сущность с провенансом | Data Plane, паттерн doc1c/ref1c |
| 3 | Дорожка XML: поля УПД → `doc_type_rule` + уверенность полей | конвейер первички, ADR-075/076 |
| 4 | Разнос: непроведённый в 1С + HITL «Провести» | ADR-078, OData Post/Unpost |
| 5 | Fallback «выгрузка XML кнопкой» — тот же приёмник на файлах | один путь приёма после кнопки: XML попадает в ту же сущность |
| 6 | СБИС-адаптер — после живой проверки их API | тот же приём, другой транспорт |

**Fallback, который ничего не блокирует** (сказано Елене на техпроверке): пока идёт заявка на
интеграционное решение Контура, документы выгружаются кнопкой из Контура — XML-дорожка и разнос
проверяются на этих файлах, а приёмник API потом лишь заменяет источник.

## 4. Что НЕ делаем

Не ставим ничего в базу клиента и не заводим там объектов: только чтение ЭДО по API и запись
непроведённых в 1С через штатный OData служебным пользователем, который заказчик отключает
одним движением. Не распознаём сканы «на всякий случай»: OCR заказан только там, где XML-дорожки
нет, и только за распознанное (ADR-074).
