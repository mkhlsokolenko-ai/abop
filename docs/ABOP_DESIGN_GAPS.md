# ABOP — Расхождения дизайн-системы и требования к дизайнеру

**Что это:** gap-анализ готовой дизайн-системы (брендкит `docs/brand/`) относительно PRD v1.1 (что нужно) и реальной реализации LUDA (что уже работает во фронте). Указывает: **каких функций нет** в дизайн-системе, **где они логически должны жить** в UI/UX, **как настраиваются и сохраняются**. Выдаётся как требования дизайнеру по улучшению UI/UX и user-flow.
**Источники:** брендкит ABOP (Brand & Motion Kit); PRD `ABOP_PRD.md`; экраны `ABOP_SCREENS.md`; kit `ABOP_DESIGN_KIT.md`; реализация LUDA — компоненты MIRA v3 (сайдбар-маршрут, канва, паспорт, Пульт HITL, коннекторы, формы, модалки type-to-confirm, слайдер прав СВОД, помощь-ассистент).
**Статус:** v1.0.

---

## 0. Резюме за 30 секунд

Брендкит ABOP — **сильный, но узкий**: он закрывает бренд и «язык ожидания» (лого, маскот Эйп, спиннеры, прогресс-бары, тайминги), но это **не полная UI-система**. В нём НЕТ функционального слоя: навигации, форм и контролов, таблиц, модалок, карточек-паттернов, темы light, токен-системы, состояний пусто/ошибка, настроек и **персистентности**.

**Всё это уже реализовано в LUDA (MIRA v3).** Требование: **не рисовать функциональный слой с нуля — перенести его из LUDA MIRA v3 и одеть в бренд ABOP** (dark-first индиго/Эйп). Ниже — пофункционально: чего нет, где место, как настраивать/сохранять.

## 3. Как настраивается и сохраняется — модель персистентности (ключевое)

Дизайнеру важно нарисовать **правильную модель сохранения** — где что живёт:

| Слой данных | Что | Контрол в UI | Где сохраняется | Ограничения |
|---|---|---|---|---|
| **Безопасность навыка** | `mode/egress/cite` | **не редактируется** (read-only чип) | в ядре (`SKILL_SAFETY`) | это инвариант навыка, юзер не крутит |
| **Права агента** | автономия/HITL-точки | слайдер прав (§6) | спека агента (стор) | **≤ DeploymentContract LUDA** — потолок залочен, ослабление → мини-аудит |
| **Рецепт данных** | source/map/rules/emit | форма (§5) | файл рецепта (сервер), версионируется | декларатив, без кода |
| **Собранный агент** | поток/роли/навыки | канва автосейв (§6) | стор агентов | draft → prod через type-to-confirm |
| **Прогон** | волны/доска/вердикт | — (исполнение) | сервер + `cost_journal` | доска = память ПРОГОНА (per-run) |
| **Долговременная память** | находки | — (пишет агент) | `longterm` + TTL | забывание по критичности |
| **Настройки среды** | модели/подключения | формы (§8) | серверный конфиг | роль-гейт (admin) |
| **UI-предпочтения** | тема, активная вкладка, фильтры | тумблер/URL | localStorage / URL | не чувствительное |

**Правило для дизайнера:** каждый экран с вводом обязан показывать **состояние сохранения** (сохранено/несохранённые изменения/ошибка) — как автосейв-чип канвы LUDA. Необратимое (В прод, Вывести, отправка HITL) — только через явное подтверждение (type-to-confirm / dry_run+approve).

## 4. Улучшения user-flow (где рвётся сейчас → что добавить)

1. **Настройка безопасности негде.** По PRD права/безопасность — центральны, но в брендкит-макетах нет места их крутить. → **Слайдер прав в инспекторе канвы** (§6) с мгновенным семафор-фидбеком на узле; безопасность навыка — read-only чип с раскрытием «почему».
2. **Рецепт данных → агент рвётся.** Создал рецепт (§5) — но не видно, как он попадает в агента. → В палитре канвы (§6) рецепты/сущности как перетаскиваемые источники; связь `data_query` узла с сущностью.
3. **Сборка → запуск → результат.** Собрал агента (§6) → `[Запустить]` → §3 Пульт → результат → §7 Паспорт. Нарисовать этот путь **сквозным** (золотой путь), с сохранением агента между шагами.
4. **Переоткрытие прогона.** Прогон закрылся — где его перечитать? → Обзор (§2) «Последние» + архив; клик → §3 в read-режиме.
5. **HITL переживает перезагрузку.** Очередь подтверждений не должна теряться при F5. → HITL-очередь персистится (сервер), бейдж в сайдбаре, undo-окно на решении.
6. **Тема и предпочтения не сохраняются.** → тумблер темы + запоминание (localStorage); дефолт dark (бренд).
7. **«Ожидание называет чего ждём» — применить везде.** Принцип брендкита («волна 3/5», не «Загрузка…») распространить на ВСЕ асинхронные места (рецепт-preview → «Сканирование · 500 записей», сохранение → чип).

## 5. Требования к дизайнеру (приоритизировано)

**M (MVP, блокирует прототип):**
1. **Токены** `tokens.css` — dark+light, вынести палитру брендкита в переменные (роли: bg/surface/brand/семафор/text). Основа всего.

3. **Атомы форм**: input/select/textarea/checkbox/**слайдер прав**/поиск-фильтр — из LUDA MIRA v3 в бренд ABOP.
4. **Семафор-чип безопасности** (`mode/egress/cite`) как компонент (read-only, раскрытие).
5. **Состояния** пусто/ошибка для каждого экрана (загрузка уже есть в брендките).
6. **3 MVP-экрана** целиком (§3 Пульт, §4 Навыки, §5 Данные) со всеми состояниями и в 2 темах.

## 7. ❗ Критичный пробел: вкладка «Безопасность» (ИБ) — вернуть из LUDA 1

**Что не так.** В прототипе безопасность есть только **на уровне навыка** (`mode/egress/cite` на карточке) — это микро-уровень «что навык умеет». Но в LUDA 1 была отдельная **вкладка «Настройка ИБ»** (admin-gated, маршрут `#security`) — макро-уровень governance СРЕДЫ: кто что может, аудит ИБ, ре-аттестация. В ABOP она **пропала**, хотя для регулируемого периметра (ФСТЭК/ФЗ-152/ДСП) она обязательна. Подтверждено: `RBAC / политика доступа / эскалация / ре-аттестация / аудит-лог / scope` — 0 упоминаний в прототипе.

**Разница уровней (обязательно развести в UI):**
- **Безопасность навыка** (есть) — `mode/egress/cite`, read-only чип. Что навык может в принципе.
- **Безопасность среды** (нет) — КТО (роли/люди) что может; scope агента ⊆ прав создателя; аудит ИБ; ре-аттестация. Это вкладка Безопасность.

**Требование: добавить вкладку «Безопасность»** — отдельный пункт маршрута (admin-gated, после Настроек), перенести структуру из LUDA 1 (`SVOD_SECURITY_SPEC`). Секции:

| Секция | Содержание | Как настраивается | Как/где сохраняется |
|---|---|---|---|
| **Политика доступа (RBAC)** | таблица `роль → права` (developer/operator/viewer/admin) + YAML side-by-side | admin редактирует таблицу/YAML | серверный конфиг RBAC; версия + кто менял |
| **Периметр агента (scope)** | инвариант «scope агента ⊆ права создателя»; 2 класса агентов (read-only / действующий) | не редактируется — проверяется при сборке/деплое | вычисляется из спеки агента + роли создателя |
| **Модель эскалации** | когда действие уходит человеку/выше (дисижн-движок, порог) | пороги/правила (admin) | конфиг эскалации |
| **Ре-аттестация** | периодический пересмотр прав и прод-агентов (срок, очередь) | расписание + очередь на пересмотр | стор ре-аттестаций + напоминания |
| **Аудит-лог ИБ** | кто/что/когда, хэш-цепочка (неизменяемый) | read-only + фильтры + экспорт | серверный аудит-стор (append-only) |

**Где в UI:** отдельная вкладка `security` в сайдбаре (admin-gated, видят только admin/оператор безопасности), бейдж при нарушениях (scope > конверт, просроченная ре-аттестация). **User-flow:** нарушение конверта в прогоне (§3) или превышение автономии (§7 Паспорт) — ссылка «разобрать в Безопасности».

**Связь с ядром:** RBAC/роли — из Keycloak realm (уже есть: developer/operator/viewer/admin); scope-инвариант — из `SKILL_SAFETY` + автономии агента ≤ `DeploymentContract` LUDA; аудит-лог — из `cost_journal`/аудит-следа прогонов. То есть данные уже есть — нужен экран управления и просмотра.

**Приоритет:** S (следующий за MVP-экранами) — governance-вкладка отличает ABOP как «среду для регулируемых», это часть рва. Без неё продукт функционально неполон для целевого периметра.
