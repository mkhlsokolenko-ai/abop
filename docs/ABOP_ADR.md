# ABOP — Architecture Decision Records

**Продукт:** ABOP (Agent-Based Orchestration Platform) — рантайм исполнения агентов
**Версия:** 0.3
**Статус пакета:** к утверждению
**Связанные документы:** `ABOP_ARD.md`, `../cli/README.md`, LUDA v2 `ADR.md`/`AOP.md`

Формат записи (Nygard): контекст (какие силы давят) → решение → последствия, включая принятую цену.

Записи, помеченные **[переворот]**, отменяют модель «один процесс = один агент» (Process Agent Spec / VRATA v1) и связанные с ней допущения.

## Продукт и позиционирование

### ADR-001. ABOP — рантайм исполнения, продуктизация LUDA v2, отдельный продукт и репозиторий **[переворот]**

**Статус.** Принято.

**Контекст.** В прежней модели агент был неотделим от процесса: `Process Agent Spec` описывал «агента для закрытия месяца». LUDA v2 расщепила агента и процесс (Role Family, Skill, Capability, Module, эфемерные воркеры) — спецификация «один агент = один процесс» в этой модели не инстанцируется. При этом рантайм исполнения агентов — самостоятельная ценность: заказчику нужно не только знать *можно ли* запускать агента (это диагностирует LUDA), но и *чем* его запускать в регулируемом периметре.

**Решение.** ABOP развивается как самостоятельный продукт и репозиторий — рантайм исполнения агентов, продуктизация LUDA v2 и эволюция VRATA на паттернах openclaw (Gateway / Channel / Tool-Skill / pairing-approval HITL / security-first). ABOP **не является самим LUDA**: LUDA — аудитор готовности (диагноз), ABOP — исполнитель (рантайм). Связь между репозиториями — только версионированные схемы контрактов.

**Последствия.** Отдельный биллинг, релизный цикл, техдолг и CI. Дублирование части кода со sLAVA/LUDA принимается сознательно как цена независимости релизов (см. ADR-021). Цена принята: рантайм продаётся и эволюционирует отдельно от диагностики.

### ADR-019. APE (учебный CLI) — полигон принципов; прод-ABOP наследует Agent Plane

**Статус.** Принято.

**Контекст.** Отрабатывать архитектуру рантайма сразу в регулируемом периметре (ФСТЭК/ФЗ-152) — дорого и рискованно: любая ошибка касается продуктивных систем заказчика. Нужна безопасная площадка, где обкатываются принципы (агенты/волны/Blackboard/tools/Data Plane) без доступа к реальному контуру.

**Решение.** Учебный CLI `ape` (`cli/ape.py`) — безопасный полигон, где реализуются и проверяются ПРИНЦИПЫ и АРХИТЕКТУРА Agent Plane. Прод-ABOP **наследует** обкатанный в `ape` Agent Plane: онтологию Семья→Роль→Навык, оркестрацию волнами, Blackboard, единый контракт вызова. Готовое в `ape` портируется, а не переписывается.

**Последствия.** Два контура (учебный и прод) с общей идеологией, но разными периметрами. Требуется дисциплина обратного переноса: принцип считается принятым, только если он отработан в `ape`. Учебный контур не имеет доступа к продуктивным данным заказчика — граница жёсткая.

### ADR-020. Оркестрация волнами (fan-out/fan-in), а не свободный цикл агента **[переворот]**

**Статус.** Принято.

**Контекст.** Свободный ReAct-цикл одиночного агента («думай → действуй → наблюдай, пока не решишь остановиться») недетерминирован по числу шагов, стоимости и траектории. В регулируемом периметре нужен аудируемый ход исполнения: кто, когда, на основании чего действовал. Свободный цикл этого не даёт — он воспроизводит модель «один агент делает всё сам».

**Решение.** Исполнение — оркестрация **волнами**: fan-out (диспетчер раскидывает задачи по stateless-воркерам) → барьер → fan-in (синтез результатов). Следующая волна видит доску предыдущей. Диспетчер, а не сам агент, решает границы волны. Свободный цикл внутри одного узла ограничен и подотчётен.

**Последствия.** Часть задач, естественных для свободного цикла, приходится раскладывать на волны — это дороже в проектировании потока. Взамен каждый прогон воспроизводим и аудируем: ход зафиксирован волнами и доской, а не скрыт во внутреннем цикле модели.

## Онтология агентов

### ADR-005. Онтология Семья→Роль(член)→Навык, роли переиспользуют навыки **[переворот]**

**Статус.** Принято.

**Контекст.** Модель «один процесс = один агент» плодит монолитных агентов, дублирующих одни и те же способности. Навык «сверить числа с источником» переписывается в каждом агенте. Нет единицы переиспользования способностей между агентами.

**Решение.** Онтология Role Family: **Семья** (домен компетенций) → **Роль/член семьи** (конкретный исполнитель) → **Навык** (атомарная способность с телом). Реализовано в `cli/ape.py`: 10 семей, 37 навыков с телами. Роли **переиспользуют** навыки — один навык подключается к разным ролям. Агент собирается из роли и её навыков, а не пишется целиком.

**Последствия.** Способности становятся общим ресурсом, а не собственностью агента. Требуется реестр навыков и дисциплина их версионирования. Один навык, изменённый ради одной роли, затрагивает все роли, что его переиспользуют — нужен контроль совместимости.

### ADR-006. Два яруса навыков: глобальные (CLI) vs специализированные (в семьях)

**Статус.** Принято.

**Контекст.** Часть навыков универсальна (нужна любой роли: базовый tool-calling, работа с доской), часть — узко доменная (нужна только конкретной семье). Держать всё в одном плоском списке раздувает контекст каждого агента и стирает границу «общее/доменное».

**Решение.** Два яруса навыков: **глобальные** — доступны на уровне CLI/платформы любой роли; **специализированные** — живут внутри семей и подключаются только их ролям. Ярус определяет область видимости и владения навыком.

**Последствия.** Ясная граница ответственности: глобальный навык меняет платформенная команда, специализированный — владелец семьи. Риск дублирования на стыке (доменный навык, ставший общим) разрешается повышением яруса через явное решение, а не копированием.

### ADR-008. Progressive disclosure навыка: use_skill грузит полное тело по требованию

**Статус.** Принято.

**Контекст.** Тела 37 навыков не помещаются в системный промпт без раздувания контекста и потери фокуса модели. Но агент должен знать, какие навыки существуют, чтобы выбрать нужный.

**Решение.** Progressive disclosure: в системном промпте — только **карточки** навыков (имя, назначение, метаданные безопасности). Полное **тело** навыка подгружается по требованию вызовом `use_skill` в момент применения. Модель видит каталог, но грузит инструкцию только когда решила её исполнять.

**Последствия.** Системный контекст остаётся компактным независимо от числа навыков. Цена — дополнительный шаг загрузки тела перед исполнением и зависимость от того, что карточка достаточно информативна для выбора. Качество карточек становится критичным.

### ADR-010. Handoff через доску (эстафета роль↔семья), оркестратор поднимает stateless-воркерами

**Статус.** Принято.

**Контекст.** Передача работы между ролями/семьями через прямой вызов «агент зовёт агента» создаёт связность, скрытое состояние и цепочки, которые невозможно прервать и переиграть. Нужна эстафета без прямой связи исполнителей.

**Решение.** Переключение исполнителя — через механизмы `use_skill` / `become` / `handoff`, где **handoff идёт через доску**: сдающий кладёт результат/задачу на Blackboard, оркестратор поднимает принимающего **stateless-воркером**. Воркеры не держат состояние между волнами — вся преемственность через доску.

**Последствия.** Исполнители развязаны: любой воркер эфемерен, взаимозаменяем, перезапускаем. Состояние прогона целиком на доске — единая точка восстановления и аудита. Цена — вся преемственность обязана проходить через доску (нельзя «передать в уме»), что требует дисциплины фиксации.

## Данные (Data Plane)

### ADR-002. Три плоскости: Agent / Tool / Data Plane

**Статус.** Принято.

**Контекст.** Смешение «кто думает», «чем делает» и «на каких данных» в одном слое делает агента монолитом: смена источника данных задевает логику, смена инструмента задевает данные. Нужно разделение ответственности.

**Решение.** Три плоскости. **Agent Plane** — агенты, харнесс, оркестрация (ReAct, волны, синтез, Blackboard). **Tool Plane** — примитивы и рецепты под JWT (`run_python`, `web_fetch`, `data_query`…). **Data Plane** — агент-нативный слой данных (Source Adapters → Canonical Schemas → Data Contracts). Рецепт = Agent Plane (кто думает) + Tool Plane (чем делает) + Data Plane (на каких данных).

**Последствия.** Каждая плоскость эволюционирует независимо: новый источник — только Data Plane, новый инструмент — только Tool Plane. Цена — три контракта на стыках вместо одного и обязательность прохождения данных через `data_query`, а не «как удобно».

---

### ADR-003. Data Plane — агент-нативный слой (Source Adapter→Canonical Schema→Data Contract→data_query)

**Статус.** Принято.

**Контекст.** Агент потребляет данные не как человек. Человеку системы отдают данные «для глаз» — HTML, UI, PDF, разрозненные API. Агенту нужен типизированный, самоописываемый, стабильный JSON с провенансом и свежестью. Скрейпить человеческие интерфейсы каждым агентом — хрупко, дорого, недетерминированно.

**Решение.** Data Plane — цепочка **Source Adapter** (источник→нормализация: mail, Jira, CRM, БД, файлы-OCR) → **Canonical Schema** (единая типизированная сущность: Email, Issue, Customer, Document…) → **Data Contract** (стабильная выдача: поля, типы, провенанс, свежесть) → **`data_query`** (агент берёт данные ТОЛЬКО так). Каждая запись самоописываема: `schema`+`schema_version`, `id`, `provenance`, `ttl`, нормализованные `refs`. Часть слоя уже есть в LUDA (`connectors/`, `canon/`, `spec/`) — переиспользуется, а не пишется заново.

**Последствия.** Агенты работают с предсказуемым JSON, а не парсят форматы «для глаз» — устойчивость и воспроизводимость. Цена — обязательный слой адаптеров и канонических схем: новый источник требует адаптера и схемы до того, как агент его увидит.

### ADR-004. Data Recipe декларативен, пишет доменный эксперт, без исполняемого кода, валидируется схемой

**Статус.** Принято.

**Контекст.** Если для подключения нового источника нужен разработчик, Data Plane не растёт. Кроме того, рецепт устанавливается в периметр заказчика и обращается к продуктивным системам — произвольный исполняемый код в такой позиции не пройдёт службу ИБ.

**Решение.** Адаптер источник→canonical описывается **Data Recipe** — декларативным версионируемым артефактом (YAML/JSON) в стиле LUDA **VerticalPack**: `source` (адаптер+фильтр), `entity`, `map` (маппинг полей без кода), `rules` (assert/pii_mask), `emit` (схема+ttl). **Исполняемого кода нет.** Рецепт **валидируется схемой** (нельзя сломать канон), пишет его **доменный эксперт**. Не путать с *Agent Recipe* (плейбук агент+tools+LLM).

**Последствия.** Data Plane растёт силами доменных экспертов, а не только разработчиков — self-serve. Часть источников не выразить декларативно; они реализуются как расширения с ревью и по накоплении пересматриваются как расширение языка рецептов. Нужен строгий валидатор с понятными сообщениями — эксперт не читает трассировки.

## Память

### ADR-009. Blackboard — рабочая память прогона (event-sourced), воркеры stateless

**Статус.** Принято.

**Контекст.** При оркестрации волнами и stateless-воркерах нужна общая память прогона без конфликтов записи, потерь и вопроса «кто чистит». Прямая передача состояния между воркерами воспроизводит связность, от которой уходим.

**Решение.** **Blackboard** — рабочая память одного прогона, **event-sourced**: append-only журнал (facts / notes / claims / snapshots), состояние = свёртка событий, snapshot-компакция. `claim` исключает дубли. Воркеры **stateless** — всё состояние на доске, ничего в воркере между волнами.

**Последствия.** Нет конфликтов записи и потерь; прогон восстановим из журнала и полностью аудируем. Цена — всё значимое обязано попасть на доску append-only (нельзя держать «в уме» воркера), плюс механика компакции снапшотов для контроля роста журнала.

### ADR-011. Долговременная память с ЗАБЫВАНИЕМ по TTL от критичности

**Статус.** Принято.

**Контекст.** Blackboard — память одного прогона; между прогонами нужна долговременная память. Но бессрочное хранение всего в регулируемом периметре нарушает принцип минимизации данных (ФЗ-152) и раздувает хранилище. Разные факты имеют разный законный срок жизни.

**Решение.** Долговременная память с **ЗАБЫВАНИЕМ по TTL, производным от критичности** записи: `operational` — 7 дней, …, `regulatory` — 5 лет (retention банков/корпораций), `permanent` — ∞. По истечении TTL запись забывается автоматически. Критичность задаёт срок — забывание встроено, а не опционально.

**Последствия.** Хранилище соответствует принципу минимизации и требованиям retention «из коробки». Цена — обязательная классификация записи по критичности при сохранении (иначе TTL не назначить) и риск потери факта, если критичность занижена. Классификация становится частью контракта записи в память.

## Безопасность и governance

### ADR-007. Безопасность — метаданные навыка (mode · egress · cite)

**Статус.** Принято.

**Контекст.** Безопасность, привязанная к агенту целиком, слишком груба: агент из десятка навыков получает права по самому опасному из них. Нужна гранулярность на уровне способности, а не исполнителя.

**Решение.** Свойства безопасности — **метаданные навыка**: `mode` (read / write / action), `egress` (internal / external), `cite` (обязательность цитирования источника). Права определяются набором подключённых навыков, а не агентом в целом. Метаданные видны в карточке навыка (ADR-008) до загрузки тела.

**Последствия.** Точный контроль: роль без `action`-навыков физически не может писать во внешние системы. Каждый навык обязан нести корректные метаданные — ошибка в метаданных навыка = дыра в периметре. Ревью навыка включает ревью его безопасности.

### ADR-014. Действия во внешние системы — только dry_run + подтверждение человека (HITL)

**Статус.** Принято.

**Контекст.** Автономное действие агента во внешней продуктивной системе (запись в Jira, отправка почты, удаление) необратимо и в регулируемом периметре недопустимо без человека. При этом полный запрет действий обесценивает рантайм.

**Решение.** Любой навык с `mode: action` и `egress: external` исполняется в два такта: **`dry_run`** (агент показывает, что именно сделает) → **подтверждение человека (HITL)** → реальное исполнение. Без подтверждения действие не выходит наружу. Read/write внутри периметра могут идти автоматически; отсылка/критичные/удаление — под человеком.

**Последствия.** Необратимые операции всегда проходят через человека — периметр защищён от автономной ошибки. Цена — латентность и участие оператора на каждом внешнем действии; поток проектируется так, чтобы точки HITL были осмысленны, а не на каждом шаге.

### ADR-015. Внешний контент — anti-injection + PII-маскирование на границе

**Статус.** Принято.

**Контекст.** Данные из внешних источников (письма, веб, документы) могут содержать инструкции, адресованные модели (prompt injection), и персональные данные. Исполнение инструкций из данных = захват агента; вынос ПДн наружу = нарушение ФЗ-152.

**Решение.** Внешний контент проходит через два фильтра: **anti-injection** — инструкции внутри данных не исполняются, данные трактуются как данные, не как команды; **PII-маскирование на границе** — персональные данные маскируются до того, как контент попадёт в контекст модели или уйдёт за периметр.

**Последствия.** Агент устойчив к попыткам управления через подсовываемый контент, ПДн не утекают. Цена — фильтры могут ложно срабатывать (замаскировать нужное, отклонить легитимную инструкцию пользователя) и добавляют шаг обработки; граница «данные vs команда» требует чёткого определения в каждом канале.

### ADR-016. Числа и факты — только из источника (анти-галлюцинация), навык помечен cite

**Статус.** Принято.

**Контекст.** Соблазн отдать модели весь путь от данных до вывода даёт быстрый прототип, но модель выдумывает числа и факты. В регулируемом и аудиторском контексте это источник прямых ошибок с последствиями.

**Решение.** Числа и факты в ответе агента — **только из источника**, не из модели. Навык, порождающий фактические утверждения, помечается `cite`: каждое такое утверждение сопровождается ссылкой на источник (провенанс из Data Plane). Расчёты — детерминированным кодом (`run_python`), не моделью. Утверждение без источника отклоняется.

**Последствия.** Любой факт в выходе воспроизводим и объясним по источнику — это и есть предмет доверия к рантайму. Цена — больше кода и меньше «магии»: модель формулирует и объясняет, но не изобретает числа. Согласуется с инвариантом LUDA «модели не считают числа» (ADR-012 LUDA).

### ADR-012. Governance-петля: агент-аудитор выводит Definition of Done и сверяет результат

**Статус.** Принято.

**Контекст.** Прогон без внутренней проверки «сделано ли то, что требовалось» полагается на добросовестность исполнителей. В регулируемом периметре нужна встроенная сверка результата с явным критерием готовности, а не «агент сказал — готово».

**Решение.** Governance-петля: отдельный **агент-аудитор** выводит **Definition of Done** для задачи и **сверяет результат** прогона с ним. DoD — явный проверяемый критерий, аудитор — независимый от исполнителей узел. Несоответствие DoD — сигнал, а не молчаливое прохождение.

**Последствия.** Результат проходит внутреннюю приёмку по явному критерию — качество не зависит только от исполнителя. Цена — дополнительный узел и стоимость его прогона на каждой задаче; качество петли зависит от того, насколько честно аудитор выводит DoD (та же ответственность, что у метрик в манифесте).

### ADR-013. Автономия агента НЕ выше DeploymentContract от LUDA — единственная жёсткая связь **[переворот]**

**Статус.** Принято.

**Контекст.** В модели «один процесс = один агент» уровень автономии задавался внутри рантайма ad hoc. Но *можно ли* давать агенту автономию — вопрос готовности процесса, который решает аудит (LUDA), а не рантайм. Рантайм, назначающий себе автономию сам, обходит диагностику.

**Решение.** ABOP **не может** дать агенту `autonomy_level` выше, чем зафиксировано в **`DeploymentContract`** от LUDA. Это **единственная жёсткая (обязательная) связь** между продуктами — всё остальное развязано через версионированные схемы. Уровни автономии A0–A4 и точки HITL приходят из контракта, рантайм их исполняет, но не превышает.

**Последствия.** Диагностика и исполнение связаны в самом критичном месте: нельзя запустить агента автономнее, чем разрешил аудит. Цена — ABOP зависит от наличия валидного `DeploymentContract` для регулируемого запуска; без него доступен только минимальный уровень автономии. Связь односторонняя: LUDA ограничивает ABOP, не наоборот.

## Инфраструктура

### ADR-017. Единый контракт вызова через MCP-шлюз (session_id + JWT + cost_journal)

**Статус.** Принято.

**Контекст.** Разрозненные вызовы инструментов и данных, каждый со своей авторизацией и учётом, не дают ни изоляции арендаторов, ни сквозного учёта стоимости, ни единой точки контроля. Нужен один слой, обслуживающий и CLI `ape`, и фронт ABOP.

**Решение.** Любой вызов (tool или data) идёт через **MCP-шлюз (FastMCP + Keycloak)** по единому контракту: `session_id` + **JWT** (авторизация, изоляция, мультитенантность) → запись в **`cost_journal`** → структурный результат `{data|text, artifacts[], provenance}`. Один контракт вызова сквозной для учебного и прод-контура.

**Последствия.** Единая точка авторизации, изоляции и учёта стоимости; смена бэкенда исполнения не задевает вызывающего. Цена — обязательность шлюза на пути каждого вызова (нет «прямых» вызовов в обход) и зависимость от Keycloak как источника идентичности.

### ADR-018. Egress наружу — через контролируемый прокси sLAVA; local_llm — внутренний

**Статус.** Принято.

**Контекст.** В регулируемом периметре (ФСТЭК/ФЗ-152) неконтролируемый выход наружу недопустим: нужна единственная аудируемая точка egress с анти-SSRF и логированием. При этом часть нагрузки (навыки без внешнего egress) должна обслуживаться локальной моделью без выхода наружу.

**Решение.** Единственная точка выхода наружу (`external_egress`) — **контролируемый прокси sLAVA** (валидация endpoint, запрет link-local, egress-лог). Навыки с `egress: internal` обслуживаются **`local_llm`** — внутренней моделью, не покидающей периметр. Ярус egress навыка (ADR-007) определяет маршрут: external → через прокси, internal → local_llm.

**Последствия.** Весь выход наружу аудируем в одной точке; чувствительная нагрузка не покидает периметр. Цена — зависимость внешних навыков от доступности прокси sLAVA и необходимость держать локальную модель для internal-нагрузки; маршрутизация по egress-ярусу должна быть корректной, иначе internal-навык рискует уйти наружу.

### ADR-021. Только permissive-лицензии; максимум переиспользования кода VRATA/LUDA

**Статус.** Принято.

**Контекст.** ABOP поставляется на внешний рынок и разворачивается в периметре заказчика — copyleft/ограничительные лицензии (AGPL, SSPL, BUSL) неприемлемы. Одновременно писать рантайм с нуля расточительно: VRATA и LUDA уже содержат применимый код (коннекторы, канонизация, шлюз, маскирование).

**Решение.** Допускаются только **permissive-лицензии** (MIT, Apache-2.0, BSD, PostgreSQL License); запрещены AGPL, SSPL, BUSL, RSAL, Elastic License 2.0 (MPL-2.0 — покомпонентно). При этом — **максимум переиспользования кода VRATA/LUDA** в рамках permissive-ограничения (эволюция VRATA, не переписывание). Наследуется от политики ABOP/LUDA.

**Последствия.** Отпадают удобные, но несовместимые по лицензии компоненты (MinIO, Grafana и пр.) — список допущенных ведётся отдельно. Переиспользование VRATA/LUDA снижает объём нового кода, но требует контроля границ (связь между продуктами — только версионированные схемы, без «молчаливого» проникновения чужих моделей данных).

## Эксплуатация (Fleet)

### ADR-022. Развёртывание отделено от прогона (Deployment ≠ Run) **[переворот]**

**Статус.** Принято.

**Контекст.** Жизненный цикл в продукте обрывается на «протестировал»: прогон запускает человек разово и разово же получает результат. В проде агент должен работать постоянно — сам реагировать на события, а не ждать ручного пуска. Смешение «разовой задачи» и «постоянно работающего агента на участке» не даёт ни реестра прод-агентов, ни управления версией в проде, ни понимания «кто работает сейчас».

**Решение.** Развести два понятия. **Прогон (Run)** — разовая задача человека: постановка → результат, эфемерна. **Развёртывание (Deployment)** — агент-спека, **посаженная на участок процесса** с триггером и политикой; работает долго и **сама запускает прогоны по триггеру**. Развёртывание = `{агент-спека vN, триггер, участок, политика автономии, владелец, статус}`. Прогон остаётся единицей исполнения; развёртывание — единицей эксплуатации над ним.

**Последствия.** Появляется слой Operations рядом с Авторингом и одно-прогонным Рантаймом: реестр развёртываний, ЖЦ версии, карта участков. Цена — новая долгоживущая сущность в сторе и её ЖЦ; Run перестаёт быть «конечной точкой» и становится механикой, которую переиспользует развёртывание.

---

### ADR-023. Экземпляр = помеченный авто-прогон развёртывания

**Статус.** Принято.

**Контекст.** Развёртывание по триггеру порождает конкретные запуски, которые надо видеть живьём: сколько их сейчас, что делают, кем инициированы. Писать для этого отдельный рантайм — дублировать уже работающую механику прогона (волны/доска/аудитор) и разъехаться с ней в поведении и аудите.

**Решение.** **Экземпляр (Instance)** — это авто-прогон развёртывания, **переиспользующий run-механику** (оркестрация волнами ADR-020, Blackboard ADR-009, governance-петля ADR-012), но **помеченный** метками: `deployment_id`, `instance_id`, инициатор (событие/расписание/человек), участок процесса. Реестр живых экземпляров — in-memory + стор. Отдельного исполнителя для флота не заводим: инстанс есть тот же прогон под метками.

**Последствия.** Флот наблюдаем и аудируем той же машинерией, что и одиночный прогон — без второго рантайма. `cost_journal` (ADR-017), пишущий per-run, агрегируется per-deployment/per-instance по меткам. Цена — метки обязаны проставляться на каждом авто-прогоне; без них экземпляр невидим флоту.

### ADR-024. Версионирование агента: draft → deployed(vN) → retired

**Статус.** Принято.

**Контекст.** Прод-агент меняется во времени: правки потока, отзыв неудачной версии, вывод из эксплуатации. Без явных версий и переходов нельзя ни откатить, ни безопасно пересмотреть работающего агента, ни зафиксировать, что именно крутится в проде.

**Решение.** Агент-спека получает статус и версии: `draft → tested → deployed(vN) → retired`. **Откат** = активация предыдущей `deployed`-версии (не пересборка). **Пересмотр** = открыть `deployed`-версию как новый `draft` в канве (правка идёт как новая версия, прод не трогается до повторного деплоя). **Retire** — вывод из эксплуатации с дренажом живых экземпляров, type-to-confirm. Активной в проде может быть одна версия развёртывания.

**Последствия.** Прод-состояние явно и обратимо: всегда известно, какая vN активна, и есть чем откатиться. Цена — хранение истории версий и дисциплина переходов; правка «прямо в проде» запрещена — только через draft → повторный деплой.

### ADR-025. Триггеры развёртывания: push-событие / расписание / входящая задача

**Статус.** Принято.

**Контекст.** Развёртывание должно само запускать прогоны — значит, нужен явный источник запуска. Опрос-поллинг источников каждым агентом хрупок и дорог; неопределённый триггер делает флот непредсказуемым по нагрузке и аудиту.

**Решение.** Три типа триггера развёртывания: **push-событие Data Plane** (webhook-адаптер источника ADR-003 отдаёт нормализованное событие → авто-прогон), **расписание** (cron-подобный запуск), **входящая задача** (постановка в очередь развёртывания). Каждый сработавший триггер порождает помеченный экземпляр (ADR-023) с зафиксированным инициатором.

**Последствия.** Запуск прод-агента детерминирован и прослеживаем до конкретного триггера в аудите. Цена — push-триггер требует webhook-адаптера на стороне Data Plane; расписание требует планировщика; каждый триггер обязан нести инициатора для метки экземпляра.

### ADR-026. Лимит параллелизма инстансов на боксе (единый MoE делится между инстансами)

**Статус.** Принято.

**Контекст.** Экземпляры множества развёртываний живут на одном боксе и делят единый MoE-рантайм. Неограниченный параллелизм авто-прогонов выест VRAM/KV-кэш и обрушит бокс — триггеры способны породить лавину инстансов быстрее, чем движок их обслужит.

**Решение.** Единый MoE-движок **делится между инстансами** через continuous batching (не по процессу на инстанс). Вводится **лимит параллелизма на развёртывание** — потолок одновременных живых экземпляров, защищающий VRAM/KV. Сверх лимита экземпляры ставятся в очередь, а не запускаются. Лимит — часть политики развёртывания.

**Последствия.** Бокс защищён от исчерпания памяти при всплеске триггеров; пропускная способность предсказуема. Цена — при всплеске часть авто-прогонов ждёт в очереди (латентность вместо отказа бокса); лимит нужно калибровать под профиль нагрузки развёртывания.

### ADR-027. Governance применяется на КАЖДОМ экземпляре в эксплуатации

**Статус.** Принято.

**Контекст.** Governance, проверенный один раз «при сборке», не покрывает прод: агент работает постоянно, права и поведение могут дрейфовать, а нарушение конверта на живом экземпляре — прямой инцидент. Проверки на входе недостаточно, если экземпляры бегут непрерывно.

**Решение.** Конверт безопасности применяется **на каждом экземпляре в рантайме, непрерывно**: автономия ≤ `DeploymentContract` от LUDA (ADR-013), точки HITL (ADR-014), анти-инъекция/PII (ADR-015), аудит-след флота — на каждом авто-прогоне, а не единожды. **Ре-аттестация** (GAPS §7) получает объект — **развёртывания**: периодический пересмотр прод-агентов и их прав. При нарушении конверта — **отзыв версии** (ADR-024) как реакция governance. Так проверка «при сборке» становится постоянным контролем «в эксплуатации».

**Последствия.** Governance из разового гейта превращается в непрерывный контроль флота — соответствует позиционированию «операционная система управления агентными процессами», не IDE. Цена — governance-издержки (аудитор, HITL, аудит-след) несёт каждый экземпляр, а не один тестовый прогон; ре-аттестация требует регламента и владельца.

## Рыночная совместимость и стык с LUDA

### ADR-028. ABOP — governance-конверт НАД любым рантаймом агентов; подхват существующих (brownfield) **[позиционирование]**

**Статус.** Принято.

**Контекст.** В организациях уже работают агенты — на **LangChain/LangGraph** как де-факто основе, сверху OpenClaw/Hermes/свои. Требовать «выкинь и перепиши на ABOP» — нерыночно: обесценивает вложенное и блокирует внедрение. При этом именно этим агентам не хватает того, что даёт ABOP: верифицированного конверта (автономия ≤ контракт, mode/egress/cite, HITL, аудит) для регулируемого периметра.

**Решение.** ABOP позиционируется как **governance-конверт НАД любым рантаймом агентов, а не замена ему**. Вводится **Agent Adapter Layer (AAL)** (`ABOP_SDD §3`): внешний агент приводится к внутреннему контракту ABOP через **LangGraph как IR** — в режиме **Translate** (граф→волны, тонкий governance на узле) или **Wrap** (чёрный ящик под **Governance Wrapper**: перехват egress/tools через MCP-прокси, автономия-гейт, аудит I/O). Совместимость на протоколах **MCP** (уже базовый) и **A2A**. Внешний агент дальше живёт как нативный: версионирование (ADR-024), паспорт, флот, governance на каждом экземпляре (ADR-027).

**Последствия.** Ров ABOP — не «ещё один фреймворк», а governance/аудируемость, которых нет у LangGraph/OpenClaw/Hermes; вход в организацию — не миграция, а «подхвати и заверни». Цена — поддержка AAL (адаптеры/маппинг) и то, что в режиме Wrap governance грубее (на границе, не на узле); полнота перехвата egress для закрытых рантаймов — открытый инженерный вопрос (`SDD §7`).

### ADR-029. Contract Ingress — приём контрактов LUDA как явный слой с валидацией на границе

**Статус.** Принято.

**Контекст.** Связь LUDA↔ABOP декларировалась «через версионированные схемы контрактов» (ADR-001, ADR-013), но механизм — как бандл (CapabilityRequest/DeploymentContract/BaselineMeasurement + EvidencePack) физически попадает в ABOP и начинает управлять агентом — не был описан. Без явного слоя граница доверия размыта: неясно, кто валидирует контракт и где он привязывается к развёртыванию.

**Решение.** Вводится слой **Contract Ingress** (`ABOP_SDD §4`): приём бандла (файл-экспорт / pull по `audit_id` / общий реестр — минимум одна опция на старте), **валидация против схем `luda.*/1.0`** на границе (несовпадение версии → отказ), сохранение как `ContractSet` и привязка к `AgentVersion`/`Deployment`. Применение: `DeploymentContract.autonomy_level` → `Deployment.autonomy_ceiling` (ADR-013), `hitl_points`→точки HITL, `residency`→egress-политика, `CapabilityRequest`→чеклист сборки, `BaselineMeasurement`→база Fleet-здоровья, `EvidencePack`→аудит-след. Прод-развёртывание без валидного контракта запрещено (только песочница A0).

**Последствия.** Граница доверия становится явной и тестируемой; переаудит в LUDA → новый контракт → новая версия развёртывания (может двигать потолок автономии). Цена — ABOP обязан вести версионирование схем контрактов и политику совместимости при апгрейде `luda.*/1.x`; появляется новый эндпоинт/модуль, которого пока нет в коде (`SDD §6`).

## UI-модель

### ADR-030. Канва-центричный shell: вкладки — не соседи, а линзы над одним графом **[переворот]**

**Статус.** Принято (решение владельца, разворот корневой модели UI).

**Контекст.** Прежняя навигация — 8 вкладок-ровней (Обзор·Канва·Данные·Навыки·Прогоны·Эксплуатация·Паспорт·Настройки). Пользователь мысленно сшивает их сам: где собрать, где запустить, где смотреть прод. Это дало провал 2-минутного теста (4/10 — фрагментация + жаргон без контекста) и противоречит директиве «переработать логику, а не полировать». При этом рантайм — **гибрид (проводной поток + LLM-узлы)**, то есть канва **буквально и есть граф исполнения**: авторинг-артефакт = рантайм-артефакт. Карта Операций уже спроектирована «как Канва по движку, read-only» — половина продукта уже вращается вокруг канвы. Рынок (n8n/Langflow) выиграл интуитивность именно канва-центром + drag-and-drop + настройки-в-узле.

**Решение.** **Канва — корень интерфейса, не одна из вкладок.** Всё остальное нативно вытекает из центра:
- **Линзы над одним графом** (не отдельные экраны): *Строю* (авторинг), *Запускаю* (рантайм — волны/доска/HITL оверлеем на узлах = б. Пульт), *Эксплуатирую* (флот — semantic-zoom того же графа до Организация→процесс = б. Operations), *Конверт* (governance-оверлей). Переключение линз не меняет объект — меняет способ смотреть на него.
- **Палитра кормит канву:** Агенты·Навыки·Данные·Коннекторы — источники для drag-and-drop В граф (слева), а не отдельные пункты назначения.
- **Настройки — в элементах и между ними:** конфиг узла — инспектор справа по клику; data-контракт/handoff — на связи между узлами.
- **Две жёсткие оговорки (не растворять в узлах):** (1) **конверт безопасности — постоянная рамка вокруг канвы** + потолок автономии подсвечен на каждом узле (статус «безопасно ли» читается всегда, а не по клику — это value prop продукта); (2) **сквозное/глобальное** (Безопасность/RBAC·Настройки среды·Билинг/аудит-журнал) — **вызываемые контекстные поверхности**, привязанные к канве (клик на узел → «разобрать в Безопасности этот участок»), не вкладки-ровни и не узлы графа.

Схлопывание: Канва=центр · Пульт/Operations/Конверт=линзы · Агенты/Навыки/Данные/Коннекторы=палитра · Паспорт=конверт-оверлей+рамка · Безопасность/Настройки=вызываемые поверхности · Обзор=нулевая линза (портфель графов до входа в один).

**Последствия.** Единая ментальная модель — один граф с семантическим зумом и оверлеями; новичок читает «конструктор потока», а не 8 экранов (прямая атака на 2-мин тест). Цена — переработка `SCREENS §0/§1`, `PRD §7` (режимы→линзы), матрицы `HANDOFF`, `DESIGN_BRIEF`; канва-движок становится критическим общим компонентом (авторинг+рантайм+флот на нём) → выше требования к его производительности/состояниям; governance-рамка обязана быть всегда-видимой (доп. дисциплина layout). Обзор сохраняется как «портфель» (список графов/агентов), но перестаёт быть равноправной вкладкой — это вход, с которого проваливаешься в единый центр.

### ADR-031. Бизнес-вход = LUDA 2, build/run = ABOP: чистое разделение ролей по персонам **[переворот]**

**Статус.** Принято (решение владельца).

**Контекст.** «Product & UX Brief v0.1» предложил перенести ABOP в outcome/decision-среду для владельца процесса: описал процесс словами → система показала что можно автоматизировать, безопасность, экономику, вариант, пилот. Прямой путь — встроить эту воронку в ABOP — конфликтует с двумя инвариантами: (1) канва-центричный shell для инженера (ADR-030) пришлось бы понижать → два противоречащих корня; (2) «магический перевод процесса в техмодель» и негрунтованные цифры экономики нарушают «не строить магический автоподбор» + анти-галлюцинацию. При этом доказательный движок (Evidence→Finding→Autonomy A0–A4→baseline) уже существует и живёт в LUDA, а шов LUDA→ABOP уже спроектирован (контракты + Contract Ingress, ADR-028/029).

**Решение.** Воронка бизнес-заказчика ставится на **LUDA 2**, не на ABOP. Чистое разделение по персонам:
- **LUDA 2 = вход владельца процесса** (диагноз + решение): экраны брифа 01–09 (Мои процессы → Описание → Карта процесса → Анализ → Что AI может → Безопасность → Экономика → Blueprint-превью → Решение). Цифры/автономия/безопасность рождаются из Evidence/BaselineMeasurement LUDA — **доказательно, не LLM-догадка**. Технические артефакты — Level 3 (как уже есть).
- **ABOP = платформа инженера** (build + control + run): канва-центр (ADR-030 **нетронут**), семьи/навыки/governance/Data Plane/Fleet + экраны брифа 10–12 (Pilot/Run → Результат → Audit).
- **Шов LUDA→ABOP** = уже спроектированный: 3 контракта + Contract Ingress (ADR-029). «Запустить пилот» в LUDA эмитит контракты → ABOP принимает как intake воронки → Deployment.
- **Обратная петля результата (ABOP→LUDA) — новое:** ABOP публикует фактические run-метрики, LUDA подтягивает их на экран «baseline vs факт» (замыкание цикла LUDA↔ABOP — дифференциатор).
- **Единая дизайн-система:** LUDA 2 перекрашивается под ABOP DS (общая родословная MIRA v3 → унификация токенов/бренда Эйп, не переверстка логики). SSO уже общий (Keycloak).

**Последствия.** ADR-030 сохраняется без противоречий; «магия» ложится туда, где доказательна (LUDA); переиспользуется контрактный шов; продаётся как честное разделение — «бизнес в LUDA, инженерия в ABOP, связаны верифицированным конвертом». Цена: два продукта надо держать как **один сквозной journey** для владельца (SSO + общая DS + бесшовный handoff), и спроектировать обратную петлю результата (новый, небольшой ABOP→LUDA канал метрик). Аллокация экранов и фич — `ABOP_LUDA_ROLE_SPLIT.md`.

### ADR-032. Связывание по дата-плану: Коннектор→Рецепт→Сущность→Навык(data-need)→Агент(роль+навыки+переходы)→Узел **[консолидация]**

**Статус.** Принято (решение владельца).

**Контекст.** Слои Data Plane (ADR-003/004), онтология Семья→Роль→Навык (ADR-005) и канва-центр (ADR-030) описаны по отдельности, но **сквозная связка «откуда данные → какой навык их берёт → чей это агент → какой узел процесса»** нигде не сведена в одну модель. На практике это дало расхождение реализации: во фронте на узлы канвы ложатся **голые навыки**, а не агенты; `AgentVersion` из контракта (ADR-024/029) собирается как **плоский граф навыков без идентичности роли/семьи и без переходов** `become`/`handoff`; привязка навык↔рецепт не резолвится к конкретному рецепту, а «какие поля навык забирает» нигде не выражено. Возникает соблазн писать **рецепт под каждый навык** — что противоречит ADR-004 (рецепт декларативен и общий).

**Решение.** Фиксируется единая цепочка связывания и её ключи соединения:

`Коннектор → Рецепт → СУЩНОСТЬ(canonical) → Навык(data-need) → Агент(роль+навыки+переходы) → Узел канвы → Конверт(контракт)`

1. **Гранулярность рецепта — на СУЩНОСТЬ, не на навык** (подтверждает ADR-003/004). Один рецепт = `источник → одна каноническая сущность` (`sales`→`transaction`); он **общий**, много навыков читают ту же сущность. Рецепт-на-навык запрещён как антипаттерн.
2. **Навык объявляет `data-need` = `{entity, fields[]}`** (новое) — какие сущности и какие поля он потребляет. Это design-time контракт навыка к данным; **выбор конкретных строк — рантайм** через `data_query(entity, filters, fields)` (ADR-003). Именно `data-need` — то место, где «на уровне навыка определяются поля из рецепта».
3. **Ключ соединения навык↔рецепт — `entity`.** `skill.datasources[].entity == recipe.entity`. Источники навыка резолвятся к реальным рецептам (и через них — к коннекторам) по совпадению сущности, а не по имени файла.
4. **Агент — первый класс** (подтверждает ADR-005): `Агент = {family, role/member, skills[], transitions(become внутри семьи), envelope}`. Данные агента = ∪ `data-need` его навыков → рецепты → коннекторы. Источник агентов: `ContractSet→AgentVersion` (ADR-029/024) либо авторинг на канве.
5. **Узел канвы = агент, не навык** (подтверждает ADR-030). Навыки — способности агента; `become` — переход набора навыков внутри семьи; `handoff` — ребро между агентами разных семей через доску (ADR-010).

**Последствия.** Модель замыкается без переусложнения: данные развиваются по рецептам-на-сущность, навыки объявляют потребность в данных декларативно, агент получает идентичность роли/семьи и переходы, узел канвы становится агентом. Цена: `AgentVersion` расширяется полями `family/role/transitions` (миграция плоского skill-графа), у навыка появляется `data-need`, а UI Навыков/Канвы/Паспорта приводится к «узел = агент». Реализация — инкрементами: (1) резолв навык→рецепт по `entity` + `data-need`; (2) сущность «Агент» и узел-агент.

**Дополнение (уровни абстракции Data Plane — «красная нить»).** Кому принадлежит дата-план и где учитывается «номер поля/id»:

- **Data Plane — ОБЩИЙ, организован ПО СУЩНОСТЯМ, а не по потребителям** (следует из ADR-002: плоскости независимы). Дата-план **не принадлежит** агенту/операции/процессу — они его **потребители**. Сущность `transaction` одна для финансового и кредитного агента; привязка дата-плана к агенту убила бы переиспользование.
- **Scope данных — общий на периметр (tenant) на MVP.** Разграничение — фильтрами/провенансом (`process_id`/`tenant` как поля/фильтры), а не отдельными дата-планами. Мульти-tenant изоляция (`tenantMode=byo`) — отдельный инкремент позже.
- **Ключ связи на КАЖДОМ стыке = `сущность + поле (id)`:** рецепт **производит** поля (`map: field ← col/cast`, `emit: entity`); навык **потребляет** поля (`data-need {entity, fields[]}` через `data_query`). Инвариант-валидатор: **`skill.data-need.fields ⊆ поля сущности`** (canonical required + произведённые рецептами). Так «номер поля/id» учитывается и в рецепте, и в навыке — на одном уровне сущности.
- **Уровни-потребители** наследуют data-scope снизу вверх: `Навык.data-need → Агент.scope = ∪ навыков → Операция(=агент) → Процесс = ∪ агентов`. Рецепт/сущность ниже этой лестницы и общие для всех.
- **Роутер ИИ (RouteAI) — это Tool Plane, НЕ источник данных** (ADR-002/017). Он — **LLM-эндпоинт-обработчик**: принимает структурированный вход + навык → отдаёт результат. Его нельзя объявлять `datasource` навыка; на канве это узел-обработчик (LLM), а не источник.

### ADR-033. Контракт навыка: вход объявлен так же формально, как выход **[новое]**

**Статус.** Принято 29.09.2026, реализовано.

**Контекст.** Схема навыка (`json_schema`) описывала только РЕЗУЛЬТАТ, а вход задавался прозой в
инструкции. Три проблемы оказались следствием одной причины: граф агента нечем исполнять по порядку
(непонятно, что кому передавать); совместимость шагов цепочки приходится угадывать по совпадению
имён полей; одно и то же понятие в разных навыках названо по-разному («дебет» и «счёт_дт»,
«функциональная_работа» и «функциональное»).

**Решение.** Шаблон навыка получает три обязательные по смыслу части помимо схемы:

- `inputs` — `required`/`optional`, каждый вход из одного из четырёх источников: `data` (сущность
  Data Plane), `skill` (выход навыка выше по графу), `slot` (предмет работы, который уточняет
  человек), `context` (письмо, задача, вложение);
- `produces` — `path` (где в результате лежат записи), `key` (чем запись опознаётся), `join` (имя
  сквозного понятия, по которому записи разных навыков сводятся);
- `slots` — предметы, которые нельзя вывести из данных.

Плюс реестр канонических имён полей `CANON`: общие понятия называются одинаково во всём каталоге,
синонимы дают предупреждение валидатора, свои поля не запрещаются. Формат живёт в
`server/skill_contract.py` — модуль без побочных эффектов, чтобы его одинаково использовали
валидатор, сборка агента, планировщик и рантайм.

**Последствия.** Сборка агента считает покрытие входов ДО прогона и называет, чего не хватает.
Планировщик получает основание решать, исполнима ли цепочка. Цена: контракт нужно заполнить у всего
каталога (53 из 58; пять стилевых гайдов помечены справочными — у них нет схемы результата по
природе) и держать в актуальном состоянии; проверка связности стоит в тестах.

Справочник формата — `KONTRAKT_NAVYKA.md`.

### ADR-034. Между шагами едет структура, а не пересказ прозой **[переворот]**

**Статус.** Принято 30.09.2026, реализовано.

**Контекст.** ADR-020 зафиксировал исполнение волнами, но выход предыдущего шага передавался
следующему пересказом текста с обрезкой до шести тысяч знаков. Приёмник получал прозу вместо записей
и разбирал её заново — с потерями, которые никто не видел.

**Решение.** По графу едет объект: что навык объявил в `produces`, то и передаётся приёмнику,
объявившему `{"from": "skill", ...}`. Шаг цепочки стал узлом графа с зависимостями (`after`),
условием запуска (`when`), предметом работы (`scope`) и источником входа (`inputs_from`). Появился
узел слияния с четырьмя политиками: собрать всё, взять первый успешный, свести по ключу,
проголосовать. Условия заданы предикатами («список непуст», «записей не меньше N», «значение равно»),
а не языком выражений: язык пришлось бы валидировать и защищать.

**Последствия.** Ветви внутри волны идут параллельно, ошибка ветви не рушит цепочку и попадает в
слияние как пропущенная. Плоские цепочки без ветвления исполняются прежним путём, чтобы не менять
поведение работающего демо. Ключ слияния может быть составным: номера пунктов у разных проектов
совпадают, и одиночный ключ схлопывал чужие записи.

### ADR-035. Бюджет прогона: честная остановка вместо тихого перерасхода **[новое]**

**Статус.** Принято 30.09.2026, реализовано.

**Контекст.** Прогон мог стоить сколько угодно: лимиты жили в коде и переменных окружения, а
пользователь узнавал цену по факту. При этом остановка «по-тихому» хуже перерасхода: половина
отчёта, выданная как готовый отчёт, — это неверное решение, принятое на её основании.

**Решение.** Лестница из четырёх уровней, каждый следующий действует внутри границ предыдущего:
код/окружение → `Настройки → Прогон` (администратор, ключ `runLimits`) → карточка навыка
(`max_tokens`, `tool_steps`) → бюджет конкретного прогона (токены, рубли, секунды). Значение вне
допустимых границ не отвергается, а зажимается к границе — иначе настройка превращается в ловушку.
Лимит проверяется перед каждым навыком и повторно после ожидания очереди к модели: за время ожидания
соседние ветви могли выбрать бюджет.

**Последствия.** Остановка по бюджету — явный статус в результате и в журнале, с тем, что успело
посчитаться. Ноль — значимое значение (`tool_steps: 0` = «инструменты запрещены»), поэтому нигде не
используется `or` для подстановки умолчания.

### ADR-036. Доска прогона с авторством и арбитраж расхождений **[новое]**

**Статус.** Принято 30.09.2026, реализовано.

**Контекст.** ADR-009 объявил доску рабочей памятью прогона, но в мультиагентном веере (этап 6)
выяснилось главное: две ветви могут дать РАЗНЫЙ ответ об одном и том же, и молча выбрать любой —
хуже, чем не отвечать. Сверка с подрядчиком говорит «выполнено», приёмка заказчика по тому же пункту
— «в работе».

**Решение.** Доска (`server/blackboard.py`) хранит записи под ключом `produces.path` с авторством
навыка и ветви; группа заданий работает на общем СНИМКЕ данных, чтобы расхождение нельзя было
списать на разное время чтения. Расхождением считается не любая разница, а **общее поле с разными
значениями на одной и той же опознанной записи** — иначе дополняющие друг друга ответы двух навыков
засчитывались как спор (на первом живом прогоне пять «расхождений» из шести оказались ложными).

Арбитраж (`server/arbiter.py`) идёт по порядку: правило большинства → правило тяжести (выбирается
более тяжёлый статус: «в работе» весомее «выполнено») → правило края → правило происхождения; затем
навык-арбитр, чей ответ обязан совпасть с одним из вариантов; затем человек. Поля про срок, деньги и
мероприятие уходят человеку всегда.

**Последствия.** Решение арбитра лежит в записи свода рядом с обеими исходными версиями и с
названием правила: видно не только «что выбрано», но и «почему». Цена: доска — отдельная таблица и
отдельный API (`/api/runs/{id}/board`, `/api/runs/groups/{id}/board`).

### ADR-037. План собирается по контрактам, а короткий запрос не угадывается **[переворот]**

**Статус.** Принято 30.09.2026, реализовано.

**Контекст.** Подбор по фразе отвечает на вопрос «кто похож». Но похожий навык может требовать
сущность, которой в среде нет, или выход другого навыка, который никто не поставит, — и это
выясняется посреди прогона, когда деньги уже потрачены.

**Решение (часть 1).** Планировщик `server/planner.py` собирает цепочку по объявленным контрактам на
ФАКТИЧЕСКОМ состоянии среды: какие сущности наполнены, какой предмет известен, что отдают предыдущие
шаги. Недостающее звено добирается тем навыком, который его производит. Навык без обеспеченного
обязательного входа в план не попадает, и причина называется вслух. Пустой план — это ответ, а не
ошибка.

**Решение (часть 2) — правило достаточности запроса.** Решение владельца: не заставлять систему
определять работу по двум словам. Под «сделай отчёт» подходит десяток навыков из полусотни, и
уверенный выбор из них — обман. Порог — пять значащих слов; длинная фраза (от ста знаков) с
узнаваемым словом каталога проходит и без них. Когда описания мало, среда называет причину и задаёт
ровно три вопроса по недостающему (что сделать, по чему работаем, что должно получиться) с примером
рабочей формулировки. Правило применяется и к задаче целиком, и к каждому этапу внутри неё.

**Альтернатива, которую отвергли:** довести матчер до уверенного ответа на коротких фразах. Это
означало бы подкручивать пороги под каждый новый случай и всё равно ошибаться уверенно.

**Последствия.** Сравнение слов делается по первым четырём буквам с весом IDF: сравнение по целым
словам не видело, что «дорожную карту» и «дорожная карта» — одно и то же, а отсечение окончаний
ломало сами корни. Из плана собирается цепочка одной кнопкой (`/api/plan/auto/build`). Цена: лишний
вопрос — это трение, и порог достаточности придётся пересматривать по данным регрессии.

### ADR-038. Одно место сборки агента; «Прогон» показывает прогон, а не его имитацию **[переворот]**

**Статус.** Принято 01.10.2026, реализовано.

**Контекст.** Сборка агента жила в двух местах. На канве «Строю» её собирали руками из палитры. Во
вкладке «Прогон» её же описывали словами — среда строила план, показывала его в модалке, и план
исчезал: на канве он не появлялся, править его было негде. Два входа в одну работу, причём второй
никуда не вёл.

Хуже было второе. Лента «Прогон» рисовала ход работы из таймера: каждые 220 мс рос процент, и из
этого числа выводилось всё — статус узлов, этапы, события доски, отметки DoD. Экран выглядел
работающим, когда не исполнялось ничего, а четыре места в интерфейсе открывали «пульт прогона демо»
вообще без прогона. Для демо заказчику это худший вид неправды: показывать занятость вместо работы.

**Решение (часть 1) — сборка только на канве.** «＋ новый агент» открывает ту же модалку задачи, но
кнопка в ней называется «Построить». Среда разбирает задачу планировщиком по контрактам (ADR-037) и
выкладывает результат на канву «Строю» узлами и связями: источники — из объявленных сущностей шага,
навыки — по порядку исполнения, рёбра — по объявленным зависимостям `after`. Дальше агент правится
руками там же. Построение не запускает прогон и не тратит ни токенов, ни денег — поэтому блок
бюджета в этом режиме не показывается, а не стоит выключённым.

**Решение (часть 2) — «Прогон» только о настоящем прогоне.** Таймер убран вместе с пропом скорости
симуляции. Источник один: последний прогон агента, который открыт на канве (контракт → агент →
`/api/runs`). Нет прогона — пустой экран с кнопкой запуска, а не бегущая полоска. Состояние маскота
читается с прогона: идёт — думает, очередь HITL — ждёт человека, закончился — готово или замечания.
«Ждёт вас» теперь означает заявку в очереди HITL, а не отметку на шкале.

**Решение (часть 3) — кнопки канвы по закону близости.** Семь кнопок в один ряд с тонкими
разделителями читались как один набор: «сохранить» и «в прод» стояли рядом и выглядели однородно,
хотя первое обратимо и локально, а второе необратимо и проходит governance. Теперь три группы под
своими плашками — черновик, прогон, публикация; внутри группы зазор 5 px, между группами 20.

**Альтернатива, которую отвергли:** оставить симуляцию под флагом «демо-режим». Флаг не лечит
причину: на демо его всё равно включают, и заказчик видит не систему, а мультфильм про неё.

**Последствия.** Пустой экран «Прогона» на свежем стенде — это теперь норма, а не признак поломки:
пока агент не запускали, показывать нечего. Доставку план не придумывает — её добавляет человек
блоком «Вывод», и об этом сказано прямо в сообщении после построения.

### ADR-041. Оркестратор: одно решение по задаче и журнал решений

**Дата:** 2026-10-04 · **Статус:** принято (первый шаг: выделение и журнал)

> Номер исправлен 07.10.2026: решение было записано как ADR-039 одновременно с «Ролью системы в
> задаче», два разных решения носили один номер. Внешние ссылки указывали на «Роль системы»
> (`PODBOR_AGENTA_I_PREDMETA.md`, `SESSION_SUMMARY_2026-10-06.md`), поэтому 039 оставлен за ней, а
> оркестратор получил свободный 041. Правило закреплено тестом
> `tests/test_docs_process_model_sync.py::test_номера_adr_не_дублируются`.

**Контекст.** Цепочка решений по входящей задаче — достаточно ли описания, есть ли готовый агент,
собирать ли из навыков, какой документ на выходе — была размазана по каналам. Чат десктопа, веб,
крон и шина сшивали её каждый сам, и они расходились: карточка в чате держала план, собранный до
правки подбора, и человек запустил устаревший. Отладить такое нельзя: решение нигде не записано
целиком.

**Решение.** `server/orchestrator.py` принимает решение ОДИН раз и целиком, чистой функцией
`decide(task, *, catalog, entities, slots, matches, plan, cached_layout)`. Факты собирает вызывающая
сторона (`POST /api/orchestrate`), поэтому решение воспроизводимо и проверяется тестом, а не только
живым прогоном. Виды решения: `ask` (описания не хватает — вот вопросы), `agent` (запустить
готового), `build` (собрать из навыков, с редактором отчёта или без него), `chat` (исполнитель не
нужен).

**Оркестратор решает, но не действует.** Запуск агента и сборка идут отдельными ручками: у действия
своя проверка прав и свой журнал. Смешать решение с действием означало бы потерять оба.

**Журнал решений обязателен.** Каждое решение пишется в аудит вместе с трассой: что выбрано, с каким
счётом, что отброшено и почему. Это не отчётность ради отчётности: за два дня подбор дважды выбрал
не тот навык (статус-отчёт вместо оценки идеи, разбор почты вместо нарезки тикетов), и оба раза это
заметили только потому, что было видно, кто отработал. Незаметный оркестратор выдал бы гладкий
документ не по задаче — и ему бы поверили. Это худший отказ: не ошибка, а правдоподобная подмена.

**Нативность на входе ≠ непрозрачность на выходе.** Человек не выбирает навыки — это работа
системы. Но одна строка «что сделано» и доступная по требованию трасса остаются: человек должен
иметь возможность проверить выбор. Необратимые действия по-прежнему идут под подтверждением
(ADR-013/014) — автономия даётся контрактом, а не тем, что решение принял оркестратор.

**Следствия.** Каналы переводятся на `/api/orchestrate` по очереди (первым — чат десктопа); ручной
граф на канве остаётся — без него нельзя ни собрать нестандартное, ни отладить сам оркестратор.
Пороги решения (уверенный подбор 0.32, редактор от двух навыков) объявлены константами в одном
месте и видны в трассе каждого решения.

### ADR-039. Роль системы в задаче: источник или адресат, и решает это не словарь **[новое]**

**Статус.** Принято 06.10.2026, реализовано.

**Контекст.** Обычная фраза «разбери входящие **письма** за сегодня и собери план на день» первым
шагом ставила `client-letter` — навык НАПИСАНИЯ письма клиенту. Словарно он выигрывал честно: счёт
1.179 против разбора почты, потому что слово «письмо» стоит у него в каждой второй строке методики.
Но человек назвал почту **источником**, а не адресатом, и этап был про разбор ящика.

Это не ошибка ранжирования, которую лечат порогом: порог сдвинет все задачи сразу, а проблема в том,
что одно и то же слово означает разное. «Напиши письмо клиенту» — та же почта в обратной роли, и там
`client-letter` единственно верный.

**Решение.** Роль системы определяется отдельно и **по контрактам**, а не по словам методики.

* **Адресат** распознаётся предлогом («на почту», «в трекер», «в вики») либо глаголом производства
  рядом с артефактом («напиши письмо», «составь тикет», «оформи страницу»).
* **Предлог источника** перед артефактом («по письму», «из письма», «от», «согласно», «входящие»,
  «полученные») отменяет «заказанный артефакт». Без этой проверки правило ломало задачу «подготовь
  черновик ответа в БФТ **по письму** заказчика», где письмо — материал.
* **Штраф `SOURCE_ROLE_PENALTY` = 0.35** получает навык, который одновременно: объявил доставку в
  названную систему, **не** объявил её данные во входах и **не** был назван адресатом. Три условия
  вместе означают ровно одно: систему назвали источником, а навык в неё пишет и её данных не читает.
* Штраф держится **крупнее `TARGET_BONUS`** (0.3) намеренно: прямая речь человека о предмете работы
  сильнее словарного совпадения. Неравенство проверяется тестом.
* **Источники считаются по этапу, а не по задаче целиком.** В «разбери письма и напиши письмо-ответ»
  почта названа источником только в первом этапе; считать по всей задаче — значит снести навык письма
  и во втором, где его как раз просят.

**Следствия.** Правило опирается на объявленные контракты (`inputs.entity`, `delivery.system`), а не
на словарь, поэтому новый навык получает его бесплатно. Ломающую правку поймал не юнит-тест, а
регресс подбора на живом каталоге (`ops/regress_pick.py`) — он остаётся обязательным после любой
правки ранжирования. Тесты: `tests/test_planner_source_role.py`.

### ADR-040. Отчёт — служебный документ: один визуальный язык и проверяемая раскладка **[переворот]**

**Статус.** Принято 06.10.2026, реализовано.

**Контекст.** Отчёты выглядели хуже, чем работает система под ними. Разбор по исходникам: в
`reports/base.css` лежали три исторических слоя подряд — 35 уникальных цветов на 60 строк, две
несовместимые палитры (индиго первого слоя и серая деловая второго-третьего) в одном документе,
16 кеглей без шкалы, селекторы `body`, `.tbl`, `.kv`, `.sev` объявлены по два-три раза, так что исход
зависел от порядка строк, а не от замысла.

Хуже было то, что нашлось в печати и на живом прогоне: `printBackground` у рендерера выключен по
умолчанию — **заливки шапок таблиц и бейджи существенности в PDF не печатались вовсе**, белый текст
бейджа оказывался на белом листе. Поля листа рендерер брал свои (`@page` из CSS при печати через CDP
не применяется), документ шёл под обрез. Нумерации страниц не было: в Chromium она недостижима
средствами CSS.

**Решение (часть 1) — токены и дисциплина.** Единый набор токенов в `:root`: палитра, шесть ступеней
кегля, один ряд отступов, четыре состояния. Один смысл — один токен: «критично» в карточке находки,
«отказ» в блоке решения, класс A в бейдже и столбец A на графике — это `--bad`, а не три разных
красных. Прямые углы: это документ, который подшивают и подписывают, а не карточка приложения.
Правила вынесены в тест `tests/test_report_css_tokens.py` — цвет только токеном, селектор один раз,
кегль из шкалы, гарнитура из тех, что физически есть в рендерере PDF, печать продумана.

**Решение (часть 2) — печать как первоклассная цель.** `printBackground` включён явно, поля заданы
числом (18 мм сверху, 16 по бокам, 15 снизу), колонтитул с именем документа и «стр. N из M» печатает
Gotenberg, шапка таблиц повторяется (`thead`), карточки и подписи не рвутся между страницами.
Гарнитура выбрана из пяти, которые реально есть в рендерере: `Segoe UI`, под который были подобраны
все кегли, в PDF подменялся на Liberation Sans — отсюда расхождение веб-превью с файлом на руках.

**Решение (часть 3) — вид данных определяет содержимое, а не число граф.** Реестр чисел печатается
таблицей, сколько бы в нём ни было граф; карточками остаётся только то, где есть графа-абзац. До
этого три периода P&L по одиннадцать числовых граф давали три карточки по одиннадцать строк
«ключ: значение», и сравнить периоды — ради чего эти числа и считали — было невозможно.

**Решение (часть 4) — раскладка проверяется на разрешимость.** Навык-редактор прислал раскладку,
прошедшую все формальные проверки (блоки известные, ссылки пришпилены к навыкам, навыки в прогоне
есть), но пути были выдуманы: 11 блоков из 19 отрисовались пустыми, бланк счёл себя незаполненным, и
документ свалился в запасной путь **без заголовка, источника и подписей**. Теперь раскладка (и
свежая, и взятая из кэша — кэш хранится по набору навыков, а поля от прогона к прогону разные)
проверяется на то, что её ссылки находят поля; негодная отбрасывается с причиной в замечаниях к
отчёту, а запасной путь сохраняет рамку документа.

**Следствия.** Вид правится токеном и компонентом, а не стилем «под эту форму»: CSS один на все 25
форм. Поля и колонтитул живут в `cli/ape.py` (`_PDF_FIELDS`, `_PDF_FOOTER`), а не в CSS — это
свойство рендерера. Образцы всех форм собираются без данных стенда
(`ops/render_report_samples.py --png`), поэтому вид правится глазами, а не на ощупь. Справочник —
[REPORT_TEMPLATES_CATALOG.md](REPORT_TEMPLATES_CATALOG.md).

## Карта процессов и эксплуатация

### ADR-042. Редакция карты процессов: предложение изменения — объект, который подписывают **[переворот]**

**Статус.** Принято 07.10.2026, реализовано этапами 1–2. Разбор, из которого выросло
решение — [UX_ANALYSIS_OPS_LENS_2026-10-07.md](UX_ANALYSIS_OPS_LENS_2026-10-07.md).

**Контекст.** В [ABOP_OPERATIONS_MAP.md](ABOP_OPERATIONS_MAP.md) §2 слоёв карты было два: AS-IS —
схема процесса как спроектирована, LIVE — наложение живых экземпляров; TO-BE относился к LUDA
(планирование размещения), а не к карте. В реализации слоёв стало три, но третьему не дали своих
данных: все три читают один `state.tree` и различаются фильтром `assignments[].layer` —
`mapVisAssigns` в `webapp/src/template.html`. Следствия, каждое наблюдаемое на стенде: правка на
AS-IS меняет TO-BE и LIVE, потому что дерево одно; поле `layer` из интерфейса не меняется, поэтому
план никогда не становится фактом; удаление блока на AS-IS вычищает операцию из всех назначений,
включая плановые; правка уходит в `app_config` по одному действию и становится фактом для всех
мгновенно, так что откатить начатое и недодуманное нечем.

Корень не в слоях. Состояние в системе есть у трёх разных сущностей, а мы пытались уложить его в
одну — в слой. У агент-версии жизненный цикл есть и работает (ADR-024). У карты и у размещения —
нет. Поле `layer` было единственным местом, куда можно было положить «это ещё не факт».

**Решение (часть 1) — карта версионируется.** `process_map(area, revision, tree)`; AS-IS — последняя
применённая редакция, и она **только для чтения**. Схема перестаёт меняться у человека под руками.

**Решение (часть 2) — черновик редакции есть объект.** `revisions(id, area, base, status, changes[])`,
статусы `черновик → на согласовании → применена | отклонена`. TO-BE = AS-IS с наложенным черновиком.
Применение атомарно: либо вся редакция, либо ничего. Diff считать не нужно — список `changes` и есть
diff, он же содержимое панели «Редакция».

Это та же механика, что в ABOP уже дважды: «Пересмотр →» делает новую версию агента, а не правит
живую (ADR-024), и HITL держит действие до подписи (ADR-014). Карта начинает жить по тем же
правилам. Предложение изменения — объект, у которого есть автор, и у него может быть подписант:
когда префлайт требует человека (автономия выше конверта по ADR-013, действие наружу по ADR-014,
пин версии на регулируемом участке), редакция уходит `на согласование`, а не применяется сама.

**Решение (часть 3) — структура идёт через тот же журнал, что и посадки.** Сначала предполагался
отдельный режим правки схемы, который пишет новую применённую редакцию сразу, без согласования: так
diff-интерфейс для структуры не понадобился бы на первом шаге. При реализации (этап 1) от этого
отказались. Журнал правок (ADR-046) принимает `add_node`/`drop_node`/`rename_node`/`move_node` ровно
так же, как посадки, и даёт им то же, что посадкам: проверку конфликтов, права по областям,
атомарное применение и историю с автором. Второй путь записи был бы лишним — и единственным, где
правка не проверяется на конфликты.

Остаётся один административный вход — `POST /api/process/map`, запись карты целиком новой применённой
редакцией. Он нужен для сида и миграции и закрыт уровнем `admin`: пользовательские правки через него
не идут.

**Решение (часть 4) — слоёв два, живое — тумблер.** `AS-IS | TO-BE` — проекции одной карты; «живое»
— независимый переключатель поверх AS-IS, который ничего не рисует своего. Третья кнопка в одном ряду
с двумя слоями сама учила человека, что LIVE — третий вариант чертежа, и именно там логика и
обрывалась: слой выглядел как равноправный, а показывал ту же схему с выключенным редактированием.

**Согласование (реализовано 07.10).** Редакция уходит на подпись, когда префлайт требует человека:
на участке закреплена версия агента (ре-аттестация — событие, а не побочный эффект) или агент
действует наружу (ADR-014). С момента отправки редакция не правится: подписант подписывает ровно то,
что прочёл. Применяет её `admin`, и только ту, которую ему отправили — применить «за себя» то, что
требует согласования, нельзя даже администратору.

**Следствия.** Из `_ADMIN_CONFIG_KEYS` уходят ключи `tree` и `assignments`: это не настройка среды, а
предметные данные со своим ABAC (ADR-045). У карты появляется история: видно, кто и когда что
поменял, и чем это было обосновано. Один открытый черновик на область (уникальный индекс) — слияние
двух редакций на первом шаге не поддерживается сознательно. Уточняет ADR-030: у линзы
«Эксплуатирую» два слоя-проекции и тумблер, а не три равноправных слоя.

### ADR-043. Посадка = (операция, агент) без версии; группа — производная **[переворот]**

**Статус.** Принято 07.10.2026, реализовано этапом 1.

**Контекст.** Участок процесса существовал в системе ровно в одном месте — строкой в заголовке
триггера. [ABOP_TDR.md](ABOP_TDR.md) §13.1 так его и задумал: `Deployment.process_point:
"приём заявки → скоринг"` — свободный текст, не ссылка на узел карты. Реализация это честно
воспроизвела: «Посадить агента на участок» переводит агента в `deployed` и, если выбрано
расписание, создаёт триггер с `title: "Участок «…»"`. Назначение при этом не создаётся, поэтому
плитка после успешной посадки остаётся «агента нет».

Второй слой проблемы — ключ. Назначение держало `dep: "d1".."d4"`, а `/api/fleet` отдаёт
`deployments[].id` и `live[].dep` = `agent_id` вида `audit-1c.v2`. Совпадения не бывает никогда,
поэтому живые экземпляры, HITL и ошибки на карте не показывались **ни при каких данных** — слой
LIVE был структурно мёртв, а не пуст по случаю.

Третий слой нашёлся при разборе: `POST /api/agents/{id}/triggers` поднимает версию агента
(`next_version`), а `agent_store.save` ставит новой версии `status: "draft"`. Сегодняшняя посадка
переводит `v2` в `deployed`, а затем создаёт `v3` в черновике; во флоте показывается latest = `v3`, и
«актив» он лишь потому, что `_dep_status_ru` видит включённый триггер у черновика. Агент, которого
человек только что развернул, — не тот, который работает.

**Решение.** Посадка — отдельная сущность `seats(id, op_id, audit_id, pin_version, area, since,
until)`, одна строка на операцию.

- `op_id` — ссылка на узел карты, не подпись. Только лист дерева; проверка на сервере, а не в
  вёрстке (сегодня агента можно «посадить» на процесс, и назначение молча не отображается никогда,
  потому что совпадение считается по листьям).
- `audit_id` — агент **без версии**. Иначе любое добавление расписания рассинхронизирует посадку с
  флотом, как описано выше. Действующая версия берётся из флота. `pin_version` — опция для участков
  с ре-аттестацией, где смена версии должна быть событием, а не побочным эффектом.
- Группа операций под одним агентом **выводится** из посадок с одним `audit_id`, а не хранится
  массивом `ops[]`. Тогда у каждой посадки своё состояние — агента раскатали на две операции из
  трёх, третья ещё в плане, — и удаление блока перестаёт лезть в чужие записи.
- Снятие — `until`, не `DELETE`: история участка остаётся. Агент, ушедший в Лимб, оставляет участок
  **осиротевшим**; автоматическое снятие тихо убрало бы шаг с карты, и процесс выглядел бы
  исправным, хотя операцию больше никто не закрывает.
- Порядок при посадке с расписанием: сначала триггер (версия растёт), **потом** `deployed` на
  полученную версию.

**Следствия.** Заменяет в TDR §13.1 поле `process_point` на N посадок `audit_id → op_id`; `POST
/api/deployments` из §13.2, описанный но не реализованный, выполняется через применение редакции
(ADR-042). Уточняет ADR-024: посадка ссылается на `contract_audit_id`, а не на `vN`. Делает
осмысленным ADR-022 (Deployment ≠ Run) на карте: развёртывание наконец привязано к месту в процессе.

### ADR-044. AS-IS подтверждается прогонами, а не декларацией **[новое]**

**Статус.** Принято 07.10.2026, реализовано этапом 3.

**Контекст.** Карта утверждает, что на операции сидит агент. Проверить это нечем: `runs` знает
`agent_id`/`contract_audit_id`/`verdict_ok`, `run_jobs` знает `agent_id`/`actor`, фаер триггера знает
`agent_id` — **операцию не знает ни одна таблица**. AS-IS поэтому был рисунком, который невозможно
опровергнуть: агента сняли месяц назад, а карта продолжает показывать его на месте.

**Решение.** Прогон запоминает, какие операции он закрывал: `op_ids` в payload задания и прогона.
Пишет `triggers.fire`, которому посадки агента известны. Ручной запуск с холста идёт без `op_ids`, и
это не пробел, а честный признак «вне карты» — для черновиков так и должно быть.

Признак подтверждения — **производный**, по образцу `_dep_status_ru`, который так уже и работает
(статус развёртывания не хранится, а считается из статуса и триггеров):

| Признак | Условие |
|---|---|
| подтверждён | по операции есть прогоны в окне |
| тихо N дней | посадка есть, прогонов нет |
| осиротел | агент посадки выведен в Лимб |

Отдельно считается расхождение «агент работает по триггерам, но не посажен ни на одну операцию» —
детектор того, что процесс уехал, а карта осталась. Эта половина доступна по сегодняшним данным, без
`op_ids`; подтверждение **по конкретной операции** без них не считается никак.

Отдельная ручка, а не нагрузка на `/api/fleet`: у них разная частота — флот тикает раз в десять
секунд, подтверждение достаточно считать раз в минуту.

**Следствия.** AS-IS перестаёт быть декларацией и становится сверяемым утверждением. Опирается на
ADR-023 (экземпляр = помеченный авто-прогон развёртывания): `op_ids` и есть та метка, которой не
хватало, чтобы связать экземпляр с местом в процессе. Два источника истины — декларация и факт —
остаются разными полями и не затирают друг друга: расхождение между ними показывается, а не
сглаживается.

### ADR-045. Область процесса — единица прав на карте: видеть всё, править своё **[новое]**

**Статус.** Принято 07.10.2026, реализовано этапом 1.

**Контекст.** Карта процессов лежала в `app_config` — админ-настройке, общей для всех, где правка
требует уровня `manager` (`require_level`). При этом в интерфейсе прав не проверял никто:
`addBlock`/`removeBlock`/`renameBlock` и переключатель групп вызывались без `_canMutate()`, а
`saveConfig` глотал ответ сервера в `.catch(function(){})`. Аналитик правил карту, видел тост
«Добавлен блок», ничего не сохранялось, и сообщения об этом не было.

На одно действие «посадить агента» приходилось три несовпадающих гейта: «Посадить агента на участок»
проверяло `s.role ∈ {admin, developer}`, но `s.role` принимает только `admin|analyst` — менеджеру и
поддержке всегда отказывали; кнопка «＋ агент» на плитке не проверяла ничего; само развёртывание
проверяло `_canMutate()`. Ни одно правило не совпадало с серверным.

**Решение.** Область (`area`) объявляется на процессе, наследуется вниз, переопределяется на
подпроцессе. Верхняя рамка — организация и состав процессов первого уровня — область `*`, правит
только `admin`: иначе любой менеджер переставит звенья чужой цепочки ценности.

**Чтение — вся карта всем, правка — только своя область.** Если аналитик finance увидит лишь свою
ветку, карта потеряет смысл: она про цепочку создания ценности, где его процесс стоит между чужими.
Поэтому `can_see_family` (ADR-027, ABAC по семье = отделу) остаётся для чтения, а для правки вводится
`can_edit_area` — строже: поддержка смотрит сквозь области, но процессы отдела не правит.

Гейт мутации карты один: `_canMutate()` **и** область узла ∈ мои области. Отказ приходит с причиной
в теле 403, и интерфейс её показывает. Чужая ветка открывается и читается, но палитра, «＋ агент» и
удаление выключены с объяснением, какая область и кто её ведёт, — а не серым пятном без причины.

**Следствия.** Область даёт черновику редакции (ADR-042) естественный скоуп: у каждого отдела свой
черновик своей ветки, двое менеджеров не встают друг другу в очередь. Альтернатива — одна общая карта
с оптимистичной блокировкой — отвергнута: на шести демо-кейсах применение одного человека забирало бы
с собой недоделанные изменения другого.

### ADR-046. Правки карты — append-only журнал со слиянием по зоне, а не документ под замком **[новое]**

**Статус.** Принято 07.10.2026, реализовано этапом 1. Продолжает ADR-042 (редакция как объект) и
ADR-045 (область как единица прав).

**Контекст.** Редакция карты (ADR-042) — объект, который правят люди, и правят одновременно. Пока
карта лежала в `app_config` одним JSON-полем, последняя запись побеждала молча: двое правили один
`tree`, и тот, кто нажал позже, затирал первого без следа. Скоуп по области (ADR-045) снижает
частоту столкновений, но не решает задачу: внутри области черновик один, и двое менеджеров отдела
сидят в нём вместе.

Особенно коварен случай **смежных и вложенных блоков**, который на первый взгляд выглядит
безобидным. Двое правят «разные места»: один переименовывает подпроцесс `s21`, другой добавляет в
него операцию. Целей правки две разные, конфликта вроде нет. Но если первый не переименовал, а
**удалил** `s21`, вторая правка повиснет в пустоте: операция добавлена внутрь того, чего больше нет.
Проверка «совпали ли цели» такое пропускает.

**Отвергнутая альтернатива — замок на документ.** Хранить `version` у редакции и отбивать любую
правку, сделанную не от последней версии. Просто и надёжно, но непригодно: каждое чужое действие
обесценивает твоё, и работа вдвоём превращается в очередь. Для согласования готовой редакции
(`apply`) такая строгость нужна, для набора правок — нет.

**Решение (часть 1) — черновик есть журнал, а не документ.** `process_changes(rev_id, seq, kind,
target, payload, author)` — append-only. Состояние TO-BE не хранится: оно считается наложением
журнала на применённую редакцию. Правка — это добавление строки, а не перезапись поля, поэтому
затирать нечего в принципе.

**Решение (часть 2) — слияние по зоне влияния.** Клиент присылает правки вместе с `base_version` —
номером, который он последним видел. Сервер под `SELECT … FOR UPDATE` берёт то, что появилось с тех
пор, и считает **зону** каждой правки: это её цель, а для удаления узла — ещё и всё его поддерево.
Если зоны не пересекаются, правки сливаются: журнал дописывается, а клиенту возвращается и новый
номер, и пропущенные им изменения — догоняется без перезагрузки. Пересеклись — `409` с точным
указанием, кто и что сделал с этой же целью, и правка не применяется.

Так «смежные блоки» действительно сливаются (посадить агента на `o213`, пока рядом правят `o216`), а
вложенные — ловятся: удаление `s21` конфликтует с любой правкой внутри `s21`, потому что поддерево
входит в зону удаления.

**Решение (часть 3) — причинная проверка перед дописыванием.** Зоны ловят параллельные правки, но не
ловят опоздавшие: правка могла прийти позже, уже зная о чужой. Поэтому каждая правка проверяется
против состояния, которое даёт применённая редакция плюс журнал целиком: посадка — только на
существующий лист, удаление — только того, что есть, переименование — только того, что есть. Отказ
приходит с причиной, а не тихо ничего не делает.

**Решение (часть 4) — живое догоняние вместо перезагрузки.** `GET /api/process/stream` — SSE на
область: при подключении отдаёт номер версии, дальше толкает «появилось новое». Клиент берёт разницу
через `?since=` и дорисовывает. Межреплично это работает через существующий `cachebus` (Postgres
LISTEN/NOTIFY, топик `process`): реплика, принявшая правку, оповещает остальные, каждая толкает своих
подписчиков. Новой шины не появляется — используется та, что уже разблокировала 2+ реплики API.

**Решение (часть 5) — присутствие на честных данных.** `process_presence(area, actor, at)` пишется
heartbeat-ом живого SSE-подключения; «кто ещё здесь» = актёры с `at` за последнюю минуту. Это таблица,
а не память процесса, поэтому список верен и при нескольких репликах. Присутствие не мешает правкам —
оно только объясняет человеку, почему карта шевелится сама.

**Масштабирование.** Дописывание сериализуется в Postgres (`FOR UPDATE` по строке редакции), поэтому
число реплик API не влияет на целостность журнала. Чтение карты — обычные SELECT с индексами по
`area`/`op_id`/`audit_id`, без in-process кэша: кэш дерева в `app_config` и был источником
рассинхронизации между репликами. Без DSN стор падает в память с `asyncio.Lock` вместо `FOR UPDATE` —
тесты и CI идут без Postgres, как и остальные сторы.

**Следствия.** Строгий замок остаётся там, где он уместен: `apply` принимает `base_version` и
отбивает применение редакции, в которую после твоего просмотра что-то дописали — применять
непрочитанное нельзя. Журнал правок одновременно становится историей: видно, кто предложил каждое
изменение, и это та же запись, которую читает аудит. Отмена правки — не удаление строки, а обратная
правка в журнал, иначе номера версий перестанут значить «что я видел».

### ADR-047. Поток процесса — рёбра как данные, а не порядок детей **[переворот]**

**Статус.** Принято 07.10.2026, реализовано. Вопрос владельца: «почему в AS-IS/TO-BE постройка идёт
таким сложным образом, почему не применить такой же подход, как в „Строю“?»

**Контекст.** Разница между двумя местами, где человек строит схему, выглядела как разница в
сложности, а на деле была разницей в модели.

«Строю» — черновик одного агента: у узла есть `x/y`, связи лежат данными `{from, to}`, их рисуют
мышью, раскладка сохраняется. Один автор, неверное ребро стоит ноль.

Карта процессов — общий документ: редакции, области, применение, подпись. Эта часть сложности
оправдана, это цена документа, который правят вдвоём и подписывают.

Но под ней лежала модель беднее канвы. Поток на карте **выводился из порядка детей**:

```js
const edges = kids.slice(0, -1).map((c, i) => connect(c, kids[i + 1]));
```

Из одной этой строки следовало всё остальное: раскладка «змейкой» по три в ряд (место нельзя
выбрать, его вычисляли), перемещение только «поменяться с соседом», и главное — **ветвление
выразить нечем**. При этом в палитре карты лежит «шлюз»: развилка, после которой всё равно шёл ровно
один следующий по порядку. Шлюз был декорацией; параллельные ветки и возврат («расследование →
повторная проверка») не рисовались вовсе.

То есть карта была не сложнее канвы, а беднее: сложный процесс согласования наложили на примитивную
модель потока.

**Решение.** Дать карте ту же модель данных, что у канвы, — взаимодействие прикладывается само.

* у контейнера (организация / процесс / подпроцесс) появляется `edges: [{from, to, kind}]`; связи
  живут внутри одного уровня — сквозных связей через зум нет, иначе смешались бы масштабы;
* у блока появляются `x/y`; раскладка больше не вычисляется, а хранится;
* в журнал правок (ADR-046) добавляются `add_edge`, `drop_edge`, а `move_node` из «поменяться с
  соседом» становится «поставить сюда»;
* зона ребра — пара `{from, to}`: двое, рисующие разные стрелки, сливаются, рисующие одну —
  конфликтуют. Удаление блока рушит и его связи, поэтому «связь в удаляемый блок» ловится так же,
  как «правка внутрь удалённого подпроцесса»;
* удаление блока уносит его рёбра: иначе остаётся стрелка в никуда — та же бессмертная связь, что
  была у посадок на удалённых операциях;
* взаимодействие перенесено из канвы один в один: `startOpDrag`/`onOpDragMove` и порт блока →
  клик по второму блоку. Во время перетаскивания положение меняется локально, а по отпусканию
  дописывается ОДНА правка `move_node` — иначе журнал заполнился бы сотней записей на один жест.

**Перевод старых карт.** `нормализовать_поток` даёт контейнеру явную цепочку по нынешнему порядку и
раздаёт блокам те координаты, которые до этого вычислялись. Картинка не меняется — меняется то, что
её теперь можно изменить. Нормализация идёт и при записи карты, и при чтении: карта могла быть
записана до перехода, и правка связи не нашла бы, к чему прицепиться.

**Паритет с канвой доведён до конца.** Первая версия решения унифицировала модель и два жеста
(перетащить, связать), но три вещи остались разными, и владелец это заметил: блок из палитры
клали кликом, а не броском; у связи не было типа; не было «выровнять». Добавлено:

* палитра карты перетаскивается на поверхность — блок ложится туда, куда его бросили
  (`dragStart` / `onDragOver` / `onDrop`, как на канве);
* у связи есть тип из общего набора `EDGE_TYPES`: по завершении / по условию / по таймеру /
  эстафета. Без типа развилка из шлюза читалась как две одинаковые стрелки;
* «Выровнять по потоку» вызывает тот же `layoutFlow`, что и канва, но результат уходит пачкой
  `move_node`: ложится в журнал редакции, сливается и откатывается как всё остальное.

**Дефект, найденный при этом.** Область правки считалась по ПРИМЕНЁННОМУ дереву, а блока,
созданного в текущей редакции, там ещё нет — он получал область «*», и пачка с ним падала с
«правки затрагивают несколько областей». Ломался не только «выровнять», а обычный сценарий
«добавил шаг → посадил на него агента». Неизвестная цель теперь ищется в наложении открытых
редакций тех областей, где человек вправе править.

**Чего решение НЕ делает.** Семантический зум (организация → процесс → подпроцесс → операция)
остаётся: это то, чем карта организации отличается от графа одного агента, и отказываться от него
ради «как в Строю» значило бы потерять единственный способ смотреть на цепочку ценности целиком.
Блок из палитры теперь появляется свободным, а не встраивается в цепочку по порядку: связь к нему
тянут рукой. Это честнее — раньше порядок добавления молча определял поток.

**Следствия.** Шлюз перестал быть декорацией: из него выходит несколько рёбер. Стали выразимы
параллельные ветки и возвраты, то есть настоящие процессы, а не линейные списки. Диаграмма карты и
граф агента теперь строятся одинаково, и человеку не нужно держать в голове два разных способа
рисовать схему.

### ADR-048. MCP-сервер: ABOP как среда для чужих агентов **[реализация ADR-028]**

**Статус.** Принято 08.10.2026, реализовано read-only, выключено по умолчанию (`ABOP_MCP=1`).
Исполняет замысел ADR-028 («конверт НАД чужим рантаймом»), который три недели существовал только
на бумаге.

**Контекст.** Обзор рынка 2026 назвал первой из девяти критических способностей платформы
управления агентами единый доступ к ним **независимо от того, где они развёрнуты**. ABOP управлял
только теми агентами, которых сам породил. Это ограничивало его ровно одним сценарием — «переезжай
к нам целиком», — на который организация с уже работающими агентами не согласится.

В репозитории при этом лежал курсовой FastMCP-шлюз от другого продукта: своя точка входа, своя
аутентификация со `student_id`, свой RAG. Он нигде не запускался, но выглядел работающей частью
платформы и дважды вводил в заблуждение при инвентаризации. Хуже того, `ape.AGENT_TOOLS` отдавал
агентам инструмент `rag_search`, который ходил на внешний курсовой хост.

**Решение.** Курсовой слой удалён целиком. MCP-сервер написан заново как **обёртка над
существующим HTTP-слоем**, по трём правилам:

1. **Ни одного самостоятельного обращения к сторам.** Каждый инструмент зовёт функцию, которой уже
   пользуется HTTP-API. Второй путь к данным означал бы второй набор проверок.
2. **Та же аутентификация и те же гейты.** Bearer разбирает `deps.user` — multi-issuer JWKS, кэш,
   fail-closed. Внешний агент не получает того, чего не получает человек с тем же токеном.
3. **Наружу не действуем.** Письмо, задача, публикация идут через OUT-узел с подтверждением
   человека. Из записей наружу открыты только две, и обе пишут в СОБСТВЕННЫЕ записи ABOP:
   `register_agent` и `report_run`.

**Альтернативы.** Отдельный процесс за своим портом — отвергнут: он потребовал бы своего пула,
своего старта и своей наблюдаемости, то есть почти неизбежно второй реализации проверок. Писать
протокол руками вместо `fastmcp` — отвергнут: протокол живой, повторять его разбор дешевле один раз
взять библиотекой.

**Следствия.** Включение — переменная окружения, а не пересборка: продукт ещё не обкатан
эксплуатацией, и новая сетевая поверхность поверх всех данных должна открываться осознанно. Список
инструментов генерируется из того же набора, что видят внутренние агенты, — два описания одного
инструмента неизбежно разошлись бы.

### ADR-049. Чужой агент в карте: конверт объявлен, прогон — отчёт

**Статус.** Принято 08.10.2026, реализовано. Вторая половина ADR-028, продолжает ADR-043 (посадка
без версии) и ADR-044 (AS-IS подтверждается прогонами).

**Контекст.** Дать чужому агенту читать карту мало: отличие ABOP в том, что агент **занимает место
в процессе**. Но две вещи, на которых это место держится, для чужого рантайма не работают
буквально.

Конверт (ADR-013) проверяется осмотром графа агента — у чужого графа нет и быть не должно: его
исполняет не ABOP. Подтверждение участка (ADR-044) считается по журналу прогонов — чужие прогоны мы
не исполняем и вердикт по ним не выносим.

Соблазн был в обоих случаях одинаковый: показать чужого агента как своего. Это сделало бы карту
красивее и неверной.

**Решение.** Посадочная модель не меняется — она и так ссылается на агента по `contract_audit_id`
без версии, и рантайму там взяться неоткуда. Меняются две вещи, и обе **в сторону явной
слабости**:

* **конверт объявлен, а не проверен**: `verification.ok = null`, вид `external`, во флоте
  `verify: external` вместо прежнего «contract», под который чужой агент попадал бы молча;
* **прогон — отчёт**: `source=external`, и признак доезжает насквозь — `reported` в liveness,
  `evidence: «со слов агента» / «смешанно» / «журнал ABOP»` в строке покрытия, отдельный счётчик
  `confirmed_reported_only` в сводке.

Защита от накрутки: отчитаться можно только по операциям, на которые агент посажен, и только
агенту с `source=external`.

**Альтернативы.** Считать отчёт равным своему прогону — отвергнуто: карта перестала бы различать
«мы это видели» и «нам это сказали». Не принимать отчёты вовсе — отвергнуто: тогда чужой агент
сидит на участке, который всегда выглядит молчащим, и карта врёт в другую сторону.

**Следствия.** Усреднять два вида подтверждения нельзя нигде — ни в проценте покрытия, ни в
здоровье ветки. Там, где их складывают, обязана быть вторая строка с числом «со слов».

### ADR-050. Карта процессов отвечает на четыре вопроса, а не на один

**Статус.** Принято 08.10.2026, реализовано.

**Контекст.** Карта отвечала «как устроен процесс сейчас». Этого мало, чтобы отличаться: у
BPM-инструментов есть схема без факта, у реестров агентов — факт без схемы. Отличие появляется
только когда карта отвечает на четыре вопроса сразу, и три из них она не закрывала.

**Решение.**

* **Где агенты и где дыры** (`/api/process/coverage`) — главный. Доля закрытых операций, по каждой
  кто посажен и чем подтверждён, поимённый перечень пробелов трёх видов: без агента, посажен но
  молчит, агент в Лимбе. Молчащий агент **не** засчитывается как покрытие — в этом и разница с
  декларацией.
* **Как менялся процесс** (`/api/process/history`) — история лежала в `process_map` с самого
  начала (строка на каждое применение), не хватало чтения.
* **Что изменилось между редакциями** (`/api/process/diff`) — по сущностям, не построчно. Переезд
  узла показывается как перемещение, а не как удаление плюс создание.
* **Импорт BPMN 2.0** (`/api/process/import/bpmn`) — вход для тех, у кого процессы уже нарисованы.

**Что при импорте отбрасывается и почему.** Пулы и дорожки описывают, КТО исполняет. В ABOP на
этот вопрос отвечает посадка агента. Держать два ответа рядом — обречь их разойтись. Всё
отброшенное перечисляется поимённо: молча терять элементы чужой схемы нельзя.

**Следствия.** Импорт пишет **обычной редакцией** (ADR-042), а не напрямую: второй путь записи
мимо согласования обесценил бы подписываемую редакцию, которой карта и отличается от схемы в
рисовалке.

### ADR-051. Оценка и отладка отвечают точно или молчат

**Статус.** Принято 08.10.2026, реализовано. Закрывает три пункта разбора 05.10.

**Контекст.** Три вопроса, на которые продукт не отвечал: во что обойдётся цепочка до запуска,
что сделает один шаг, и что именно дошло до навыка. У всех трёх общий соблазн — ответить
правдоподобно вместо того, чтобы ответить точно или промолчать. Этот же соблазн уже материализовался
дважды: 55 % в спарклайне на дне без прогонов и DoD 100 % на пустом стенде.

**Решение.**

* **Стоимость** считается по медиане токенов из собственных прошлых прогонов навыка — оценка сама
  улучшается по мере работы. У каждой строки указано ОСНОВАНИЕ: по прогонам / по каталогу /
  оценить нечем. Навык без истории не получает правдоподобного числа.
* **Один шаг** исполняется тем же `execute_agent_run`, что и обычный прогон, на временном агенте из
  одного узла. Второй путь исполнения со временем начал бы вести себя иначе, и отладка по нему
  стала бы враньём. Кэш выключен (иначе это не проверка), выход наружу выключен, `op_ids` не
  пишется: пробный шаг не вправе подтверждать участок карты.
* **Источники шага** собираются на сервере из данных, которые лежали в записи прогона всё это
  время, но были разбросаны по `findings` и `run_metrics`.

**Следствия.** Основание оценки важнее самого числа и показывается рядом с ним. Пробный шаг виден
в журнале как `step-test` и не смешивается с настоящими прогонами.

### ADR-052. Монолит расщепляется по доменам под страховкой снимка маршрутов

**Статус.** Принято 08.10.2026, **завершено 09.10.2026**: 189 маршрутов в двадцати доменах, `web_api.py` 8 648 → 1 159 строк (композиция приложения и семь служебных ручек). Раскладка — `docs/RASKLADKA_SERVERA.md`. Раскладка и порядок переноса — `docs/RASKLADKA_SERVERA.md`.

**Контекст.** `server/web_api.py` вырос до 8 648 строк и почти двух сотен ручек в одном `@app`, без единого
`APIRouter`. Шардировать сервис по домену, не расщепив файл, нельзя. Но расщепление — именно тот вид
правки, где легко потерять ручку и не заметить: тесты проверяют поведение известных эндпоинтов, а
исчезнувший никто не спросит.

**Решение.** Три правила.

1. **Снимок маршрутов** (`tests/fixtures/routes.json`) фиксирует метод и путь всех 206 маршрутов.
   Переезд между модулями его не меняет — он описывает внешнюю поверхность.
2. **Общий шов** `server/deps.py`: аутентификация, шкала уровней, ABAC. Модуль маршрутов берёт их
   оттуда; импорт `web_api` сверху запрещён и проверяется тестом — иначе расщепление сводится к
   перестановке строк между файлами.
3. **Статическая проверка имён.** При переносе ломается не поведение, а имена: функция уехала, а
   звавший её код остался. Python обнаруживает это только на живом запросе. `test_routes_modules`
   разбирает AST и ищет имена, которые читаются, но нигде не объявлены.

**Следствия.** Перекрёстные зависимости разрешаются по имени у роутера (та же функция, не копия).
Помощник, который нужен обеим сторонам и ни одной не принадлежит, — не перекрёстная ссылка, а шов:
так в `deps.py` уехал `_uid_of`, а сборка контекста отчёта — в отдельный `report_context.py`, и
только после этого домен шаблонов смог переехать, не притащив приложение за собой.

Отдельное следствие, которое легко упустить: всё, что **выводится из исходника**, обязано
разбирать весь HTTP-слой, а не монолит. Карта прав (`rbac_map`) и три статические проверки при
первом же переезде начали считать меньше, чем есть, — не сломались, а тихо ослабли. Это худший вид
регресса для экрана, который показывает права.
Один поздний импорт `web_api` внутри вызова допущен сознательно — повтор задания из DLQ зовёт
прогон, который из монолита ещё не выехал; тест падает, если таких станет больше одного: это
записанный долг, а не привычка.

Третье правило себя оправдало немедленно: первым же запуском проверка нашла ссылку на
`execute_agent_run`, переданную как значение, — замена по шаблону вызова её не задела, и обработчик
событий шины упал бы при первом же событии.

### ADR-053. Правило — данные: поставка из пакета, правка заказчика поверх

**Контекст.** Проверки вертикали были кодом вертикали. Добавить одну проверку значило правку
Python, ревью, релиз и выкатку — и так для каждого «а добавьте ещё, что название не длиннее
шестидесяти знаков». Методолог заказчика, который знает требования, не мог ничего, а разработчик,
который может всё, требований не знает. Вторая вертикаль (аудит 1С) показала цену: девять
проверок — девять кусков кода с собственной детекцией, живущих рядом с движком витрины и ничего
о нём не знающих.

**Решение.** Правило — это **предикат с параметрами, и больше ничего**. Предикаты — маленькая
библиотека в коде с тестами (`cli/checks.py`); наборы правил — данные.

- **Поставка неизменяема**: набор приезжает в пакете вертикали (`verticals/*/rules/*.json`).
- **Правка ложится поверх** отдельной записью в сторе `check_rules` — отсюда возможность
  «вернуть версию пакета» в любой момент, переживание переналадки и атрибуция: аудитору отвечают
  «правило изменил такой-то такого числа», а не «правила изменились».
- **Сохранение валидирует набор** и отказывает: неизвестный предикат или неразрешимая ссылка на
  справочник означают, что правила молча не сработают, а записи окажутся «чистыми».
- **Черновик прогоняется на выборке до сохранения** — методолог видит срабатывание раньше, чем
  правило начнёт считать находки заказчику, и видит нули так же явно, как сотни.

**Следствия.** Граница «правило против предиката» проведена тремя маркерами: вычисление по
множеству, обход графа связей, нетривиальная нормализация — это код. Как только в параметрах
завелась бы арифметика или условие на условии, получился бы язык программирования без отладчика,
типов и тестов. Цена решения названа прямо: пока предикаты пишем только мы, потолок
масштабирования — наша пропускная способность, и это плата за то, что в периметре с данными
заказчика не исполняется чужой код.

Проверено переездом двух вертикалей: приёмка — не «работает», а **совпадает поле в поле** с
базовой линией, снятой до переезда (`tests/test_audit1c_rules.py`). Сверка поймала три дефекта,
которые «работает» пропустило бы: полную запись вместо короткой ссылки в цепочке, порядок
подстановки фактов и ссылку на связь без поля, которая не подставлялась вовсе.

### ADR-054. Вертикаль — единица поставки: пакет с манифестом и одна установка

**Контекст.** Вертикаль была соглашением: папка в репозитории, из которой человек раскладывал
контракт, агента, рецепты и наборы правил. Четыре операции руками, ни одна не проверяла
остальные, и ни одна не отвечала на вопрос «что сейчас стоит у заказчика». А монетизация
строится именно на вертикали как на том, за что платят (`docs/MONETIZATION.md`) — платить за
соглашение нельзя.

**Решение.** `verticals/<id>/` с манифестом `vertical.json` и одной операцией установки.

- **Манифест не имеет права врать о содержимом.** Сверка идёт в обе стороны: обещанный файл
  обязан быть, незаявленный — ошибка. Пакет читают глазами по манифесту, а ставят по файлам;
  расхождение означает, что заказчик получит не то, что прочитал. Невалидный пакет не ставится.
- **Пакет не несёт Python** — ни предикатов, ни адаптеров, ни навыков как кода. Что нужно, то
  объявлено в `требует` и должно быть в системе заранее; нет навыка — честный отказ, а не
  установка, которая «прошла», и прогон падает позже.
- **Установка не трогает правки заказчика.** Набор правил, который правил методолог, остаётся
  как есть, и это **названо в отчёте**, а не решено молча. Снять правку — только явным запросом.
- **Отчёт за каждое действие**: поставлен / обновлён / пропущен с причиной.
- **Агент ставится черновиком.** Посадка на участок карты — отдельное решение человека
  (ADR-043): установка пакета не имеет права сама начать работать в чужом процессе.

**Следствия.** `метрика` — обязательное поле манифеста: пилот продаётся как измерение на прошлом
периоде заказчика, и пакет обязан сказать, чем мерить. CLI (`ape verticals`) ходит в ту же ручку,
что интерфейс — второго пути установки нет, иначе он разойдётся с проверками; тест запрещает в
команде прямые обращения к сторам.

Чего формат не умеет, сказано в `docs/VERTIKALI.md` открытым списком: навыки и карта процесса
в пакет не входят, версионного обновления с диффом нет, арендаторов нет. Последнее — блокер
лицензионной модели целиком, и это цена входа в выбранную монетизацию, а не отдельная фича.

### ADR-055. Арендатор: изолируют сторы, а не маршруты

**Контекст.** Лицензионная модель («компания собирает своих агентов») означает, что на
платформе живут несколько компаний. Тенанта не было ни у записей, ни у агентов, ни у
прогонов, ни у карты — вторую компанию продать было нельзя. Напрашивавшийся путь — проверять
арендатора в ручках — отвергнут сразу: двести ручек, и каждая новая — новая дыра, которая
найдётся у заказчика.

**Решение.** Арендатор живёт в контексте запроса (`contextvars`, `server/tenancy.py`) и
ставится ОДИН раз — в шве аутентификации. Фильтруют по нему **хранилища**: ручка физически не
может прочитать чужое, даже если её автор о тенантах не думал. Тот же приём, что с
аутентификацией, и та же причина.

Четыре следствия, которые пришлось принять, а не обойти.

1. **Арендатор входит в ПЕРВИЧНЫЕ ключи**, а не только в фильтр. Идентификаторы у разных
   арендаторов совпадают по построению: поставили одну вертикаль — контракт у обоих
   `omninet-showcase-2026`, агент `…v1`, набор правил `showcase-b`, рецепт `omninet_feed`.
   Пока ключ был одиночным, второй заказчик затирал первого — молча и необратимо.
2. **Чужое отвечает «нет такого», а не 403.** Существование чужого агента само по себе
   сведение о другой компании; по перечню сущностей Data Plane видно, чем сосед занимается.
3. **Фоновые пути передают арендатора явно.** Прогон исполняет воркер: арендатор едет в
   задании и ставится вокруг обработчика. Планировщик обходит арендаторов списком — иначе
   расписания всех, кроме арендатора по умолчанию, МОЛЧА не запускались бы, а тихое
   неисполнение хуже ошибки.
4. **Сквозных читателей ровно два и они названы**: `claim` очереди (воркер берёт задание
   любой компании) и `agent_store.арендаторы()` (перечень для планировщика).

**Следствия.** Главной защитой стал не поведенческий тест, а статический сторож: он разбирает
все SQL-литералы в `server/*.py` и требует фильтр по арендатору в каждом запросе к таблице с
ним. Поведенческий тест проверяет то, о чём автор подумал; сторож — то, о чём забыл, а
пропущенный фильтр это утечка, а не неудобство. Сторож нашёл двадцать дыр в карте процессов
сразу после того, как заработал.

Из этого вышло требование к стилю: **фильтр по арендатору пишется текстом запроса**, а не
первым элементом списка условий — список можно переставить, и сторож этого не увидит. И
отдельный урок: первая версия сторожа искала литералы регуляркой, один апостроф в русской
строке документации съел тысячи символов, и сторож находил НОЛЬ запросов, оставаясь зелёным.
Разбор переведён на `ast`. Сторож, который ничего не разобрал, хуже отсутствующего.

Миграция идемпотентна и безопасна: колонка добавляется со значением `default`, то есть всё
уже лежащее достаётся той единственной компании, для которой система и работала. Пока в
Keycloak не добавлена заявка `tenant`, поведение не меняется вообще.

### ADR-056. Подбор исполнителя: модель называет работу, правила отвечают за исполнимость

**Контекст.** Подбор навыка под задачу стоял на словаре: основы слов, вес обратной частоты по
каталогу, контракты входов и выходов, плюс две маленькие прибавки — личная склонность человека и
связь слов запроса с прошлыми правками. Лесенка (`ops/planner_ladder.py`) измерила предел этого
подхода: на формулировке, которой журнал решений не видел, словесная прибавка оказалась РОВНО
нейтральна — 18 из 62 попаданий первым с ней и без неё. Причина не в весах и не в пороге: «кто мне
не заплатил» и «дебиторская задолженность» не имеют ни одной общей основы, и мешок слов не свяжет
их никаким коэффициентом.

**Решение.** Голос модели как отдельный довод подбора (`server/semantic_pick.py`): модели даётся
задача и ЗАКРЫТЫЙ список каталога (идентификатор, название, назначение, характерные слова из того
же индекса, по которому считает словарный подбор), она возвращает до трёх идентификаторов.

Первая версия слияния добавляла голос прибавкой с потолком — «решает ничью, а не назначает
исполнителя». Замер на 126 запросах (`ops/planner_model.py`) показал, что так разрыв не
закрывается: правила 18 из 63, правила с прибавкой 31, а предел ЛЮБОГО слияния на этом наборе —
50. Словарный счёт похожего, но неправильного навыка перебивал голос модели при любом весе ниже
своего, а большой вес вдобавок тащил в план второй и третий выбор модели и ставил их первыми.

Поэтому работы разделены по тому, в чём каждая сторона сильна:

* **модель называет РАБОТУ** — её первый выбор весит `semantic_pick.ВЕДЁТ` = 1.2, то есть больше
  любого словарного счёта вместе с прибавками за названный адресат и источник;
* **правила отвечают за исполнимость и порядок** — достраивают поставщиков входов, отсекают навыки,
  под которые нет данных сущности, ранжируют всё остальное;
* **объявленный контракт сильнее голоса модели**: если человек назвал результат («письма»), навык,
  объявивший такой выход, остаётся впереди. Это сведения, а не догадка.

Второй и третий выбор модели в счёт не идут вовсе — замер весов 0.0…0.3 для них не изменил ни
одного попадания из 126. Они остаются в ответе как сведения человеку.

**Числа.** На отложенной формулировке: 18 из 63 первым → 41 из 63; в плане 21 из 63 → 48 из 63.
Из 48 случаев, где первый выбор модели верен, 39 выходят в плане первыми, в 7 первым законно встаёт
поставщик входа (`audit1c-extract` обязан идти раньше `audit1c-checks`), в 2 правила навык не
пустили — данных сущности нет, и прогон всё равно не состоялся бы. Выдуманных идентификаторов за
126 запросов — ноль. Цена одного подбора на каталоге из 63 навыков: 2946 входных токенов,
25 выходных, 0.71 с на своём боксе.

Отдельно названо, чтобы не выглядело точнее, чем есть: `temperature=0` НЕ делает ответ побитово
повторимым на сервере, считающем запросы пачками. Два полных опроса подряд дали 40 и 41 из 63 и
два молчания против нуля. Отчёт воспроизводим по сохранённым ответам
(`ops/planner_model_votes.json`); вывод делается по разнице 18 против 41, а не по второму знаку.

**Три защиты, без которых голос модели опаснее пользы.**

1. **Закрытый список.** Перечень задаётся схемой ответа (`enum` в json_schema — движок физически не
   даст выйти за каталог) И проверяется в коде: другой эндпоинт грамматику может не поддержать.
   Выдуманный идентификатор не отбрасывается молча — он виден в ответе как `лишние`, потому что это
   признак либо плохого промпта, либо модели, которой нельзя верить.
2. **Отказ назван.** Эндпоинт недоступен, ответ не разобрался, модель назвала одну чепуху — подбор
   продолжает работать словарём, а в ответе стоит `подбор_моделью.участвовала = false` с причиной.
   «Модель подумала» там, где она молчала, — ложь в том самом месте, по которому принимают решение.
3. **«Почему» не выдаёт голос модели за совпадение слов.** Счёт навыка, названного моделью,
   складывается из её веса и словарной части; написать про такой счёт «совпадение 1.44» значило бы
   соврать в самой читаемой строке карточки. Там, где ведёт модель, так и написано, а словарная
   часть названа отдельным числом.

**Выключатель.** `ABOP_PLAN_MODEL` (по умолчанию включено — по результату замера, а не заранее).
Выключение возвращает прежний словарный подбор целиком; эндпоинт может оказаться платным или
недоступным, и тогда это единственно верное поведение.

**Чего это решение НЕ утверждает.** Фразы и правильные ответы набора `planner_sim.json` составлены
ассистентом, а не взяты у людей: абсолютный уровень — мера согласия подбора с этими формулировками,
смысл имеет разница между видами на одном наборе. Числа получены на `qwen3-30b-a3b`, который и так
обслуживает прод, — то есть шов работает на уже оплаченной модели. Замысел с маленькой моделью
(0.5–0.8B на том же боксе) остаётся оптимизацией задержки и ёмкости, а не условием работы: пока она
не поднята и не перемерена тем же `ops/planner_model.py --base/--model`, утверждать её качество
нельзя.

### ADR-057. Подбор ведёт ПОРЯДОК близости, а не прибавка за близость

**Контекст.** ADR-056 поставил в подбор голос генеративной модели по закрытому списку и дал ему
вес выше словарного счёта. Через несколько часов измерили то, что надо было измерить раньше: а
сколько даёт ЭМБЕДДЕР, который в системе уже стоял. Выяснилось два факта, и оба меняют решение.

**Факт первый: смысловой слой мог не работать вовсе, и этого не было видно.** В рабочем `.env`
разработчика стояло `ROUTEAI_EMBED_MODEL=bge-m3`, RouteAI отвечает на такой идентификатор
`400 Model not found`, а `_skill_semantics` глушила исключение как best-effort: мёртвый эндпоинт
выглядел ровно как «ничего похожего не нашлось» — ни в ответе ручки, ни в интерфейсе.

Поправка к первой редакции этого ADR: на ПРОДЕ переменной не было задано вообще, то есть действовал
верный дефолт `baai/bge-m3` и смысл там работал. Утверждение «на проде слой мёртв» было ошибкой —
проверено 13.10 чтением `/opt/abop/.env`. Дефект реален (машина разработчика), а урок общий:
молчаливая деградация опаснее поломки, и проверять надо ту установку, про которую делаешь
утверждение.

**Факт второй: прибавка за близость почти ничего не даёт, а порядок даёт много.** На 63 отложенных
формулировках прибавка с порогом `SEM_FLOOR=0.45` и потолком `SEM_CAP=0.25` добавляет +1 попадание
(18 → 19). Тот же эмбеддер, ведущий подбор своим ПОРЯДКОМ, даёт 34 из 63, а `gemini-embedding-2` —
53 в плане. Причина в распределении: средняя близость к верному навыку 0.518, к лучшему чужому
0.509; выше порога оказываются 55 верных близостей и 56 чужих. Порог по абсолютному косинусу на
коротких русских формулировках не несёт сведений — несёт порядок.

**Решение.**

1. Работу называет **ведущий голос**: самый близкий по смыслу навык получает вес
   `semantic_pick.ВЕДЁТ` = 1.2, больше любого словарного счёта. Правила отвечают за исполнимость и
   порядок: достраивают поставщиков входов, отсекают навыки без данных сущности.
2. **Генеративный подбор становится фолбэком** и выключается по умолчанию
   (`ABOP_PLAN_MODEL=0`). Замер: эмбеддер 51–53 из 63 в плане против 48 у 30B, дешевле в сорок
   раз; поверх эмбеддера голос модели не добавляет ничего (43–44 против 46 — проверено
   двухступенчатой схемой «сузить до пяти, выбрать из пяти»). `1` — спрашивать, когда смысл молчит;
   `всегда` — для сравнения механизмов на стенде.
3. **Молчание слоя названо в ответе**: `подбор_смыслом` (работает, какая модель, кого повёл, почему
   молчит) и `работу_назвал` (`смысл` / `модель` / `правила`). Выключатель `ABOP_PLAN_SEMANTICS`
   для закрытого контура без эмбеддера.
4. **Реранкер не нужен**: `cohere/rerank-v3.5` 23 из 30 и `qwen3-reranker-8b` 24 из 30 против 26 у
   эмбеддера на тех же случаях, при большей цене. Клиент `clients.rerank` никем не вызывается.

**Что ставить — в `docs/MODELI_PODBORA.md`** (сравнение восьми моделей, цена подбора, арифметика
видеопамяти бокса, команды для перезамера). Коротко: демо — `google/gemini-embedding-2` через
RouteAI; закрытая установка — `Qwen/Qwen3-Embedding-4B` своими силами (её 51 из 63 и есть то число,
по которому можно давать продуктовое обещание, потому что веса gemini закрыты и в контур заказчика
она не поедет). Версия 0.6B той же семьи даёт 37 из 63 — не лучше уже стоящего `bge-m3`, то есть
экономия 6.8 ГБ видеопамяти стоит 22 процентных пункта точности.

**Следствия и честные оговорки.** Фразы набора составлены ассистентом, а не взяты у людей:
абсолютный уровень — мера согласия с этими формулировками, сравнивать механизмы между собой он
позволяет, обещать «точность продукта» — нет. Набор один и каталог один (63 навыка); на каталоге в
триста навыков порядок моделей может измениться. Отдельный урок про тесты: как только
идентификатор эмбеддера починили, прогон набора начал отправлять 63 описания навыков в платный
эндпоинт на каждом запуске — появился `tests/conftest.py`, который гасит ключ и оба сетевых слоя.

### ADR-058. Канал в мессенджере: узкий токен и запрет необратимого

**Контекст.** Десктоп и веб требуют рабочего места. Руководитель в дороге хочет не «посмотреть
дашборд», а спросить словами и получить ответ. Это те же агенты и тот же подбор — меняется только
доставка. Но доставка в мессенджер приносит два вопроса, которых не было ни у одного канала: чем
процесс, доступный из интернета, ходит в ABOP, и что ему вообще позволено.

**Решение по аутентификации.** Не offline-токен Keycloak, а собственный узкий токен ABOP на каждую
привязку. Offline-токен был первым кандидатом и отвергнут: он несёт ПОЛНЫЕ права человека, включая
внешние действия через другие каналы и, если человек admin, всю админку, — то есть утечка файла с
токенами бота равна утечке учётных записей. Узкий токен имеет уровень `analyst` (свойство самой
личности: `require_level` считает по ней, а не проверка в каждом маршруте), не переключает
арендатора, сохраняет отдел человека и отзывается одной строкой в своей базе без обращения к
Keycloak.

Привязка без браузера: человек в приложении берёт одноразовый код (восемь знаков, 15 минут, один
раз, алфавит без `0/O` и `1/I` — его диктуют), отправляет боту, бот меняет код на токен через ручку,
защищённую секретом бота и пределом 10 попыток в минуту. В базе только `sha256`. Код и токен САМИ
устанавливают арендатора — бот его не знает и знать не может; это второй законный сквозной читатель,
объявленный в стороже с обоснованием.

**Решение по правам.** Канал запускает только то, что читает и считает:

1. **Внешние действия запрещены на ЗАПУСКЕ прогона**, а не фильтром списка агентов. Спрятать агента
   в списке — защита от интерфейса, а не от запроса. Правило «действует наружу» вынесено в
   `assembly.действует_наружу` (спрашивают из трёх мест, три копии разошлись бы на первой правке).
2. **Подтверждать необратимое через мессенджер нельзя**: там нет ни карточки действия, ни вида на
   последствия, а сообщение прокручивается и кнопка нажимается случайно.
3. **Сборку агента бот не обещает** — это мутация уровня `manager`. Если готового исполнителя нет,
   он называет навыки и отправляет в приложение.
4. **Групповые чаты отклоняются.** Привязка даётся на чат, и в группе ею воспользовался бы любой
   участник: запускал бы агентов от имени привязавшего и читал его данные.
5. **Каналом нельзя выпустить ещё один канал** — иначе утёкший токен плодит привязки без конца.

**Честность ответов — часть решения, а не стиль.** Ответ на задачу всегда несёт номер прогона, имя
агента и стоимость: в мессенджере спрашивают часто, и без цены человек не видит, что спросил за
деньги. Обрезка списка находок помечается («и ещё N»), обрезка длинного ответа помечается, идущий
дольше четырёх минут прогон не выдаётся за неудачу (бот называет номер задания), отказ сервера
пересказывается целиком вместе с тем, куда идти.

**Устройство.** Отдельный процесс `ops/telegram_bot.py` на стандартной библиотеке, долгий опрос
`getUpdates` (webhook потребовал бы публичного адреса для бота; опрос работает и из закрытого
контура). Файл привязок `~/.abop-bot/bindings.json` с правами 600 — это секрет, и именно поэтому
токены в нём узкие. Подробности и команды запуска — `docs/KANAL_TELEGRAM.md`.

**Чего в канале нет и почему** — названо в документе: вложения (приём файла без просмотра
содержимого — загрузка неизвестного в прогон), подтверждения HITL, уведомления о чужих прогонах,
webhook.

### ADR-059. Канал в мессенджере: письмо коллеге можно, необратимое за пределами почты — нет

**Контекст.** ADR-058 запретил каналу любое внешнее действие. Владелец уточнил замысел (13.10):
канал нужен ровно для двух вещей — **спросить данные и отослать их коллегам**. Прежний запрет
отрезал вторую, то есть половину смысла канала.

**Решение.** Запрет «любое внешнее действие» заменён точным перечнем:

* разрешены навыки режимов `read` и `write` — в том числе составление письма; `action` нет;
* разрешён один канал доставки — почта (`channel_tokens.КАНАЛЫ_ДОСТАВКИ`); задача в трекере,
  запись в систему учёта, публикация — нет;
* проверка стоит **на запуске прогона** и перечисляет, что именно запрещено.

**Почта необратима, поэтому к ней идут две защиты, а не одна.**

1. **Подтверждение человеком — всегда.** Прогон из канала рождает заявку принудительно, даже если
   автономия агента позволяет отправить саму: признак канала едет с заданием в очередь и доходит до
   доставки (`run_exec._deliver_out_nodes`). Бот показывает письмо целиком — кому, тема, текст — и
   ждёт слова «отправить»; «не надо» отклоняет; любое другое сообщение заявку не трогает, потому что
   случайное «ок» в переписке не должно отправлять письмо.
2. **Адресат обязан быть коллегой.** Перечень доменов организации — `ABOP_COLLEAGUE_DOMAINS`. Не
   задан ⇒ отправка из канала закрыта (fail-closed): ограничение без перечня — это предложение, а
   не ограничение, и молча считать всех коллегами нельзя.

**Исключение в правах — точное и в одном месте.** Канал имеет уровень `analyst` и мутаций не
проходит, иначе он не смог бы подтвердить отправку. Поэтому `routes/hitl._можно_решать` пускает
канал, если: заявка по разрешённому каналу (почта), заявка СВОЯ (её запросил тот же человек) и
адресат — коллега. Отклонить каналу можно всегда: отказ от отправки необратимым не бывает. Обычный
путь (`manager+` подтверждает что угодно) не изменился.

**Поправка к ADR-057.** Там написано, что смысловой слой был мёртв в проде из-за неверного
`ROUTEAI_EMBED_MODEL`. Это ошибка: на проде переменной не было задано вообще, действовал верный
дефолт `baai/bge-m3`, слой работал. Неверный идентификатор был в рабочем `.env` разработчика.
Проверено 13.10 чтением `/opt/abop/.env`. Дефект реален, но радиус — машина разработчика; урок
общий: проверять надо ту установку, про которую делаешь утверждение.

### ADR-060. Лестница ответственности: уровень действия решает цена отката и адресат

**Статус.** Принято 13.10.2026. Реализует `docs/PRD_RESHENIYA_I_RUKOVODITEL.md`, раздел 2.

**Контекст.** Подтверждения у нас было два вида: HITL-гейт на OUT-узле (ADR-014, «наружу — под
подтверждением») и уровень доступа `manager+` на решение заявки. Оба отвечали на вопрос «можно
ли», но ни один — на вопрос «**кто** решает». Из этого вышли три беды, и третья хуже первых двух:

1. заявка адресовалась отделу, а не человеку, — ответственность размывалась;
2. подтверждать требовалось **последний шаг** цепочки, когда всё остальное уже произошло;
3. решение упиралось в уровень доступа, а не в обязанности, — то есть отправку КП подтверждал бы
   не менеджер по продажам, а его начальник. Владелец отверг это прямо: *«агентный подход
   определяет, что решения принимаются быстро, а значит точкой решения должен быть менеджер в зоне
   ответственности; иначе мы превращаем руководителя в нажимателя кнопок»*.

**Решение.** Введён один модуль `server/levels.py` — класс действия → уровень → кто решает:

| уровень | класс | кто решает | примеры |
|---|---|---|---|
| У1 | `внутри` | никто, выполняется сразу | задача в трекере, страница в вики, письмо коллеге |
| У2 | `наружу` | **исполнитель прогона** | письмо клиенту, КП, публикация наружу |
| У3 | `необратимое` | `manager+` (менеджер зоны) | платёж, подписание, массовая рассылка |

Четыре свойства решения, каждое из которых выбрано против очевидной альтернативы:

* **`egress` реестра систем за основу НЕ взят.** В `systems_store` `egress` — сетевой факт («вызов
  уходит с хоста»), и Redmine по нему `external`. Взяв его, мы заставили бы половину внутренней
  работы спрашивать человека; люди привыкли бы жать «да» не читая, и подтверждение обесценилось бы.
  Класс канала объявлен отдельной таблицей `levels.КЛАСС_КАНАЛА`.
* **У почты класс зависит от адресата, а не от канала.** Письмо коллеге — У1, то же письмо
  клиенту — У2; решает перечень доменов организации `ABOP_COLLEAGUE_DOMAINS`, который перестал
  быть особенностью бота и стал общим правилом. Поддомены доверие не наследуют: граница
  безопасности не должна быть хитрым выражением.
* **У3 никогда не выводится из имени.** «Платёж» в названии навыка — совпадение слов, а не
  доказательство; выводы такого сорта мы критикуем у чужого продукта (`RAZBOR_SCADA.md`). У3
  возникает только объявлением `out.класс = "необратимое"` у узла. Объявление **поднимает** класс,
  но не опускает — иначе оно стало бы способом обойти лестницу.
* **У3 подтверждается ДО запуска.** Агент с объявленным необратимым действием не запускается
  напрямую: рождается заявка `kind: spawn`, человек видит сценарий целиком и решает один раз.
  Заявка несёт исходный запрос (предмет работы, контекст, выбор доставки, заказчика), иначе
  подтверждённый прогон ушёл бы с пустым контекстом — то есть сделал не то, что подтвердили.

**Политика канала осталась отдельно от лестницы, и это не дубль.** Лестница отвечает «какого
уровня действие», политика канала (`channel_tokens.вне_канала`) — «что вообще можно начинать из
переписки», и она **уже** лестницы: по лестнице задача в трекере — У1, но из мессенджера она не
заводится (решение владельца: канал нужен спросить данные и отослать их коллегам письмом). При
первой попытке свести оба вопроса в одну проверку бот получил бы право писать в Redmine и вики — не
потому, что так решили, а потому что уровень позволил.

**Последствия.** `analyst` теперь подтверждает **свою** внешнюю отправку (У2) — это и есть перенос
решения туда, где лежит ответственность. Чужую заявку по-прежнему закрывает `manager+` (человек в
отпуске — письмо не должно висеть), необратимое — только `manager+`. Прежнее правило «любая заявка
требует `manager`» отменено.

**Принятая цена.** Класс объявляют люди, и объявить его можно забыть: агент с реальным платежом,
но без `класс: необратимое`, пройдёт как У1/У2. Альтернатива — угадывать необратимость по именам —
хуже: она даёт ложное чувство защиты и ломается молча. Поэтому путь обратный: класс виден в
карточке решения и в ленте контроля руководителя, и незаявленное необратимое обнаруживается
просмотром того, что уже ушло, а не доверием к догадке движка.

**Что проверено.** `tests/test_levels.py` (18 проверок, включая лазейку с занижением класса,
fail-closed на пустом перечне доменов, запрет вывода У3 из имени и единственность чтения перечня
доменов) + `tests/test_channel_tokens.py` (политика канала уже лестницы). Девять сторожей проверены
мутациями: каждый краснеет на сломанном коде.

### ADR-061. Путь по умолчанию у точки решения: черновик вместо отправки, цепочка доходит до конца

**Статус.** Принято 13.10.2026. Реализует `docs/PRD_RESHENIYA_I_RUKOVODITEL.md`, раздел 3.

**Контекст.** Шаг, требующий подтверждения, переводил задание в `awaiting_hitl` и ждал человека.
Техническая часть была в порядке — воркер не блокировался (чекпоинт, `locked_by=NULL`), — но
**обещание бизнесу не выполнялось**: цепочка не доходила до конца, и всё, что ждало её результата,
ждало человека. Это разные вещи, и первая легко маскирует вторую: метрики очереди зелёные, работа
не сделана. Карточка при этом говорила «ожидает подтверждения оператора» — то есть сообщала об
ожидании, а не о том, что работа уже готова.

**Решение.** У точки решения объявлен **путь по умолчанию, который делает обратимое вместо
необратимого**:

* письмо не отправляется — кладётся **готовым черновиком** (`levels.ОБРАТИМОЕ`);
* задача в трекере не создаётся — готовится заготовкой;
* цепочка **идёт дальше**: downstream получает результат, необратимое не происходит;
* человек решает не «можно ли продолжать», а «превратить ли обратимое в необратимое».

**Где цепочка всё-таки ждёт — и почему это не исключение, а то же правило.** Ждать приходится там,
где обратимого аналога НЕТ: у команды в шине черновика не бывает — она либо опубликована, либо нет,
и «черновик команды» был бы выдумкой. Плюс автор узла может потребовать ожидания явно (`wait`),
если следующий шаг читает именно отправленное. Оба случая — объявление, а не догадка движка.

**Жизнь черновика — 30 дней в «Результатах» как обычный файл** с пометкой «не отправлено» и
действием «отправить» из карточки (решение владельца). Дальше фоновая уборка переводит его в
`expired` — **закрывает, но не удаляет**: стереть черновик значит потерять ответ на вопрос «что мы
не отправили и почему». Уборка — один идемпотентный UPDATE, без выбора главной реплики.

**Последствия.** Ожидание перестаёт быть тормозом: ждёт одно последнее действие, а не процесс.
Карточка доставки теперь несёт уровень, основание, имя черновика и признак «не отправлено», а
чекпоинт цепочки — список того, что осталось черновиком: иначе человек узнавал бы об этом от
клиента, а не от нас.

**Принятая цена.** Цепочка может дойти до конца, не выполнив внешнего действия, — и это надо
читать правильно: «работа сделана, отправка ждёт решения», а не «всё готово». Поэтому формулировки
в карточке говорят прямо: «черновик письма готов, не отправлено — ждёт вашего решения». Второй
риск — черновик, о котором забыли; он снимается сроком (30 дней) и разделом «Решения» со
счётчиком, а не надеждой на внимательность.

**Что проверено.** `tests/test_default_path.py` (12 проверок: обратимый аналог, неотправленность,
ожидание только невозвратного, срок, идемпотентность уборки, состав карточки). Десять сторожей
прогнаны мутациями — каждый краснеет на сломанном коде, включая самый опасный исход: «не вставать»
прочитано как «отправлять».

### ADR-062. Срок решения — свойство действия; молчание не согласие и не смерть цепочки

**Статус.** Принято 13.10.2026. Реализует `docs/PRD_RESHENIYA_I_RUKOVODITEL.md`, раздел 3.

**Контекст.** Задание в `awaiting_hitl` висело **бессрочно и молча**: ни срока, ни исхода, ни
строки «кто не ответил и что не доехало». Человек ушёл в отпуск — цепочка ждёт его возвращения, и
узнать об этом можно было только из журнала прогонов, если догадаться туда посмотреть.

**Решение.** У действия есть срок решения. Он **объявляется у OUT-узла** (`срок_часов`,
`deadline_hours`, `срок_сек`), не объявлен — действует `decisions.СРОК_ПО_УМОЛЧАНИЮ` = 3 суток;
явный ноль означает «ждать сколько потребуется». Разных сроков по уровням намеренно нет: придумать
«У3 — сутки, У2 — трое» легко, обосновать нечем, а число, за которое никто не отвечает, мы не
показываем.

**По истечении срока происходит ровно три вещи, и ни одной больше:**

1. запись в журнал `hitl.expired` с причиной словами: «решение не принято за N ч — доставка не
   состоялась, черновик письма остался черновиком»;
2. пометка на карточке (`срок_истёк`), по которой это видно в «Решениях» и в ленте контроля;
3. припаркованное задание цепочки возвращается в очередь с решением `expired` — следующий шаг идёт
   с этим знанием, а не висит навсегда.

**Чего НЕ происходит: отправки.** Молчание не согласие на необратимое — это главный инвариант
записи, и он проверяется тестом, который читает сам модуль: появление `_send_channel` или
`approve` в проходе по срокам ломает сборку. Иначе срок стал бы способом отправить письмо без
человека, то есть прямо противоположным тому, зачем он введён.

**Двое часов, а не одни.**

| часы | сколько | конец |
|---|---|---|
| срок решения | 3 суток или объявленный у узла | перестаём ждать; черновик остаётся на полке |
| жизнь черновика (ADR-061) | 30 суток | черновик уходит в `expired` с полки «Результатов» |

Свести их в одни значило бы либо выбросить черновик через трое суток (владелец решил — месяц),
либо месяц делать вид, что цепочка не закончена. Тест держит и это: срок решения обязан быть
короче жизни черновика.

**Где это живёт.** Новый модуль `server/decisions.py`: срок связывает заявку (`hitl_store`),
припаркованное задание (`run_queue`) и журнал (`audit_store`) — в стор такую связку класть нельзя
(дал бы стору зависимости на половину сервера), в маршрут тоже (фоновая работа спряталась бы в
HTTP-домене). Туда же переехал возврат задания из ожидания: его зовут и маршрут, и фоновый проход,
и двух копий у него быть не должно.

**Принятая цена.** Проход идёт раз в 5 минут, то есть отметка о просрочке запаздывает на минуты —
для срока в сутки это незаметно, для срока в минуты механизм не годится, и так и объявлено.
Идемпотентность держится пометкой в payload, поэтому реплик может быть сколько угодно без выбора
главной.

**Что проверено.** `tests/test_decision_deadline.py` (15 проверок). Одиннадцать сторожей прогнаны
мутациями, включая оба перегиба: «по истечении срока отправить» и «по истечении срока выбросить
черновик».

### ADR-063. Решение адресовано человеку: `addressed_to` и владелец операции в карте

**Статус.** Принято 13.10.2026. Реализует решение владельца 1 и `PRD_RESHENIYA_I_RUKOVODITEL.md`,
раздел 2 (строка «адресат заявки — человек, а не отдел»).

**Контекст.** Заявка на подтверждение была адресована ОТДЕЛУ: видимость считал `can_see_family`, и
«кто решает» означало «кто угодно с нужным уровнем в этом отделе». Это классическое размывание
ответственности — каждый думает, что подтвердит другой, — и оно же мешало поставить решение туда,
где лежит обязанность (ADR-060).

**Решение.** У заявки есть `addressed_to` — кому адресовано решение:

* **У2 — исполнителю прогона.** Решает тот, чей это прогон: отправку КП подтверждает менеджер по
  продажам, а не его начальник.
* **У3 — владельцу операции в карте процессов.** Формальный источник истины — поле `owner` у узла
  карты (новый вид правки `set_owner`). Выбрана **карта, а не уровень доступа**: карта описывает
  ответственность за участок, уровень — права; смешать их значит получить два источника истины,
  которые разойдутся на первом кадровом движении.
* **Владелец ищется ВВЕРХ по дереву** — операция → процесс → область. Ответственность в
  организации наследуется, и карта не обязана называть владельца у каждого листа.
* **Не нашлось — поле пустое, заявка видна отделу, как раньше.** Честный фолбэк: лучше отдел, чем
  выдуманный адресат. Неизвестный идентификатор операции владельца НЕ получает — иначе директор
  станет ответственным за опечатку, и опечатка спрячется.

**Адресность сужает отдел, а не заменяет его.** `can_see_family` остался: заявка с опечаткой в
адресате не должна стать невидимой вообще для всех. Адресат решает сам **независимо от уровня
доступа** (владелец операции может быть `analyst` — требовать от него `manager` значит вернуть
размывание), а чужое адресованное решение закрывает только `manager+`: человек ушёл в отпуск, а
письмо осталось.

**Почему `set_owner` — отдельный вид правки со своим множеством записи.** Назначить владельца и
переименовать блок — разные поля одного узла, и общий ключ конфликта (`цель`) делал бы их спором на
пустом месте. Два назначения владельца одному узлу конфликтуют, удаление поддерева рушит назначение
внутри — это те конфликты, которые нужны.

**Последствия.** `hitl_items` получила колонку `addressed_to` (миграция `ADD COLUMN IF NOT EXISTS`
+ частичный индекс по ждущим). Раздел «Решения» (`/api/hitl/queue?mine=1`) отдаёт адресованное мне
ПЕРВЫМ, затем моё по прогонам: где ждут именно меня — важнее, чем где я и так в курсе.

**Принятая цена.** Владелец в карте — текст, а не ссылка на учётную запись: карта называет
ответственного так, как его называют в компании. Сверка с аккаунтами — дело сквозного ID
(ADR-«Identity Map»), и пока её нет, опечатка в имени владельца означает заявку, которую закроет
`manager+` отдела. Это заметно и исправимо, в отличие от молчаливой потери адресата.

**Что проверено.** `tests/test_addressed_to.py` (13 проверок: наследование вверх, снятие владельца,
конфликты правок, права адресата и чужого, фолбэк У3 без владельца). Девять сторожей прогнаны
мутациями.

### ADR-064. Итог прогона в числах с происхождением; «вы у экрана» считает приложение

**Статус.** Принято 13.10.2026. Реализует `PRD_RESHENIYA_I_RUKOVODITEL.md` раздел 10.5 и
`RAZBOR_SCADA.md` 2.1 / 4.4.

**Контекст.** Под результатом прогона у нас не было ответа на вопрос «что мне это дало». Числа
существовали — шаги, время, стоимость лежали в `run_metrics`, — но на экран не выносились, а
четвёртого числа, «минут человека», не было вовсе. Отдельно: «что идёт прямо сейчас» жило в трёх
местах (очередь заданий, ожидание в чате, расход в шапке), и человек, открывший приложение, не мог
ответить на это, не прокручивая экраны.

**Решение.**

* **Итог собирает одна функция — `server/run_card.итог_в_числах`.** Не каждая панель: карточка
  прогона в чате однажды уже разошлась с карточкой в журнале (держала план, собранный до правки
  подбора), и разошлась молча. Итог едет в теле прогона, поверхности его только показывают.
* **У набора чисел обязательна строка происхождения.** Чем посчитано: модель и токены, сколько
  времени ушло в модель, сколько было решений человека. Прогон без обращений к модели так и
  говорит — «посчитал движок правилами»: это наш случай и наше отличие, прятать его незачем.
* **«Вы у экрана» считает приложение на компьютере человека и хранит у себя** (таблица `attention`
  в базе сайдкара). Сервер не знает, сколько карточка была открыта, и узнать не может; делать вид,
  что знает, — врать. В происхождении так и написано: «время у экрана считает приложение на этом
  компьютере». Замер копится (карточку открывают несколько раз), имеет порог снизу (2 с — мелькнувшая
  карточка не «время у экрана») и предел сверху (30 мин на один заход: счётчик в окне не
  останавливается на спящем компьютере, и восемь часов «внимания» означали бы закрытый ноутбук).
* **Строка живой работы** — одна строка над содержимым, видна из любого раздела: что идёт, какой
  шаг, сколько времени, место в очереди, кнопка «Открыть». Источник — `pending_runs` местной базы,
  то есть задания, которые запустил ЭТОТ человек, а не общий `/api/fleet` (там флот целиком по
  всему отделу). Пауза опроса растёт, когда ничего не идёт: пустой опрос раз в пять секунд — это
  батарея ноутбука за то, что никому не нужно.

**Чего в итоге нет.** «Сэкономлено N часов» — норматива отдела у нас нет, и выдумывать его нельзя
(PRD, раздел 7); появится названный человеком норматив — появится число. Карточка из одного «0 ₽»
тоже не показывается: это не ответ на вопрос «что мне это дало», а шум.

**Принятая цена.** «Вы у экрана» живёт только на компьютере человека: переустановил приложение —
число начинается заново, и в управленческие срезы оно не попадает. Альтернатива — гнать его на
сервер — означала бы хранить личное наблюдение за человеком в общей базе, причём с сомнительной
точностью. Для сводок руководителя есть другие числа (ADR следующего пункта: вынос полей `runs`).

**Что проверено.** `tests/test_run_card.py` (12 проверок: состав чисел, происхождение, прогон на
правилах, одинокий ноль, запрет выдуманных величин, границы замера, строка живой работы).
Двенадцать сторожей прогнаны мутациями; два из них по ходу оказались слепыми (проверяли наличие
имени, а не его использование) и переписаны на проверку самого выражения.

### ADR-065. Управленческие поля журнала — колонками; срезы руководителя в Grafana, а не новыми экранами

**Статус.** Принято 13.10.2026. Реализует `PRD_RESHENIYA_I_RUKOVODITEL.md`, раздел 10.6.

**Контекст.** Руководителю нужны срезы: сколько стоил отдел за неделю, кто сколько запускал, что
ушло наружу, что не дошло. Решение владельца — **брать для этого Grafana, а не строить новые экраны
в вебе**: экран надо проектировать, поддерживать и объяснять, а сводка в Grafana правится запросом.

Но журнал прогонов к этому не был готов: всё, кроме вердикта и автономии, лежало в `payload JSONB`
(`payload->>'started_by'`, `payload->'run_metrics'->'cost'->>'rub'`), а **отдел не хранился вовсе** —
его доставали join'ом по агентам. Для интерфейса терпимо, для Grafana нет: SQL-панель с тремя
стрелками в JSONB и join'ом за отделом никто не станет править, а значит срезов не будет.

**Решение.** Четыре поля выносятся колонками `runs`: `actor`, `family`, `cost_rub`, `seconds`, плюс
индексы `(tenant, family, created_at)` и `(tenant, actor, created_at)`.

* **Колонками, а не вьюхой.** Вьюха не убирает разбор JSONB на каждый запрос и не даёт индекс: на
  «покажи неделю по отделам» это полный проход по журналу.
* **`family` появляется в теле прогона.** Отдел — факт о прогоне, а не вывод из текущей карточки
  агента: агента переводят в другую семью, и прошлые прогоны «переехали» бы вместе с ним.
* **NULL, а не 0, когда числа не было.** Прогон на своём боксе стоит 0 ₽ — это факт, и он
  записывается нулём. Прогон, в котором стоимость не посчиталась, стоит **неизвестно сколько**; в
  сумме по отделу это разные вещи, и подменять второе нулём значит занижать сводку молча.
* **Досыпка задним числом** — один идемпотентный `UPDATE … COALESCE(…) WHERE … IS NULL` при
  инициализации стора. Без неё срезы начинались бы с сегодняшнего дня, а месяц работы выглядел бы
  как «ничего не делали». Каждая строка заполняется **из себя самой**, поэтому проход идёт по всем
  арендаторам и объявлен сквозным в сторожe многоарендности с этой причиной. Сбой досыпки не роняет
  запуск, но пишет предупреждение: молча оставить колонки пустыми хуже.

**Grafana получает ВТОРОЙ источник данных.** Prometheus отвечает «как работает система» (очередь,
память, задержки), Postgres — «что сделали люди и их агенты». Дашборд `abop-manager`: прогоны и
стоимость по дням и отделам, таблица «кто что запускал», «что ушло наружу» (подтверждённые
доставки с уровнем и адресатом) и — самая полезная панель — **«не дошло»**: отклонённые и
просроченные решения с причиной.

**Доступ — отдельная роль только на чтение (`grafana_ro`), а не прикладной пользователь.** Grafana
— это SQL-консоль в руках вошедшего: с прикладными правами из неё можно править журнал прогонов.
Пароль в репозитории не лежит, он приходит переменной среды контейнера.

**Чего в сводке нет.** «Сэкономлено N часов»: норматива на ручную работу у нас нет (PRD, раздел 7).
Панель суммарного времени агентов прямо оговаривает, что это **не** часы людей. «Вы у экрана» тоже
нет — его мерит приложение на компьютере человека и хранит у себя (ADR-064).

**Принятая цена.** Колонки дублируют то, что уже лежит в `payload`, и при расхождении правдой
считается `payload`: он пишется вместе с прогоном, колонки — из него. Альтернатива (считать всё
из JSONB на лету) делает сводки неподдерживаемыми.

**Что проверено.** `tests/test_manager_cuts.py` (14 проверок: колонки и индексы, заполнение при
записи, NULL вместо нуля, фиксация отдела, идемпотентность досыпки, фильтр арендатора в каждой
панели, объяснение источника на экране, роль только на чтение, отсутствие пароля в репозитории).
Двенадцать сторожей прогнаны мутациями; два из них по ходу оказались слепыми (искали слово, а не
настройку) и переписаны — один через разбор кода (`ast`), другой на проверку строки `user:`.

### ADR-066. Лента контроля руководителя: смотреть свершившееся и управлять полномочиями

**Статус.** Принято 13.10.2026. Реализует `PRD_RESHENIYA_I_RUKOVODITEL.md`, 5.1, и
`DIZAJN_DESKTOPA_ENTERPRISE.md`, 5.5.

**Контекст.** У руководителя не было места, где видно, что происходит в отделе: данные есть
(журнал решений, аудит, привязки каналов), экрана нет. Соблазн был сделать из этого экран
согласования — и владелец его отверг прямо: *«руководитель не должен принимать решения, но видеть
то, что его сотрудники и кому отправили… иначе мы превращаем руководителя в нажимателя кнопок»*.

**Решение.** Раздел «Лента контроля» (desktop, `manager+`) из четырёх частей, и ни одна не
добавлена «для полноты»:

| раздел | вопрос |
|---|---|
| аномалии | на что посмотреть первым |
| не дошло | где работа встала: отказы и просроченные решения |
| необратимое по людям | что ушло наружу, кому, по какому агенту |
| постоянные разрешения | кто сам себе разрешил и что можно снять |

**Аномалия — отклонение от собственной нормы человека, а не превышение порога из головы.** «Больше
десяти писем в день — подозрительно» не работает: у одного отдела десять писем это вторник, у
другого — квартал. Всплеск считается от медианы ЭТОГО человека по дням, в которые он вообще
отправлял (нули за отпуск занизили бы медиану до единицы, и всплеском стал бы обычный день).
Виды: новый адресат, нерабочее время, всплеск объёма, **решил не адресат** (подтвердил не тот, в
чьи обязанности это входит).

**«Новый адресат» означает новизну, а не край окна.** В любом окне каждый адрес встречается
впервые; без перечня прежних адресатов (`hitl_store.адресаты_до`) аномалией стала бы вся переписка,
и список перестали бы читать. Перечня нет — раздел молчит.

**Авто-правил в ленте нет, и это не пропуск.** PRD называет раздел «кто сам себе разрешил»; правил
«подтверждать за меня» в ABOP **не существует** — необратимое всегда подтверждает человек.
Подставить в ленту несуществующую сущность значило бы нарисовать рычаг, которого руководитель не
найдёт. Постоянное разрешение в сегодняшнем продукте — это **привязка канала** в мессенджере: после
неё агенты человека запускаются из переписки и готовят письма коллегам. Это и перечислено.

**Единственное действие — снять разрешение.** Кнопка «отозвать письмо» была бы ложью: отправленное
не вернуть. Кнопка «запретить агента» ударила бы по работе всего отдела из-за одного случая.
Подпись к экрану говорит прямо: «Отправленное письмо не вернуть. Здесь вы видите, что уже
случилось, и управляете тем, что будет можно дальше». Снятие объяснено последствием — «человек
сможет привязать канал снова»: это не запрет навсегда.

**Отзыв чужой привязки — новая возможность, узкая по построению.** `channel_tokens.отозвать` умеет
только своё (самообслуживание); руководителю добавлен `снять(ид, отдел=…)`, и **отдел участвует в
самом SQL**: проверка в маршруте защищала бы от интерфейса, а не от запроса. Ответ на «чужой отдел»
и «нет такой привязки» одинаковый (404) — иначе по кодам ответа перебирают, у кого какие привязки
есть. Снятие пишется в аудит (`control.revoke_permission`, severity `warn`): через месяц вопрос
«почему у меня перестало работать» должен иметь ответ с именем и временем.

**Принятая цена.** Аномалии считаются по журналу решений, то есть видят только то, что проходило
через подтверждение. Действие уровня У1 (задача в трекере, письмо коллеге) в ленту не попадает — и
это осознанно: иначе экран превратится в поток, в котором риск не виден. Второе: «решил не адресат»
— не нарушение прав (их проверяет сервер), а повод спросить; так и подписано.

**Что проверено.** `tests/test_control_feed.py` (19 проверок: все виды аномалий, медиана против
порога, группировка по людям, состав «не дошло», права, границы отзыва, отсутствие согласования в
ленте). Пятнадцать сторожей прогнаны мутациями; два по ходу оказались непроверяемыми — данные не
доходили до порога, и проверка проходила на сломанном коде — и переписаны со снижением порога,
чтобы защита действительно работала.

### ADR-067. Агент тактического бэклога: сопоставляет и закрывает по DoD, а не интерпретирует

**Статус.** Принято 13.10.2026. Реализует `PRD_RESHENIYA_I_RUKOVODITEL.md`, 5.2 (первая версия:
сопоставление и закрытие).

**Контекст.** Руководителю нужно знать, что из поручённого сделано. Данные для этого есть по обе
стороны — журнал прогонов знает, что агенты сделали, трекер знает, что поручено, — но связки
«вот этот прогон закрывает вот эту задачу» не знает никто.

**Соблазн при такой задаче один и очень сильный:** отдать модели задачу и прогон и спросить «это
оно?». Так устроен чужой продукт, который мы разбирали (`RAZBOR_SCADA.md`), и именно поэтому его
вывод нельзя предъявить аудитору. Мы сделали ровно наоборот.

**Решение. Связка возникает только по ПРОВЕРЯЕМОМУ основанию:**

| основание | откуда берётся | достаточно для закрытия |
|---|---|---|
| прогон создал задачу | результат доставки: «задача создана в Redmine: #123» | да |
| задача ссылается на прогон | идентификатор `run-…` в описании или комментариях | да |
| участок карты | объявленное поле задачи («Операция») ∩ `op_ids` прогона | **нет** — только показ связи |

Никакого сопоставления «по смыслу текста»: тест проверяет это на задаче и прогоне, которые говорят
об одном и том же разными словами, и требует, чтобы связки **не** возникло.

**Готовность — по ОБЪЯВЛЕННОМУ DoD.** Критерий читается из поля задачи `DoD` или из чек-листа в
описании. Не объявлен — задача не закрывается, а помечается «DoD не объявлен» с подсказкой, что
добавить. Все пункты отмечены и есть артефакт прогона → `закрыть`; артефакт есть, пункты нет →
`двинуть`; артефакта нет → `нет подтверждения выполнения` с причиной из состояния прогона (нет
данных, ждёт решения человека, упёрлось в лимит, ошибка).

**Обещание доставки артефактом не считается.** Доставка в состоянии `awaiting_hitl` — это «уйдёт,
если человек скажет да», а не «ушло». Закрывать задачу по обещанию значит закрывать по намерению.

**Исход решения записывается в прогон (правка 13.10, вслед за находкой ниже).** Когда человек
говорит «отправить» или «оставить черновиком», запись доставки в прогоне обновляется: `real` или
`rejected` плюс пометка «не отправлено». Выбран путь «одна запись при решении», а не join при
каждом показе: пишет одно место, правду получают все читатели — журнал, чат, отчёт, выгрузка.
Альтернатива заставляла бы каждую поверхность помнить про join, и однажды кто-то забыл бы — ровно
та беда «каждая панель решает сама», от которой мы ушли в примитивах карточки. Это не
переписывание истории: доставка в состоянии «ждёт решения» — не факт о прошлом, а незавершённое
действие, и его завершение обязано быть видно. Правится **та** запись, что ссылается на решённую
заявку; чтение идёт под `FOR UPDATE` (два решения по одному прогону приходят независимо); сбой
пометки не роняет ответ человеку — письмо уже ушло, промах пишется предупреждением.

**Старые прогоны задним числом не правятся**, поэтому чтение журнала решений в агенте бэклога
остаётся: для прогонов, решённых до этой правки, оно единственный источник.

**Подтверждённая отправка ищется в журнале РЕШЕНИЙ, а не в прогоне, и это самая дорогая находка
пункта.** Когда человек говорит «отправить», запись в прогоне **не меняется** — она навсегда
остаётся `awaiting_hitl`, потому что подтверждение живёт в своей заявке. Первая версия агента
смотрела только в прогон, и закрыть не смогла бы ни одну задачу с внешней доставкой — то есть
практически ни одну. Нашлось не в тестах, а на живом стенде: прогонов с `real` там **ноль**, а
подтверждённых отправок — больше сорока. Отсюда и следствие, которое стоит знать отдельно: **карточка
прогона в журнале показывает «ожидает подтверждения» и после того, как человек подтвердил** — чат
прикрывает это своим состоянием, а журнал нет. Это отдельный дефект отображения, он назван и ждёт
решения владельца, но на агента больше не влияет.

**Границы, объявленные в коде и закреплённые тестами:**

* **людей не оценивает.** Оценивается выполнение ЗАДАЧИ; исполнитель задачи в решение не попадает
  вовсе, и в комментарии к задаче стоит оговорка, что работа сотрудников не оценивалась;
* **каждое закрытие объяснимо**: комментарий называет прогон, число находок, артефакт и состояние
  каждого пункта DoD;
* **очерёдность объяснима**: срок из трекера и число ждущих подзадач. «Важности» и «веса», выведенных
  моделью, здесь нет — выдуманный приоритет нельзя оспорить, а значит он хуже отсутствующего;
* **состав эпика — из трекера** (решение владельца 4): задача без родителя в эпик не попадает, свой
  список подзадач мы не ведём.

**Разбор и применение — разные ручки, и это принципиально.** `GET /api/backlog/review` ничего не
меняет и показывает, что агент сделал бы. `POST /api/backlog/apply` закрывает только то, что прошло
разбор с решением «закрыть»; `issue_ids` может сузить набор, но не расширить. Закрытие — **У1**
(своя система учёта, обратимо), подтверждения не требует, но ручка требует `manager`: массовое
закрытие задач отдела — работа руководителя, а не рядовое действие.

**Статус «закрыта» не угадывается.** В каждой установке Redmine свои идентификаторы статусов;
`REDMINE_CLOSED_STATUS_ID` без значения означает «комментировать, статус не трогать». Поставить 5 и
надеяться — значит перевести задачу заказчика в непредсказуемое состояние.

**Отказ трекера не выглядит как пустой бэклог.** Нет ключа, сеть легла — ручка отвечает 502 с
текстом отказа. Пустой список читался бы как «задач нет», и это была бы ложь.

**Принятая цена.** Без объявленного DoD агент не закроет ничего — на складе задач, где критериев не
пишут, он будет только показывать «DoD не объявлен». Это осознанно: альтернатива (закрывать по
мнению модели) даёт закрытые задачи, за которые никто не отвечает. Второе: `redmine_update_issue`
по умолчанию сухой, и боевое закрытие идёт только из ручки применения.

**Что проверено.** `tests/test_backlog_agent.py` (20 проверок) + `cli/ape.py` получил чтение и
обновление задач Redmine (было только создание). Пятнадцать сторожей прогнаны мутациями; два по
ходу оказались непроверяемыми — мутация не задевала тестовые данные — и переписаны так, чтобы
задевала: прогон теперь говорит теми же словами, что задача, и в наборе есть задача без родителя.
