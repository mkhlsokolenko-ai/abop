# ABOP — Architecture Decision Records

**Продукт:** ABOP (Agent-Based Orchestration Platform) — рантайм исполнения агентов
**Версия:** 0.2
**Статус пакета:** к утверждению
**Связанные документы:** `ABOP_ARD.md`, `../cli/README.md`, LUDA v2 `ADR.md`/`AOP.md`

Формат записи (Nygard): контекст (какие силы давят) → решение → последствия, включая принятую цену.

Записи, помеченные **[переворот]**, отменяют модель «один процесс = один агент» (Process Agent Spec / VRATA v1) и связанные с ней допущения.

## Продукт и позиционирование

### ADR-001. ABOP — рантайм исполнения, продуктизация LUDA v2, отдельный продукт и репозиторий **[переворот]**

**Статус.** Принято.

**Контекст.** В прежней модели агент был неотделим от процесса: `Process Agent Spec` описывал «агента для закрытия месяца». LUDA v2 расщепила агента и процесс (Role Family, Skill, Capability, Module, эфемерные воркеры) — спецификация «один агент = один процесс» в этой модели не инстанцируется. При этом рантайм исполнения агентов — самостоятельная ценность: заказчику нужно не только знать *можно ли* запускать агента (это диагностирует LUDA), но и *чем* его запускать в регулируемом периметре.

**Решение.** ABOP развивается как самостоятельный продукт и репозиторий — рантайм исполнения агентов, продуктизация LUDA v2 и эволюция VRATA на паттернах openclaw (Gateway / Channel / Tool-Skill / pairing-approval HITL / security-first). ABOP **не является самим LUDA**: LUDA — аудитор готовности (диагноз), ABOP — исполнитель (рантайм). Связь между репозиториями — только версионированные схемы контрактов.

**Последствия.** Отдельный биллинг, релизный цикл, техдолг и CI. Дублирование части кода со sLAVA/LUDA принимается сознательно как цена независимости релизов (см. ADR-021). Цена принята: рантайм продаётся и эволюционирует отдельно от диагностики.

### ADR-019. APE (учебный CLI) — полигон принципов; прод-ABOP наследует Agent Plane

**Статус.** Принято.

**Контекст.** Отрабатывать архитектуру рантайма сразу в регулируемом периметре (ФСТЭК/ФЗ-152) — дорого и рискованно: любая ошибка касается продуктивных систем заказчика. Нужна безопасная площадка, где обкатываются принципы (агенты/волны/Blackboard/tools/Data Plane) без доступа к реальному контуру.

**Решение.** Учебный CLI `ape` (`cli/ape.py`) — безопасный полигон, где реализуются и проверяются ПРИНЦИПЫ и АРХИТЕКТУРА Agent Plane. Прод-ABOP **наследует** обкатанный в `ape` Agent Plane: онтологию Семья→Роль→Навык, оркестрацию волнами, Blackboard, единый контракт вызова. Готовое в `ape` портируется, а не переписывается.

**Последствия.** Два контура (учебный и прод) с общей идеологией, но разными периметрами. Требуется дисциплина обратного переноса: принцип считается принятым, только если он отработан в `ape`. Учебный контур не имеет доступа к продуктивным данным заказчика — граница жёсткая.

### ADR-020. Оркестрация волнами (fan-out/fan-in), а не свободный цикл агента **[переворот]**

**Статус.** Принято.

**Контекст.** Свободный ReAct-цикл одиночного агента («думай → действуй → наблюдай, пока не решишь остановиться») недетерминирован по числу шагов, стоимости и траектории. В регулируемом периметре нужен аудируемый ход исполнения: кто, когда, на основании чего действовал. Свободный цикл этого не даёт — он воспроизводит модель «один агент делает всё сам».

**Решение.** Исполнение — оркестрация **волнами**: fan-out (диспетчер раскидывает задачи по stateless-воркерам) → барьер → fan-in (синтез результатов). Следующая волна видит доску предыдущей. Диспетчер, а не сам агент, решает границы волны. Свободный цикл внутри одного узла ограничен и подотчётен.

**Последствия.** Часть задач, естественных для свободного цикла, приходится раскладывать на волны — это дороже в проектировании потока. Взамен каждый прогон воспроизводим и аудируем: ход зафиксирован волнами и доской, а не скрыт во внутреннем цикле модели.

## Онтология агентов

### ADR-005. Онтология Семья→Роль(член)→Навык, роли переиспользуют навыки **[переворот]**

**Статус.** Принято.

**Контекст.** Модель «один процесс = один агент» плодит монолитных агентов, дублирующих одни и те же способности. Навык «сверить числа с источником» переписывается в каждом агенте. Нет единицы переиспользования способностей между агентами.

**Решение.** Онтология Role Family: **Семья** (домен компетенций) → **Роль/член семьи** (конкретный исполнитель) → **Навык** (атомарная способность с телом). Реализовано в `cli/ape.py`: 10 семей, 37 навыков с телами. Роли **переиспользуют** навыки — один навык подключается к разным ролям. Агент собирается из роли и её навыков, а не пишется целиком.

**Последствия.** Способности становятся общим ресурсом, а не собственностью агента. Требуется реестр навыков и дисциплина их версионирования. Один навык, изменённый ради одной роли, затрагивает все роли, что его переиспользуют — нужен контроль совместимости.

### ADR-006. Два яруса навыков: глобальные (CLI) vs специализированные (в семьях)

**Статус.** Принято.

**Контекст.** Часть навыков универсальна (нужна любой роли: базовый tool-calling, работа с доской), часть — узко доменная (нужна только конкретной семье). Держать всё в одном плоском списке раздувает контекст каждого агента и стирает границу «общее/доменное».

**Решение.** Два яруса навыков: **глобальные** — доступны на уровне CLI/платформы любой роли; **специализированные** — живут внутри семей и подключаются только их ролям. Ярус определяет область видимости и владения навыком.

**Последствия.** Ясная граница ответственности: глобальный навык меняет платформенная команда, специализированный — владелец семьи. Риск дублирования на стыке (доменный навык, ставший общим) разрешается повышением яруса через явное решение, а не копированием.

### ADR-008. Progressive disclosure навыка: use_skill грузит полное тело по требованию

**Статус.** Принято.

**Контекст.** Тела 37 навыков не помещаются в системный промпт без раздувания контекста и потери фокуса модели. Но агент должен знать, какие навыки существуют, чтобы выбрать нужный.

**Решение.** Progressive disclosure: в системном промпте — только **карточки** навыков (имя, назначение, метаданные безопасности). Полное **тело** навыка подгружается по требованию вызовом `use_skill` в момент применения. Модель видит каталог, но грузит инструкцию только когда решила её исполнять.

**Последствия.** Системный контекст остаётся компактным независимо от числа навыков. Цена — дополнительный шаг загрузки тела перед исполнением и зависимость от того, что карточка достаточно информативна для выбора. Качество карточек становится критичным.

### ADR-010. Handoff через доску (эстафета роль↔семья), оркестратор поднимает stateless-воркерами

**Статус.** Принято.

**Контекст.** Передача работы между ролями/семьями через прямой вызов «агент зовёт агента» создаёт связность, скрытое состояние и цепочки, которые невозможно прервать и переиграть. Нужна эстафета без прямой связи исполнителей.

**Решение.** Переключение исполнителя — через механизмы `use_skill` / `become` / `handoff`, где **handoff идёт через доску**: сдающий кладёт результат/задачу на Blackboard, оркестратор поднимает принимающего **stateless-воркером**. Воркеры не держат состояние между волнами — вся преемственность через доску.

**Последствия.** Исполнители развязаны: любой воркер эфемерен, взаимозаменяем, перезапускаем. Состояние прогона целиком на доске — единая точка восстановления и аудита. Цена — вся преемственность обязана проходить через доску (нельзя «передать в уме»), что требует дисциплины фиксации.

## Данные (Data Plane)

### ADR-002. Три плоскости: Agent / Tool / Data Plane

**Статус.** Принято.

**Контекст.** Смешение «кто думает», «чем делает» и «на каких данных» в одном слое делает агента монолитом: смена источника данных задевает логику, смена инструмента задевает данные. Нужно разделение ответственности.

**Решение.** Три плоскости. **Agent Plane** — агенты, харнесс, оркестрация (ReAct, волны, синтез, Blackboard). **Tool Plane** — примитивы и рецепты под JWT (`run_python`, `web_fetch`, `data_query`…). **Data Plane** — агент-нативный слой данных (Source Adapters → Canonical Schemas → Data Contracts). Рецепт = Agent Plane (кто думает) + Tool Plane (чем делает) + Data Plane (на каких данных).

**Последствия.** Каждая плоскость эволюционирует независимо: новый источник — только Data Plane, новый инструмент — только Tool Plane. Цена — три контракта на стыках вместо одного и обязательность прохождения данных через `data_query`, а не «как удобно».

---

### ADR-003. Data Plane — агент-нативный слой (Source Adapter→Canonical Schema→Data Contract→data_query)

**Статус.** Принято.

**Контекст.** Агент потребляет данные не как человек. Человеку системы отдают данные «для глаз» — HTML, UI, PDF, разрозненные API. Агенту нужен типизированный, самоописываемый, стабильный JSON с провенансом и свежестью. Скрейпить человеческие интерфейсы каждым агентом — хрупко, дорого, недетерминированно.

**Решение.** Data Plane — цепочка **Source Adapter** (источник→нормализация: mail, Jira, CRM, БД, файлы-OCR) → **Canonical Schema** (единая типизированная сущность: Email, Issue, Customer, Document…) → **Data Contract** (стабильная выдача: поля, типы, провенанс, свежесть) → **`data_query`** (агент берёт данные ТОЛЬКО так). Каждая запись самоописываема: `schema`+`schema_version`, `id`, `provenance`, `ttl`, нормализованные `refs`. Часть слоя уже есть в LUDA (`connectors/`, `canon/`, `spec/`) — переиспользуется, а не пишется заново.

**Последствия.** Агенты работают с предсказуемым JSON, а не парсят форматы «для глаз» — устойчивость и воспроизводимость. Цена — обязательный слой адаптеров и канонических схем: новый источник требует адаптера и схемы до того, как агент его увидит.

### ADR-004. Data Recipe декларативен, пишет доменный эксперт, без исполняемого кода, валидируется схемой

**Статус.** Принято.

**Контекст.** Если для подключения нового источника нужен разработчик, Data Plane не растёт. Кроме того, рецепт устанавливается в периметр заказчика и обращается к продуктивным системам — произвольный исполняемый код в такой позиции не пройдёт службу ИБ.

**Решение.** Адаптер источник→canonical описывается **Data Recipe** — декларативным версионируемым артефактом (YAML/JSON) в стиле LUDA **VerticalPack**: `source` (адаптер+фильтр), `entity`, `map` (маппинг полей без кода), `rules` (assert/pii_mask), `emit` (схема+ttl). **Исполняемого кода нет.** Рецепт **валидируется схемой** (нельзя сломать канон), пишет его **доменный эксперт**. Не путать с *Agent Recipe* (плейбук агент+tools+LLM).

**Последствия.** Data Plane растёт силами доменных экспертов, а не только разработчиков — self-serve. Часть источников не выразить декларативно; они реализуются как расширения с ревью и по накоплении пересматриваются как расширение языка рецептов. Нужен строгий валидатор с понятными сообщениями — эксперт не читает трассировки.

## Память

### ADR-009. Blackboard — рабочая память прогона (event-sourced), воркеры stateless

**Статус.** Принято.

**Контекст.** При оркестрации волнами и stateless-воркерах нужна общая память прогона без конфликтов записи, потерь и вопроса «кто чистит». Прямая передача состояния между воркерами воспроизводит связность, от которой уходим.

**Решение.** **Blackboard** — рабочая память одного прогона, **event-sourced**: append-only журнал (facts / notes / claims / snapshots), состояние = свёртка событий, snapshot-компакция. `claim` исключает дубли. Воркеры **stateless** — всё состояние на доске, ничего в воркере между волнами.

**Последствия.** Нет конфликтов записи и потерь; прогон восстановим из журнала и полностью аудируем. Цена — всё значимое обязано попасть на доску append-only (нельзя держать «в уме» воркера), плюс механика компакции снапшотов для контроля роста журнала.

### ADR-011. Долговременная память с ЗАБЫВАНИЕМ по TTL от критичности

**Статус.** Принято.

**Контекст.** Blackboard — память одного прогона; между прогонами нужна долговременная память. Но бессрочное хранение всего в регулируемом периметре нарушает принцип минимизации данных (ФЗ-152) и раздувает хранилище. Разные факты имеют разный законный срок жизни.

**Решение.** Долговременная память с **ЗАБЫВАНИЕМ по TTL, производным от критичности** записи: `operational` — 7 дней, …, `regulatory` — 5 лет (retention банков/корпораций), `permanent` — ∞. По истечении TTL запись забывается автоматически. Критичность задаёт срок — забывание встроено, а не опционально.

**Последствия.** Хранилище соответствует принципу минимизации и требованиям retention «из коробки». Цена — обязательная классификация записи по критичности при сохранении (иначе TTL не назначить) и риск потери факта, если критичность занижена. Классификация становится частью контракта записи в память.

## Безопасность и governance

### ADR-007. Безопасность — метаданные навыка (mode · egress · cite)

**Статус.** Принято.

**Контекст.** Безопасность, привязанная к агенту целиком, слишком груба: агент из десятка навыков получает права по самому опасному из них. Нужна гранулярность на уровне способности, а не исполнителя.

**Решение.** Свойства безопасности — **метаданные навыка**: `mode` (read / write / action), `egress` (internal / external), `cite` (обязательность цитирования источника). Права определяются набором подключённых навыков, а не агентом в целом. Метаданные видны в карточке навыка (ADR-008) до загрузки тела.

**Последствия.** Точный контроль: роль без `action`-навыков физически не может писать во внешние системы. Каждый навык обязан нести корректные метаданные — ошибка в метаданных навыка = дыра в периметре. Ревью навыка включает ревью его безопасности.

### ADR-014. Действия во внешние системы — только dry_run + подтверждение человека (HITL)

**Статус.** Принято.

**Контекст.** Автономное действие агента во внешней продуктивной системе (запись в Jira, отправка почты, удаление) необратимо и в регулируемом периметре недопустимо без человека. При этом полный запрет действий обесценивает рантайм.

**Решение.** Любой навык с `mode: action` и `egress: external` исполняется в два такта: **`dry_run`** (агент показывает, что именно сделает) → **подтверждение человека (HITL)** → реальное исполнение. Без подтверждения действие не выходит наружу. Read/write внутри периметра могут идти автоматически; отсылка/критичные/удаление — под человеком.

**Последствия.** Необратимые операции всегда проходят через человека — периметр защищён от автономной ошибки. Цена — латентность и участие оператора на каждом внешнем действии; поток проектируется так, чтобы точки HITL были осмысленны, а не на каждом шаге.

### ADR-015. Внешний контент — anti-injection + PII-маскирование на границе

**Статус.** Принято.

**Контекст.** Данные из внешних источников (письма, веб, документы) могут содержать инструкции, адресованные модели (prompt injection), и персональные данные. Исполнение инструкций из данных = захват агента; вынос ПДн наружу = нарушение ФЗ-152.

**Решение.** Внешний контент проходит через два фильтра: **anti-injection** — инструкции внутри данных не исполняются, данные трактуются как данные, не как команды; **PII-маскирование на границе** — персональные данные маскируются до того, как контент попадёт в контекст модели или уйдёт за периметр.

**Последствия.** Агент устойчив к попыткам управления через подсовываемый контент, ПДн не утекают. Цена — фильтры могут ложно срабатывать (замаскировать нужное, отклонить легитимную инструкцию пользователя) и добавляют шаг обработки; граница «данные vs команда» требует чёткого определения в каждом канале.

### ADR-016. Числа и факты — только из источника (анти-галлюцинация), навык помечен cite

**Статус.** Принято.

**Контекст.** Соблазн отдать модели весь путь от данных до вывода даёт быстрый прототип, но модель выдумывает числа и факты. В регулируемом и аудиторском контексте это источник прямых ошибок с последствиями.

**Решение.** Числа и факты в ответе агента — **только из источника**, не из модели. Навык, порождающий фактические утверждения, помечается `cite`: каждое такое утверждение сопровождается ссылкой на источник (провенанс из Data Plane). Расчёты — детерминированным кодом (`run_python`), не моделью. Утверждение без источника отклоняется.

**Последствия.** Любой факт в выходе воспроизводим и объясним по источнику — это и есть предмет доверия к рантайму. Цена — больше кода и меньше «магии»: модель формулирует и объясняет, но не изобретает числа. Согласуется с инвариантом LUDA «модели не считают числа» (ADR-012 LUDA).

### ADR-012. Governance-петля: агент-аудитор выводит Definition of Done и сверяет результат

**Статус.** Принято.

**Контекст.** Прогон без внутренней проверки «сделано ли то, что требовалось» полагается на добросовестность исполнителей. В регулируемом периметре нужна встроенная сверка результата с явным критерием готовности, а не «агент сказал — готово».

**Решение.** Governance-петля: отдельный **агент-аудитор** выводит **Definition of Done** для задачи и **сверяет результат** прогона с ним. DoD — явный проверяемый критерий, аудитор — независимый от исполнителей узел. Несоответствие DoD — сигнал, а не молчаливое прохождение.

**Последствия.** Результат проходит внутреннюю приёмку по явному критерию — качество не зависит только от исполнителя. Цена — дополнительный узел и стоимость его прогона на каждой задаче; качество петли зависит от того, насколько честно аудитор выводит DoD (та же ответственность, что у метрик в манифесте).

### ADR-013. Автономия агента НЕ выше DeploymentContract от LUDA — единственная жёсткая связь **[переворот]**

**Статус.** Принято.

**Контекст.** В модели «один процесс = один агент» уровень автономии задавался внутри рантайма ad hoc. Но *можно ли* давать агенту автономию — вопрос готовности процесса, который решает аудит (LUDA), а не рантайм. Рантайм, назначающий себе автономию сам, обходит диагностику.

**Решение.** ABOP **не может** дать агенту `autonomy_level` выше, чем зафиксировано в **`DeploymentContract`** от LUDA. Это **единственная жёсткая (обязательная) связь** между продуктами — всё остальное развязано через версионированные схемы. Уровни автономии A0–A4 и точки HITL приходят из контракта, рантайм их исполняет, но не превышает.

**Последствия.** Диагностика и исполнение связаны в самом критичном месте: нельзя запустить агента автономнее, чем разрешил аудит. Цена — ABOP зависит от наличия валидного `DeploymentContract` для регулируемого запуска; без него доступен только минимальный уровень автономии. Связь односторонняя: LUDA ограничивает ABOP, не наоборот.

## Инфраструктура

### ADR-017. Единый контракт вызова через MCP-шлюз (session_id + JWT + cost_journal)

**Статус.** Принято.

**Контекст.** Разрозненные вызовы инструментов и данных, каждый со своей авторизацией и учётом, не дают ни изоляции арендаторов, ни сквозного учёта стоимости, ни единой точки контроля. Нужен один слой, обслуживающий и CLI `ape`, и фронт ABOP.

**Решение.** Любой вызов (tool или data) идёт через **MCP-шлюз (FastMCP + Keycloak)** по единому контракту: `session_id` + **JWT** (авторизация, изоляция, мультитенантность) → запись в **`cost_journal`** → структурный результат `{data|text, artifacts[], provenance}`. Один контракт вызова сквозной для учебного и прод-контура.

**Последствия.** Единая точка авторизации, изоляции и учёта стоимости; смена бэкенда исполнения не задевает вызывающего. Цена — обязательность шлюза на пути каждого вызова (нет «прямых» вызовов в обход) и зависимость от Keycloak как источника идентичности.

### ADR-018. Egress наружу — через контролируемый прокси sLAVA; local_llm — внутренний

**Статус.** Принято.

**Контекст.** В регулируемом периметре (ФСТЭК/ФЗ-152) неконтролируемый выход наружу недопустим: нужна единственная аудируемая точка egress с анти-SSRF и логированием. При этом часть нагрузки (навыки без внешнего egress) должна обслуживаться локальной моделью без выхода наружу.

**Решение.** Единственная точка выхода наружу (`external_egress`) — **контролируемый прокси sLAVA** (валидация endpoint, запрет link-local, egress-лог). Навыки с `egress: internal` обслуживаются **`local_llm`** — внутренней моделью, не покидающей периметр. Ярус egress навыка (ADR-007) определяет маршрут: external → через прокси, internal → local_llm.

**Последствия.** Весь выход наружу аудируем в одной точке; чувствительная нагрузка не покидает периметр. Цена — зависимость внешних навыков от доступности прокси sLAVA и необходимость держать локальную модель для internal-нагрузки; маршрутизация по egress-ярусу должна быть корректной, иначе internal-навык рискует уйти наружу.

### ADR-021. Только permissive-лицензии; максимум переиспользования кода VRATA/LUDA

**Статус.** Принято.

**Контекст.** ABOP поставляется на внешний рынок и разворачивается в периметре заказчика — copyleft/ограничительные лицензии (AGPL, SSPL, BUSL) неприемлемы. Одновременно писать рантайм с нуля расточительно: VRATA и LUDA уже содержат применимый код (коннекторы, канонизация, шлюз, маскирование).

**Решение.** Допускаются только **permissive-лицензии** (MIT, Apache-2.0, BSD, PostgreSQL License); запрещены AGPL, SSPL, BUSL, RSAL, Elastic License 2.0 (MPL-2.0 — покомпонентно). При этом — **максимум переиспользования кода VRATA/LUDA** в рамках permissive-ограничения (эволюция VRATA, не переписывание). Наследуется от политики ABOP/LUDA.

**Последствия.** Отпадают удобные, но несовместимые по лицензии компоненты (MinIO, Grafana и пр.) — список допущенных ведётся отдельно. Переиспользование VRATA/LUDA снижает объём нового кода, но требует контроля границ (связь между продуктами — только версионированные схемы, без «молчаливого» проникновения чужих моделей данных).

## Эксплуатация (Fleet)

### ADR-022. Развёртывание отделено от прогона (Deployment ≠ Run) **[переворот]**

**Статус.** Принято.

**Контекст.** Жизненный цикл в продукте обрывается на «протестировал»: прогон запускает человек разово и разово же получает результат. В проде агент должен работать постоянно — сам реагировать на события, а не ждать ручного пуска. Смешение «разовой задачи» и «постоянно работающего агента на участке» не даёт ни реестра прод-агентов, ни управления версией в проде, ни понимания «кто работает сейчас».

**Решение.** Развести два понятия. **Прогон (Run)** — разовая задача человека: постановка → результат, эфемерна. **Развёртывание (Deployment)** — агент-спека, **посаженная на участок процесса** с триггером и политикой; работает долго и **сама запускает прогоны по триггеру**. Развёртывание = `{агент-спека vN, триггер, участок, политика автономии, владелец, статус}`. Прогон остаётся единицей исполнения; развёртывание — единицей эксплуатации над ним.

**Последствия.** Появляется слой Operations рядом с Авторингом и одно-прогонным Рантаймом: реестр развёртываний, ЖЦ версии, карта участков. Цена — новая долгоживущая сущность в сторе и её ЖЦ; Run перестаёт быть «конечной точкой» и становится механикой, которую переиспользует развёртывание.

---

### ADR-023. Экземпляр = помеченный авто-прогон развёртывания

**Статус.** Принято.

**Контекст.** Развёртывание по триггеру порождает конкретные запуски, которые надо видеть живьём: сколько их сейчас, что делают, кем инициированы. Писать для этого отдельный рантайм — дублировать уже работающую механику прогона (волны/доска/аудитор) и разъехаться с ней в поведении и аудите.

**Решение.** **Экземпляр (Instance)** — это авто-прогон развёртывания, **переиспользующий run-механику** (оркестрация волнами ADR-020, Blackboard ADR-009, governance-петля ADR-012), но **помеченный** метками: `deployment_id`, `instance_id`, инициатор (событие/расписание/человек), участок процесса. Реестр живых экземпляров — in-memory + стор. Отдельного исполнителя для флота не заводим: инстанс есть тот же прогон под метками.

**Последствия.** Флот наблюдаем и аудируем той же машинерией, что и одиночный прогон — без второго рантайма. `cost_journal` (ADR-017), пишущий per-run, агрегируется per-deployment/per-instance по меткам. Цена — метки обязаны проставляться на каждом авто-прогоне; без них экземпляр невидим флоту.

---

### ADR-024. Версионирование агента: draft → deployed(vN) → retired

**Статус.** Принято.

**Контекст.** Прод-агент меняется во времени: правки потока, отзыв неудачной версии, вывод из эксплуатации. Без явных версий и переходов нельзя ни откатить, ни безопасно пересмотреть работающего агента, ни зафиксировать, что именно крутится в проде.

**Решение.** Агент-спека получает статус и версии: `draft → tested → deployed(vN) → retired`. **Откат** = активация предыдущей `deployed`-версии (не пересборка). **Пересмотр** = открыть `deployed`-версию как новый `draft` в канве (правка идёт как новая версия, прод не трогается до повторного деплоя). **Retire** — вывод из эксплуатации с дренажом живых экземпляров, type-to-confirm. Активной в проде может быть одна версия развёртывания.

**Последствия.** Прод-состояние явно и обратимо: всегда известно, какая vN активна, и есть чем откатиться. Цена — хранение истории версий и дисциплина переходов; правка «прямо в проде» запрещена — только через draft → повторный деплой.

### ADR-025. Триггеры развёртывания: push-событие / расписание / входящая задача

**Статус.** Принято.

**Контекст.** Развёртывание должно само запускать прогоны — значит, нужен явный источник запуска. Опрос-поллинг источников каждым агентом хрупок и дорог; неопределённый триггер делает флот непредсказуемым по нагрузке и аудиту.

**Решение.** Три типа триггера развёртывания: **push-событие Data Plane** (webhook-адаптер источника ADR-003 отдаёт нормализованное событие → авто-прогон), **расписание** (cron-подобный запуск), **входящая задача** (постановка в очередь развёртывания). Каждый сработавший триггер порождает помеченный экземпляр (ADR-023) с зафиксированным инициатором.

**Последствия.** Запуск прод-агента детерминирован и прослеживаем до конкретного триггера в аудите. Цена — push-триггер требует webhook-адаптера на стороне Data Plane; расписание требует планировщика; каждый триггер обязан нести инициатора для метки экземпляра.

### ADR-026. Лимит параллелизма инстансов на боксе (единый MoE делится между инстансами)

**Статус.** Принято.

**Контекст.** Экземпляры множества развёртываний живут на одном боксе и делят единый MoE-рантайм. Неограниченный параллелизм авто-прогонов выест VRAM/KV-кэш и обрушит бокс — триггеры способны породить лавину инстансов быстрее, чем движок их обслужит.

**Решение.** Единый MoE-движок **делится между инстансами** через continuous batching (не по процессу на инстанс). Вводится **лимит параллелизма на развёртывание** — потолок одновременных живых экземпляров, защищающий VRAM/KV. Сверх лимита экземпляры ставятся в очередь, а не запускаются. Лимит — часть политики развёртывания.

**Последствия.** Бокс защищён от исчерпания памяти при всплеске триггеров; пропускная способность предсказуема. Цена — при всплеске часть авто-прогонов ждёт в очереди (латентность вместо отказа бокса); лимит нужно калибровать под профиль нагрузки развёртывания.

### ADR-027. Governance применяется на КАЖДОМ экземпляре в эксплуатации

**Статус.** Принято.

**Контекст.** Governance, проверенный один раз «при сборке», не покрывает прод: агент работает постоянно, права и поведение могут дрейфовать, а нарушение конверта на живом экземпляре — прямой инцидент. Проверки на входе недостаточно, если экземпляры бегут непрерывно.

**Решение.** Конверт безопасности применяется **на каждом экземпляре в рантайме, непрерывно**: автономия ≤ `DeploymentContract` от LUDA (ADR-013), точки HITL (ADR-014), анти-инъекция/PII (ADR-015), аудит-след флота — на каждом авто-прогоне, а не единожды. **Ре-аттестация** (GAPS §7) получает объект — **развёртывания**: периодический пересмотр прод-агентов и их прав. При нарушении конверта — **отзыв версии** (ADR-024) как реакция governance. Так проверка «при сборке» становится постоянным контролем «в эксплуатации».

**Последствия.** Governance из разового гейта превращается в непрерывный контроль флота — соответствует позиционированию «операционная система управления агентными процессами», не IDE. Цена — governance-издержки (аудитор, HITL, аудит-след) несёт каждый экземпляр, а не один тестовый прогон; ре-аттестация требует регламента и владельца.

## Рыночная совместимость и стык с LUDA

### ADR-028. ABOP — governance-конверт НАД любым рантаймом агентов; подхват существующих (brownfield) **[позиционирование]**

**Статус.** Принято.

**Контекст.** В организациях уже работают агенты — на **LangChain/LangGraph** как де-факто основе, сверху OpenClaw/Hermes/свои. Требовать «выкинь и перепиши на ABOP» — нерыночно: обесценивает вложенное и блокирует внедрение. При этом именно этим агентам не хватает того, что даёт ABOP: верифицированного конверта (автономия ≤ контракт, mode/egress/cite, HITL, аудит) для регулируемого периметра.

**Решение.** ABOP позиционируется как **governance-конверт НАД любым рантаймом агентов, а не замена ему**. Вводится **Agent Adapter Layer (AAL)** (`ABOP_SDD §3`): внешний агент приводится к внутреннему контракту ABOP через **LangGraph как IR** — в режиме **Translate** (граф→волны, тонкий governance на узле) или **Wrap** (чёрный ящик под **Governance Wrapper**: перехват egress/tools через MCP-прокси, автономия-гейт, аудит I/O). Совместимость на протоколах **MCP** (уже базовый) и **A2A**. Внешний агент дальше живёт как нативный: версионирование (ADR-024), паспорт, флот, governance на каждом экземпляре (ADR-027).

**Последствия.** Ров ABOP — не «ещё один фреймворк», а governance/аудируемость, которых нет у LangGraph/OpenClaw/Hermes; вход в организацию — не миграция, а «подхвати и заверни». Цена — поддержка AAL (адаптеры/маппинг) и то, что в режиме Wrap governance грубее (на границе, не на узле); полнота перехвата egress для закрытых рантаймов — открытый инженерный вопрос (`SDD §7`).

### ADR-029. Contract Ingress — приём контрактов LUDA как явный слой с валидацией на границе

**Статус.** Принято.

**Контекст.** Связь LUDA↔ABOP декларировалась «через версионированные схемы контрактов» (ADR-001, ADR-013), но механизм — как бандл (CapabilityRequest/DeploymentContract/BaselineMeasurement + EvidencePack) физически попадает в ABOP и начинает управлять агентом — не был описан. Без явного слоя граница доверия размыта: неясно, кто валидирует контракт и где он привязывается к развёртыванию.

**Решение.** Вводится слой **Contract Ingress** (`ABOP_SDD §4`): приём бандла (файл-экспорт / pull по `audit_id` / общий реестр — минимум одна опция на старте), **валидация против схем `luda.*/1.0`** на границе (несовпадение версии → отказ), сохранение как `ContractSet` и привязка к `AgentVersion`/`Deployment`. Применение: `DeploymentContract.autonomy_level` → `Deployment.autonomy_ceiling` (ADR-013), `hitl_points`→точки HITL, `residency`→egress-политика, `CapabilityRequest`→чеклист сборки, `BaselineMeasurement`→база Fleet-здоровья, `EvidencePack`→аудит-след. Прод-развёртывание без валидного контракта запрещено (только песочница A0).

**Последствия.** Граница доверия становится явной и тестируемой; переаудит в LUDA → новый контракт → новая версия развёртывания (может двигать потолок автономии). Цена — ABOP обязан вести версионирование схем контрактов и политику совместимости при апгрейде `luda.*/1.x`; появляется новый эндпоинт/модуль, которого пока нет в коде (`SDD §6`).

## UI-модель

### ADR-030. Канва-центричный shell: вкладки — не соседи, а линзы над одним графом **[переворот]**

**Статус.** Принято (решение владельца, разворот корневой модели UI).

**Контекст.** Прежняя навигация — 8 вкладок-ровней (Обзор·Канва·Данные·Навыки·Прогоны·Эксплуатация·Паспорт·Настройки). Пользователь мысленно сшивает их сам: где собрать, где запустить, где смотреть прод. Это дало провал 2-минутного теста (4/10 — фрагментация + жаргон без контекста) и противоречит директиве «переработать логику, а не полировать». При этом рантайм — **гибрид (проводной поток + LLM-узлы)**, то есть канва **буквально и есть граф исполнения**: авторинг-артефакт = рантайм-артефакт. Карта Операций уже спроектирована «как Канва по движку, read-only» — половина продукта уже вращается вокруг канвы. Рынок (n8n/Langflow) выиграл интуитивность именно канва-центром + drag-and-drop + настройки-в-узле.

**Решение.** **Канва — корень интерфейса, не одна из вкладок.** Всё остальное нативно вытекает из центра:
- **Линзы над одним графом** (не отдельные экраны): *Строю* (авторинг), *Запускаю* (рантайм — волны/доска/HITL оверлеем на узлах = б. Пульт), *Эксплуатирую* (флот — semantic-zoom того же графа до Организация→процесс = б. Operations), *Конверт* (governance-оверлей). Переключение линз не меняет объект — меняет способ смотреть на него.
- **Палитра кормит канву:** Агенты·Навыки·Данные·Коннекторы — источники для drag-and-drop В граф (слева), а не отдельные пункты назначения.
- **Настройки — в элементах и между ними:** конфиг узла — инспектор справа по клику; data-контракт/handoff — на связи между узлами.
- **Две жёсткие оговорки (не растворять в узлах):** (1) **конверт безопасности — постоянная рамка вокруг канвы** + потолок автономии подсвечен на каждом узле (статус «безопасно ли» читается всегда, а не по клику — это value prop продукта); (2) **сквозное/глобальное** (Безопасность/RBAC·Настройки среды·Билинг/аудит-журнал) — **вызываемые контекстные поверхности**, привязанные к канве (клик на узел → «разобрать в Безопасности этот участок»), не вкладки-ровни и не узлы графа.

Схлопывание: Канва=центр · Пульт/Operations/Конверт=линзы · Агенты/Навыки/Данные/Коннекторы=палитра · Паспорт=конверт-оверлей+рамка · Безопасность/Настройки=вызываемые поверхности · Обзор=нулевая линза (портфель графов до входа в один).

**Последствия.** Единая ментальная модель — один граф с семантическим зумом и оверлеями; новичок читает «конструктор потока», а не 8 экранов (прямая атака на 2-мин тест). Цена — переработка `SCREENS §0/§1`, `PRD §7` (режимы→линзы), матрицы `HANDOFF`, `DESIGN_BRIEF`; канва-движок становится критическим общим компонентом (авторинг+рантайм+флот на нём) → выше требования к его производительности/состояниям; governance-рамка обязана быть всегда-видимой (доп. дисциплина layout). Обзор сохраняется как «портфель» (список графов/агентов), но перестаёт быть равноправной вкладкой — это вход, с которого проваливаешься в единый центр.

## Разделение продуктов

### ADR-031. Бизнес-вход = LUDA 2, build/run = ABOP: чистое разделение ролей по персонам **[переворот]**

**Статус.** Принято (решение владельца).

**Контекст.** «Product & UX Brief v0.1» предложил перенести ABOP в outcome/decision-среду для владельца процесса: описал процесс словами → система показала что можно автоматизировать, безопасность, экономику, вариант, пилот. Прямой путь — встроить эту воронку в ABOP — конфликтует с двумя инвариантами: (1) канва-центричный shell для инженера (ADR-030) пришлось бы понижать → два противоречащих корня; (2) «магический перевод процесса в техмодель» и негрунтованные цифры экономики нарушают «не строить магический автоподбор» + анти-галлюцинацию. При этом доказательный движок (Evidence→Finding→Autonomy A0–A4→baseline) уже существует и живёт в LUDA, а шов LUDA→ABOP уже спроектирован (контракты + Contract Ingress, ADR-028/029).

**Решение.** Воронка бизнес-заказчика ставится на **LUDA 2**, не на ABOP. Чистое разделение по персонам:
- **LUDA 2 = вход владельца процесса** (диагноз + решение): экраны брифа 01–09 (Мои процессы → Описание → Карта процесса → Анализ → Что AI может → Безопасность → Экономика → Blueprint-превью → Решение). Цифры/автономия/безопасность рождаются из Evidence/BaselineMeasurement LUDA — **доказательно, не LLM-догадка**. Технические артефакты — Level 3 (как уже есть).
- **ABOP = платформа инженера** (build + control + run): канва-центр (ADR-030 **нетронут**), семьи/навыки/governance/Data Plane/Fleet + экраны брифа 10–12 (Pilot/Run → Результат → Audit).
- **Шов LUDA→ABOP** = уже спроектированный: 3 контракта + Contract Ingress (ADR-029). «Запустить пилот» в LUDA эмитит контракты → ABOP принимает как intake воронки → Deployment.
- **Обратная петля результата (ABOP→LUDA) — новое:** ABOP публикует фактические run-метрики, LUDA подтягивает их на экран «baseline vs факт» (замыкание цикла LUDA↔ABOP — дифференциатор).
- **Единая дизайн-система:** LUDA 2 перекрашивается под ABOP DS (общая родословная MIRA v3 → унификация токенов/бренда Эйп, не переверстка логики). SSO уже общий (Keycloak).

**Последствия.** ADR-030 сохраняется без противоречий; «магия» ложится туда, где доказательна (LUDA); переиспользуется контрактный шов; продаётся как честное разделение — «бизнес в LUDA, инженерия в ABOP, связаны верифицированным конвертом». Цена: два продукта надо держать как **один сквозной journey** для владельца (SSO + общая DS + бесшовный handoff), и спроектировать обратную петлю результата (новый, небольшой ABOP→LUDA канал метрик). Аллокация экранов и фич — `ABOP_LUDA_ROLE_SPLIT.md`.
