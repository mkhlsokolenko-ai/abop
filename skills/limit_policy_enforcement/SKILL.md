# Limit Policy Enforcement

Ты применяешь кредитную политику детерминированно: вход → правила → вердикт с лимитом и ставкой. Не «модель решила» вслепую — каждое решение трассируемо к пункту политики и входным данным. LLM не назначает лимит от себя; числа считает политика/скоринг-движок.

## Когда применять
- Валидная заявка прошла intake — нужен вердикт: одобрить/отказать, лимит, условия.
- Пересмотр лимита по действующему клиенту в рамках политики.

## Метод (пошагово)
1. **Собери вход:** результат скоринга/риск-балл, доход и долговая нагрузка (PTI/DTI), КИ, запрошенная сумма/срок, продукт.
2. **Примени правила по порядку:** hard-decline (стоп-факторы) → расчёт предельного лимита (по доходу/PTI и продуктовым потолкам) → ставка/срок по риск-сегменту.
3. **Возьми минимум ограничений.** Итоговый лимит = min(запрошено, лимит по доходу, продуктовый потолок, лимит по риск-сегменту). Явно покажи, какое ограничение связывающее.
4. **Трассировка.** Каждый шаг: пункт политики (id), вход, результат. Вердикт воспроизводим и объясним регулятору/клиенту.
5. **Вердикт:** `approved(лимит, ставка, срок) / counter-offer / declined(причина)`. Counter-offer — когда запрошено > доступного лимита.
6. **Границы автономии.** Решение готовится агентом; фактическое одобрение/выдача — по DeploymentContract (обычно HITL на пограничных/крупных суммах). Локально автономию не повышать.

## Definition of Done
- Каждый элемент вердикта привязан к пункту политики и входу (трассируемо).
- Связывающее ограничение лимита названо явно.
- Тот же вход → тот же вердикт (детерминизм); отказ — с причиной, понятной клиенту.

## Анти-паттерны
- Лимит «из головы» LLM без расчёта по политике.
- Игнорирование PTI/долговой нагрузки при расчёте предельной суммы.
- Молчаливое одобрение суммы выше порога, требующего HITL.
