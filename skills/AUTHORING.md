# Как создавать и проверять скиллы

Скилл — повторяемый способ решения класса задач: инструкции + (опц.) скрипты, шаблоны,
критерии проверки. Плохой скилл **ухудшает** результат, поэтому создание = дисциплина,
а не «скачал из маркетплейса».

## Формат (обязательный)
```
skill-name/
├── SKILL.md          # frontmatter + инструкции (≤ 5000 токенов)
├── references/       # шаблоны, спеки, глубокие доки — читаются по необходимости
├── scripts/          # исполняемые помощники — запускаются по необходимости
└── assets/           # файлы-артефакты (картинки, семплы)
```
`SKILL.md`:
```
---
name: kebab-case-имя
description: Что делает + КОГДА применять («Вызывать, когда …»). ~100 токенов.
---
Короткие пошаговые инструкции. Тяжёлое выноси в references/ и ссылайся:
«Шаблон — в references/template.md, читай при заполнении».
```

## Прогрессивная загрузка (почему так)
1. Агент всегда видит только `name` + `description` (~100 токенов).
2. Полный `SKILL.md` подгружается, только когда скилл подходит задаче.
3. `references/` и `scripts/` читаются/запускаются лишь при необходимости.
Поэтому SKILL.md держим коротким, а объёмное (шаблоны, справочники) — в references.

## Как создавать (эффективный путь)
1. **Не выдумывай проактивно** — анализируй свои повторяющиеся задачи/сессии и упаковывай
   то, что реально делаешь снова и снова.
2. Одна задача — один сфокусированный скилл. **2–3 модуля работают лучше, чем большой
   пакет документации** (SkillsBench).
3. `description` — самое важное: по нему агент решает, брать скилл или нет. Пиши явный
   триггер «Вызывать, когда …».
4. Тяжёлые артефакты (шаблоны, рубрики, справочники) — в `references/`, не в SKILL.md.

## Как проверять (eval — обязательно)
Прежде чем подключать скилл потоку:
1. **Code review SKILL.md и скриптов** — нет ли небезопасных инструкций/скриптов, лишних
   разрешений, шагов «не по окружению».
2. **A/B на реальных задачах** — прогони 3–5 типовых задач **со скиллом и без**. Скилл
   должен поднимать pass-rate, а не «выполнять избыточный процесс».
3. **Правь после реальных ошибок агента** — не по интуиции, а по логам сессий.
4. Не подключай скилл, который на A/B **ухудшил** результат (такое бывает — см. ниже).

## Антипаттерны (из исследований)
- **Авто-retrieval из огромного каталога** ухудшает результат — не подключай «всё подряд».
  У нас курируемый набор из 21 скилла, без поиска по маркетплейсу.
- **Большие пакеты доков** проигрывают сфокусированным модулям.
- **Скилл не по окружению** заставляет агента гонять ненужные проверки — держи инструкции
  привязанными к нашему стеку (MCP, профили code/research, Qdrant, cost-журнал).
