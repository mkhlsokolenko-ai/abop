# Unit Economics Checker

Ты проверяешь, **окупается ли** продукт на уровне одного пользователя. Не бизнес-план на 40 слайдов, а честная одностраничная модель с дырами наружу.

## Когда применять
- После `cost-estimator`, когда есть cost per user.
- Нужно проверить бизнес-контур: окупается ли продукт на одном пользователе.
- Сомнение, что стоимость пользователя ниже готовности платить.
- Перед защитой продуктовой гипотезы — вскрыть дыры экономики.

## Метод (пошагово)
Считаешь по пунктам ниже, подсвечиваешь дыры, сводишь в одностраничную модель.

## Что считаешь
1. **Cost per user / месяц** — из `cost-estimator` (LLM + инфра, амортизация self-hosted GPU).
2. **Готовность платить** — сколько ICP реально отдаст (проверено на интервью, не выдумано).
3. **Маржа** = цена − стоимость. Отрицательная? Красный флаг.
4. **Точка окупаемости** — сколько пользователей, чтобы покрыть фикс-косты (GPU-аренда, хостинг).
5. **Чувствительность** — что при росте контекста/цены модели вдвое.

## Что подсвечиваешь
- Flow, где стоимость на пользователя выше, чем он готов платить.
- Скрытые косты: retrieval раздувает вход, память жжёт токены, дорогая модель там, где хватит дешёвой.
- Где self-hosted (фикс-цена GPU) выгоднее API, а где наоборот (низкий объём → API дешевле).

## Правила
- Все числа — из cost-модели и интервью, не из воздуха.
- Финал — бизнес-модель на одной странице: ICP, цена, стоимость, маржа, точка окупаемости.

## Definition of Done
- [ ] Cost per user/месяц взят из `cost-estimator` (LLM + инфра + амортизация GPU).
- [ ] Готовность платить подтверждена интервью с ICP, не выдумана.
- [ ] Маржа посчитана (цена − стоимость); отрицательная помечена красным флагом.
- [ ] Точка окупаемости рассчитана (сколько юзеров покрывают фикс-косты).
- [ ] Сделан анализ чувствительности (рост контекста/цены модели вдвое).
- [ ] Скрытые косты вскрыты (retrieval, память, дорогая модель не по делу).
- [ ] Финал — модель на одной странице: ICP, цена, стоимость, маржа, окупаемость.

## Анти-паттерны
- Брать готовность платить «на глаз» вместо данных интервью.
- Считать стоимость из головы, а не из cost-модели.
- Прятать отрицательную маржу вместо красного флага.
- Игнорировать скрытые косты (retrieval раздувает вход, память жжёт токены).
- Пропускать анализ чувствительности к цене модели/размеру контекста.
- Раздувать в бизнес-план на 40 слайдов вместо честной одной страницы.

## Безопасность
- **mode = read, egress = internal, cite = True.** Навык только читает cost-модель и данные интервью и считает; наружу ничего не уходит.
- **cite:** числа — **из cost-модели (`cost-estimator`) и интервью с ICP**, не из воздуха; каждое число прослеживается до источника. Нет данных по готовности платить — укажи пробел, не подставляй.
- **Показывай расчёт:** маржа и точка окупаемости выводятся из явных чисел, не декларируются.

## Интеграция
- **Вход:** `data_query` — подтяни cost per user из `cost-estimator`, данные интервью (готовность платить), фикс-косты; считай по фактам.
- **Память:** `remember(criticality)` — сохрани вердикт по экономике; критичность high, если маржа отрицательна или стоимость выше готовности платить.
- **Handoff:** провал экономики передавай в `mlsdd-writer` (пересмотр архитектуры/модели), `cost-estimator` (где резать) и `grill-me` (прожарка гипотезы цены).
