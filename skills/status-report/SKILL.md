# Status Report

Ты собираешь **честный статус проекта**: RAG-оценку, обоснованную критериями, прогресс относительно плана в цифрах, риски с владельцами и планом снятия, конкретные следующие шаги. Всё — на фактах из трекера, а не по памяти или ощущениям.

## Когда применять
- Регулярный статус для стейкхолдеров, руководства, заказчика.
- Нужно понять и показать: успеваем ли, что мешает, что дальше.
- Перед вехой/релизом, когда важна объективная картина, а не оптимизм.

## Метод (пошагово)
1. **Собери факты.** Через `data_query` подтяни из трекера состояние задач, burndown/прогресс спринта, открытые баги/блокеры, даты вех. Отчёт строится на данных, не на памяти.
2. **Определи RAG по критериям.** Заранее объяви, что значит red/amber/green (напр. green = в графике и без блокеров; amber = отставание ≤N% или есть риск с планом; red = веха под угрозой / блокер без владельца). Присвой цвет и **сошлись на критерий**, по которому он выставлен.
3. **Покажи прогресс vs план.** Конкретные цифры: сделано X из Y задач/поинтов, план был Z к дате. Отклонение — с причиной, а не «идём нормально».
4. **Зафиксируй риски и блокеры.** Каждый риск: описание, влияние, вероятность, **владелец**, план снятия и срок. Блокер без владельца = red.
5. **Сформулируй next-steps.** Конкретные шаги на период: что, кто, к какому сроку. Не «продолжаем работу».
6. **Приведи цитаты/ссылки.** Каждое утверждение о статусе привязано к источнику в трекере (тикет/спринт/доска).

## Definition of Done
- [ ] RAG-цвет обоснован явным критерием, а не интуицией.
- [ ] Прогресс показан цифрами (сделано vs план), отклонения объяснены.
- [ ] Каждый риск/блокер имеет владельца и план снятия со сроком.
- [ ] Next-steps конкретны (что/кто/срок).
- [ ] Все факты подтверждены ссылками на трекер (`cite = True`).
- [ ] Нет утверждений «по памяти» без источника.

## Анти-паттерны
- «Зелёный» статус при скрытых блокерах, чтобы не тревожить руководство.
- RAG без критериев — цвет «на глаз».
- Прогресс словами («движемся хорошо») вместо цифр.
- Риск без владельца и без плана снятия.
- Статус по памяти, без сверки с трекером на момент отчёта.

## Безопасность
- **mode = write, egress = internal, cite = True.**
- Отчёт публикуется во **внутренний** контур (внутренний дашборд/канал), не наружу. Каждое утверждение о статусе сопровождается ссылкой на источник — цитирование обязательно.
- Не выдумывай метрики: если данных в трекере нет — так и пиши «нет данных», а не оценивай на глаз.
- Внутри отчёта не раскрывай ПДн сверх необходимого (имена исполнителей — по политике команды).

## Интеграция
- **Вход:** `data_query` — источник истины для статуса (задачи, прогресс, риски, даты). Без него отчёт не строится.
- **Память:** `remember(criticality)` — фиксируй критичность рисков/блокеров (red = high), чтобы отслеживать их между отчётами и видеть динамику.
- **Handoff:** при эскалации риска — `handoff` ответственному с контекстом и планом снятия.
