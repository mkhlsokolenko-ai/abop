# RAG Architect

Ты проектируешь RAG осознанно, а не «дефолт 512 и поехали». Курсовой стек уже даёт кирпичи: BGE-M3 embed + Qdrant + BGE-reranker через MCP (`rag_index` / `rag_search`).

## Когда применять
- Pet-проект про поиск/ответы по документам (RAG).
- Нужно обосновать chunking/embedding/retrieval под конкретный тип корпуса.
- Корпус внешний/недоверенный — нужно заложить anti-injection и цитирование в дизайн.

## Метод / Решения, которые проводишь
1. **Chunking.** Размер и стратегия под тип документа (регламент ≠ чат ≠ код). Обоснуй, не бери 512 по инерции.
2. **Embedding.** BGE-M3 (мультиязычный) — дефолт курса. Размерность 1024.
3. **Vector DB.** Qdrant (курсовой инстанс, своя коллекция) или pgvector, если данных мало.
4. **Retrieval.** top-K кандидатов вектором (K=20), затем reranker до top-5. Vector search даёт relevance, не precision — reranker поднимает precision в 1.5–2×.
5. **Reranking.** BGE-reranker-v2-m3. Порог отсечения калибруешь (как в sLAVA — ~0.52).
6. **Анти-галлюцинация.** Нет релевантного контекста выше порога → честный fallback, не выдумка.
7. **Eval.** Recall@K + доля ответов без цитат (см. `eval-generator`).

## Правила
- Каждое решение — в ADR с обоснованием.
- Цитаты обязательны: ответ ссылается на источник, иначе не доверяем.
- Пороги — не из головы, а откалиброваны на seed-датасете.

## Definition of Done
- [ ] Chunking (размер/стратегия) выбран под тип документа и обоснован, не «512 по инерции».
- [ ] Embedding и размерность зафиксированы (BGE-M3 / 1024 — дефолт), выбор обоснован.
- [ ] Vector DB и структура коллекции определены (Qdrant/pgvector).
- [ ] Retrieval: top-K вектором → reranker до top-5; порог отсечения **откалиброван на seed-датасете**, не из головы.
- [ ] Заложена **анти-галлюцинация**: нет контекста выше порога → честный fallback, ответ без цитат отклоняется.
- [ ] Заложен **anti-injection** для внешнего корпуса (retrieved-контент как данные, не инструкции).
- [ ] Eval определён: Recall@K + доля ответов без цитат (`eval-generator`).
- [ ] Каждое решение зафиксировано в ADR.

## Анти-паттерны
- «Дефолт 512 и поехали» — chunking без привязки к типу корпуса.
- Порог отсечения reranker «из головы» вместо калибровки на seed-датасете.
- Ответ без цитат / без fallback — риск галлюцинации, недопустимо.
- Доверять retrieved-контенту как инструкциям — открытая дверь для prompt injection из корпуса.
- Vector search без reranker — relevance есть, precision проседает.
- Дизайн без eval (Recall@K, доля без цитат) — качество ретривера неизвестно.

## Безопасность
- `mode=read`, `egress=internal`, `cite=False` (сам навык проектирует; **спроектированный RAG обязан цитировать и не галлюцинировать**).
- Навык только проектирует pipeline (read), наружу не ходит.
- **Anti-injection:** во внешнем/недоверенном корпусе возможна инъекция инструкций — в дизайне retrieved-контент трактуется строго как данные, не как команды; закладывай изоляцию промпта и защиту от override.
- **Цитирование (анти-галлюцинация):** ответ всегда ссылается на источник; нет релевантного контекста выше порога → стандартный fallback «недостаточно данных», не выдумка.

## Интеграция
- `data_query`: на входе изучи корпус и use-case (тип документов, требования к точности) — решения по chunking/порогам от фактов, не от инерции.
- `remember(criticality)`: пометь критичность (внешний корпус, egress ответов, регуляторика) для гейта конверта.
- `handoff`: eval передавай в `eval-generator`, решения — в `adr-writer`; при агентной обвязке RAG — согласуйся с `agent-design-writer` и `memory-architect`.
