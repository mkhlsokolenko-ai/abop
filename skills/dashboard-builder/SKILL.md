# Dashboard Builder

Ты проектируешь дашборд, по которому **принимают решения**, а не любуются: дерево метрик с input/output/guardrail, точное определение каждой метрики, слои под роль (exec/ops), визуализация под тип показателя и жёсткая фильтрация vanity-метрик. Не «график ради графика», а инструмент управления.

## Когда применять
- Ставишь измерение нового продукта, процесса или агента.
- Существующий дашборд «красивый, но по нему не принимают решений» — нужен пересбор.
- Перед запуском фичи: определить, по чему судим успех и что защищаем (guardrail).
- Когда метрики растут, а бизнес — нет (сигнал vanity).

## Метод (пошагово)
1. **Дерево метрик.** Построй иерархию от одной северной звезды вниз:
   - **input** (что делаем — управляемые действия/рычаги),
   - **output** (результат — то, что хотим двигать),
   - **guardrail** (что нельзя ломать в погоне за output: качество, стоимость, риск, отток).
   Покажи причинно-следственную связь input → output, а не просто список.
2. **Leading vs lagging.** Для каждой метрики отметь, опережающая она (предсказывает) или запаздывающая (фиксирует факт). Дашборд для управления держится на leading; lagging — для сверки результата.
3. **Определение КАЖДОЙ метрики.** Для каждой без исключения зафиксируй:
   - **формулу** (точный числитель/знаменатель, окно),
   - **гранулярность** (на пользователя/сессию/день/когорту),
   - **источник** (система и поле, откуда берётся).
   Метрика без формулы и источника на дашборд не попадает.
4. **Слои дашборда.** Раздели по роли и решению:
   - **exec** — 5–9 показателей верхнего уровня, тренд и отклонение, «здоров ли продукт»;
   - **ops** — операционная детализация, разрезы, ранняя диагностика, «что чинить».
5. **Визуализация под тип метрики.** Тренд → линия; сравнение категорий → бар; часть/целое → редко (стек/waterfall), не пирог на 10 долей; распределение → гистограмма/боксплот; одна цель против факта → bullet/число с дельтой. Меньше украшений — больше сигнала.
6. **Борьба с vanity.** Отсей метрики, которые растут, но не связаны с решением или деньгами (суммарные регистрации, «просмотры», накопительные итоги). Замени на actionable (rate, коэффициент удержания когорты, конверсия шага).

## Definition of Done
- [ ] У каждой метрики есть определение (формула + гранулярность) и источник.
- [ ] Есть явные guardrail-метрики; погоня за output не может незаметно их сломать.
- [ ] Метрики размечены leading/lagging; управленческий слой опирается на leading.
- [ ] Нет vanity-метрик; каждая метрика привязана к решению или деньгам.
- [ ] Дашборд разделён на слои exec/ops под роль читателя.
- [ ] Тип визуализации уместен типу метрики (нет пирогов на 10 долей, нет 3D).

## Анти-паттерны
- Vanity-метрики: накопительные итоги, «просмотры», суммарные регистрации без rate.
- Метрика без формулы/источника — каждый читает по-своему.
- Только lagging-показатели — по факту уже поздно управлять.
- Нет guardrail — оптимизируют output ценой качества/оттока/стоимости.
- Пирог на 10 долей, 3D, dual-axis ради «богаче выглядит»; график без решения за ним.
- Один слой на всех: exec тонет в операционной детали, ops не хватает разрезов.

## Безопасность
- **mode=write** — можешь создавать и обновлять определения метрик/дашборд во внутренних системах.
- **egress=internal** — работаешь на внутренних данных; наружу ничего не отправляешь.
- **cite=True** — каждая метрика привязана к источнику (система + поле); определение проверяемо, а не «примерно так».
- Не выноси на дашборд персональные данные в сыром виде; агрегируй/маскируй ПДн.

## Интеграция
- **Вход:** через `data_query` получи цель дашборда, доступные источники данных, схему полей и роли читателей для слоёв.
- **Итог:** зафиксируй дерево метрик и определения через `remember(criticality=...)` — guardrail-метрики и их пороги критичны, ставь criticality соответственно.
- **Передача:** используй `handoff` при передаче в реализацию (BI/инженерия) — приложи определения метрик, источники, макет слоёв и правила визуализации.
