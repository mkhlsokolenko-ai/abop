# API Design

Ты проектируешь API так, чтобы **контракт был первичен**, а код — его реализацией. Сначала OpenAPI-спека, потом хендлеры. Чужой клиент должен уметь интегрироваться по спеке, не читая твой код.

## Когда применять
- Появляется новый сервис/эндпоинт, наружу или между сервисами.
- Меняешь существующий контракт — нужно оценить обратную совместимость.
- Договариваешься об интерфейсе между командами до реализации.

## Метод (пошагово, профессионально)

**Шаг 1. Contract-first (OpenAPI).**
Пиши спеку до кода. Спека — источник истины, из неё генерируются клиенты, моки, валидация.
```yaml
paths:
  /v1/collections/{id}/documents:
    get:
      summary: Список документов коллекции
      parameters:
        - { name: id, in: path, required: true, schema: { type: string } }
        - { name: cursor, in: query, schema: { type: string } }
        - { name: limit, in: query, schema: { type: integer, default: 50, maximum: 200 } }
      responses:
        "200": { description: OK }
        "404": { $ref: "#/components/responses/Problem" }
```

**Шаг 2. Ресурсы и именование.**
- URL = **существительные во множественном числе**: `/documents`, `/collections`, не `/getDocument`.
- Глагол — это HTTP-метод (`GET`/`POST`/`PUT`/`PATCH`/`DELETE`), не часть пути.
- Иерархия через вложенность: `/collections/{id}/documents`. Не вкладывай глубже 2 уровней.

**Шаг 3. Версионирование.**
- Явная версия в URL (`/v1/...`) — просто, кэшируемо, видно в логах. Дефолт.
- Или в заголовке (`Accept: application/vnd.api.v2+json`) — чище URL, но менее прозрачно.
- Выбери одну стратегию и держись её. Мажорная версия = ломающие изменения.

**Шаг 4. Идемпотентность.**
- `GET`, `PUT`, `DELETE` — идемпотентны по определению (повтор не меняет результат).
- `POST` (создание) — НЕ идемпотентен. Для безопасных ретраев вводи **ключ идемпотентности**: клиент шлёт `Idempotency-Key: <uuid>`, сервер дедуплицирует и возвращает тот же результат.

**Шаг 5. Пагинация.**
- **Cursor-based** — дефолт для больших/меняющихся коллекций: стабильна при вставках, дёшева. Ответ несёт `next_cursor`.
- **Offset/limit** — только для маленьких статичных наборов; на больших едет производительность и появляются дубли/пропуски.

**Шаг 6. Ошибки по RFC 7807 (`application/problem+json`).**
Единый формат ошибок на весь API:
```json
{
  "type": "https://api.example/errors/validation",
  "title": "Ошибка валидации",
  "status": 422,
  "detail": "Поле 'limit' превышает максимум 200",
  "instance": "/v1/collections/abc/documents"
}
```
Коды статусов по смыслу: `400` — синтаксис, `401` — не аутентифицирован, `403` — нет прав, `404` — нет ресурса, `409` — конфликт, `422` — валидация, `429` — rate-limit, `5xx` — ошибка сервера. Не отдавай `200` с телом об ошибке.

**Шаг 7. Обратная совместимость.**
- **Можно** без слома: добавить новое **опциональное** поле, новый эндпоинт, новое значение enum (если клиент толерантен).
- **Нельзя** без новой версии: удалить/переименовать поле, сделать опциональное обязательным, сузить тип, изменить семантику существующего поля.
- Правило Postel: будь строг к тому, что отдаёшь, толерантен к тому, что принимаешь (игнорируй незнакомые поля).

**Шаг 8. Безопасность контракта.**
- Авторизация проверяется **на входе** (единожды, с кэшированием токена), не на каждом внутреннем вызове.
- Rate-limit на мутирующие эндпоинты; ответ `429` с `Retry-After`.
- Валидация входа по схеме (Pydantic/OpenAPI), никаких сырых данных в логику.

## Definition of Done (проверяемый чеклист)
- [ ] Контракт (OpenAPI) написан ДО реализации и валиден.
- [ ] Ресурсы — существительные, глагол = HTTP-метод.
- [ ] Стратегия версионирования выбрана и применена единообразно.
- [ ] Обратная совместимость продумана: перечислено, что менять можно, что — только с новой версией.
- [ ] Ошибки единообразны (RFC 7807, `problem+json`), коды статусов корректны.
- [ ] Идемпотентность обеспечена там, где ретраи возможны (ключ идемпотентности для `POST`).
- [ ] Коллекции пагинируются (cursor по умолчанию), лимит ограничен сверху.
- [ ] Authz на входе, rate-limit на мутациях.

## Анти-паттерны
- Глаголы в URL (`/createUser`, `/getList`) — это RPC, а не REST.
- `200 OK` с `{"error": ...}` в теле — ломает клиентов и мониторинг.
- Разные форматы ошибок в разных эндпоинтах.
- Offset-пагинация на больших меняющихся коллекциях.
- Ломающее изменение без бампа версии — «тихо» рушит интеграции.
- Проверка авторизации на каждом внутреннем хопе вместо валидации на входе.

## Безопасность
- `mode=read`, `egress=internal`, `cite=False`.
- Навык только проектирует контракт (read) — не поднимает сервисы и не ходит наружу.
- В спеке не публикуй внутренние секреты, приватные хосты, реальные токены в примерах — только плейсхолдеры.
- Явно фиксируй в контракте схемы authz (security schemes) и rate-limit — безопасность часть контракта, а не «потом добавим».

## Интеграция (data_query; remember(criticality); handoff)
- `data_query`: сверься с существующими контрактами/моделями данных, чтобы новый API был консистентен (именование, версии, формат ошибок).
- `remember(criticality)`: пометь критичность эндпоинтов (мутации, egress-точки, доступ к чувствительным данным) — вход для гейта конверта.
- `handoff`: получай границы сервисов от `c4-diagram` (Container → набор API); передавай контракт в реализацию (`fastapi-patterns`) и в ADR-навык для фиксации решений по версионированию/совместимости.
