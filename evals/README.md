# Регрессия на эталонных запросах

Набор проверяет не текст ответа — он у модели каждый раз свой, — а **проверяемые инварианты**: кого
среда подобрала на фразу, тот ли предмет работы, покрыт ли вход навыка данными, какие поля результата
обязаны быть заполнены. Плюс цена и время: лишний вопрос это трение, а работа не по тому проекту —
потеря доверия.

## Запуск

```bash
# без модели: подбор, предмет работы, покрытие входов (быстро, годится для CI)
python evals/run_evals.py --base http://127.0.0.1:8099

# с настоящими прогонами: ещё поля результата, стоимость и время
python evals/run_evals.py --base http://127.0.0.1:8099 --live

# один случай
python evals/run_evals.py --only roadmap-plain
```

Код возврата ненулевой, если хоть одна проверка провалилась. Отчёт — `evals/last_report.json`.

## Что в наборе

| Случай | Что проверяет |
|---|---|
| `roadmap-plain` | предмет назван в фразе — уточнять нечего |
| `roadmap-no-subject` | метазапрос без предмета: среда обязана спросить, а не смешать проекты |
| `acceptance` | формулировка про приёмку ведёт к другому исполнителю, чем про отчёты подрядчиков |
| `audit1c` | аудит по всей выгрузке: предмет не нужен, но объём проверки обязан быть в результате |
| `invest1c` | расследование от симптома — другая форма результата, чем список находок |
| `mail-digest` | разбор почты даёт структурный список задач |
| `vague` | расплывчатая фраза: подобрать исполнителя и спросить предмет |
| `wrong-domain` | запрос вне области: честно сказать, что исполнителя нет |
| `fanout` | «по всем проектам» — это веер |
| `chain-two-sources` | два независимых источника по одному предмету: цепочка и разбор расхождений |

## Метрики

| Метрика | Смысл | Порог |
|---|---|---|
| подбор верный | доля случаев, где выбран исполнитель нужной семьи (или честно показана неуверенность) | 100% |
| предмет верный | предмет определён или корректно запрошен | 100% |
| исполнимость | обязательные входы навыка покрыты данными без ручной правки | 100% |
| прогон полный | все ожидаемые поля результата заполнены | 100% |
| уточнений среднее | сколько вопросов среда задаёт на запрос | ≤ 0.5 |
| время, стоимость | средние по прогонам | наблюдаем тренд |

## Как добавлять случаи

Один случай — одна реальная формулировка пользователя и то, что среда обязана по ней сделать.
Ожидания пишите инвариантами, а не текстом: семья исполнителя, навык, предмет, обязательные поля
результата. В поле `почему` — зачем этот случай в наборе; без него набор со временем превращается в
список непонятных строк.

Стенд должен быть наполнен: агенты с нужными навыками и данные в сущностях. Если агента с навыком нет,
набор честно помечает случай как непроверяемый и не портит метрику молча.
